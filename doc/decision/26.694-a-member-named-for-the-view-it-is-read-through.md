# 26.694: a member named for the view it is read through

Status: recorded -- fixed in C++; a third instance left open
Date: 2026-10-27
Source: `project.md` section 26

**A generated class derives from `::situ::rt::view`, so a member named for
one of the base's accessors HIDES it rather than overloading it.** `u8 raw`
emits `std::uint8_t raw() const`, C++ name lookup stops at the derived
class, and every `situ_in_bounds(raw(), ...)` the backend wrote for the
VIEW was handed a `uint8_t`:

    error: could not convert '((const situ::s*)this)->situ::s::raw()'
           from 'uint8_t' {aka 'unsigned char'} to 'situ_view_t'

From `struct s { u8 raw [max = 4]; u8 b[raw + 1]; u16 tail; }`, whose only
unusual feature is a three-letter field name.

**`this->raw()` does not help, which is the part worth holding.** Hiding is
not about the object expression -- a qualified-by-`this` call looks up in
the derived scope just the same, and the error above names
`situ::s::raw()` reached through `this`. Only naming the BASE bypasses it.
So the fix is `::situ::rt::view::raw()` at the 35 view-intended sites, and
the 24 that already said `this->raw()` were no safer than the 10 that said
`raw()`.

**This is a DIFFERENT mechanism from the two it was filed with, and
history proved it rather than argument.** 26.490 recorded five names
breaking C++ and attributed all five to *"a generated local shadows the
getter its own initialiser calls"*. 26.501 fixed that cause -- emitter
locals, qualified with `this->` -- and `n`, `at`, `need`, `have` and
`value` all went clean. **`raw` survived it**, in three constructs of
four, which is the measurement no reading of the entry would have given.
Re-measured 2026-10-27 against `b14f433`:

    name   plain   arith b[N+1]   reserved[N+1]   bare b[N]
    raw    clean   BROKEN         BROKEN          BROKEN
    n/at/need/have/value           clean everywhere
    i (control)                    clean everywhere

**Nor is it 0062's case, and a guard built on 0062's framing cannot catch
it.** 0062 refuses a Python class that binds one name twice, by parsing the
emitted module, and lists `validate` and `size_bytes` for C++. Measured
here: the generated class declares `raw()` exactly ONCE, and the second
declaration is the base's at `runtime/cpp/situ.hpp:167`. **Nothing binds
`raw` twice.** A double-binding detector is structurally blind to this,
whichever backend it is pointed at -- which matters because 0062 leaves
C++ and Rust to their compile-time refusals "for now", and the eventual
guard is the thing that would otherwise be trusted.

26.80 is the rule met a third time: a schema name must not be able to hide
what generated code needs.

**Rust is unaffected, with a control.** All eight names compile clean under
`-D warnings`; a deliberate syntax error in the same crate is reported, so
the harness can speak. Rust resolves an inherent method through the impl
rather than by derived-scope lookup, and has no base to hide.

**Blast radius: the qualification and nothing else.** 46 generated headers
differ from the baseline ONLY by `::situ::rt::view::` -- compared after
normalising both sides, since the emitter already used `this->raw()` in 24
places and stripping one side alone manufactures differences. 481
base-qualified calls emitted, 0 headers differing in anything else, and
**46 of 46 compile**. C, Rust and Python: 184 files byte-identical.

**The control is the test reverted.** The qualified
`situ_in_bounds` spelling put back to the bare one, at all 10 sites, fails
`test_a_member_named_raw_does_not_hide_the_view_it_is_read_through` with
the real compiler error above, at two lines -- the check under test
speaking, not a neighbour.

## What is left open: `raw_`, a third instance

**A field named `raw_` is still broken, and it is not a regression from
this change.** It generates a getter `raw_()` which hides the base's
*protected data member* `raw_`, and the emitter reads that member as
`raw_.limit`:

    error: invalid use of non-static member function
           'uint8_t situ::s::raw_() const'

It breaks in all four constructs INCLUDING `plain`, where `raw` was clean
-- so it is reached by more schemas, not fewer. Verified pre-existing by
building the same fixture against a `git archive HEAD` copy of the
emitter, confirmed to lack this change: the baseline produces the same
error. Reasoning would have been enough here and was not what settled it.

Left open deliberately: the fix qualifies every `raw_` reference in the
emitter rather than 35 call sites, and a data member's base qualification
is uglier than a method's. Whether that trade is worth making is the
holder's.

**Corpus exposure for both:** two committed fields are named `raw`, none
with a member whose size or offset depends on it, and none named `raw_` --
which is why 46 of 46 headers compiled before this change as well.

## The count assertion accepted a comment as a call site

**The change was made with a count assertion -- 35 sites, refuse if the
number moves -- and 35 was right while one of them was prose.** Site 35 is
inside a `/** ... */` block, and a qualified name backticked in a doc
comment is an explicit link request Doxygen cannot resolve. It failed
`test_doxygen_reads_the_generated_headers_without_complaint` on three
schemas: ble, mqtt and edges.

**The remedy was already written two lines below the line changed**, as a
comment saying that the element class is deliberately not named there
because a backticked qualified name "failed the doc gate on three
schemas" -- the same three. A pattern that matched 35 spellings walked
past the note explaining why one of them must not be qualified.

So the assertion was the right instrument for the wrong population: it
proves the number of SPELLINGS and says nothing about whether each is
code. The comment is unqualified again, with a note at the site saying it
is deliberate, and the generated-output proof is re-taken -- 46 headers
differing only by the qualification, 46 of 46 compiling.

**What a count cannot check, read.** Thirty-five is a small enough list
that reading it would have cost less than the gate run that caught it.

## An instrument note worth keeping

The first re-verification grid reported `NO OUTPUT` in four cells,
including the `i` control that had been clean. The scratch directories
were named from the construct, so they contained `[` and `]`, and
`ls $d/gen/*.hpp` read those as a glob character class and matched
nothing. **A harness that names a directory after the thing under test can
be defeated by the thing under test.** The tell was the control failing;
without `i` in the grid it would have read as four findings.
