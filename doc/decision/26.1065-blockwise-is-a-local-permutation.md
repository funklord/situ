# 26.1065: `seekable = blockwise(N)` is a permutation that stays in its block

Status: recorded
Date: 2026-11-17
Source: the goal gap, walked in /go run 3 -- 26.492 and 26.494 left the
value meaning nothing, and the holder's standing word (2026-11-17) is to
build what a protocol needs properly

**`blockwise` was accepted and read by nothing.** Its N was parsed and
dropped; a field inside a `blockwise(16)` region mapped exactly as one
under CTR, a contiguous span to hand out (measured: no `address` effect,
the same line as `linear`); a pipeline holding one was refused (26.494,
which declined to decide where it ranks); and `gen-codec-tests` emitted
nothing for it, which that suite's own rule reads as coverage. Meanwhile
the one kernel that IS blockwise -- `permutation(rows, columns)`, which
permutes each block of `rows * columns` bytes on its own -- was derived as
merely `permuted`.

## The meaning

`blockwise(N)` is a bijection over positions that keeps every position
inside its own N-byte block. It is therefore a `permuted` map that is
local, and ranks between the two: linear < blockwise(N) < permuted < none.
`blockwise(any)` promises the locality without its extent.

- **Composition.** `none` or `permuted` in a pipeline wins as before.
  Otherwise two blockwise stages compose to `blockwise(lcm(N, M))`, whose
  blocks are unions of both stages' blocks; with linear stages it stays
  blockwise. Across a stage that changes the length, a block in no longer
  lines up with a block out, so the claim left is `permuted` -- what
  `rs |> interleave` already composed to. An unsized stage gives
  `blockwise(any)`.
- **The map.** Rule `codec-blockwise`: `address := Unstable`, since a
  field's bytes sit scattered across its block. Random access survives as
  under `permuted`; mutation is the granularity's to say, as it already
  was (`block(n)` gives `InPlaceSlack`).
- **The kernel.** `permutation(rows, columns)` derives
  `blockwise(rows * columns)`; a bare `span` names some permutation's
  extent without saying it repeats, and stays `permuted`. The derived
  bijection test (`_derived_permuted`) asks both, so the kernel it was
  written for does not leave it on the day it gains the stronger claim.
- **The claim, tested.** For a length-preserving `blockwise(N)` codec the
  codec suite changes the input byte on each side of a block edge -- the
  first block's last byte and the last block's first -- and asserts the
  output changed only inside that byte's block. A value test would be
  wrong here: a block cipher in a blockwise mode transforms every byte,
  and the claim is about reach, not values.

## A cell corrected

`project.md`'s kernel table said a linear block code derives
`seekable = blockwise(n)`. The kernel derives `linear` -- a prefix of
whole codewords encodes to a prefix, which `_derived_seekable` tests --
and blockwise is defined above for a length-preserving map only, which a
block code is not. `linear` is the stronger claim and the true one; the
cell now says so.

## Measured

`test_kernels.py`: unsized blockwise with linear composes to
`blockwise(any)`; `blockwise(4) |> blockwise(6)` to `blockwise(12)`; with
`permuted`, and across `expansion = +4`, to `permuted`; the 4x4
interleaver to `blockwise(16)` and a `span` one to `permuted`; a
standalone `blockwise(16)` keeps 16. `test_propagate.py`: the field maps
`address=Unstable` under `codec-blockwise`.
`test_a_blockwise_codec_keeps_a_change_in_its_block.py` compiles the
generated suite against three encoders: one local to its 4-byte block
passes, one carrying forward (CBC-like) and one carrying back fail. With
the changed bytes moved inside their blocks, both leaking encoders pass,
which is why they sit on the edges. `std/kernels.situ.map`'s
`interleave_16` line reads `seekable=blockwise(16)`; nothing else in any
committed map or wire changes.
