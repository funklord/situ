# 26.941: the dissector shows the number a varint spells

Status: recorded
Date: 2026-11-08
Source: 26.932, after which the dissector read every varint's value and still showed its bytes

**An unsigned varint is declared a `uint64` field and shown as its number**: a CBOR count
of three reads 3 rather than `83`, an EBML ID reads 163 rather than `a3`. Its bytes were
shown because "a varint's bytes are not the value it spells" and the dissector could not
read the value; since 26.932 it does, by the walker's rules.

Wireshark refuses a Lua number for a `uint64` field -- "userdata expected, got number"
-- so the value is built from its two words. They are exact whatever the value, the high
one being a multiple of 2^32 divided by 2^32, so 2^64 - 1 comes back as written. A
signed varint -- `sleb128`, or `transform = zigzag` -- is an `int64`, decoded from the
zigzag form in the same two words: halved, and complemented where it is odd. In real
tshark -1, 3 and -2^63 read as written.

The Lua harness takes a value handed with the range and a `UInt64` as the real API does,
and the differential compares the number with the walker's `value=`, where it had held
a varint's length only.
