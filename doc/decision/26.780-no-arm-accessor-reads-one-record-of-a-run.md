# 26.780: No arm accessor reads one record of a run

Status: recorded -- fixed
Date: 2026-10-31
Source: `project.md` section 26 (the lens 26.779 left)

    struct pt { u8 x; u8 y [max = 9]; }
    ... variant body switch (kind) { case 2: pt pts[n];
                                     case 3: pt q[2];
                                     case 1: piece two[2]; ... }

26.779 found C++, Rust and Python taking `piece recs[n]` in an arm for
one `piece`, and declined it where the element has no single size. The
same branch takes every run of structs in an arm: `body_pts` handed back
the first `pt` under the run's name, in all three, for fixed-size
records and for a literal count alike. C declines them all.

`validate` was sound on the frame -- the variant's length covers a run
of fixed records -- but not agreed on the elements. Python delegated to
that one-record accessor, and both walkers validated the arm as one
struct, so `[max]` on element 0 refused in three of six and on element
1 in none. No backend validates a top-level run's elements ("a caller
who wants it should walk the elements"), so the three now agree with C.

## The change

- `traverse.is_struct_run`: a run of a struct, of one size or not,
  counted or literal. C++, Rust and Python decline it in an arm with
  C's sentence, and Python's `validate` no longer delegates to it.
- The Python walker's `_arm_validates` and member loop, and the C
  walker's `arm_validates`, hold a run of fixed records to the frame
  through the variant's size and do not validate it as one struct; a
  run of variable records is walked, as 26.779 has it.

The corpus has no such arm and generates byte-identically.

## Tests

`test_a_run_in_an_arm_is_walked.py` gains the shape: all four backends
and both walkers agree on seven messages, two with element 0 over its
`[max]`, and no backend emits `body_two`, `body_pts` or `body_q`. With
`situc` and `walker` reverted, all three of those fail.
