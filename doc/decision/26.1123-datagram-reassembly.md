# 26.1123: one message reassembled from many datagrams

Status: recorded; reviewed by fuzznet (inbox 20261121T1000Z); built in all four backends 2026-11-21
Date: 2026-11-20
Source: fuzznet (inbox 20261120T1231Z, item 1, its largest): "Your rung 4
frames a byte stream; fuzznet reassembles one message from many datagrams:
a buffer sized from the first piece, `same_message` held by each later
one, a map of pieces held, bounds on messages and bytes in flight stated up
front, pieces of a message timed out. Wanted: that rung, keyed by a
relation, its bounds in the schema, telling the driver `part_held` itself
and able to say which pieces are missing." 648 lines in fuzznet.

## Where it sits

Beside rung 4, not on top of it: 0032 already says `frame` and `converse`
are orthogonal, and a datagram protocol needs no byte-stream framing.
Reassembly holds BYTES between calls, as `frame` does, keyed by a relation
-- the one 0030 introduced for exactly this, `same_message`, whose
equalities are the key and whose comparison with the FIRST piece is the
security property (a later piece claiming another total is refused before
it touches the buffer).

## The shape proposed

    reassemble pieces(f: fzn_frame) by same_message [
            index = f.head.index, count = f.head.chunks,
            piece = f.sealed.payload, messages = 8, bytes = 65536,
            timeout = 30000, unit = ms];

- `by` names the relation; its key fields identify a message, and a later
  piece is checked against the first with the relation's own `must`s.
- `index` and `count` place a piece; `piece` is the bytes it carries --
  behind a gate where it is sealed, so the call takes the gate (26.1122's
  rule, applied the same way).
- `messages` and `bytes` are the bounds in flight, stated up front; a piece
  that would pass either is refused, not queued -- the window's FULL rule
  (26.1120).
- `timeout` drops a message whose pieces stopped arriving, in the caller's
  `unit` with the clock the caller's, as everywhere above rung 4.

Generated, per declaration: a table in the caller's memory (`messages`
slots, `bytes` of buffer), `add(table, gate, now) -> PARTIAL | COMPLETE |
REFUSED(why)` handing the whole message back on COMPLETE without a copy
the caller did not ask for, `missing(table, key, out, max) -> n` listing
the absent indices for a bounded re-request, and `expire(table, now)`. The
driver (rung 6) calls `add` where it now calls `part_held`, and asks
`missing` for its re-request.

## For review

- Whether every piece's size is the same but the last (a buffer sized
  `count x first piece's size`) or a total is carried; fuzznet sizes from
  the first piece.
- Erasure coding (item 4) sits on this table: a parity piece rebuilding a
  lost one is a codec over the table's pieces, decided after this lands.
- Whether `missing` lists indices or emits the re-request message itself.

## fuzznet's answers (inbox 20261121T1000Z)

Read from its `chunk/reassembly.c` (648 lines), `chunk/split.c` and
`node/pieces.c`:

1. **No total is carried; a stride is.** Every piece but the last is
   exactly the stride, the last no longer. The slot is sized `count x
   stride` up front, the bound checked by division -- `stride <= capacity /
   count` -- since a product once wrapped to zero. The stride comes from
   the first NON-LAST piece to arrive: under loss piece 0 is often the one
   lost, so a last piece arriving first is held aside with the stride
   unknown, never guessed (that would let whoever sends the final piece
   choose it), and placed when a stride-setting piece arrives. Every later
   piece is held to the first's count and stride -- the `same_message`
   check. Its key is (sender, msg); index and count are u16.
2. **Erasure coding is not on this table** in fuzznet: its k-of-m pieces
   are of a STORED item, spread across hosts, each piece a whole message,
   above the datagram layer. The table needs no parity hook.
3. **`missing` lists ranges**, `(first, count)` each capped at a
   caller-given maximum, into a caller array, saying how many; the caller
   builds its own want message, which carries an expiry and is sealed --
   neither the table's business.

## Built (C, 2026-11-21)

`reassemble NAME(p: T) by REL [index = p..., count = p..., piece = p...,
messages = N, bytes = N, timeout = N, unit = ms];` -- every bound
required, since situ supplies no number for what a sender who never
finishes gets to spend. The relation is over two `T`; its equalities are
the key. `<stem>_reassemble.h` at `--layer converse`:

- `NAME_t`, the caller's: `messages` slots, each owning `bytes / messages`
  of buffer and a mark bit per piece it can hold. A message past a slot's
  capacity is refused rather than spilled into a neighbour's.
- `NAME_add(t, piece, now, &message, &length)`: SITU_OK with the whole
  message (valid until the next `_add`, the slot freed), TRUNCATED while
  more is wanted -- a resent piece is that too -- CONSTRAINT for a piece
  that cannot be, BOUNDS for no free slot or a message too large. The
  stride rules are fuzznet's, above. A piece behind a sealed region is
  taken through its gate.
- `NAME_missing(t, key, first[], count[], cap, most)`: ranges, each at
  most `most` pieces; the key is the conversation table's `_key(...)`.
- `NAME_expire(t, now)`: drops what is `timeout` past its first piece.

The key ceiling (0042's `KEY_MAX_BYTES`) moved 32 -> 64 for this: fuzznet
keys a message by its sender's 32-byte static key, the message number and
the piece count, 38 bytes.

Held by `test/unit/test_one_message_from_many_datagrams.py`: in order, last
first, one alone, duplicates, each refusal, ranges, expiry, capacity and a
full table, under ASan and UBSan; 3000 shuffled, duplicated messages
reassembling exactly; the sealed form. Python has the same table --
`add` answering the message or None and raising where C refuses, held to
the same cases and 500 shuffled messages. Rust has it laid out as C's,
fixed arrays in a `no_std` runtime, `add` answering `Ok(Some(message))`,
`Ok(None)` or the refusal. C++ has it too, allocating nothing, `add`
answering `err::ok` with the message, `err::truncated` while more is
wanted, or the refusal. Building it found the C++ conversation and
drive headers declaring one nested view per member, so a key reading two
parts through one struct (`h.msg`, `h.sender`) did not compile; each is
named after its binding now.

## A fuzz harness (2026-11-21)

`gen-fuzz` gives each table a harness: the fuzzer's bytes as frames (a
two-byte length, a clock step, the frame), each that views and validates
handed to `_add`, then `_missing` for every message held and `_expire`.
What comes back is held to the table's bounds with `abort`. The first
frame's key bytes are copied into each later one, the relation harness's
device, or pieces would meet one draw in 2^112. A piece behind a sealed
region is declined by name: the harness has no key. Sixty seconds of
libFuzzer took the fixture from 83 to 148 edges and found nothing; with
the stride bound loosened (`CAPACITY` for `CAPACITY / count`) UBSan
stopped it inside the table within two minutes.

Building it found the relation harness calling a variable struct's view
without the length it takes, so a relation over any frame with a body
had a harness that did not compile. Only fixed participants had met it;
DNS's harness is unchanged byte for byte.

## A piece saying another count (2026-11-21)

Every backend took a message's count from its first piece and checked a
later piece's index only against that piece's own count. Where the
relation's key leaves the count out -- nothing requires it in -- a later
piece could say a larger count, and was placed at `index * stride`, past
the slot: a write half a megabyte beyond the table in C and C++ (a SEGV
in `memmove` under ASan), a slice panic in Rust, a KeyError at the join
in Python. The fuzz harness could not reach it, its fixture's key holding
the count. A piece whose count is not its message's is now refused as
malformed, in all four, and the message completes as before; held by a
fixture whose relation has no count, failing in C when the check is
taken out.

The four tables are now held to each other as well: one seeded stream of
3000 colliding, malformed and late pieces -- counts disagreeing with
their message's, lengths off the stride and empty, a count past a slot, a
clock wrapping past 2^32 -- with every answer compared, what `add` said
and gave, what `missing` lists for every key, what `expire` dropped.
Every kind of answer occurs in it, and loosening one backend's stride
bound fails it at the first piece that bound decides.

The driver does not call the table itself, which the proposal above had
it doing in place of `part_held`. The completed message is the pieces'
payload, not a reply the relation can match, and fuzznet's own loop
peeks each piece and matches only the completing one (20261121T0600Z,
item 2): the caller adds each piece and hands on what completes.

## What fuzznet needs to move onto it (inbox 20261122T1804Z)

Measured by fuzznet against this table as generated, before moving its
`chunk/reassembly.c` (648 lines, nine call sites over seven table
instances) onto it. Six gaps, in its order of cost:

1. a cap on the slots one value of a key field holds -- the sender --
   its DoS bound (`per = f.head.sender, 1`), refused as BOUNDS;
2. **forget a message by its key**, for an exchange the caller abandoned;
3. an add from parts already opened (key, index, count, bytes), for a
   caller that verifies a piece itself before the table sees it;
4. a per-piece deadline (`expires = f.sealed.expires_at`), the slot's
   the earliest seen, and a piece already expired refused;
5. the bounds at init, in the caller's memory, the schema's numbers as
   maxima -- seven instances of one declaration at different sizes, and
   embedded builds sizing them down;
6. a 64-bit clock, or a word that seconds suffice.

**Built (2026-11-22): 2.** `NAME_forget(t, key)` in all four -- C and
C++ answer 1 where a message was held and 0 where none was, Rust `true`
or `false`, Python 1 or 0 -- keyed as `_missing` is. The four-table
stream test forgets a key on every fifth clock value, and the four agree
on every answer, the forgetting among them.
