# 26.643: The fifth count, and a field read three times before the right question

Status: recorded
Date: @ -31306,0 +31307,46 @@ reproductions, in a file that was not its own.
Source: `project.md` section 26, where it was written

`walker/report.py` answers `count=` for a run the message sizes now --
`_sized_runs` as the complement of the four lists that existed, and
`walk.sized_run_count` beside the four counters. mqtt's two filter
lists, ble's reports, message's recs and edges' segments.parts are
counted, which closes the first of 26.641's two obstacles.

**The count comes from the EXTENT, and getting there took three
readings of one field.**

    first   `size_code` computes the member's byte extent        wrong
    second  it means elements here and bytes there, so the
            packer must record the unit                          too big
    third   the count follows from `size_bits`, which already
            resolves both forms                                  measured

The first was read off one call site and generalised. The second was
measured and true -- `size_code` evaluates to 12 for
`mqtt.subscribe_body.filters` over two six-byte subscriptions, where a
counted run's evaluates to a number of elements -- but it answered a
question nobody needed to ask. The third is that `size_bits` already
walks the elements for a variable run and multiplies for a fixed one, so
the extent is right for both forms and the count is the extent divided
by the element's size, or a walk inside it where the element has none.

**The lesson is not about `size_code`.** Each reading was a better
answer about the wrong field, and the right move was to ask what the
COUNT needs rather than what the field means. Two corrections published
in one session, both to my own entries, and the second one over-shot --
which is the direction a correction tends to go when it is written in
the same breath as the mistake it fixes.

A test asserts both sub-cases through `report._members` rather than
through the counter, for the reason the alignment test gives: a helper
that returns the right number and a renderer that never calls it are
indistinguishable from the lists.

**The probe stays off.** The walker gap is closed and the second
obstacle is not: the four backends still answer a count differently
where the message lies about it, C in `uint32_t` and the other two
wider, and which answer is right is a decision about what a count
larger than the frame means. `HELD_BACK` now carries one live reason
instead of two, with the closed half struck through where somebody
turning it on will read it.
