# 26.807: C names what a parent hands a child

Status: recorded
Date: 2026-11-02
Source: 0068 step 2's note that a C caller supplies the argument itself

    struct vol { u16 block; entry(block = block) ent; entry(block = 2) two; }

C's view carries no arguments (`_argument_tail` says why), so a caller
holding `situ_vol_ent_view`'s result passes `block` to every accessor on
`entry`. Until now the only way to know what `vol` hands `ent` was to
re-derive the schema's expression by hand. That is the wrong-number
failure 0050 exists to prevent, moved into the caller.

## The change

For every member of a struct, or of its variants' arms, that takes
arguments, C emits one function per argument:

    static inline uint16_t situ_vol_ent_arg_block(situ_view_t view);

It is the argument's expression rendered over the parent's view, which
is the same rendering the parent's own calls into `entry` use. It is
emitted after the offset functions, since an argument can read a member
at a dynamic offset. C++, Rust and Python need none, because the child
view they return carries its arguments.

## Tests

`test_c_says_what_a_parent_hands_a_child.py` compiles a driver against
the header and reads 258 (`vol.block` from `01 02`) and 2 (a constant).
With `situc/codegen/c/emit.py` reverted it does not compile.
