# 26.997: IEEE 802.3 Manchester was Thomas's

Status: recorded
Date: 2026-11-13
Source: found while writing 26.996's test, which asserted the published
pattern and got the other one

**The two tables were swapped.** `NAMED_CODES` gave `manchester_802_3`
a one as `10` and a zero as `01`, and `manchester_thomas` the reverse.
IEEE 802.3 puts the complement of the bit in the first half of the cell
and the bit itself in the second, so a one is LO then HI -- `01`, a
rising edge -- and a zero `10`. G.E. Thomas's original convention is the
inverse. So what situ called 802.3 was Thomas's, and the other way round.

**Sources**, all secondary, since the clause itself (802.3 section 7.3)
was not retrieved, and agreeing on the rule:

- SMSC LAN91C111 user manual, an 802.3 controller: "the first half of
  the data bit contains the complement of the data, and the second half
  of the data bit contains the true data".
- itwissen.info: the first half carries the complement, the second the
  value, "specified for IEEE 802.3 Ethernet".
- Digi-Key, "Old, but Still Useful: The Manchester Code": 802.3 and 802.4
  use a rising edge for a one, Thomas's a falling edge.

Some secondary pages state the opposite, which is how two conventions
under one name came about; the record follows the complement-first rule
because it is stated as the standard's and by a part that implements it.

**Why nothing caught it.** Every backend reads the one table, so the
differential agreed; round trips cannot see an inversion; and the two
tests that pinned "published" vectors -- `test_kernels`' C probe and its
`TABLE_CODES` -- had been written from the same reading as the table, so
they were situ checked against situ under the standard's name. The
`std/codecs.situ` note says no property can see the inversion, and the
wire and map contracts for `std/kernels.situ` are unchanged for that
reason.

**What moves.** Both table entries swap, and so do the two vectors: 0xB0
encodes as `65 AA` under 802.3 (it was `9A 55`), and the two-bit input
`01` as `1001`. Any message encoded under the old `manchester_802_3`
decodes under the new one as its complement; such a consumer should name
`manchester_thomas`, which is the code it was actually using. No example
in this tree uses either.
