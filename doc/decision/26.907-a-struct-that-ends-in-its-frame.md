# 26.907: A struct that ends in its frame has a view

Status: recorded
Date: 2026-11-06
Source: RTP's two bodies had no view, and neither had MQTT's PUBLISH

    struct plain  { u8 kind [max = 9]; u8 rest[remaining]; }
    struct nested { u8 head; plain body; }

Header, then a body that runs to the end of the frame, is most of what a
protocol is. Such a body had no view as an arm or a nested member, so it could
not be read and `validate` never looked inside it: `kind` of 200 passed in all
six readers, and four of MQTT's bodies were unreachable, PUBLISH among them.

`has_computable_extent` said no because the length is the view's and not the
struct's. Its own docstring gave the answer: "an instance of the struct is
exactly whatever view it was handed". That is a number, so it says yes now.

The extent has to BE the view, and not the sum it first came out as. The near
miss sweep showed why: a `[remaining]` run of records is measured by walking
it, a walk stops at a cut element, and a view narrowed to that hid the element
from `validate`. A truncated MQTT SUBSCRIBE validated clean. Where every arm
ends in the frame the extent is the view's length, in all four backends, and a
struct flag says so to the walkers.

Two things it must go on refusing, and each has a name:

- `has_element_extent`: an element of a run. The first would take the rest.
- `ends_in_the_frame` in `frameable`: `required`. A prefix of a stream cannot
  say how long such a struct is; the transport can.

A member after such a nested struct has no accessor, as before, and is the same
question as the resizing region with a trailer, which is parked with the holder.

`example/mqtt` still reads a packet identifier as payload. A parameter says it
now, and the file's comment says so, but `gen-tests` hands no arguments.
