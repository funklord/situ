# 26.829: the fourth artifact reached one language

Status: recorded -- the Rust half of `gen-tests` built; C++ and Python, and
the other two generators, still reach fewer languages than section 1 implies
Date: 2026-11-03
Source: `project.md` sections 1 and 22; the CLI's own `--help`

Section 1 says `situc` generates four things, and names four languages:

- accessors "in C, C++, Rust and Python"
- a capability map
- design advice
- "test scaffolding: golden-vector tests and a fuzz harness per schema"

**Walked against the CLI rather than against a record, the fourth reached
one language.** `situc build --target` takes `{c,cpp,python,rust}`.
`gen-tests` and `gen-checks` took **no `--target` at all**, and `gen-fuzz`
takes `{c,cpp}`. So a user who generated Rust or Python accessors got no
golden-vector suite for them, no capability-conformance suite, and no fuzz
harness -- and nothing in the tree marked it open, because every one of
those generators works perfectly for the language it serves.

| artifact | C | C++ | Rust | Python |
|---|---|---|---|---|
| accessors | yes | yes | yes | yes |
| golden vectors | yes | no | **yes, now** | no |
| capability checks | yes | no | no | no |
| fuzz harness | yes | yes | no | no |
| derived codecs | yes | via C | yes | yes |

## One gap in that table was not a gap

`gen-derived` takes `{c,rust,python}` and no `cpp`, which reads as a C++
user being unable to use a schema with `impl x derived`. It is by design and
it works: the C++ header declares the codec entry points inside an
`extern "C"` block, so a C++ consumer links the C implementation. Checked
end to end rather than inferred -- a C++ caller compiled against
`edges_derived.o` and run prints `scramble_decode -> 4, crc7(in,4) -> 100`.

Worth recording because the table invites the wrong conclusion, and the
answer is one `extern "C"` thirty lines into a generated header.

## What was built

`situc gen-tests --target rust` emits a test crate root: `mod situ_rt;`,
`mod <name>;`, and the cases in a `#[cfg(test)] mod vectors`, which is what
`rustc --test` compiles. Over every schema in the tree that has a vectors
file: **27 schemas, 102 tests, all compiling and passing, none refused.**

**One vector file, one parser, one validator.** `rust/vectors.py` imports
`parse_vectors` and `_check` from the C backend rather than reimplementing
them. The vector file is language-independent, and two copies of "is this
vector well formed" is the shape this run spent four commits removing -- one
question answered in two places from different text. So a vectors file
naming a field the schema does not have is refused for Rust exactly as for
C, and the length rules that took 26.36 and a BMP header to get right are
not re-derived. The type name comes from the Rust backend's own `_pascal`
for the same reason.

`refuse_parameters` is called first, which is the whole family's bargain:
`validate` takes the argument tail and a `parameter` gets no accessors, so
the generator declines the schema rather than emitting a suite nobody can
build. Gated, because a new member of that family that did not call it would
be the defect the family is named for.

## What it does not do, said with a number

**Per-field expectations are read and schema-checked, and not yet
compared.** The shared validator does the reading and the checking; the
Rust body asserts only that the bytes take a view and that validation
accepts them.

That is not nothing -- it is what a vector says before it says anything
about a field, and it catches the two faults a Rust accessor can have that
no cross-backend comparison would notice: refusing bytes the layout admits,
and admitting a length it should not. The differential compares the four
backends against each other, so it cannot see all four agreeing and all
four being wrong about a committed vector.

The generated file prints the count it is not comparing -- 197 across the
corpus -- and names `--target c` as the suite that does. Silence there would
read as coverage of the input, which is this family's own rule and the one
`gen-codec-tests` states for a signature that claims nothing.

The positive control: truncating a vector's byte array to one byte fails
that case and nothing else, so the assertion is not vacuous.

## What is still open, and it is work rather than a decision

The expectation comparison is the second step and the larger one: an
expectation takes the form its field admits, and the C emitter's own history
is that both the byte-run form and the nested-struct form were first written
as though every field were a scalar. Whoever does it should expect that to
be where the work is, not in the plumbing.

`gen-tests --target cpp` and `--target python`, `gen-checks` for anything
but C, and `gen-fuzz` for Rust and Python are the rest of the table. None is
a decision -- section 1 states the artifacts and the languages, and these
are the artifacts not reaching them.
