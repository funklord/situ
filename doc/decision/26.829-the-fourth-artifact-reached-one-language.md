# 26.829: the fourth artifact reached one language

Status: recorded -- `gen-tests` reaches all four languages now, which makes
it the first of section 1's four artifacts to do so. `gen-checks` and
`gen-fuzz` still reach fewer
Date: 2026-11-03
Source: `project.md` sections 1 and 22; the CLI's own `--help`

Section 1 says `situc` generates four things, and names four languages:

- accessors "in C, C++, Rust and Python"
- a capability map
- design advice
- "test scaffolding: golden-vector tests and a fuzz harness per schema"

**Walked against the CLI rather than against a record, the fourth reached
one language.** `situc build --target` takes `{c,cpp,python,rust}`.
`gen-tests` and `gen-checks` took **no `--target` at all**, and `gen-fuzz`
takes `{c,cpp}`. So a user who generated Rust or Python accessors got no
golden-vector suite for them, no capability-conformance suite, and no fuzz
harness -- and nothing in the tree marked it open, because every one of
those generators works perfectly for the language it serves.

| artifact | C | C++ | Rust | Python |
|---|---|---|---|---|
| accessors | yes | yes | yes | yes |
| golden vectors | yes | **yes, now** | **yes, now** | **yes, now** |
| capability checks | yes | no | no | no |
| fuzz harness | yes | yes | no | no |
| derived codecs | yes | via C | yes | yes |

## One gap in that table was not a gap

`gen-derived` takes `{c,rust,python}` and no `cpp`, which reads as a C++
user being unable to use a schema with `impl x derived`. It is by design and
it works: the C++ header declares the codec entry points inside an
`extern "C"` block, so a C++ consumer links the C implementation. Checked
end to end rather than inferred -- a C++ caller compiled against
`edges_derived.o` and run prints `scramble_decode -> 4, crc7(in,4) -> 100`.

Worth recording because the table invites the wrong conclusion, and the
answer is one `extern "C"` thirty lines into a generated header.

## What was built: Rust

`situc gen-tests --target rust` emits a test crate root: `mod situ_rt;`,
`mod <name>;`, and the cases in a `#[cfg(test)] mod vectors`, which is what
`rustc --test` compiles. Over every schema in the tree that has a vectors
file: **27 schemas, 102 tests, all compiling and passing, none refused.**

**One vector file, one parser, one validator.** `rust/vectors.py` imports
`parse_vectors` and `_check` from the C backend rather than reimplementing
them. The vector file is language-independent, and two copies of "is this
vector well formed" is the shape this run spent four commits removing -- one
question answered in two places from different text. So a vectors file
naming a field the schema does not have is refused for Rust exactly as for
C, and the length rules that took 26.36 and a BMP header to get right are
not re-derived. The type name comes from the Rust backend's own `_pascal`
for the same reason.

`refuse_parameters` is called first, which is the whole family's bargain:
`validate` takes the argument tail and a `parameter` gets no accessors, so
the generator declines the schema rather than emitting a suite nobody can
build. Gated, because a new member of that family that did not call it would
be the defect the family is named for.

## And C++, which completes the row

`situc gen-tests --target cpp` emits a standalone program rather than a
framework suite: the C target uses cmocka and the C++ fuzz harness uses
libFuzzer, and neither is a thing to ask a consumer for. Section 24's
no-third-party rule is about what situ asks of the people who use it as
much as of itself, so this counts its own failures, names each one and
exits non-zero -- which is what a make target reads. 27 schemas, 102 cases,
all building and passing.

**So one of section 1's four artifacts now reaches all four of its
languages**, and the same 102 cases are asked in each. That is the property
worth having over the count: one vector file, four suites, no target
quietly skipping a construct it cannot express.

The gate for that is keyed on the case symbol every emitter names its body
after, and **its limit is written into it**: with the C++ emitter cut to one
case every symbol still appeared, because `main` dispatches to all of them
and a text check cannot tell a call from a definition. What catches a
dropped body is the compiler -- `error: 'header_minimum' was not declared in
this scope` -- so the generate-compile-run sweep is the gate for that and
the unit gate is for the case nobody emitted at all. An earlier version of
it keyed on four per-language markers and two were wrong about their own
language, which is a count inheriting its detector.

## And Python, which is the one that matters most

**Python has no compiler.** A generated C, C++ or Rust accessor that names a
field wrongly, or builds an expression that does not typecheck, fails at the
build; the Python one fails at the call. So for a Python consumer this suite
is not a second opinion, it is the first time the generated accessors run at
all.

`situc gen-tests --target python` emits a `unittest` module -- not pytest,
because section 24 requires `situc` itself to run from a bare interpreter
with no third-party packages, and a suite handed to a user should ask no
more than the compiler does. Over the same 27 schemas: **102 tests, all
passing**, the same count as Rust because they are the same cases.

**And the Python half found its own bug the moment it ran, which is the
argument for the target in one sentence.** The first version called
`at(msg, 0)` for every struct. A variable struct's `at` takes the message
length and a fixed one's does not -- the Python backend branches on
`layout.is_fixed_size` -- so **13 of the 27 vector files raised
`TypeError: at() missing 1 required positional argument: 'length'`**. That
is 26.36 in another language: the C emitter learned the same thing from a
vector for every real protocol in the tree, and its own comment says so.

Rust did not have the fault because `new(&BYTES)` takes a slice and the
length is in the slice. The two backends ask the same question and only one
of them can get this wrong, which is why running the generated suite is not
optional for the one that can.

## The Python half compares the scalar expectations now

Measured before building it, which is what made the slice worth having:
of the corpus's **197 expectations, 142 are a plain scalar against an
integer** -- 72 per cent. The rest divide into four classes for four
different reasons, and each is its own piece of work:

| n | class | why it is declined |
|---|---|---|
| 22 | a field inside a nested struct | ~~reads through its own view~~ compared in Python; see below |
| 18 | a C enum constant, `SITU_LEAP_INDICATOR_NONE` | ~~not the Python enum's spelling~~ resolved to its number; see below |
| 11 | a byte run | ~~compares as bytes, not as a number~~ compared now; see below |
| 4 | a text number | ~~its getter is fallible~~ compared in Python; see below |

So `--target python` emits `self.assertEqual(view.<field>, <value>,
"<field>")` for the 142 and **says in the module how many it compared, how
many it did not, and why each class was declined**. A suite that compares
72 per cent of its input and does not say so reads as coverage of all of
it, which is this family's own rule.

The C integer suffix is stripped rather than refused: `0xDEADBEEFu` is in
`test/schema/header.vectors` and is the same number without it. Allowing
it moved the comparable share from 140 to 142 -- small, and also two
expectations that would otherwise have gone silently uncompared.

**Watched discriminating**, which is what `test/generated/Makefile` did
for the C target and records: `length = 1501` against bytes that say 1500
fails with `AssertionError: 1500 != 1501 : length`. A comparison nobody
has seen fail is not one.

## All three compare the scalars now, and the veto is per backend

Rust and C++ got the same comparison. The classifier moved to
`situc/codegen/__init__.py` beside `refuse_parameters` when the second
backend needed it: it answers a question about the vector FILE, so it must
have one answer, and leaving it in `python/vectors.py` would have made the
Rust emitter import the Python one -- the shape that makes a change to one
backend break another.

**But "can this be compared against an integer" is not only a question
about the file, and Rust is where that showed.** An enum-typed field's Rust
getter returns `Option<T>`, because an unknown value is not a variant, so

    assert_eq!(view.pid(), 0x2D, "pid");
    //                     ^^^^ expected `Option<PacketId>`, found integer

`example/usb` and `example/netlink` are the two schemas it fires on and
they are the two that failed to compile. Python needs no such veto, an
`IntEnum` comparing equal to its number; C++ needs none, `static_cast`
from an enum class to an integer being legal. **One shared question, three
backend vetoes, and only one of them is non-empty** -- and the count
subtracts the vetoed ones, or the module would overstate what it compares.

**So the three do not compare the same number, and saying "142" of all of
them would have been the convenient figure rather than the measured one:
Python 142, C++ 142, Rust 138.** The four are the enum-typed expectations
in those two schemas. Counted by running each emitter over the corpus and
matching its own comparison form, rather than by reasoning from the two
schema names.

It was caught by the corpus gate and by nothing else, which is the whole
reason that gate builds the generated code rather than reading it. The task
that ran it reported exit 0 while the pytest log said `2 failed, 79
passed`: read the gate log, not the task status.

## The C enum constants are resolved, not declined

`SITU_LEAP_INDICATOR_NONE` is the C backend's spelling and no other
language's, so it cannot be spliced -- **but the schema knows the number,
and the number is what the four languages agree on.** 18 of the 197
expectations were this shape and were the largest class no target could
compare.

So the shared classifier resolves them, and **Python and C++ went from 142
to 159 of 197 -- 81 per cent.** Rust gains none and correctly: every one of
the 18 is on an enum-typed field, whose getter returns `Option<T>` whatever
the right-hand side says.

The mapping is built by asking `names.macro` for each member's constant
rather than by taking the constant apart, which inverts the rule the C
backend actually emits with. Guessing at `SITU_` plus an underscore split
breaks on an enum or member whose own name contains one -- `leap_indicator`,
`last_minute_61` -- which is most of them.

**And Rust is handed the constants although it declines every expectation
they unlock**, which looks redundant and is not: without them the shared
classifier reports a C enum constant as "not an integer literal", which is
true and is not the reason. The obstacle is the getter's type, and a reader
who wants to fix one of these needs to be told which. That is 26.828's
shape met in a reason string rather than in a claim.

## The byte runs are compared too

One shape, three spellings: `memoryview` in Python, `&[u8]` in Rust,
`::situ::rt::bytes` -- a `span` with `data()` and `size()` -- in C++. The
count comes from `_byte_run` and the value from `_hex`, both the C
emitter's, which is why `00:1A:2B:3C:4D:5E` and `C0 A8 01 0A` are the same
kind of thing here.

**Rust 149, Python 170, C++ 170 of 197 now** -- 86 per cent for two of the
three. This is the class that made `example/arp`, twenty of whose
twenty-eight bytes are addresses, unable to state almost anything about
itself before the C emitter grew the form (26.35).

Two details worth keeping. `bytes(...)` around the Python getter is not for
the comparison -- a memoryview already compares equal to bytes -- but so
that a failure prints the bytes instead of `<memory at 0x...>`. And C++
compares the length as well as the content, because a span of the right
bytes and the wrong length is not the run the vector names.

**And the ordering is load-bearing: nested is asked before byte run,
exactly as the C emitter orders it.** A byte run inside a nested struct
reads through that struct's own view, so the dotted path is not a method
name; asking the byte-run question first emitted `view.header_magic()` for
`example/cpio`'s `cpio_entry.header.magic` and nothing defines it.

**Caught by a count that did not match** -- 13 comparisons where the
byte-run class measured 11 -- and not by the compiler. Two of the class
were nested and had been counted under nested, so the emitters were
reaching two expectations the classification said belonged elsewhere. The
cheaper place to catch it was the arithmetic, and the only reason the
arithmetic was there to check is that this record carries the counts.

## Python reaches a nested field by chaining, and the other two cannot yet

A nested struct's **Python** accessor is a property returning its own view,
so the dotted path a vector writes IS the attribute chain:
`view.head.magic`. Both leaf kinds come free, a nested byte run and a
nested scalar taking different right-hand sides with the same chain.

**Rust's accessor returns `Result<Inner>` and C++'s takes an out-parameter**,
so each needs a block where Python needs a dot. That is a real difference
in the generated API rather than an oversight, and it is why the per-target
counts now diverge further:

| target | compared, of 197 |
|---|---|
| Python | **197 -- all of them** |
| Rust | **186** |
| C++ | **186** |

The flag that carries it is `nested`, and it is the veto pattern inverted:
a backend says what it can REACH rather than what it declines. Rust's enum
veto says the opposite about the same question, and both belong to the
backend rather than to the shared classifier, which answers only about the
vector file.

**And `tally` was not counting byte runs**, found while adding this: it
asked `comparable` alone, so every generated preamble had been understating
what its own suite compares since the byte-run class landed. A count that
is computed by one path and used by another, which is this run's most
expensive shape in its fifth instance.

## Python compares all 197 now, and the last one was a minus sign

Two more classes, both of them Python's to take because the obstacle was
per-backend rather than in the file:

- **A text number's getter is fallible**, and what that costs differs. C
  takes an out-parameter and returns a code, so calling it as a plain
  getter does not compile; Python makes it the one property that can RAISE,
  which for a golden vector's valid digits is simply the number. So `text`
  joined `nested` as a flag a backend sets about itself.
- **`example/ntp`'s `precision = -23`** is an `i8`, and `INT_LITERAL` did
  not admit a sign. It was the LAST of the 197 that nothing compared, and
  it was found by asking which one remained rather than by assuming the
  tail was empty -- the same question that found the other four classes,
  asked once more when the obvious ones were gone.

Admitting the sign also raised Rust by one and C++ by one, which is the
tell that the regex was a shared gap and not a Python one.

**So one of situ's four stated artifacts reaches all four of its stated
languages, and in one of them it compares every expectation the corpus
states.** Rust at 150 and C++ at 171 are held back by two things that are
their own generated APIs rather than oversights: a nested accessor
returning `Result` or taking an out-parameter, and Rust's enum getter
returning `Option<T>`.

## Rust compares an enum field against its variant

An enum-typed field's Rust getter returns `Option<T>`, so the number is not
the right-hand side -- **the variant is, and the number is how we find
which**. 18 expectations, and Rust goes from 150 to 171, level with C++.

Where the value names no variant the getter returns `None`, and that is
what a wrong vector and an unknown value look like alike, so those are
declined with the reason saying which rather than asserted.

**Two faults the corpus gate caught and nothing else could**, both from
compiling the output rather than reading it:

- **the type needs qualifying by its module.** Unqualified gave
  `error[E0433]: use of undeclared type PacketId` for eight of the 27
  schemas: the cases live in `mod vectors` and the generated module is a
  sibling, so nothing of its is in scope by a bare name.
- **the accessor needs the Rust backend's own `_ident`, not `c_name`.** A
  field called `type` is a Rust keyword and its accessor is `r#type`.
  `test/schema/header` has one and it was the last schema this broke --
  the fourth time in this run that reaching for the wrong backend's name
  function cost a build.

## And all three reach a nested field, each its own way

The last substantial class, and it landed three different ways because the
three generated APIs are three different things:

- **Python chains a property** -- `view.head.magic` -- a nested accessor
  being a property that returns its own view.
- **Rust chains the accessor's `Result`** --
  `view.head().expect(..).magic()` -- one expression, because `expect`
  yields an owned view whose borrow of `view` outlives the call on it.
- **C++ declares a view and passes it** to an out-parameter, one
  declaration and one check per level, with an early return on failure as
  the view and validate checks above it already do.

None of those is a choice. Rust 186 and C++ 186 of 197 now, from 171.

**The failure names the LEVEL and not the case** in the two that can fail
reaching it, because a vector whose bytes take a view can still fail to
reach a nested one -- a bounds check per level is what section 12.3 asks
for -- and "`one` failed" would not say which.

## What the other two still do not do The shared validator does the reading and the checking; the
Rust body asserts only that the bytes take a view and that validation
accepts them.

That is not nothing -- it is what a vector says before it says anything
about a field, and it catches the two faults a Rust accessor can have that
no cross-backend comparison would notice: refusing bytes the layout admits,
and admitting a length it should not. The differential compares the four
backends against each other, so it cannot see all four agreeing and all
four being wrong about a committed vector.

The generated file prints the count it is not comparing -- 197 across the
corpus -- and names `--target c` as the suite that does. Silence there would
read as coverage of the input, which is this family's own rule and the one
`gen-codec-tests` states for a signature that claims nothing.

The positive control: truncating a vector's byte array to one byte fails
that case and nothing else, so the assertion is not vacuous.

## What is still open, and it is work rather than a decision

The expectation comparison is the second step and the larger one: an
expectation takes the form its field admits, and the C emitter's own history
is that both the byte-run form and the nested-struct form were first written
as though every field were a scalar. Whoever does it should expect that to
be where the work is, not in the plumbing.

`gen-checks` for anything but C, and `gen-fuzz` for Rust and Python, are
the rest of the table, and they are not the same size as each other or as
what came before. Sized so the next pass need not:

- **One expectation class remains, and it is the smallest**: C++'s 4 text
  numbers, whose getter takes an out-parameter and returns an error there
  as in C. **Sized, because the cost is not in the emitter**: naming the
  out-parameter's type needs `cpp/emit.py`'s `_ctype`, which is a METHOD
  on the emitter class and so not importable. Doing it properly means
  extracting it to a module-level function and delegating -- 19 call sites
  that keep working unchanged -- rather than writing the two-line rule a
  second time, which is the fault this run spent four commits removing.
  Mechanical, and in an 11,000-line file, so it wants the C++ suite behind
  it rather than the tail of a run.

  Everything else in the five classes is done in every language that can
  express it: Python 197 of 197, Rust 186, C++ 186. Rust's remainder is
  enum values naming no variant, where the getter returns `None` and a
  wrong vector is indistinguishable from an unknown value. Each needs a comparison form per
  language and nothing else -- the byte runs are `memoryview` in Python,
  `&[u8]` in Rust and `::situ::rt::bytes` in C++, so the shape is the same
  three times. The classifier and the counts are already in place, so each
  class is one function per emitter plus its gate.
- **`gen-checks` for three languages is not small.** `situc/codegen/c/checks.py`
  is **3239 lines over 70 functions**, asserting three axes -- `MUTATE`,
  `OFFSET`, `SIZE` -- and emitting 26 test functions for `test/schema/header`
  alone. That is a port rather than an increment, and the vector work's
  pattern does not carry: a vector suite reads committed data, where this
  one derives assertions from the capability map.
- **`gen-fuzz` for Rust and Python genuinely waits**, which is different
  again. Rust wants `cargo-fuzz`, not installed here; Python wants
  `atheris`, a third-party package section 24 forbids situ to depend on.
  Neither is a size and neither is a decision -- they are a toolchain and a
  policy, and the policy one may have no answer that keeps section 24. None is
a decision -- section 1 states the artifacts and the languages, and these
are the artifacts not reaching them.
