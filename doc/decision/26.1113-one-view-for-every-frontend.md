# 26.1113: one view for every frontend, and the window on a terminal

Status: recorded
Date: 2026-11-20
Source: the holder, 2026-11-20: "make gui/tui just like the other projects
... we will still need non-Qt tui as well ... it needs to work without huge
deps too. Can we share most of the pertinent code at least?"

0034 kept the editing RULES in `editor/`, and the three frontends held
none. The DISPLAY was not shared: the text table and the curses TUI drew
from `text.render_rows`, and the Qt window had its own C++ copy of what a
value reads as, which rows may be edited, whether a typed value is hex or
a number, and what the header says. They had already drifted -- a
`[secret]` field read `<withheld: 4 secret byte(s)>` in the table and
`<withheld: secret>` in the window, and the window showed no write marker,
only the sentence behind it.

## The change

- **`editor/view.py`** decides what a frontend shows: `heading`, one `Row`
  per field (offset, size, name, value, marker, note, cost, how an edit is
  put, whether it opens a nested struct) and `trailer`. `render_rows`
  draws the text table from it, which the curses TUI uses, and
  `--format json` carries it as `view`, which the window draws cell for
  cell. The window no longer reads a field to word a cell. What a
  frontend still decides is only what its medium decides: the table
  shortens a long byte run to fit a line, and a window has room for all of
  it.
- **`situ-edit --put NAME=TEXT`** stores text read the way the field shows
  it -- hex for a byte run, a number otherwise. `view.put` is that rule, and
  the TUI's prompt and the window's cell both send it, so neither decides
  between `--set` and `--set-bytes` any more.
- **The window is built as the siblings build theirs**: `gui/gui.pro`
  under qmake, `make gui`, `situ-edit-gui` (renamed from `situ-edit-qt`,
  as hull's is `hull-gui`), and **vendor/qtty** as a submodule, which `make
  gui` fetches where it was never checked out. With it the same window
  runs on a terminal (`--tui`, or on its own where there is no display);
  `--snapshot COLSxROWS` prints it as the terminal shows it, for the test.
  Without it the window is built alone and `make gui` says so.
- **`make gui-example`** opens the window on NTP's server reply from
  `example/ntp`'s golden vectors (`GUI_FLAGS=--tui` on a terminal).
- **A bit field says where it is in bits.** In bytes, NTP's `leap`,
  `version` and `mode` all read offset 0, size 0 -- three fields at one
  place, none with a width -- and IPv4's flags the same; seen in the
  window's first run on a real message. `Field.bits` carries the bit
  offset and width where either is not whole bytes, the JSON gives it as
  `bits`, and the view shows `byte.bit` (the bit in walk order, as
  `offset_bits` counts it) and a width like `3b`.
- **A missing message or image is a sentence** (`cannot read PATH: ...`),
  not a traceback. It was a traceback in all three frontends, the window's
  status line included, and
  `test_every_frontend_refuses_without_a_traceback` never fed one a path
  that was not there.

## What was weighed

- **Replace the curses TUI with the qtty one.** Rejected: qtty needs Qt
  (QtWidgets and QtDBus), and situ's reason to keep `curses` is that
  `situc`, `situ-edit` and `situ-edit-tui` need Python and nothing else --
  for a tool meant to be in every protocol project's CI and on every
  developer's machine, that is the property worth most. So there are two
  terminal frontends, and they differ by what they need, not by what they
  show: both draw `view`.
- **Port the curses TUI to C++ to share widgets with the window.**
  Rejected: it would give the zero-dependency frontend a compiler and a
  build, and the code worth sharing is not the drawing -- it is the
  wording and the rules, which are Python already and now reach the window
  through the JSON.
- **Keep CMake for the window.** Rejected for qmake because qtty is a
  qmake library with a `.pri`, and hull and netcfgd build their windows
  this way; one build shape per window across the workspace.
