# 26.821: three more backends wrote the parameter

Status: recorded -- fixed in C++, Rust and Python; C is 26.818 and the
differ 26.820
Date: 2026-11-03
Source: `project.md` section 26

**26.818 said "fixed in C" and I did not ask the other three.** They all
had it, and two of them had it worse.

    struct kid { parameter u8 b [stream]; u8 body[b]; u8 mark; }
    struct p {
            parameter u8 b [stream];
            authenticated body { kid(b = b) k; }
            tag u8 mac[16] covers(body);
    }

Each of C++, Rust and Python emitted a writer for `k.b` -- a `parameter`,
which occupies no bytes -- storing at offset 0, the first byte of
`kid.body`:

    void set_k_b(::situ::rt::message &owner, std::uint8_t value) noexcept
    { *(situ_base(raw_) + 0) = static_cast<std::uint8_t>(value); ... }

    pub fn set_k_b(&mut self, dirty: &mut Dirty, value: u8) {
            situ_rt::write_be(self.bytes, 0, 1, value as u64); ... }

    def set_k_b(self, msg: Message, value: int) -> None:
            self._write(0, 1, int(value), signed=False, big=True)

## The half that is worse than C's

All three also emitted a writer for `k.mark`, a field at a dynamic offset
inside the nested member, and computed its offset as **`advance(16,
k_extent())`** -- where 16 is the width of `mac`, the TAG. The answer is
`k`'s offset plus `mark`'s offset inside `kid`, which is 2 at `b = 2`.
They summed the parent's own chain for a member that is not in it.

At 19 bytes the wrong offset is 19, so the bounds check refuses and the
write is a **silent no-op**: a caller writes `p.k.mark`, nothing happens,
and nothing says so. C's version called a `situ_p_k_mark_offset` that
nothing defined, so a compiler stopped it. **The backend with a link step
failed loudly and the three with methods on a view failed quietly**,
which is the asymmetry this tree already records about Python and which
holds for Rust and C++ here too: the fault is identical and only the
instrument differs.

## The fix, and the duplication it removed

The same two carve-outs as 26.818: a `parameter` is not a field, and a
nested member's interior at a dynamic offset is addressed by that
member's own type.

By the time all four backends and the differ needed the second test,
`_inside_a_nested_member` had been written **three times** -- once in C's
emitter, once in the differ, and about to be twice more. It is
`traverse.inside_a_nested_member` now, called by all five. That is this
whole family of records stated as a diff: the fault is two places
answering one question, and writing the answer a fourth time would have
been committing it.

## Both gates were vacuous, measured twice

`test_the_differ_asks_for_setters_that_exist.py` stayed green through a
revert of the carve-out, because the construct lived in
`test_a_block_s_member_takes_its_arguments.py` and not in the corpus. So
`edges.situ` gains `blocked_arg`.

**And the first construct written for it was the wrong one, which is the
instructive part.** It declared `parameter u8 block [stream]` and handed
the child its own parameter -- and the gate stayed green through the
revert a second time, because the four-way driver has ONE argument list
for a whole listing and therefore skips a struct that declares a
`parameter` at all. The construct has to pass a FIELD, which is 26.811's
shape. With `u8 block` the revert fails two tests and names
`blocked_arg.one_block`.

**A construct is in the corpus to ask a question, and a construct that
cannot be reached by the thing that was wrong asks nothing.** Two reverts
is what established which one this was; neither reading of the schema
would have.

## The gate, and a correction to my own instrument

The first version of the parameter gate searched each backend's emitted
text for the setter's name. C qualifies a setter with its struct and the
other three name the method by the member alone, so `set_block(` --
emitted legitimately for `hands_on_arms.block`, a real `u8` field --
matched for every struct whose PARAMETER is also called `block`. It
reported fourteen faults in `edges.situ` and every one was its own
search, and the comment I had written for it claimed the looseness "can
only make this test miss a setter that should not exist, never invent
one". It invented fourteen.

So the gate asks the differ, which is what all four drivers obey and
which names a struct exactly. The four backends were separately measured
to agree on every covered write the differ asks over the whole corpus,
which is what makes that one question rather than four.

**The Rust census needed correcting too.** Adding `blocked_arg` moved
`edges.situ` from 29 subtraction sites to 30, and the census asserted
that a row growing is "the emitter rather than the corpus". It is not: a
row grows when its schema gains a construct as well. That claim was a
count inheriting its detector one level finer than the floor the census
replaced, and the message says now what the row actually buys -- the
question is about one schema rather than the corpus.

## The predicate was wrong, and the corpus construct found that too

`offset_bits is None` was the test for "the parent cannot address this
interior", and it is not one: **`offset_bits` is FRAME-relative.**
`blocked_arg.one.carried.marker.tag` carries `offset_bits=8` while its
byte moves with `payload[block]` four levels up, so it passed the guard
and C emitted

    static inline void situ_blocked_arg_one_carried_marker_tag_set(
                    situ_msg_t *msg, situ_view_t view, uint8_t value)
    {
            if (!situ_in_bounds(view, 1u + 1u, 1u)) { return; }
            ((situ_base(view) + 1u))[1u] = (uint8_t)value;

-- byte 2, where the field sits at 5 for `block = 0`. And the generated
coverage check **wrote through it and passed**, because marking the tag
dirty is all it asserts; a wrong byte marks the tag exactly as well as a
right one.

The question is whether the parent can write the interior as a constant
offset from the nested member. So the test is one thing: **is every
intermediate's TYPE fixed size.**

**The second attempt was too wide and removed two working setters**,
which is worth recording because the commit that pushed it claimed
otherwise. It also required the intermediate to be at a STATIC offset,
and that is not needed: the parent has an offset function for a nested
member of its own, dynamic or not. `covered_tail.head.seq` is the case
-- `head` is a `beacon`, three bytes, sitting after `pad[n]` -- and the
parent addresses it perfectly well as `head_offset(view) + 0`. The
disjunct deleted that setter and its sibling.

It was caught by counting: the commit message said the predicate
"excludes exactly `blocked_arg.one`'s eight fields and nothing else in
the corpus", and re-measuring the claim after the call sites were
simplified gave **ten**. The two extra were the regression. With the
disjunct removed it is eight, which is what the claim said all along --
so the claim was right about the intended behaviour and wrong about the
code, and only a count could tell those apart.

That is `evidence.md`'s rule about quoting a count, met from the inside:
I wrote the number from a measurement taken before the last edit, and
the number is what found the fault.

This is the sixth form of the same fault in one run, and the first where
my own fix was the thing that was wrong. The construct in the corpus is
what caught it -- within minutes of landing, and twice over: once through
`gen-checks`, once through the offset.

## Verified

- Generated output for all 46 schemas is byte-identical to the prior
  commit in all four backends -- 230 files -- for the three emitter
  carve-outs, so they remove nothing any corpus schema had.
- `edges.situ` gains one struct; the images are regenerated and all four
  backends build it, with C and C++ compiling under the project's flags
  and Rust under `rustc -O`.
- Reverting the carve-out fails two tests and names the member.
- **The bytes.** `blocked_arg` at `block = 1`, twelve bytes -- `one` at 1
  with extent 7, `tag` at 8 reading 0xE0..0xE3, `tag_covered` answering
  (1, 7), `required` asking 12, and the child read through its own
  accessors on `one`'s view: `payload`, `trailer`, `checksum`, `kind` and
  the arm's `flag`. Seventeen reads, all agreeing with the hand-computed
  layout. The covered span is the one to check, being what the removed
  setters existed to mark stale.

## The lens

**"Fixed in C" is a status line that should have read as a question.**
26.818 recorded it plainly and I committed it, pushed it, and wrote a
record and a gate before asking whether the other three backends did the
same thing. They are four emitters of one decision; the only reason C was
the one looked at is that C is the one a compiler complains about.

So the rule the run keeps relearning, in its fourth form: **ask every
consumer, not the one that failed** -- and when a record's status names
one backend, that is the list of what was checked, not the list of what
was wrong.
