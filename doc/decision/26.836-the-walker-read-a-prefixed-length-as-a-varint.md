# 26.836: the walker read a `prefixed(T)` length as a varint

Status: recorded -- fixed in `walker/image.py`; the C walker was already
right, which is what made the two walkers disagree
Date: 2026-11-03
Source: found by `test_walker.py::test_the_walker_agrees_with_the_compiled_
backends` on `edges.situ` the moment 26.833 added a `prefixed(u16)` tlv to
the corpus

## What it did

Over a 38-byte buffer whose tlv item declares a value of 8433 bytes:

| reader | verdict |
|---|---|
| C, C++, Rust, Python accessors | 0 items -- "an item of 8433 bytes at 6 runs past the region" |
| the C walker | 0 items |
| **the Python walker** | **1 item** |

The accessors are right. The Python walker accepted a truncated message as
a well-formed one, which for a hostile input is the whole point of the
bounds check it was skipping.

## Why

`decode_number(view, start, max_bytes, terminal_bits, big, fixed=False)`
reads a varint unless told the number is a fixed-width scalar. Its own
docstring names the hazard: without `fixed`, "the image's fallback made
both a ten-byte leb128, so a `u8` tag at or above 0x80 consumed the byte
after it and every offset past that item was wrong (26.664)."

The image carries the bit. `situc/pack.py`'s `_number_params` sets
`TLV_FIXED_WIDTH` for a tag and for a length alike, and says so: "Anything
else that NAMES a scalar is a fixed-width read of that many bytes, flagged
so the walkers do not take it for a varint -- which is what they did, for
every `u8` tag and every `prefixed(u8)` length in the tree."

`walker/image.py` read that bit for the **tag** row and not for the
**length** row:

    image.tlvs[where] = (selector, tag_bytes, tag_terminal,
                         bool(tag_flags & 2),      # big
                         bool(tag_flags & 1))      # fixed

    image.tlv_rules...append((label, kind, default, size,
                              (len_bytes, len_terminal,
                               bool(len_flags & 2)),   # big, and nothing else
                              size_code))

So `*length_rule` spread three arguments where the tag spread four, `fixed`
fell to its default, and a `prefixed(u16)` length was decoded as a varint.
On the failing buffer that reads `0x20` -- top bit clear, so the varint
stops after one byte -- as 32 rather than reading `20 f1` as 8433. 32 bytes
fit, so the item was accepted; the next tag ran off the end, so the walk
returned 1.

## The shape, which is this tree's most frequent one

**26.664 fixed the tag and the length in the packer, and the tag alone in
the image reader.** A clause true of the case that motivated it, asserted
of the class -- the third instance in two days, after 26.665 setting
`endian = scope.endian` on two placements and `marker` on neither, and
26.833's own first predicate answering `BIG` or `little` and nothing else.

What is particular here is **where** the half-fix survived. The packer, the
C walker and all four backends were corrected; one reader of the image was
not, and it is the reader whose whole job is to be the independent witness.
A differential between the accessors and the walker is the tree's strongest
instrument, and it was comparing against a reader that had quietly kept the
bug the comparison exists to find.

## Why nothing caught it for so long

`example/coap` is the corpus's only other tlv with a computed value size,
and it reads `length` out of its own tag rather than a `prefixed(T)`. So
no schema in the tree had a fixed-width length prefix in a tlv at all, and
the arrangement in which the question can be asked did not exist until
26.833 needed one for an unrelated reason.

That is the corpus argument stated again and from the other side: the
construct was added to ask about byte order, and it answered a question
about varint fallbacks that nobody had asked. **A construct pays for itself
twice** -- once for the defect it was added for, and again for the ones it
meets on the way.

## The fix

Read both bits, as the tag row does, and widen `tlv_rules`' type to carry
the fourth element. `walk.py` already spreads `*length_rule` into
`decode_number`, so nothing there changes.

Verified: the walker answers 0 items for the failing buffer, with and
without a marker in the struct, which is what every other reader says. The
C walker needed nothing -- it reads
`len_fixed = (found[22] & TLV_FIXED_WIDTH) != 0` and always has.
