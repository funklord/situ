# 26.770: A placed versioned member stays in the frame

Status: recorded -- fixed
Date: 2026-10-30
Source: `project.md` section 26

    struct varv [version = ver] { u8 ver; u8 n; u8 d[n]; u16 x [since = 2]; }

`x` sits where `n` says. 26.746 put a frame check behind every versioned
accessor's version test, and `_versioned_bounds` returns nothing where
the offset is not a constant, in all four backends. So a whole version-2
message that stops after `d` -- it claims `x` and does not hold it --
was read past by C's getter (`validate` calls it) and written past by
C's and C++'s setters: ASan, heap-buffer-overflow, both directions.
Rust's setter emitter took its dynamic-offset branch before its
versioned one, so `set_x` asked no version at all and stored into a
version-1 message whatever followed `d`: in a stream, the next message.

26.73 already settled what a versioned member at a dynamic offset does
where it does not fit: what every other member the message places does
(26.27). The getter answers zero and the setter writes nothing, after
the version test. C++'s getter and both of Python's accessors followed
it. C's getter and setter and C++'s setter now carry the same `_fits`
guard, and Rust's dynamic setter asks the version first and returns a
`Result`, as its static versioned setter does.

Found by the lens 26.768 left: a `[since]` member handled at a static
offset and not at a dynamic one. The corpus has no versioned member at
a dynamic offset and generates byte-identically.

## Tests

`test_a_placed_versioned_member.py`: C and C++ under ASan, and Python,
read and write `x` in exactly-sized version-1, short version-2,
overrunning, and whole version-2 messages: version refused, zero and no
write, zero and no write, the value written. Rust's setter asks the
version before it stores and builds under the four-way driver. With the
change reverted C overflows on the read, C++ on the write, and Rust's
check fails.
