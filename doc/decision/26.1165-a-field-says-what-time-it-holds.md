# 26.1165: a field says what time it holds

Status: recorded; steps 1, 2 and 3 built
Date: 2026-11-23
Source: the holder, relayed verbatim by fuzznet (inbox 20261123T1050Z,
its sec 368): "Situ should have a very unambiguous way to describe time
units, and it should support all of them, its job isn't to make design
decisions for the user. (for fuzznet I suspect we need programmable and
sub-second, as it may be running over very high performance links, and
low performance links will probably take a different transport shape)"

## The problem

A `replay` window and a `reassemble` table state a clock unit, and the
field the clock is compared against states nothing. fuzznet's frame
declares `u64 expires_at;`: two consumers that read it in different
units, or from different epochs, disagree only as a horizon error, and
nothing in the schema says which of them is wrong. The same holds for
every timestamp in the corpus: NTP's 32.32 seconds since 1900, pcap's
seconds and a sub-second part whose unit the file's magic picks,
cpio's hexadecimal seconds since 1970, an MPEG PTS counting a 90 kHz
clock, Matroska's timecodes scaled by a number in the file's own header,
an RTP timestamp at a clock rate the session agreed.

## The shape

A time is a property of an integer member, stated in two words:

    u64 expires_at [time = ms, epoch = unix];   // an instant
    u32 rtt        [duration = us];             // an interval

**`time = UNIT, epoch = EPOCH`** says the value counts UNITs since
EPOCH. **`duration = UNIT`** says it counts UNITs and is no instant.
One or the other, never both, and `epoch` only with `time` -- an
instant without an origin is the ambiguity this exists to remove, and a
duration with one is a contradiction.

**A unit is a base unit, multiplied or divided by whole numbers:**

    ns    s / 1024    s / (1 << 32)    ns * 100    s / 90000

The base units are `ps`, `ns`, `us`, `ms`, `s`, `min`, `h`, `d`, `week`,
`month` and `year`. The leftmost term is always the base unit, so a
factor may be any whole-number expression without the unit's name
being mistaken for it. A factor is a positive constant in step 1; a
factor read from the message or passed by the caller is step 4 (below),
which is where "programmable" lands.

`s / (1 << 32)` is NTP's fraction, `ns * 100` Windows' FILETIME tick,
`s / 90000` MPEG's system clock: none of them is a decimal unit, and
none needed a word of its own. Nothing narrows the choice, which is
the holder's point -- situ does not pick a set of units it thinks
schemas ought to use.

**`month` and `year` are calendar units**: neither is a fixed number of
seconds, so a value in one converts only to the other (a year is twelve
months), never to seconds. They stand as units because formats use
them -- a card's expiry month, a certificate's validity in years -- and
a schema saying so is better than one saying nothing.

**An epoch is one of five names, or a date:**

| epoch    | origin                  | scale                                   |
|----------|-------------------------|-----------------------------------------|
| `unix`   | 1970-01-01T00:00:00Z    | POSIX: UTC, leap seconds not counted    |
| `ntp`    | 1900-01-01T00:00:00Z    | UTC as NTP counts it, leap seconds not counted |
| `gps`    | 1980-01-06T00:00:00Z    | GPS: continuous, no leap seconds        |
| `tai`    | 1958-01-01T00:00:00 TAI | TAI: continuous                          |
| `caller` | the caller's own clock  | none: a monotonic count with no civil meaning |
| `"YYYY-MM-DD"` or `"YYYY-MM-DDTHH:MM:SSZ"` | that instant, proleptic Gregorian, UTC | POSIX |

The name carries the scale because the scale is what decides whether
two instants a day apart are 86400 seconds apart, and an epoch written
as a date alone cannot say it. `caller` is fuzznet's case: a deadline
on the sender's monotonic clock, meaningful only to a peer sharing it,
and saying so is the unambiguous description -- a schema that wrote
`unix` there would be claiming a civil time nobody keeps. A date covers
the rest (`"1601-01-01"` for FILETIME, `"2001-01-01"` for Apple's
reference date) without situ choosing which of them deserves a name.

**On which members.** Any integer the schema reads as a number: a binary
integer of any width or signedness, a bit field, a text number
(`decimal u32 mtime[11] [time = s, epoch = unix]`), and a `let`
assembling one from parts (step 2's grammar: NTP's two halves are one
instant). Not a byte run, a struct or an enum: none of them is a count.

## The steps

1. **The attribute, its checks and the wire signature.** Parsed and
   refused where it cannot hold -- an unknown unit or epoch, a factor
   that is not a positive whole number, both words or neither epoch,
   on a member that is no number. `wire` writes `time=ms@unix` or
   `duration=us` on the member's line, so two consumers whose schemas
   say different units fail `wire --check` by name.
2. **A `let` takes attributes**, so a time split across fields is one
   value with one unit: `let u64 t [time = s / (1 << 32), epoch = ntp]
   = seconds << 32 | fraction;`. Built: a `let` takes attributes before
   its `=`, only these three, and `wire` writes `let at time=...` for
   one that states a time -- a value stating none adds no line, so no
   signature already committed moves.
3. **The kernels follow the field.** A `replay` window's `expires` and a
   reassembly's `expires` name a field; where that field states a time,
   the kernel's `unit` may be left out and is the field's, and a kernel
   unit that differs from the field's is refused rather than converted
   silently. The clock the caller hands the kernel is then in the
   field's unit -- one number, stated once. Built: `timespec.field_time` follows the path
   from the struct the kernel reads; a duration, a calendar unit or a
   differing `unit` there is refused, and each backend's generated
   comment names the field's unit (`1/90000s`) where the kernel states
   none. fuzznet's `expires_at` is Unix seconds (its reply,
   2026-11-23): `[time = s, epoch = unix]`; its reassembly timeouts run
   on the receiver's own clock.
4. **Programmable units.** A factor that is a field of the message
   (`[time = ns * hdr.timecode_scale]`, pcap's sub-second unit chosen by
   its magic) or a parameter of the struct (`struct frame(tick_ns: u32)`,
   a unit chosen per deployment and handed in at run time) is read where
   the value is. The reader can always tell which unit a value is in,
   because the schema names where the unit comes from.
5. **Generated conversions.** Each reader gains a getter returning the
   value with its unit as a pair (count, numerator, denominator of a
   second) and a runtime conversion to a unit the caller names, which
   refuses an overflow and says when the result is inexact. Between two
   epochs of different scales situ refuses rather than carry a
   leap-second table.

## Rejected

- **A fixed menu of decimal units.** It would answer fuzznet and fail
  NTP, MPEG and FILETIME, which is narrowing the author's choice.
- **`since =` for the epoch.** `since` is a member's version (section
  19); one word with two meanings on one member is a trap.
- **Units on the kernels only, as now.** The field is what both peers
  read; a kernel's unit is one consumer's reading of it.
- **A time type (`time64`).** A width, a signedness and a byte order are
  already the member's; a type would duplicate them, and a text number
  could not carry it.
