# 26.723: the floor 26.693 removed was also a bounds guard

Status: recorded -- fixed in the three backends that lacked the guard
Date: 2026-10-29
Source: `project.md` section 26

Reported by bbq-predictor 2026-10-28, found by five minutes of the same
fuzz case that produced 26.693, against the C++ generated from their own
`src/wire/bbq.situ` at `97d1343`. **A regression from `601fa96`, and their
diagnosis is right:** the floor 26.693 took out of `required` was unsound
as a claim about the message, which is why it went, and sound as a bounds
guard, which is what went with it.

    ERROR: AddressSanitizer: heap-buffer-overflow ... READ of size 1
      #0 situ_get_le16                     situ.h:324
      #1 situ::stations_body::ids_count()  bbq.hpp:5881
      #2 situ::stations_body::framed()     bbq.hpp:6039
      #3 situ::stations_body::required()   bbq.hpp:6076

    uint8_t *p = new uint8_t[5];          // any n < 10
    stations_body::required(p, 5, need);  // reads p[8]

With `n = 0` and `p == nullptr`, UBSan reports "applying non-zero offset 8
to null pointer" at the same line, which is how the fuzzer found it
(input `BAQ=`: kind 4, struct 4, empty body).

## Reproduced in this tree in twelve lines

    struct item { u8 len [min = 1, max = 32]; u8 id[len]; }
    struct body { i64 stamp; u16 count [max = 4096]; item ids[count]; }

`body` is `stations_body` member for member: eight fixed bytes, a `u16`
count at offset 8, a counted run of variable-size records. The same ASan
report, at `situ_get_be16` through `ids_count()`.

## Measured across all four, which is where the answer was

| backend | the guard | behaviour on a short buffer |
|---|---|---|
| C | **emitted, before the run branch** | truncated, need 10 |
| C++ | absent | **reads offset 8 out of bounds** |
| Rust | absent | truncated, need 10 |
| Python | absent | truncated, need 10 |

So three of four lack the guard and only one of the three is unsafe.
**Rust and Python escape on their readers' laxity, not on a check**:
`situ_rt::read_be` and the Python `_read` both return 0 for bytes that
are not there, the run's `n >= count` test is satisfied at once, and the
walk falls out answering the fixed prefix -- which happens to be the right
answer. C++'s accessors are not lax, and deliberately: `ids_count()` is a
static offset and reads through `situ_get_be16` with no bounds check,
because the invariant is that a view has passed `view()`'s
`length >= size_min` guard (the comment at `cpp/emit.py:8256` states it).

**`required` is the one caller that builds a view without that guard.**
It constructs `situ_view_t{ data, have, 0u, nullptr }` directly, so the
object's own precondition is violated by its own framing entry point.
Until 26.693 the `have < size_min` floor re-established it by accident one
line later. That is the whole mechanism, and it is why the fault is a
regression rather than an old bug: the floor was load-bearing for a reason
nobody had written down, in a different direction from the reason it was
there.

## The fix: the guard moves above the run branch, where C has it

Every backend emits, per variable placement,

    /* <path>: reading its length means reading bytes that
     * have to be here first. */
    if (have < pos) { *need = at; return TRUNCATED; }

C emits it **before** the counted-run branch. The other three emit it
**after**, and the run branch `continue`s -- so a run never got one, while
the delimited and single-length cases in the same function always did.
Hoisting it is the whole change, and it makes the four backends one shape
again, which is this project's central claim about them.

This is the form 26.693's own record said the surviving half would have to
take: *"Either the floor is the STRUCTURAL minimum with value constraints
ignored, or `required` has no business having one."* The cursor already
carries the structural minimum -- it is `pos`, every fixed byte before this
member, derived from the layout and from no `[min]` -- so the guard is that
sentence's first branch and the floor was its second.

**It also tightens three backends' answer for a non-run member.** The
guard now precedes the varint `_len() == 0` check rather than following it,
so a struct with a fixed prefix in front of a varint answers `need = at`
where it answered `need = have + 1`. That is C's answer, and the tighter
of the two.

## What it is pinned by

`test_codegen_cpp.py::test_required_reads_no_count_the_buffer_is_too_short
_to_hold`: every prefix below ten bytes, each in a `malloc` of exactly
that size, under `-fsanitize=address,undefined
-fno-sanitize-recover=all`, plus the `(nullptr, 0)` call. It aborts on a
`git archive HEAD` export of the parent commit and passes here.

**The buffer is `malloc`ed at exactly `n` bytes and that is the test, not
a detail of it.** The existing prefix sweep for this backend
(`test_every_prefix_of_a_real_request_answers_honestly`) walks every
prefix of a real HTTP request out of a `const char req[]` on the stack --
so an over-read lands inside some other object, answers from whatever is
there, and reports nothing. The sweep was right and its *allocation* was
what hid this. A framing function is asked about a buffer whose end is
real, so the test has to give it one.

## What this says about the population, again

26.693 closed with "the property was right and the population was not",
and this is that for the second time in three days on the same function.
The shapes in `test_required_answers_every_prefix.py` read their count
from offset 0 or from a varint there, so one byte already carries it;
**not one of the seven has a multi-byte fixed prefix in front of its
count**, which is the only arrangement in which this fault can exist.
bbq-predictor's two structs both do. Pointing that sweep at the corpus is
26.675's standing finding and is the next piece of work rather than a
remark.

## Their exposure

bbq-predictor is not taking `97d1343` and stays vendored at `601fa96`;
their reader calls neither `framed()` nor `required()`, so nothing there
is exposed. Their fuzz case now holds the never-backwards rule asked of
one byte fewer and of the frame the answer named, which is ready to judge
this fix.
