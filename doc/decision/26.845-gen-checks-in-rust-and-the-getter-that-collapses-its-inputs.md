# 26.845: gen-checks in Rust, and the getter that collapses its inputs

Status: recorded -- seven of nine kinds in `--target rust`, 1007 checks
compiled and run over 42 schemas; the two it declines are named in the
generated file and here
Date: 2026-11-03
Source: 26.844, whose closing line said this would be the cheapest of the
four. It was, and it still found two things.

## Section 1's fourth language

`gen-checks` reaches all four now: C, Python, C++, Rust. A test crate root
with `#[test]` functions, which is `rust/vectors.py`'s shape and for its
reason -- `rustc --test` compiles it with no dependency to declare.

**The third independent confirmation that the four ask one question.**
Inverting the Rust emitter's byte order fails **129** decode checks across
27 schemas, which is the same 129 the C++ and the Python backends give for
the same sabotage of their own emitters. Three backends, three emitters,
one number, because none of them computes the arithmetic -- it is all in
`situc/codegen`.

120 round-trip checks fail alongside them, the write going through the
correct order and the read-back through the wrong one, which is the kind
doing exactly what it is for.

## The getter that collapses its inputs

The instructive finding, and the second attempt is the one worth keeping.

Rust's getter for an enum-typed field answers `Option<T>`, so
`i64::from(view.r#type())` does not compile and rustc said so at once. The
generated enum derives `PartialEq`, so comparing the two `Option`s
directly looked like the better answer than declining the field -- keeping
a check beats dropping one. It compiled. **And then it failed**: "byte 1 is
claimed and does not reach it".

Because `Option` is lossy exactly where that check looks. A zeroed
`header.type` names no variant and reads `None`; flipping its byte to 0xFF
names no variant either and reads `None` as well. Two different bytes, one
observation -- and a check about which bytes REACH a value cannot be built
on an observation that collapses them.

So the first instinct was right and **the reason is worth more than the
instinct**: not "the type is awkward" but "the getter does not distinguish
the inputs this check varies". That is a test for the whole class. Before
building a check on an accessor, ask whether the accessor can tell apart
the inputs the check is going to vary -- and a type that maps many inputs
to one answer cannot, however comparable its answers are.

## The escape in the middle of a name

`set_` + `_ident("type")` is `set_r#type`, which rustc rejects with
"prefix `set_r` is unknown". The raw-identifier escape belongs in front of
the identifier it escapes, and `set_type` is not a keyword so it needs
none. `test/schema/lenient` caught it.

The vectors port made the mirror of this in 26.829 -- `c_name` where
`_ident` was wanted -- so the pair is worth stating as one rule: **a name
escape applies to the whole identifier that reaches the compiler, and a
backend that builds an identifier out of parts has to escape the result
rather than a part.**

A second corpus finding alongside it: `i64: From<u64>` does not hold, so
the comparison is `i128::from` now, which every situ scalar converts into.

## And the vacuous-pass guard was itself vacuous

The gate for each language ends with a guard against a suite that checked
nothing, a crate of no tests passing as loudly as one that checked
everything. For Rust it read:

    assert "0 passed" not in done.stdout

**`20 passed` contains `0 passed`.** So the guard failed for seven schemas
whose test count happens to end in a zero, and the line it was copied from
-- in the Rust VECTORS gate, written this morning -- has been passing only
because no vector crate's count ends in one.

A guard whose whole purpose is to catch a check that asked nothing,
answering about the wrong thing itself. Both read the number now:

    ran = re.search(r"test result: \w+\. (\d+) passed", done.stdout)
    assert int(ran.group(1)) > 0

The two sibling guards are safe and worth saying why rather than leaving
to luck: `"0 of 0 check(s) failed"` cannot appear unless the total really
is zero, failures exceeding a total of zero being impossible, and
`"Ran 0 tests"` is not a substring of `"Ran 10 tests"`.

**The pair with 26.843 is the lesson.** There, a check survived every
single mutation because two guards backed each other up, and the natural
reading -- "nothing tests this" -- was wrong. Here, a guard fired on
inputs it was never about. Both are the instrument being the thing at
fault, and in both the only thing that caught it was running it over a
corpus wide enough to contain the awkward case. Seven schemas with a
count ending in zero is not a case anybody would think to write.

Once both were honest they immediately found a real empty suite:
`example/register` is every struct a bus transaction and
`example/protobuf` has none with a minimum, so each emitted a crate of no
tests. Each now carries one test saying which of the two reasons applies
-- the same answer the Python and C++ backends give, arrived at for the
third time because the gate asked for the third time.

## The two it declines, and why they are named

- **a nested member starts where the map says** -- a Rust view holds a
  private slice, so nothing can read a sub-view's offset to compare
  against the map. The C and C++ backends read `situ_base(inner) -
  situ_base(view)` and Python reads `inner._at - view._at`; Rust exposes
  neither. A formulation exists -- write a distinctive byte at the
  expected offset and read it through the nested struct's first field --
  and it asks the property by a different observation, which is a decision
  about whether the four backends must share the observation as well as
  the question. Not taken here.
- **a framing reader reassembles across every boundary** -- deferred with
  it, the reader's own vocabulary being the next thing to establish.

Both are in the generated file with those reasons, because a reader of
seven checks would otherwise take them for nine.
