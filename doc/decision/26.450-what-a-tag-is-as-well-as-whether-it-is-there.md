# 26.450: What a tag is, as well as whether it is there

Status: recorded
Date: @ -30713,0 +30714,102 @@ reproductions, in a file that was not its own.
Source: `project.md` section 26, where it was written

**A tag read at the wrong offset answered `present=1` in all five
readers.** The probe asked whether the bytes were reachable and nothing
else, so five descriptions could disagree about WHICH bytes the tag is and
agree perfectly. 26.448 was a tag's location computed wrongly one accessor
away, which is what suggested the question.

It reports `present=N len=N first=N` now, in the four backends and in the
walker. `_tags`'s docstring says a tag is "asked only whether their bytes
are there. Not what they hold and not whether they verify", and that rule
is untouched: reading a length and a first byte runs no algorithm and
verifies nothing. It asks where the bytes are, which is the compiler's
answer rather than the caller's.

**It found nothing. 146 differential tests pass and no backend disagrees**,
so this is a regression guard and not a defect report -- said plainly
because a probe added after a fix invites the reading that it caught
something.

**The label had to change and eight tests said why.** Printing
`<tag> covers=...` for 26.449's range probe gave two lines beginning with
the same first token, and `test_walker.py::_by_member` keys a listing by
exactly that, last wins. C's `present=` line was replaced by the covers
line while the walker still had only `present=`, so the comparison paired
two different questions about one member. The contract is one line per
member per backend; `<tag>.covered` restores it.

**And the field is `bytes=`, not `len=`, because ten tests said so in two
waves.** `test_walker.py::_by_member` keys a listing by each line's first
token, last wins, so 26.449's first spelling -- `<tag> covers=...` -- gave
two lines beginning with the tag's name and replaced its `present=` line
in C's map while the walker still had only `present=`. Eight tests paired
two different questions about one member. `<tag>.covered` restores one
line per member per backend.

Then `len=` on the tag line failed two more, and those are the
interesting ones. `test_dissector.py` harvests `len=` from ANY line into
`<name>#len` and compares it against a Wireshark row's length -- and its
docstring already says why that is the wrong question for a tag:
"`present=` is a tag's presence and not its bytes". Spelling the field
`len=` forced a comparison that test deliberately does not make.

**What it forced is real and stays out of scope.** `packet.tag` and
`edges.sealed_run.seal_mac` both sit after a `sealed` region, where the
extent is the codec's: the walker calls them unplaceable and answers
`present=0`, C's pointer accessor hands back NULL and agrees, and the
dissector shows a 16-byte row. That is a genuine difference between the
dissector and the other readers, it is about PRESENCE rather than length,
and the comparison excludes presence on purpose. Recorded here rather
than smuggled into a length check -- which is what `len=` was doing.
