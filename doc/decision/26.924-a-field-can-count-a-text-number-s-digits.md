# 26.924: a field can count a text number's digits

Status: recorded
Date: 2026-11-07
Source: 26.880's refusal, against the holder's "anything theoretically a need"

**`decimal u16 code[n]` reads now.** hull's `3:493` is the shape, and so is an ISO
8583 LLVAR: a count, then that many digits. 26.880 refused it because four readers
had four answers, and weighed building it as twelve sites for a convenience. That
weighing was the wrong question: a run of `u8` frames the bytes and cannot say the
number, and a size can hang off that number, which `u8` cannot do.

A digit is a byte, whoever states how many, so the layout says so and every length
is the count. The accessors are the written form's: `code`, `code_digits` and
`code_value`. What differs is one thing: **a count the message states is held to the
frame**, where a written width was the acquiring check's. `_len` clamps, so no read
goes past the view, and the fallible read answers BOUNDS for digits that are absent.
A number with no digits, `n` of zero, is refused as the delimited form refuses one.

The written form's range rule has no number to work from, so the ceiling is the
type's.

The verdicts in the test are by hand. A seeded comparison of all six readers over
nearly right messages found the one fault the chosen samples had not: the Python
report parsed a short slice of `code[n + 1]` and called it bad digits, where the frame
was what ran out.

A builder takes the digits as bytes and states the count, as for any run, and
`validate` holds them to being digits. `hex u32 v[w]` behind a text count is not built:
a text number sizing something needs `[minimal]` or a width, as it always has.
