# 26.834: the check that locates a nested member, and the kind that cost no discovery

Status: recorded -- the fifth of `gen-checks`' nine kinds in Python, with a
control that isolates it, and the reason this one needed no exclusion
Date: 2026-11-03
Source: 26.831, 26.832; `situc/codegen/c/checks.py`'s
`_nested_placement_check`

## What it asks

Where a nested struct sits inside its parent: acquire the parent, take the
sub-view, and require `inner._at - view._at` to be the offset the map
claims. `_at` is a view's absolute position in the message, so the
subtraction is the parent-relative start -- the quantity `--target c` reads
as `inner.base - view.base`.

One assertion rather than a re-derivation. Recomputing the offset from the
parent's members would be asking the emitter what it thinks twice, which is
the circularity 26.832 was written against.

## The hole it closes, which is not obvious

A nested struct's interior is checked thoroughly by the kinds already
ported -- **but under its own struct's section, against a buffer where it
begins at zero.** That says nothing about where the parent puts it.

`--target c` found this by mutation testing: moving every nested member one
byte late passed its whole generated suite, because each nested field still
agreed with every other nested field. The suite was internally consistent
and wrong by one byte throughout.

**Reproduced here, and it isolates cleanly.** Making the Python emitter's
fixed-size nested accessor start one byte late (`where = f"({start}) + 1"`)
fails **20 checks across 12 of the corpus's 42 schemas, and every one of
the 20 is this kind.** The four kinds before it catch none of it. 27 such
checks are emitted over 16 schemas, so the kind is not vacuous and the 20
are most of what it can reach.

## What it declines, said rather than left silent

**35 of the corpus's 72 nested members can be located and 37 cannot**, for
five reasons: 14 have an offset the message decides, 10 are runs, 10 have an
extent another member drives, and 3 are arrays.

That is nearly half, and the generated module names each one -- `# Not
located: \`will_message.payload\`, because its offset is one the message
decides.` The preamble already argues that a suite checking one of nine
things and not saying so reads as the whole map having been checked; the
same argument applies INSIDE a kind, and it applies more strongly here
because nothing else in the suite locates a nested member at all. 27 located
checks and 16 named declines over the corpus as `gen-checks` accepts it.

A comment rather than a failing or skipped test, because every one of the
five reasons is the map being right: there is no sub-view accessor to call,
or the thing is not a nested struct in the first place. A scalar member gets
no line, since there is nothing a reader could mistake for a located nested
struct.

## Why this kind cost no discovery, which breaks the run

26.831 and 26.832 both predicted that each kind's cost is the exclusions the
corpus finds rather than the writing, and that was four for four: a register
has no view, a variable extent has no byte range, a covered field has no
plain setter, a driving field invalidates its own view, BCD is not a plain
integer, a marker's order is not static.

**This one was green on its first corpus run.** The reason is not that the
prediction was wrong but that the exclusions were not mine: they are
`--target c`'s, copied from a backend that had already paid for every one of
them, including one it had first got right for the wrong reason -- it
excluded a run via a false `array_count = 1`, where the real reason is that
a run reaches its elements through an `_at` of its own and has no property
to locate.

So the rule to carry forward is narrower than 26.831's: **budget the
discovery for a kind whose exclusions nobody has found yet, and read the C
backend first for one whose exclusions somebody has.** The remaining four
kinds all have a C implementation to read.

## The state, and what the next piece of work actually is

Five of nine kinds in Python, asserting `OFFSET`, `SIZE`, `MUTATE` and
`REPR`. The four that remain are `must_eq`, `reserved`, an enum rejecting an
unnamed value, and a framing reader across every boundary -- and then C++ and
Rust, which have no `gen-checks` at all.

**Three of those four share one prerequisite, and it is where the work is.**
Each is a constraint check, and a constraint check needs a BASELINE: a
buffer satisfying every constraint the struct has, written before anything
is broken. Without it the check can only show that a wrong value is refused,
which for `must_be_one` is vacuous -- a zeroed buffer already breaks it, so
the check would pass against a validator that did nothing. Establishing that
the RIGHT value is accepted first is what gives the refusal meaning.

`--target c`'s `_baseline` is what that costs, and reading it is the
estimate: text numbers (a zeroed `hex u32 ino[8]` is eight NULs, which is
not a number in any radix, and `cpio_header` is thirteen of those), pinned
byte runs in all three spellings (`edges.sig` is `u8 sig[4] [must_eq =
"WOZ2"]`, and skipping it as an array left the baseline claiming a validity
it did not have), only the SELECTED arm's members (Modbus has ten exception
arms sharing one byte, and satisfying all ten wrote ten mutually exclusive
layouts over each other), and `None` where no valid baseline can be built at
all.

So the next run should port `_baseline` as its own piece, with the three
constraint kinds following it, rather than taking `must_eq` and discovering
the baseline underneath it. The framing kind is independent of all of this.
