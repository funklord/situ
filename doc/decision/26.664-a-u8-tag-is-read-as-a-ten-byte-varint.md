# 26.664: A `u8` tag is read as a ten-byte varint

Status: recorded
Date: 2026-10-20
Source: `project.md` section 26

Found by probing the accumulator of 0066 against a real CoAP option
list, where the second option's delta is 8 and its tag byte is `0x82`.

**Measured.** Every backend reads a `tlv` item's tag with a leb128
varint decoder bounded by `_tlv_tag_bytes`, and that function asks the
schema for a *declared varint type*:

    declared = next((decl for decl in self.schema.varints()
                     if decl.name == placement.tlv_tag_varint), None)
    bits = declared.max_bits if declared is not None else 64
    return (bits + 6) // 7

`tag_type = u8` is a scalar rather than a declared varint, so
`placement.tlv_tag_varint` is `None`, `bits` falls back to 64, and the
tag is read as a **ten-byte** leb128. Reproduced in four lines:

    tlv items (
        tag_type = u8,
        tag_decode = { kind = tag >> 4, len = tag & 0x0F },
        tag_identity = kind,
        value_size = switch (kind) { default: len },
    );

generates `situ_varint_get(situ_base(view) + at, view.limit - at, 10u,
&tag)`. Over the bytes `31 77 82 01 02 00` the second item reads a tag
of 130 consuming two bytes, where a `u8` tag is one byte of value 130:
the generated walk reported `at=3 delta=8 len=2 next=7` for an item that
ends at 6, and the third item was never seen.

**What it costs.** Any tag byte at or above `0x80` swallows the byte
after it; the tag value can exceed what the declared type holds; and
every offset after that item is wrong. CoAP meets it immediately,
because an option delta of 8 or more sets the high bit -- which is to
say the defect is invisible for small tags and certain for real ones.

**Why nothing caught it.** `example/protobuf` declares `pb_varint`, so
its tags are varints and the decoder is right. Until today no committed
schema used a scalar tag type at all, and the hand-written vectors in
the five-reader and two-walker tests all use tags below `0x80`, where a
leb128 read of one byte and a `u8` read of one byte agree exactly. The
simple form in section 9.5 has shown `tag_type = u8` since the
scaffolding commit.

**Fixed 2026-10-20, on the holder's instruction.** A scalar tag type is
read as that scalar -- one byte for `u8`, two for `u16`, in the region's
byte order -- and a declared `varint_type` by its own encoding. Six
readers: the four backends' tag read, and both walkers through the
image, whose `tag_flags` and `len_flags` gained a bit saying the number
is fixed-width. `prefixed(u8)` had the same fallback in the image and is
fixed with it.

**And the silent door is shut.** `tag_type` was not checked at all:
`tag_type = nonesuch` was accepted and read as a ten-byte leb128, the
same as `u8`. A name that is neither a declared varint nor a scalar is
refused now, with the declared varints listed and a near-miss
suggestion.

**Each half has its own control**, because the compiler and the image
could have been fixed separately and the vectors would not have said so:
withholding the scalar width in `layout` fails the new vectors, and
withholding the fixed-width flag in `pack` fails them too. Both were
run.

**The vectors reach above `0x80` now, which they could not before.**
Every hand-written tag in the five-reader and two-walker tests was below
it -- the range where a one-byte leb128 and a one-byte scalar agree
exactly -- so five columns agreed about a tag none of them read
correctly. `0x82 01 02` is in both suites.

`test/schema/edges.situ` carries the tree's only scalar-tag region and
says what changed above it.

**One layer under this was another fault, and it is 26.665**: the `tlv`
placement carried no byte order at all, so Python's helper answered
"little" for it and Rust's answered big-endian. Invisible while every
scalar read in a `tlv` region in this tree is one byte wide.
