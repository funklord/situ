# 26.1031: a dissector checks a checksum

Status: recorded
Date: 2026-11-14
Source: the lens 26.1023 left -- a consumer holding the whole message that
never asks a checksum's own check

**A generated dissector showed a CRC's bytes and nothing else.** Wireshark's
own dissectors mark a header checksum correct or say what it should be,
and a user debugging a framing reaches for exactly that. Nothing recorded
a decision against it; the walker's report is the one consumer that
declines on purpose (14.1: it says whether a tag's bytes are there).

**Now the dissector recomputes a tag over the span it covers** and adds a
status row beside it -- `Good`, or `Bad, should be 0x...` with an
Error/Checksum expert, Wireshark's own group for it. The arithmetic is the
backends': `kernel_math`'s table and the loop each of them spells, so this
is a fifth spelling and not a fifth derivation, and a `[self_as]` tag's
own bytes are read as its value, as the readers read them.

**Narrow on purpose**, each exclusion a span this file cannot state
exactly: a tag covering a pseudo-header (UDP's), more than one region, a
variant of the struct itself (ICMP's arms, 26.579), or bits (USB's); and a
kernel other than a CRC of at most 32 bits or RFC 1071's sum.

**Lua 5.2 is kept (0021)**: the bitwise operators are `bit32`'s there and
syntax it cannot parse in 5.3 and later, so they are chosen at load time
and the 5.4 ones loaded from a string. Measured on 5.4 only -- the harness
and Wireshark 4.4 -- since no 5.2 is installed here; the 5.2 branch is
checked by the suite's operator scan and by nothing that runs it.

**Measured**: PNG's IEND CRC `AE426082`, the IPv4 header checksum `b861` of
Wikipedia's worked example (with the sum covering itself), and a FLAC
frame header's CRC-8 from the committed corpus each read `Good`, and each
with one bit changed reads `Bad` with the right value and the expert; and
tshark 4.4 shows both verdicts for PNG. Every dissector still parses, and
the walker differentials are unchanged.
