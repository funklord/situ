# 26.693: `required` answered from bytes past the frame it named

Status: recorded -- reported, not yet reproduced here
Date: 2026-10-26
Source: `project.md` section 26

Reported by bbq-predictor 2026-10-26, in two messages, found by fuzzing
the C++ generated from their own `src/wire/bbq.situ` against situ at
`601fa96`. **This is the framing contract this tree states and tests, and
it is broken for shapes the corpus does not have.**

## The two reproductions, in their numbers

`month_body`, on 95 bytes:

    month_body::required(b, 95, need);     // ok,        need = 82
    month_body::required(b, need, again);  // truncated, again = 87

`head_body`, on 13 bytes, which is the one that matters because it is
small:

    hex: 00 00 00 0e 00 00 50 70 00 00 80 94 64

    head_body::required(b, 13, need);      // ok,        need = 10
    head_body::required(b, need, again);   // truncated, again = 11

So **`need` goes DOWN as `have` goes up**, which is the same statement as:
the answer was computed from bytes past the end of the frame it reported.
A caller doing the obvious thing -- wait for `need`, ask again -- is told
82 and then 87, and loops.

`validate` refuses both inputs, with a constraint error and a bounds error
respectively, which is ordinary for bytes a framer is asked about.

## The invariants their fuzzer holds, which are worth taking verbatim

    ok        implies need <= have
    truncated implies need >  have
    the `need` bytes alone answer ok with the same need
    if the whole input validates, the `need` bytes validate too

Only the third broke, in five minutes, once -- and then again in a second
struct with month_body excluded from the run.

**The third is a stronger statement than anything tested here**, and that
is the finding behind the finding. `test_required_answers_every_prefix`
holds three properties: no prefix is reported complete before the message
is, the answer never goes backwards, and an incomplete message asks for
more than arrived. The second one covers this -- a `need` that falls as
`have` rises is going backwards -- but it is swept over six shapes written
for 26.683 through 26.686, all of them runs of records or varints. bbq's
two structs are neither.

So the property was right and the population was not, which is 26.675's
finding for the fifth time: every dynamic check here is driven by the
corpus, and a shape no example contains is a shape nothing executes.

## What is known about the shape, and what is not

Not reproduced in this tree yet. What the numbers say on their own:

- `need` falling as `have` rises means some term is read from, or clamped
  against, bytes outside the frame being reported. A length clamped by the
  remaining bytes grows with `have`; something here shrinks, so the
  suspect is a term whose VALUE changes rather than whose clamp does -- a
  count read at a different offset, or an alignment computed from one.
- `padded.situ` is the corpus's only `align_up` shape and is one of the
  four whose C++ frame layer does not compile (26.692), so the prefix
  sweep has never been pointed at an aligned member either.
- Five other structs the same fuzz case drives -- `bbq_file`,
  `index_body`, `stations_body`, `columns`, `band_` -- did not break in
  the time it took to find these two, which their own message says is not
  evidence they are sound.

The reproduction to build here is a shape with an alignment or a
wide length field ahead of a variable member, added to `SHAPES` in
`test_required_answers_every_prefix.py` so that the monotonicity property
already written sweeps it. If that fires, the test that should have caught
this catches it.

## Their exposure, and the one thing to say back

bbq-predictor calls neither `framed()` nor `required()`, so their reader
is unaffected -- a property of their design rather than of situ's state,
which is the second time that sentence has been true of one of their
reports. The fuzz case stays behind `make fuzz-wire FUZZ_FRAMING=1` in
their tree until this is fixed.

**They are fuzzing situ's output against invariants situ states and do
not test.** That is worth more than the two bugs: the four invariants
above are a better specification of `required` than anything in this
repository, and three of them hold.
