# 26.131: Three answers to the consumers

Status: recorded
Date: 2026-08-26
Source: `project.md` section 26, where it was written

The `suggestion/` directory is six files of evaluations written from the
other private projects, and it turned out to be the backlog: concrete asks
with reproductions attached, from the sessions that actually tried adoption.
Three are answered; the answers went back into the files that asked, because
the directory is correspondence rather than an archive.

**fuzznet asked for one sentence and got a normative paragraph.** Their
traffic reconfigures infrastructure across untrusted networks, and they
wanted the timing division confirmed: who owns the constant-time comparison?
Measured rather than asserted: the generated code never computes or compares
a tag anywhere -- `_open()` takes the caller's *verdict* as a parameter, and
the one `== tag` in any backend compares a TLV wire-tag number. 14.6 now
states the division: the primitive and its constant-time comparison are the
caller's; the bytes it runs over are the schema's; a future generated
comparison would be a decision record, not a drive-by.

**netcfgd's version question became 21.1 and a banner.** Every generated
file now names its generator -- `Generated by situc 1.0 from x.situ`, from
the same `VERSION` the package and `situc --version` read -- so a
regeneration under a different situc is a visible diff line rather than a
silent substitution. The policy beside it: the committed `.situ.wire` is the
compatibility oracle, not the generator version, and byte-stable emitted
code across versions is deliberately not promised, because it would freeze
every emitter bug. The sweep that stamped 33 files also produced this
entry's incident: the script inserted the version import "before the first
import line, which is always safe" -- and `from __future__` must be first,
so four files stopped parsing and 139 CLI tests went red at once. An
insertion rule that is safe in most files is a rule, not a fact, and the
suite said so immediately.

**netcfgd's flagship ask is `situc gen-tamper`.** They adopted for the
verify gate and hold that a gate nobody has watched fail is not evidence;
the generated harness is the watching. It takes the caller's verifier as a
callback -- the division of 14.6, load-bearing within a week of being
written -- and drives it across the schema's own coverage geometry through
the same generated `_covered` helpers the caller's recompute uses: every
covered byte and every tag byte flipped one at a time with refusal required,
and, for a fixed layout, every outside byte flipped with the answer required
not to change, which is what catches a verifier covering more than the
schema says. The outside half is deliberately absent for dynamic layouts --
a flipped byte can be a length there, and a parse that legitimately moved is
not an over-covering verifier.

The executable test is its own control pair: an honest XOR verifier survives
every flip, and a deliberately lying one that ignores the last covered byte
is caught with `failed_at` naming that byte's exact offset. A harness only
the honest half exercised could pass vacuously; the liar is what proves the
flips reach the verifier.
