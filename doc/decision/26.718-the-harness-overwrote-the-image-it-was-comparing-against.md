# 26.718: The harness overwrote the image it was comparing against

Status: recorded -- both walker drivers allocate exactly the message, and a
packet of `LONGEST` bytes is pinned as compared rather than dropped
Date: 2026-10-28
Source: `project.md` section 26

The two walkers are the only independent witnesses in this tree. The four
backends are five spellings of `situc/traverse.py`, so a wrong decision
there is a consensus rather than a disagreement; `walker/walk.py` and
`walker/c/situ_walk.c` read the packed image instead. Three comparisons
hold them to each other over the whole corpus -- the verdict (26.349),
which check refused (0051) and every offset (26.538) -- and each one
found a real defect the day it landed.

For eleven weeks all three were throwing about one case in seven away,
because the C side's driver wrote over the image it had just opened.

## The defect

Both drivers in `test/unit/test_walker_c.py` declared

    static uint8_t img[65536];
    static uint8_t msg[512];

and decoded the packet off the command line with no bound:

    for (const char *p = argv[2]; p[0] && p[1]; p += 2) {
            ...
            msg[len++] = (uint8_t)strtoul(pair, NULL, 16);
    }

`fourway.draw` reaches `LONGEST = 1200` bytes and takes that branch one
draw in four. Measured over 4000 draws from the seed these comparisons
use: **586 exceed 512 bytes, 14.7 per cent, the longest 1196.** The
twelfth packet of the identity deal is 1019 bytes, so it fires on the
first schema.

ASan, on that packet:

    ERROR: AddressSanitizer: global-buffer-overflow
    WRITE of size 1 at 0x5653eb4d8540
        #0 in main drive.c:52
    0x5653eb4d8540 is located 0 bytes after global variable 'msg' of size 512
    0x5653eb4d8540 is located 32 bytes before global variable 'img' of size 65536

Thirty-two bytes of padding, and then the image. `example/udp`'s image is
976 bytes and that packet is 1019, so 475 bytes of the image were
overwritten -- **after `situ_walk_open` had already taken pointers into
it.** Five of thirty-nine drawn packets report under ASan before the fix
and none after.

## What it cost, which is not the overflow

The corrupted image made `situ_walk_members` fail, so the driver exited
1, so `_run_driver`'s `assert ran.returncode == 0` fired. All three
corpus comparisons catch exactly that:

    try:
            c_said = c_why(tmp_path, blob, packet, which)
    except (AssertionError, IndexError):
            continue	# no driver can acquire this shape

So the case was discarded as a shape the driver cannot acquire, when what
had happened was that the harness had destroyed its own image. **A
comparison that quietly stops comparing passes exactly as loudly as one
that agrees**, which is what the non-vacuity tests in that file exist to
catch -- and they could not see this, because they count what was asked
and nothing counted what was dropped.

The two drivers side by side on `example/udp` with the 1019-byte packet:

    old      exit 1, no output
    new      36156 56947 15260 refused refused
    walk.py  36156 56947 15260 refused refused

The fixed driver and the Python walker agree exactly. The old one had
nothing to say, and silence is what the comparison was reading as a
reason to skip.

## It is the mechanism behind a luck 26.689 had already named

26.689 recorded that `edges.varint_driver` "has very likely been divergent
since it was written" and that "what found it was luck re-dealt" -- two
packets per struct from a fixed seed, with the deal changing whenever
somebody adds a struct. That reading was right and the luck had a cause
nobody had looked for: the hostile-length class needs a packet long enough
to carry a large length field, and **long packets were exactly the ones
being thrown away.** The deal was not merely unlucky; the instrument was
discarding the interesting end of it.

## The fix is 26.317's answer rather than a new one

Allocate exactly the message:

    uint32_t len = (uint32_t)(strlen(argv[2]) / 2u);

    msg = (uint8_t *)malloc(len != 0u ? len : 1u);

`situc/codegen/differ.py`'s C driver already did this and says why
(26.317): a fixed buffer with the message at the front hands every
accessor a tail of slack, and a read past the frame that lands there is a
valid read of a valid object -- invisible to a sanitizer as well as to a
segfault. Its C++ driver sizes a `std::vector` for the same reason, and
`walker/c/main.c`'s `from_hex` takes a cap and honours it.

**So three of the five hex decoders in the tree were bounded and the two
that were not were both in the walker differential.** `msg[512]` arrived
with the C walker's first commit, `a92bc3c` on 2026-08-10; `LONGEST = 1200`
predates it by eight days, `8646d6f` on 2026-08-02. The three corpus
comparisons were then written on top of it over six weeks, each one
finding a real defect as it landed -- which is what a working instrument
looks like from outside, and is why nobody went back to the driver.

That is the same shape as 26.717 the day before, a mechanism settled in
one reader and never carried to the other, and the two are worth keeping
apart: 26.717 was a fault in the software and this is a fault in the thing
that checks the software. The second is worse per line, because a wrong
answer gets argued with and a missing question does not.

## The test pins the compared case, not the overflow

`test_a_long_packet_is_compared_rather_than_dropped` asks the driver for
`LONGEST` bytes and compares its answers with the Python walker's. It
fails on the commit before this one -- the driver exits 1 and the
assertion in `_run_driver` fires -- and it is written against `LONGEST`
rather than a number of its own, so the property is "the longest packet
the corpus tests can deal is one this driver reads whole" and it follows
the draw if the draw moves.

Asserting the absence of the overflow would have needed a sanitizer build
of the driver, which is a second compile of every case in the file for a
property the compared answer already implies.

## What is not settled here

The four entries in `IDENTITY_APART` are untouched. They are a real
divergence between the two walks about which check refuses a hostile
length -- C's placement guard is the wider one and records no identity,
the Python walk reaches `fits_frame` -- and 26.689 raised the
reconciliation rather than making it, because which walk is right is a
question about both of them.

That parking is confirmed rather than weakened by looking for an arbiter:
`fits_frame` is the PACKER's name for an image check (`situc/pack.py`),
and the only readers of the image's check table are these two walkers. So
there is no third witness for this question in the way the generated
backend is a third witness for a value, and the comparison's own docstring
is right that asking one walker whether it agrees with the other is one
witness twice.
