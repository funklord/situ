# 26.690: A memory-safety closure nobody had tested

Status: recorded -- supersedes 26.678, which is closed
Date: 2026-10-26
Source: `project.md` section 26

26.678 is a heap read past the buffer in `framed` and `required`: with
`n = 8` in a two-byte message, `s::framed` handed `one::required` a length
of `have - at` with `at` already past the end, and the varint reader
walked from a pointer outside it. It was recorded 2026-10-23 and **fixed
the same day**, in `b4cf766`, whose message names it in as many words --
"Guarded before each element's `required`, with a saturating length so the
two defences are independent. ... All four now say truncated, need 9."

It had no test. That is what this record is for.

## The test, and what makes it a test rather than a sample

`test_framed_does_not_read_past_the_buffer_on_a_hostile_count` sweeps
every `n` a byte can hold against every buffer length to 24, through both
`s::required` and `s::framed`, under ASan and UBSan. The buffer is
`malloc`ed and sized to the case, so a read one byte past it is a fault
the sanitizer sees rather than slack in a stack frame, and the filler is
`0x80` -- a continuation byte -- so every varint in range runs off the end
rather than terminating early.

6144 pairs, no report.

**The control is the part that matters**, because a sweep that cannot fail
reports success exactly as loudly as one that passes. Run against the
tree at the commits either side of the fix:

    51d6c20   FAULT   (the last commit before it)
    b4cf766   CLEAN   (the fix, and every commit since)

The fault at `51d6c20` is the stack this probe is built from --
`situ_varint_get`, `one::v_len`, `one::framed`, `one::required`,
`s::framed`, `s::required` -- which is 26.678's own trace, six frames
deep. So the sweep reaches the fault, and the clean run means something.

## It was attributed to the wrong commit first, and the control is why

This pass's first reading was that 26.684's running-offset rewrite closed
it incidentally -- plausible, because that rewrite replaced every
`have - at` with `situ_remaining_u32(have, pos)` behind an
`if (have < pos)` guard, which is exactly the shape of the fix. It was
reported that way before it was checked.

Running the control killed it: the sweep is clean at `1e81500~1`, the
commit immediately before 26.684's work. So the fault was already gone,
and bisecting the fifteen commits in between named `b4cf766` -- two
commits after the reproduction, on the day of the report.

**The cheap lookup that would have answered it is `git log --grep 26.678`,
which prints the commit that names the record.** It costs nothing and
nobody ran it, including this session, until a control forced the
question. A plausible mechanism is not an attribution, and the difference
is one command.

## `Status: recorded` is not a claim about anything

The first version of this finding said 26.678 "still says `Status:
recorded`" as though that meant open. It does not: **681 of the records in
`doc/decision/` say exactly that**, including this one, and it means the
decision is written down. Only a handful carry a fix in the status line,
and those are the exceptions rather than the convention.

So there was no stale status to correct, and the record was not
misleading anybody. **The one place that said OPEN was
`suggestion/bbq-predictor.md`** -- a reply to the reporter, whose heading
read "FIXED on the validate path; `framed`/`required` is OPEN" for three
days after the fix landed. Two of its other headings were stale the same
way.

That is the shape worth keeping: a record is read by someone who already
knows they are looking something up, and it was accurate. A reply is read
top-down by somebody deciding what they still have to work around, and
its headings are the whole message for most readers. **The copy that goes
stale unnoticed is the one nobody re-reads, and in a reply that is every
line below the heading.**
