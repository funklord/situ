# 26.832: a check that asks what the bytes mean

Status: recorded -- the fourth of `gen-checks`' nine kinds in Python, with
the two exclusions the corpus forced and what the other three kinds were
blind to
Date: 2026-11-03
Source: 26.831, whose last section predicted this; `situc/codegen/c/checks.py`

26.831 ported three of `gen-checks`' nine kinds to Python and closed by
sizing the fourth:

> So the next kind -- **a field decodes a known encoding** -- should be
> expected to cost the same kind of discovery rather than the writing, and
> the corpus gate is what will supply it.

Both halves held. The emitter is about sixty lines; the two exclusions it
needs were found by the corpus failing, and neither was one I had thought
of in advance.

## What it asks, and why it is not circular

A distinctive pattern is written into the field's claimed bytes, and the
getter must return the number those bytes mean in the declared order.

**The expectation is computed with `int.from_bytes`** -- the standard
library, at generation time -- rather than by the rule the accessor reads
with. That is the whole of the check's independence: an emitter that had
the byte order backwards would otherwise produce a getter and an
expectation that agreed with each other and with nothing else.

The pattern is `PROBE_BYTES`, `(0x81, 0x23, 0x45, ...)`: distinct, so any
permutation of a field's bytes is a different value, and top bit set in the
first, so a getter that forgot to sign-extend returns something else. It
was the C backend's and is now in `situc/codegen/__init__.py`, imported by
both -- two backends writing different probes would make one question into
two.

## What the three existing kinds were blind to

This is the measurement worth keeping, because a fourth check is easy to
justify in prose and hard to justify in numbers.

**Inverting the Python emitter's byte order -- `_order`, the one line
producing the `big=` argument -- fails 129 checks across 26 of the corpus's
42 schemas. Every one of the 129 is this kind.** The three kinds already
ported stay green across all 26.

They are blind by construction rather than by oversight: they ask where a
value lives, whether the bytes outside its claim move, and whether a short
buffer is refused. None of them reads the byte order, the width or the
signedness -- which is the part of the map a reader of generated code is
most likely to take on trust, because it is the part with no visible
machinery.

`example/tiff` staying green under that sabotage is the same fact from the
other side: its order is resolved at run time and never passes through
`_order` at all.

## The two exclusions, both found by failing

Each is the map being right and the check wrong about what the map claims
-- which is what 26.831 said to expect, now four for four.

**Packed decimal.** `example/rtc` holds its year as `bcd2`, where each
nibble is a digit, so the byte `0x81` means 81. The getter said 81, the
check demanded 129, and the getter was right. `int.from_bytes` is the
independent implementation of a plain integer and of nothing else.

The guard is therefore a **whitelist** -- `UINT` and `SINT` with no
fractional bits, which is 507 of the corpus's 510 byte-aligned scalars --
rather than a list of kinds to skip. A scalar kind added later declines
until somebody writes its independent decoder, instead of being silently
asserted against the wrong one. `--target c` goes further and probes BCD
properly with a nibble pattern of its own (`_bcd_probe`); porting that is
left.

The two fixed-point fields are the subtler half of the same exclusion.
They would **pass** today, because the getter hands back the stored integer
and the schema's own comment says the caller applies the scale. But `REPR`
reads `ValueConverted` for those and for BCD alike, where the getter does
convert -- so the map does not say whose the scaling is, and a check
passing by relying on the unstated answer is resting on nothing. Declined
rather than depended on, and the ambiguity is the finding: **one axis
value, two behaviours, distinguishable only by a comment in the schema.**

**A byte order resolved at run time.** `example/tiff`'s first two bytes say
which order the rest of the file uses, so the resolved placement carries
`endian=None` and the accessor computes `big=not self.byte_order_is_little`.

The first version of this read

    order = "big" if placement.endian is ast.Endian.BIG else "little"

which is **true of the two cases that motivated it and quietly wrong about
every other** -- the shape this tree keeps finding, a two-branch predicate
absorbing a third state into one arm. `None` became `little`, and the check
failed against an accessor that was reading correctly. It is asked
positively now: `BIG` or `LITTLE` or decline.

That the positive form also declines `endian native` is not a separate
guard. Native means the host decides, so there is no one number the bytes
mean -- one predicate covering both, where `--target c` keys on
`placement.marker` for the marker case and handles native elsewhere.

## Where this backend is deliberately wider than C

`--target c` declines a covered field here, on the grounds that it is
"reached through the coverage machinery, not a plain read". **In Python it
is a plain read** -- `icmp_message.type` is `repr=MemoryIdentical` over
`self._read`, and coverage costs it only its setter, which the round-trip
kind already gates on.

40 of the corpus's byte-aligned scalars are covered, and they are a real
part of the 129 the sabotage fails. Copying C's exclusion across would have
thrown away checks that work, so the difference is recorded rather than
harmonised away: **a backend's exclusion is a fact about that backend's
machinery, not about the map.**

## A count that had already drifted

The generated preamble said **"Two of the nine kinds"** over a list of
three. The sentence and the list it counted were two copies of one number
with nothing comparing them, and the sentence lost.

It is derived from `DONE` now -- one number moving the count word, the
emitted bullets and the declined list together -- and
`test_the_preamble_counts_its_own_kinds` holds the derivation to both
lists. The gate that caught it is the instructive part: a pre-existing
assertion in `test_cli.py` hardcoded `"The six ... also emits"`, with a
comment noting the count had moved once already. **It had gone stale twice
by the same mechanism it was written to catch**, so it reads `DONE` now as
well, and asserts that the kind which just changed sides has left the
declined list rather than merely appearing somewhere in the file.

## The state

Four of nine kinds, in Python, asserting `OFFSET`, `SIZE`, `MUTATE` and now
`REPR`. 185 decode checks over 42 schemas; the one skip is `gen-checks`
declining a schema that takes a `parameter`, which is the
`refuse_parameters` family working.

**What remains: the other five kinds, and C++ and Rust.** The pattern holds
well enough now to plan against -- budget the discovery, not the writing,
and expect the corpus gate rather than review to supply it.

## One thing worth a second look

`_byte_order` in `situc/codegen/python/emit.py` -- the sibling of `_order`,
used for table entries, TLV tags and length prefixes -- still has the
two-branch shape this entry is about:

    return '"big"' if endian is ast.Endian.BIG else '"little"'

A `None` endian reaching any of its three call sites would read
little-endian with nothing said. All four `None` endians in the corpus sit
in `tiff_header`, which has no table, no TLV and no length prefix, so
nothing fails today. That is the arrangement where the question cannot be
asked, not evidence that the answer is right. Whether a schema can put a
prefix or a tag inside an `endian_marker` struct is the next thing to
establish, and if it can, this is a defect with an input.
