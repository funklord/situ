# 26.724: the run walk credited a constraint it could not enforce

Status: recorded -- fixed in all four backends
Date: 2026-10-29
Source: `project.md` section 26

Found here, while building the population 26.723 showed was missing. It
is the **second** instance of 26.693's rule, which 26.693 believed it had
closed with one:

> A framing function may not mix a bound derived from constraints with a
> total computed from unvalidated data.

The floor was the first instance. The counted-run walk is the second, and
unlike bbq-predictor's two cases it breaks in a **conformant** schema.

## Measured, all four backends agreeing

The twelve-line shape from 26.723 -- `item { u8 len [min = 1, max = 32];
u8 id[len]; }` and `body { i64 stamp; u16 count; item ids[count]; }` --
with `count = 2`, a 2-byte element and a 3-byte one, fifteen bytes whole:

    have=10  truncated  need=13
    have=11  truncated  need=14
    have=12  truncated  need=13   <-- FELL

**That is situ's second stated framing property**, the one bbq-predictor's
fuzzer holds and the one `test_the_answer_never_goes_backwards` exists
for: `need` is a lower bound on a total that does not move, so an answer
that shrinks is a quantity being read that shrinks.

The term is the tail of the run walk, written the same way in all four:

    *need = at + part + (count - seen - 1) * ELEMENT_SIZE_MIN

`item`'s `SIZE_MIN` is **two**, because `[min = 1]` makes `id` at least
one byte. The element's own honest bound when its first byte has not
arrived is **one**, because `required` may not quote that `[min]` -- which
is 26.693's fix. So the element ahead is credited two while unreached and
re-counted at one when reached, and the total falls by exactly the
difference.

## The fix: the figure is the element's structural floor

`framing_floor` in `situc/traverse.py`, the layer all four backends are
spellings of, and the four call sites take the value rather than a
constant so that nothing can disagree about it:

    max(extent_parts(structs, struct)[0], 1)

the constant bytes of the element's extent, or its `size_bytes` where it
is fixed, floored at one.

**What the figure has to satisfy**, which is the part worth keeping:

1. **No larger than the element's true size**, or `required` overshoots
   and a caller stalls waiting for bytes that will not come. The constant
   is below every complete instance by construction.
2. **No larger than the smallest answer the element's own `required` can
   give**, or the total falls -- which is what `SIZE_MIN` violated. The
   smallest answer is the one for zero bytes, since an element's own
   answer is monotone in what has arrived.

The second is the one that needed checking rather than arguing, so
`test_the_framing_floor_is_never_above_what_an_empty_buffer_is_told`
asks it of every struct in the corpus: **95 answer a bound, none is below
the floor, and the floor is EXACT for 93.** `dnsname.question` (five
against four) and `mqtt.will_message` (two against one) are the only two
it is strictly below.

**The floor of one is not cosmetic and the first version of this fix got
it wrong.** Taking the constant alone sends `one { uvar v; }` to zero,
and the four shapes in `test_required_answers_every_prefix.py` whose
element is a bare varint then answered **one byte per round trip** --
`col` went from `[4, 5, 5, 5]` to `[2, 3, 4, 5]`, four fetches for a
five-byte message, which is the pathology 26.693's record named for the
aligned case. A frameable run element cannot be zero bytes: every backend
refuses a struct a complete one of which can be, in as many words. So one
byte is honest, and it is what `size_bytes` already carried for that
shape. **The defect was never the varint's byte; it was a `[min]` on a
length counted as though the bytes had been validated** -- and the first
attempt threw away the sound half with the unsound one, which is the same
error 26.723 was about, made in the same function on the same day.

With the floor at one, the four existing shapes answer **exactly what
they answered before**. The only sequence that changes is the new one.

## What the corpus says, and what it cannot

The same prefix sweep over all 36 corpus schemas and 95 framed structs,
before and after, is **byte-identical**: 1159 round trips, no
monotonicity break either side.

**That result is very nearly vacuous and is reported as such.** Exactly
one corpus struct reaches this term at all -- `ble`'s run of
`adv_report` -- and there `SIZE_MIN` and the floor are both ten, so the
fault cannot appear in it. One witness is not a population, and this is
26.675's finding for the sixth time: every dynamic check here is driven
by the corpus, and a shape no example contains is a shape nothing
executes. Two faults in the same function in three days both sat outside
it.

So the sweep's value here is the opposite of a confirmation: it says the
corpus cannot see this class, and that `example/` wants a schema with a
counted run of records whose element has a constrained length. That is
the next piece of work rather than a remark -- `put the construct in the
corpus` has paid every time it has been done.

**Confirmed independently by 26.725 the same day**, which built the
corpus-wide prefix sweep this record asked for and ran it on an export of
`a176c43` -- this fix's parent, with the fault present. It passes. So the
corpus is measurably blind to this class, where it turned out to contain
26.723's shape all along. The two faults are not the same story and the
difference is worth keeping: one needed an allocation, the other needs a
schema.

## The tighter option, its cost, and whose it is

The floor is EXACT for 93 of 95, so little is left on the table. Where it
is loose, the element's own `required` would answer higher and a caller
makes one more round trip.

The tight figure is reachable and is **not** taken here: the generated
code could call the element's own `required` with a zero-length slice and
multiply by that, which is exact by construction and cannot disagree with
the element because it IS the element's answer. It costs one extra call
on the truncated path and a mechanism in four emitters.

It is not taken because it is the same question 26.693 parked with the
copyright holder -- whether `required` should read every length that is
readable so that the first answer is the last -- and a tighter tail term
is work on one side of a contract whose shape is undecided. Stated here
with its cost so that the decision is available rather than implied.

## What it is pinned by

`test_required_answers_every_prefix.py` gains the `wide` shape and its
sequence, `[10 x 9, 12, 13, 13, 15, 15, complete]`. On a
`git archive HEAD` export carrying `traverse.py` and the test but the old
emitters, `test_the_answer_never_goes_backwards[wide]` fails and so does
the pin; every other case passes both sides, which is the statement that
the four existing shapes did not move.
