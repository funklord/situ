# 26.919: QUIC has an integer of its own

Status: recorded
Date: 2026-11-06
Source: re-reading "varint behind a length: refused" against the holder's "anything a protocol needs is ours"

**No length in QUIC or HTTP/3 could be described.** Fifteen decision records
cite QUIC, for its header protection and its key phase, and its integer could not
be declared: `varint_type` knew two encodings, both with a continuation
bit. RFC 9000's has none. The top two bits of the first byte say one, two, four
or eight bytes and the rest is the value, high byte first.

    varint_type quic_varint { encoding = quic; max_bits = 62; }

`max_bits` is 6, 14, 30 or 62 and nothing else, as a width the first byte cannot
say has no encoding, and `max_bytes` is refused since `max_bits` decides it. A
`tlv` tag and a `prefixed` length take it, which is an HTTP/3 frame and a
transport parameter. `minimal` refuses the longer of two spellings, which is
what RFC 9000 section 12.4 asks of a frame type and of nothing else.

`example/quic` holds an Initial packet and HTTP/3's frames. Its vectors and the
tests are the RFCs' own numbers, not this tree's: appendix A.1 of RFC 9000 and
the client Initial of RFC 9001's A.2, whose 1182 is stated there as a sum.

**The image says it as big with no terminal bits**, which `be128` cannot be, so
no flag and no parameter travels through the walkers' decoders. An older walker
would read such a message as groups, so the format moves to 8 and the two refuse
each other.

**Looking for where to add it found the sites disagreeing.** Each reader chose
for itself, and only a member's reader chose well:

- A `tlv` tag and a `prefixed(T)` length were read as leb128 whatever `T` said,
  in all four backends. The walkers read them as declared, so a `be128` length
  split them. Their width ignored a declared `max_bytes` too.
- A `minimal` `be128` member was held to leb128's count in Python and C++, and
  Python's getter raised `NameError` in a schema with no `minimal` leb128, as
  `varint_len` was imported only for one. C and Rust had this right.

`situc/codegen/varint.py` now answers for all of them, so a third encoding had
one place to go and a fourth will. Python imports what the region reads rather
than `varint_get` for any `tlv`.

**A varint the frame cuts short was whole to both walkers**, for every encoding
and always. `ff ff` under `{ v; u8 last; }` measures the varint as zero wide,
which is right for the lax reader, and `validate` used that width and placed
`last` on top of it, where all four backends say short. It took a message that
ends inside a varint and a test that said what it should answer: random bytes
rarely do the first, and the walker differential compares the two walkers, which
agreed.

Rejected: a flag bit for the encoding, which every decoder would carry to read
one case. `prefix2` as the name, which says less than the RFC's own protocol does.
Bitcoin's CompactSize and MySQL's length-encoded integer are a different read, a
first byte that is a value below a threshold, and 26.921 has them.
