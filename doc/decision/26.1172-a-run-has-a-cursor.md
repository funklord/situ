# 26.1172: a run has a cursor

Status: recorded; built in the four backends. Settles what 0060 left
owed and reserved for the holder ("yes, build the run cursor", holder,
2026-11-26).
Date: 2026-11-26
Source: raidcfgd, which wrote the cursor by hand (0060); fuzznet, inbox
20261126T1227Z, which did the same over `example/json`, restating
`while (sep == ',')` outside the schema.

## The rule

Every run of structs whose elements are reached by walking -- a `while`
run, a run ended by a terminator, a counted run of elements with no
single size -- has a `_next` beside its indexed accessor:

    C     situ_S_R_next(view, &cursor, &out)        -> SITU_OK / SITU_ERR_BOUNDS
    C++   s.R_next(cursor, out)                     -> err::ok / err::bounds
    Rust  s.R_next(&mut cursor)                     -> Ok(element) / Err(Bounds)
    Python s.R_next(cursor)                         -> element / IndexError

A zeroed cursor (`situ_cursor_t c = {0}`, `::situ::rt::cursor c{}`,
`Cursor::default()`, `Cursor()`) starts at the first element. The k-th
call answers exactly what the indexed accessor answers for `k - 1` -- the
same element or the same refusal -- so the end of the run is the end of
the indexed accessor, and an element that cannot be read is passed as
the indexed accessor's next index passes it. A run indexed by stride has
none: its indexed accessor is already constant time.

## Derived, not written

Each backend builds `_next` from the lines of its own walking accessor
rather than writing a second loop. That accessor opens `at = <base>;
n = 0` and hands out the element at `n == index`; resumed from the
cursor, the same lines start at the element handed out last with `n`
one short, so they read that element again -- which is where a `while`
run asks whether it ended the run -- and hand out the next. One element
read twice per call keeps a pass linear, and the cursor need not
remember whether the last element ended the run. A second loop would
one day disagree with the accessor about where an element starts, which
is the reason the walk prologues were already shared (`_walk_prologue`).

Python's `while` and record runs are indexed through a list of starts
walked in one pass; the cursor keeps that list from its first call, so
the walk is the accessor's own there too.

Where an accessor's body lacks one of the lines the derivation keys on,
nothing is emitted. `test_a_cursor_walks_a_run_as_its_index_does.py`
pins how many cursors each corpus schema gets, in every backend, so a
derivation that stops matching fails by name rather than going quiet.

## Options weighed

- **`_at_from(view, index, known_index, known_at, &out)`**, 0060's other
  shape: two numbers the caller must keep consistent, and still no
  answer to whether the last element ended a `while` run without a
  third. Refused for the cursor, whose fields the caller never sets.
- **The cursor remembering whether the run ended**, so the last element
  is not read twice: faster by one element read per call, and a second
  place the end rule lives. Refused; the re-read is the walk's own
  question asked again.
- **An iterator** (`Iterator` in Rust, a generator in Python): idiomatic
  in two backends and impossible to state the same way in C. The same
  `_next` in four is what a reader moving between them can rely on; an
  iterator over it is a few lines a caller can write.
- **Only on runs without `max`**, which `--materialize` already indexes:
  the index costs memory the cursor does not, and a capped run is walked
  by the same callers.

## Names

The runtime type is `situ_cursor_t` (and `::situ::rt::cursor`,
`situ_rt::Cursor`, `situ_runtime.Cursor`); `situ_cursor` and
`situ_cursor_t` join the C runtime symbols a schema may not generate.
Python imports it as `_situ_cursor`, so a struct named `Cursor` keeps its
name. `--single-file` inlines `Cursor` and binds the alias after it; it
read `Cursor as _situ_cursor` as one name at first and refused every
schema with a cursor, which the gate's single-file tests caught. A tlv region's walk is `x_first` / `x_next(item)`, where the item is
the position; a run's is `x_next(cursor)`. A member is one or the other,
never both, so the two never meet in one name.

## Not covered

A run of varints keeps its indexed accessor (`_at`, handing out a value)
and gets no cursor; a run that is itself a variant's arm gets none either.
Neither consumer has asked. A struct-typed member holding the run -- json's
`members` under `object` -- is the shape both have, and it is covered.
