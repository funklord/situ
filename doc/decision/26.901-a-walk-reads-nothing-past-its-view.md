# 26.901: A walk reads nothing past its view

Status: recorded
Date: 2026-11-06
Source: a walker disagreement on `edges.held_boxes`, followed under
AddressSanitizer

    struct node [depth = 4] { u8 tag; u8 len; u8 data[len]; u8 kids; node child[kids]; }
    struct list { node all[remaining]; }

`list` over the one byte `02`: `validate` read past the buffer, in C and C++. At
2870fd1e too, with no `[holds]` in sight. 26.322 and 26.325 guarded `extent` against a short tail and neither
reached the recursive form, which is written separately beside the plain one.

## Two reads with no bound

**The recursive `extent_at`** read a length out of the fixed prefix with nothing
asking whether the prefix was there. It takes the plain form's guard now, in C
and in C++.

**A count from a field the message places.** With the prefix guarded, a fuzz run
went straight to `child_count`: `kids` sits behind `data[len]`, and the count
loaded it raw where `kids`'s own getter is bounded. It answers zero past the
view, as the getter does. C++ reads the getter already. This one needs no
recursion: any run counted by a field behind a variable member, reached from a
parent's walk.

The suite did not show either. `held_box` is how this was reached, and why no
earlier schema or fuzz harness reached it is not established.

## Measured

`test_a_walk_reads_nothing_past_its_view.py` allocates each message at exactly
its own size. Before the fixes C and C++ abort on it. After them a seeded run of
600,000 messages in C and 300,000 in C++, each tried as both `list` and `twices`,
is clean under ASan and UBSan, with 39,170 of C's 1.2 million validations
accepted. Rust with overflow checks on (400,000) and Python (30,000) raised
nothing unexpected over the same shapes.

## The depth comes first, in the walkers too

The disagreement that led here was not the over-read. `held_boxes` over a message
both too deep and cut short: the four backends ask `nesting` first and refused
for depth; both walkers met the cut element and said bounds. A cycle through
members needs no probe in a walker, because measuring the first member follows
it down and meets the ceiling. Nothing measures a `[holds]` run's interior.

So each walker has one, `_nesting_within` and `nesting_within`, asked where
`check` asks it and only for a shape with a `[depth]` in an image with HOLDS.
Past the ceiling the answer is `cannot-say`, as it is for a cycle through
members. It does not follow an arm.

The other way was to move `nesting` after the struct's own checks in the four
backends. It is what bounds the stack, so it stays first.

## How it was missed

`test-c` and `cross-test` stopped at a compile error in the same header, and the
gate before that was cut short, so a chain thought gated had not reached this.
