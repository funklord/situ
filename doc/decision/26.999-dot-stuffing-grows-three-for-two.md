# 26.999: dot-stuffing grows three for two

Status: recorded
Date: 2026-11-13
Source: 26.998's builder sizing a write from the declared bound, measured
before it was pushed

**The declared worst case was wrong, and short.** `smtp_dot` declared
`ratio_bounded(4, 3)`, from a body of nothing but `.CRLF` lines -- three
bytes in, four out. But the generated encoder takes a bare LF as a line
end, deliberately, so it can stream (a CR ending one call and an LF
starting the next would otherwise be missed). A body of `.LF` lines is two
bytes in and three out. Measured with the generated encoder: 200 bytes of
`.\n` encode to 300, where 4:3 allows 268.

**What a short bound costs.** The signature's ratio is what a consumer sizes
an encode buffer from. 26.998's builders computed their room from it, so
before this was found, unpushed, a C or C++ builder handed `.LF` content
and a capacity between the two figures would have written past the
caller's buffer; Rust would have panicked and Python raised. Any consumer
sizing its own buffer from the map had the same exposure.

**The bound is now `ratio_bounded(3, 2)`**: one dot added per line, and a
line that can be stuffed is at least two bytes (`.` and its LF), the last
line excepted, whose dot needs no LF -- so `ceil(len / 2) * 3` holds at
every length. `kernels.STUFFING_BOUNDS`, `example/smtp`, `std/kernels`,
the generated comment and every test declaring the pair say 3, 2; the
encoder is unchanged. `wire --check` calls the smtp change breaking, and
it is: a peer that sized from 4:3 was undersized.

**Why the oracle missed it.** `test_differential_oracle` measures each
stuffing encoder against its declared bound, on purpose -- and fed it the
input the schema comment named as the worst case, `.CRLF`. The comment and
the measurement were one reading, so they agreed; the measurement could only
confirm the claim it was given. It now feeds `.LF`, and
`test_a_builder_writes_a_coded_region` builds 50 such lines into exactly
the corrected room and refuses one byte less.
