# 26.1115: a run written at a new length moves what sizes it

Status: recorded
Date: 2026-11-20
Source: the goal-gap walk at the end of /go run 8, from 0034's own table,
whose second row -- "anything that shifts layout" -- was the editor's one
unbuilt kind of write

0034 put the shifting write "behind 26.99", and the editor's refusal named
"the invalidation model of 12.3". 26.99 has been done in every backend and
the walk since 2026-08; the invalidation model is not built. But the most
common shifting write needs no model of what depends on what: a string, a
label, a chunk's data, a sticker's description -- a byte run sized by one
field ahead of it, in a message that is the whole buffer.

## The change

`Document.set` with bytes of a new length splices them in and tries, in
order:

1. **The splice alone** -- a run the frame sizes (`[remaining]` over the
   whole buffer) needs nothing else to move, and changing a field for no
   reason would be a second edit nobody asked for;
2. **every writable scalar ahead of the run, moved by the same number of
   bytes** -- `n` for `name[n]`, `length` for `data[length]`, a
   `len - 4` field the same way. Which one sizes the run is not read out
   of the size program; each is tried and exactly one must hold. Two that
   both would are refused as ambiguous.

A candidate holds only by measurement, as every write here does: walked
again, everything before the run sits where it sat, everything after it is
exactly `delta` bytes on, the run reads back as written, every other member
reads the same value -- **and a message that conformed still conforms**.
The last is what keeps 26.605's property: `invariant total ==
size(payload)` derives an Immutable `total` that cannot follow, so growing
`payload` would leave it describing the old length; the verdict sees that
and the write is refused, saying which check would not hold. A tag
covering the run or the moved field is recomputed where situ carries its
codec and reported stale where it does not.

Measured on real formats: a PNG `tEXt` chunk's data grown by nine bytes
moves `length` by nine and recomputes the CRC, checked against zlib; a UDP
payload moves `length` and says the checksum is stale, since that sum
covers a pseudo-header the message does not carry (14.2a). In the window a
run that may change length (`mutate = Shifting`) is no longer held to its
length as it is typed; every other run still is, and the window's key test
writes three bytes where there was one through Qt and through qtty.

## What this does not do

- **A window inside a larger message** is refused: a parent's length, an
  outer frame or an offset table elsewhere would go stale, and finding them
  is what 12.3's invalidation model is for.
- **Two fields at once** -- a run sized by one field inside a struct framed
  by another -- finds no single candidate and is refused, naming that no
  one field does it.
- A run of wider elements grows by whole elements only when the sizing
  field counts bytes; one that counts elements (`u16 w[n]`) needs `n` to
  move by `delta / 2`, which the same-delta rule does not try.

## Found on the way

`limit` was left at the old length after a resize when a window had been
given equal to the whole file, so the next walk refused a window past the
buffer's new end; a document over the whole buffer now keeps its limit
with it. And a struct holding a `u16` run shows every one of its fields
as "cannot be read", because the owned decode the editor reads values with
is whole-or-nothing and refuses the message over that run -- recorded in
`project.md`'s open list.
