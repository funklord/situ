# 26.700: one accessor, two spellings

Status: recorded -- both halves fixed, construct in the corpus
Date: 2026-10-27
Source: `project.md` section 26

**Set out to do `raw_` on the holder's instruction, and the rename
exposed a second defect underneath it: the C++ accessor had two spelling
functions, and only the declaration used the renaming one.**

`bare_name` exists so that a member called `int` does not generate
`std::uint8_t int() const`, which is not C++; it suffixes one underscore
and `cpp/names.py` names every accessor with it. **The four sites that
spell an accessor CALL used `c_name`**, which does not suffix. So the
class declared `int_()` and the read asked for `this->int()`:

    error: expected primary-expression before '(' token

Measured over the six names `edges.situ` actually carries -- `int`,
`short`, `class`, `type`, `match`, `lambda` -- in the arithmetic
construct: all six broken. In the plain construct: all six clean.

**And that is exactly why it was latent.** `test/schema/edges.situ`'s
`struct keywords` has held those six since it was written, with a comment
saying DNS calls a field CLASS and a rule against them would be situ
declining to describe a format. Nothing sized a member by one, so no read
was ever emitted. **Six names and no reference is the shape that hid it**,
and the struct written to make keyword names safe is the one that proved
they were not.

## `raw_` needed a second thing, and the two are separable

Unifying the spelling fixes every keyword and does **not** fix `raw_`,
because `raw_` is not a keyword -- it is the base's protected data member,
which the emitter reads bare in about ninety places (`situ_base(raw_)`,
`raw_.limit`). A consistent `raw_()` accessor still hides it:

    error: invalid use of non-static member function
           'uint8_t situ::s::raw_() const'

So `bare_name` consults a second set, `CPP_BASE_MEMBERS`, and suffixes
`raw_` to `raw__`. **`raw` is deliberately not in it**: suffixing it would
land on `raw_` and create the collision this removes, and 26.694 already
fixed `raw` by qualifying the call sites.

**Both halves were controlled separately**, which is what shows neither is
decoration: with the read unification reverted, `int` breaks and `raw_`
breaks; with only `CPP_BASE_MEMBERS` reverted, `raw_` breaks and `int` is
clean.

## The construct is in the corpus now, and it earns the gate

`struct keywords` gained `u8 body[class + 1]`. Reverting the read fix
fails **`test_every_schema_compiles[schema/edges.situ-plain]` and
`[schema/edges.situ-materialized]`** -- the standing corpus gate, in both
modes, on every run, where before the question could only be asked by a
constructed probe.

Blast radius of adding it: **one packed image of 46 changed**, edges from
30,818 to 30,900 bytes, and all four backends still build it. Before the
construct, the fix itself left all 230 generated files across the four
backends byte-identical, which is the other half of the measurement -- no
committed schema read a keyword-named field.

**And the population is read from the runtime rather than listed.**
`test_a_field_named_for_the_views_surface_compiles` parses
`runtime/cpp/situ.hpp` for every name `class view` declares -- today
`base`, `limit`, `raw`, `raw_` -- and compiles a schema with a field of
each, REFERENCED in a size expression, because the plain shape cannot
reach the read path. Removing `CPP_BASE_MEMBERS` fails exactly the `raw_`
case. That is the half `RUNTIME_SYMBOLS` already argues for about itself:
a list nobody checks is a list that has drifted.

## Two lenses that came back empty, with what was looked for

**`-fanalyzer` is unused and finds nothing here.** GCC 14.2 supports it,
no Makefile or test invokes it, and it is the first strategy on the
bug-hunting list. Run over generated C for `example/dns` and
`test/schema/edges.situ` -- 1.7 KB and 144 KB of C -- it reports **zero
warnings** and costs seconds. Recorded so the next session does not spend
the same hour: what it would have found is use-after-free, leaks and NULL
derefs, and the generated decoders carry none that it can see.

**`mypy --strict` is already clean where it matters, and enabling it buys
nothing demonstrated.** `situc` (93 files), `walker` (8) and `editor` (3)
pass strict today while the Makefile runs them non-strict; `tool` and
`test` report seven findings, **all of them unresolved-import artifacts**
of invoking mypy outside the sys.path those modules build at runtime, and
none a defect. The reason not to turn it on: 26.697's `str | None` was
caught by the EXISTING non-strict gate once the call had a typed
signature, so the case for strict rests on nothing measured.
