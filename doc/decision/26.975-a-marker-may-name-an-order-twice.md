# 26.975: a marker may name an order twice

Status: recorded
Date: 2026-11-12
Source: walking the goal gap -- pcap's nanosecond files

pcap writes two pairs of magics: `a1 b2 c3 d4` for microsecond
timestamps and `a1 b2 3c 4d` for nanosecond ones, each in either byte
order. A marker took one value per order, so a nanosecond file could not
be described, and since 26.964 it was refused outright as naming no
order. Naming an order again adds a value:

    endian_marker magic : u32 {
        little = 0xD4C3B2A1, big = 0xA1B2C3D4,
        little = 0x4D3CB2A1, big = 0xA1B23C4D,
    }

A repeated member rather than `little = A | B`, which already parses as
an OR, or a list after the comma that separates members. The first value
of each order is what a writer emits -- the host constants are unchanged
-- and the marker stays readable as a number through its getter, which
is how a reader tells microseconds from nanoseconds.

Every reader's test is membership now: each backend's order test, its
argument predicate (26.961) and its `validate` (26.964); the packer
writes a marker row per `little` value and both walkers read the order
as little where any matches; the membership row `validate` uses holds
every value; the dissector compares against each. A value named for
both orders is refused at the declaration.

`example/pcap` declares both pairs. `test_a_marker_may_name_an_order_
twice.py` reads nanosecond files in both orders through all four
backends, both walkers and the dissector, refuses a fifth value, and
round-trips the declaration.
