# 26.704: two Python guards matched by a member's own name

Status: recorded -- both fixed
Date: 2026-10-27
Source: `project.md` section 26

Two independent sites, same shape as 26.696 and 26.698: a guard written
about the emitter's own output, matched by a member's name.

## `_unshadow` could see a builtin only in first position

`_unshadow` aliases a builtin a member has taken and rewrites the
annotations, with `re.sub(r"(:|->) {name}\b", ...)`. **The only place
`bytearray` and `memoryview` appear in a generated module is the union
`data: bytes | bytearray | memoryview`, where they are the second and
third alternatives.** So the alias was emitted, never used, and the
annotation resolved to the member's own property:

    error: Function "s.s.bytearray" is not valid as a type  [valid-type]

`py_compile` passes either way -- `from __future__ import annotations`
makes the annotation a string, so only a type checker looks -- and the
corpus-wide `test_every_generated_module_type_checks` cannot reach it
because no committed schema carries such a name. `|` joins the
alternation now.

**This one is NOT inert on the corpus, and the measurement is the
honest part.** `edges.situ` has `u8 bytes[4]`, so `bytes` is in the
shadowed set, and the widened rewrite now also rewrites `| bytes` into
`| _situ_bytes` -- **18 lines, in `edges.py` alone**, every other
generated module byte-identical. Both spellings pass `mypy --strict`
with zero errors, so the old output was not broken: shadowing is
per-class and `_unshadow` is module-wide, so the widening is cosmetic
where the member is in another class and load-bearing where it is not.
Narrowing it to per-class would mean restructuring a whole-module
rewrite, and is not worth it for an alias that is correct either way.

## The "already explained" guard matched the member's accessors

Section 1 asks that an absent operation be "deliberate, explained, and
assertable". The guard against explaining twice was
`any("mutate is" in line or "setter" in line for line in lines)`, and a
member called `setter` renders `def setter_offset` and the like -- so the
guard matched the member's own accessors and **the explanation was
dropped**.

Silent, and a four-way disagreement: C, C++ and Rust each still wrote
theirs for the same schema, so Python alone stopped explaining, and the
four-way refusal gate does not list this phrase. Section 1's third clause
fails with nothing to notice it.

The explanation is a COMMENT -- `# No <name> setter: mutate is ...` --
which is what tells it from code. The guard reads comment lines only now.

**Controls:** reverting either fix fails its own test -- the `valid-type`
error for the first, a missing note for the second -- with `i` passing
throughout.
