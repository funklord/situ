# 26.677: A wider check field lets undeclared bits decide the verdict

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

0067 left one question open and the copyright holder closed it: **a
`checksum` field wider than the value its code produces is refused.**

It was accepted when 0067 landed, and the reasoning given there was wrong
rather than merely incomplete: "a narrow code in a wider field is ordinary
-- the value is zero-extended and the comparison stays exact". The
comparison is not exact. The generated check reads the whole field:

    return (uint32_t)situ_base(view)[crc_at] == want

`want` is the seven bits the code produces and the left side is eight bits
of message, so the eighth bit is part of the comparison and nothing in the
schema says what it is.

## Measured, which is what settled it

A crc7 over `12 34`, in C, with the field a `u8`:

    crc7 want = 0x20
    spare bit 0: check=0      (SITU_OK)
    spare bit 1: check=8      (SITU_ERR_CHECKSUM), same crc7

**Two messages whose declared content is identical get different verdicts,
decided by a bit the schema never describes.** That is not the padding
advisory's territory, where two encodings carry one value and the cost is
canonicality; it is `validate` depending on bytes the schema does not
describe, which is the thing situ exists not to do.

Note which direction the failure goes: the spare bit set makes a *correct*
code read as corrupt. A reader cannot discover this from the schema, and a
writer who leaves the byte uninitialised produces messages that fail their
own check.

## The remedy already existed

0046 added sub-byte check fields so that a narrow code is declared at its
true width, and `std/kernels.situ` carries thirteen widths for the same
reason. `test/schema/edges.situ`'s `mmc_command` is the properly-written
form of exactly this layout -- a `u7` beside a `reserved u1
[must_be_zero]`, which is the stop bit MMC actually has -- and it is
verified against a real CMD0 in 26.372. So the wider form was the sloppy
spelling of a layout the language already describes precisely, and the
diagnostic names that file.

## What it cost

**No `.situ` schema.** The eleven comparable check fields in the corpus
were already exact, which 0067 measured.

**Three fixtures embedded in Python tests**, which is where 0067's first
attempt at this rule went wrong -- the census read `.situ` files and these
are string literals:

- `test_codegen_c.py`'s one-byte-checksum test used a crc7 in a `u8`. Its
  subject is a field that is ONE BYTE, so it takes a crc8 now, which gives
  that honestly.
- `test_region_names_are_scoped.py`'s `filler` used a crc5_usb in a `u8`.
  It exists to put a region named `body` next door and its codec is
  incidental, so it takes a crc8. The sub-byte code that file is about is
  `wrong_order`'s, unchanged.
- 0067's own `test_a_checksum_wider_than_its_kernel_is_accepted` is
  `..._is_refused`, asserting the diagnostic and that the remedy names
  `must_be_zero`.

## Why the first answer was wrong, which is the transferable part

0067 accepted the wider field because **three fixtures relied on it**, and
that was taken as evidence the form was legitimate. It was evidence that
the form was *written*, which is a different thing: all three were
incidental -- a checksum present so a region had one, a one-byte field that
wanted a one-byte code. Not one of them was a protocol that stores a narrow
code in a wider field.

So the question "does anything depend on this?" was answered by counting
call sites instead of reading them. The reading takes a minute and reverses
the answer.
