# 26.826: a decoder was only ever fed its own encoder's output

Status: recorded -- fixed, with the positive control measured
Date: 2026-11-03
Source: `situc/codegen/c/codectests.py`; 26.823; 26.482; `project.md`
sections 1, 13.1 and 22

26.823 found that `std/kernels.situ` and `std/codecs.situ` get a fuzz
harness with no dispatch arms, so the 113 derived codec entry points are
fuzzed by nothing, and parked the widening of `gen-fuzz` as the holder's.
Looking for what could be done either way found something sharper, and it
was not a gap in `gen-fuzz` at all.

**`gen-codec-tests` already generates 146 property tests over
`std/kernels.situ`'s 44 codec signatures, and not one of them calls a
decode entry point on anything but the output of its own encoder.**

Counted: 44 `invertible`, 44 `deterministic`, 32 `length`, 24
`seekable_linear`, 2 `permuted`. Every one of them encodes first. Grepping
every `_decode(` call site in the generated file returns only the `extern`
declarations and calls whose argument came from an encode -- so the
decoders are exercised exclusively over the one input class they are
guaranteed to handle.

**A decoder's whole risk surface is the input an encoder did not produce**,
and that is precisely where this project's worst memory fault was: 26.482,
a heap-buffer-overflow WRITE in `situ_slip_decode`, from a length the
decoder derived out of the input's own bytes.

## The second half, which is the part that makes it a test

The existing tests declare their buffers as

    uint8_t coded[SITU_CODEC_MAX_OUTPUT];   /* 2048 */
    uint8_t back[SITU_CODEC_MAX_OUTPUT];    /* 2048 */

against `SITU_CODEC_MAX_INPUT` of 256. So **1792 bytes of slack sit behind
every write**, and an overshoot of anything less than that writes into the
same array and is invisible -- with no sanitizer either, since this suite
is built with the ordinary test compiler. 26.482's own record says it was
found "with the buffer sized to exactly the capacity the generated guard
computes", which is the opposite of what these buffers do.

So the new property sets the capacity to the input count and puts the
guard immediately behind it. No decoder in this library expands: a
byte-counted one writes at most the bytes it was given and a bit-counted
one at most the bits, so `n` bytes is what a correct caller would supply
and one byte past it trips the guard.

## What it asserts, and what it cannot

A decoder handed arbitrary bytes may return any length and any content --
there is nothing to compare it against, which is why the round-trip tests
could not be made to do this job. What it may not do is write outside the
buffer it was given.

An over-READ is not caught: the input sits inside a larger array, so
reading past `n` stays in bounds of the object and no guard can see it.
That one needs the sanitized build, and it is the remaining half of
26.823's finding.

The input patterns are not arbitrary. A framing or stuffing codec is
driven by one distinguished byte -- `0x7E`, `0x00`, `0xDB`, `0x7D` -- so an
input of nothing but that byte drives the escape path through every branch
it has; two pseudo-random fills reach the rest. Ten lengths from 1 to 255,
seven patterns, per codec.

## The positive control

**A one-byte overshoot added to the generated `situ_slip_framing_decode`
-- `out[written] = 0;` before its return, which is 26.482's shape exactly
-- fails `test_slip_framing_derived_hostile_input` and nothing else.** 94
of 95 tests pass under that sabotage: `invertible`, `deterministic`,
`length`, `seekable_linear` and `permuted` are all blind to a write one
byte past the output capacity.

That is the measurement that says the property adds coverage rather than
count. 73 tests before, 95 after, for `std/kernels.situ`; `edges.situ`
gains 2; `std/codecs.situ` gains none, and correctly.

## What is NOT covered, and why

**Tier-1 codecs get nothing here.** `std/codecs.situ`'s signatures are
`impl ... extern` and use section 13.2a's ABI, `(in, in_len, out, out_cap,
&out_len)` -- the implementation is TOLD its capacity rather than having
to derive one, which is a different contract and a different attack. A
hostile-input test for that ABI is worth having and is not this change.

**A codec with no inverse gets nothing**, because the derived emitter
binds a decode entry point only where the kernel has one, and a test
naming a function that does not exist is 26.35's defect -- a harness
nobody could link. Gated in `test_codecs.py` rather than left to the C
compiler to notice.

**And this does not close 26.823.** Fuzzer-chosen inputs and a sanitized
build are still what that record asks for; this is the share of its value
that needed no decision about `gen-fuzz`'s stated purpose. Whether
`gen-fuzz` widens remains the holder's.
