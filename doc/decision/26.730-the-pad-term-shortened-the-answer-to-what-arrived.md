# 26.730: the pad term shortened the answer to what had arrived

Status: recorded -- fixed in C; the other three have no pad branch to fix
Date: 2026-10-29
Source: `project.md` section 26

**`required` reported a message COMPLETE three bytes short.** That is the
one-sided safety property, the only one this tree calls one, because a
caller told complete stops reading and parses bytes that are not there.

    struct s { u16 used; u8 data[used]; pad_to(4); }
    used = 3, so a whole one is eight bytes

    have=4  truncated need=5
    have=5  COMPLETE  need=5   <-- three bytes short
    have=6  COMPLETE  need=6
    have=7  COMPLETE  need=7

## The line contradicted the comment beside it

C's pad branch in `_required` carried this, and had since 26.265:

    # NOT clamped, which is why this does not reuse the accessors'
    # `situ_align_up_u32(at, n, view.limit)`. That clamp is right
    # where the question is which bytes are in the frame and wrong
    # here, where the question is how many a whole one needs:
    # clamping would shorten the answer to what has already arrived,
    # which is the one thing `required` must never do.

and emitted, four lines below it:

    const uint32_t len = situ_align_up_u32(base, 4u, view.limit) - base;

**The accessors' form, limit and all.** The paragraph is right about
everything except what the code does, and `view.limit` is `have`, so the
clamp it forbids is the one in the line it introduces.

`situ_pad_to_u32(base, n)` is the unclamped padding and has been in the
runtime since the beginning -- `situ_align_up_u32` is literally built out
of it. The fix is that call.

## Why the clamp is unsafe rather than merely loose

`at` is a running total that already includes every fixed member. The
clamp caps the pad term at `have - base`, so

    at <= constant + data + (have - base)

For `pickle_string`, `constant` is 4 (a `u16 used` and a `u16 trailer`)
and `base` is `2 + used`, which leaves `at <= have + 2`: the comparison
`have >= at` can never come out true early, and the fault shows only as
looseness. **With nothing after the pad there is no such margin.**
`constant` is 2, `base` is `2 + used`, and `at <= have` exactly -- so
`have >= at` is TRUE for every prefix from the pad's start onward, and
`need` is reported as whatever `have` happens to be.

So the two structs the corpus has are the two arrangements in which this
cannot be seen, and a trailing pad is not an exotic shape: chunk padding
in RIFF, TIFF and ELF all end a record that way.

## What the fix also removes

26.693's record measured C's aligned sweep and reported the mechanism as
a looseness:

    used=1 (6)   [1:4] [2:4] [3:4] [4:6] [5:6] [6:ok,6]

*"From n=5 the answer rises ONE BYTE PER ROUND TRIP: the pad term is
computed from a cursor clamped against `have` rather than from the `used`
the data has already given, so each byte that arrives reveals one more
byte of padding. A caller makes six round trips for a ten-byte message."*

That diagnosis was exactly right and the conclusion drawn from it -- that
an alignment cannot make `need` fall, so this branch was not the one to
look at -- was what left it alone. Measured after the fix:

    used=1 (6)   [1:4] [2:6] [3:6] [4:6] [5:6] [6:ok,6]

**The answer settles at the truth as soon as `used` is readable.** Two
round trips where there were four, and that is the same change that
removes the safety break: both were the clamp.

## What pinned it, and what did not

`test_codegen_c.py::test_required_counts_a_pad_as_the_bytes_it_occupies`
has swept every residue of a pad cycle since 26.265 and passes against
this. It calls

    situ_s_required(buf, (uint32_t)sizeof buf, &need)

with `buf` 64 bytes, for a message of at most ten. **The pad term is
never asked about a buffer that ends before the pad does**, so the clamp
inside it is unreachable from that test. A bound is only tested by an
input whose edge exists -- 26.725's finding, in the test that was closest
to this one all along.

Its counterpart, `test_required_does_not_shorten_a_pad_to_what_has_
arrived`, walks every prefix of a real message for every residue, in a
`malloc` of exactly that prefix's length, under ASan and UBSan, and
asserts the four properties together: no prefix complete before the
message, a complete answer equal to the whole, a truncated answer above
what arrived and never falling, and -- new here -- **never above the
whole**, because a bound that overshoots is a caller waiting for bytes
that will not come. It reports `used=0 have=2: COMPLETE, 2 bytes short`
on a `git archive HEAD` export.

Nor did the corpus sweeps catch it, and the reason is worth keeping:
26.725's two properties are about truncated answers, and this fault
produces a COMPLETE one. **A sweep that checks what a refusal says
cannot see a wrongful acceptance.** The property that catches it needs a
message of known length, which a fill is not.

## The other three backends

They have no pad branch in `_required` at all, so there is nothing to fix
in them: a `pad_to` member reaches a length expression that answers None
and the struct is declined. That is 26.692's open item, and porting C's
branch to them is now worth doing on the corrected form rather than the
clamped one -- which is what this record changes about that work.
