# 26.696: a member named for a builtin crashed two backends

Status: recorded -- the crash is fixed; a second finding is open
Date: 2026-10-27
Source: `project.md` section 26

**`min` and `max` are two-argument builtins AND legal field names, and the
second half killed the compiler in two backends out of four.**

    target buffer;
    endian big;

    struct s {
        u8  min [max = 4];
        u8  b[min + 1];
        u16 tail;
    }

    c       rc=0  generates
    python  rc=0  generates
    cpp     rc=1  ValueError: not enough values to unpack (expected 2, got 1)
    rust    rc=1  ValueError: not enough values to unpack (expected 2, got 1)

An uncaught traceback, not a diagnostic.

**The cause is one rewriter reading another's output, which `names.py`
documents one function away and did not apply here.** `over_fields` runs
first and rewrites the field into the target's getter -- `this->min()` in
C++, `self.min()` in Rust -- so by the time `expand_calls` reads the text,
`min(` is in it. Its pattern was `\b{name}\s*\(`, and a word boundary sits
between `>` and `min`, so **it took the getter for the builtin** and handed
`c_spelling` one argument where it unpacks two.

**C and Python were never exposed, and the reason is their spelling.**
Their reads are `situ_s_min_get(view)` and `self.min`; neither contains
`min(`. So this is not a C++/Rust defect so much as a shared rewriter whose
guard happened to hold for two of four targets -- and `over_fields`' own
docstring already warns that "a single alternation cannot match its own
output", about itself, one function up.

**The fix is what a builtin call actually is: a name reached by nothing.**
Not a member access, not a qualified name, not the tail of a longer
identifier -- `(?<![.>:\w])` in place of `\b`. Tested as a discriminator
before being applied, against the four real spellings and three genuine
call forms:

    this->min()              not a call    core::cmp::min(a, b)  not a call
    self.min()               not a call    situ_min_u32(a, b)    not a call
    min(units, 3)            a call        x + min(a, b)         a call
    leaf_u(this->min()) + 1  not a call    (min(a, b))           a call

**Blast radius: nothing.** All four backends over all 42 schemas --
**230 files, byte-identical**. And that is the control rather than a
weak result: `test/schema/edges.situ` carries `u8 clamped[min(units, 3)]`
with the comment *"an attribute name, being called"*, so output that did
not move is output where a real builtin call still expands. Rust still
emits `core::cmp::min(situ_rt::nonneg(...))` for it.

**The bare form is a different question and was already right.**
`u8 b[min]` is refused by the front end -- *"`[min]` needs a value"* --
because `[min]` is an attribute name there. Only the arithmetic form
reached the rewriter.

**Found by the Rust half of 26.695's sweep**, which swept 120 names
against six constructs; `min` and `max` were the only two of them that
crashed rather than collided, and they are not names the generator
declares -- they came in as the front end's own builtin list.

## Open: `--materialize` Rust fails `-D warnings`

**Name-independent, reproduced on the control's own field name**, so it
has nothing to do with this entry's subject beyond having been found
beside it:

    struct s { u8 i [max = 4]; u8 b[i]; u16 tail; }
    situc build s.situ --target rust --out gen --materialize

    error: unnecessary parentheses around function argument
      at = situ_rt::advance(at, (situ_rt::nonneg(situ_rt::leaf_u(...))), ...)
    note: `-D unused-parens` implied by `-D warnings`

Without `--materialize` the same schema is clean, measured both ways in
one run. It matters because 26.496 made `-D warnings` the standard for
generated Rust, on the argument that generated code which warns teaches a
reader to ignore warnings -- and the offset cache was outside what that
gate reaches.

`names._unwrap` exists for this exact shape and says so: *"the field
renderer parenthesises every read, and `-D warnings` calls a parenthesised
function argument unnecessary."* It is applied in `rust_spelling` and not
at the `advance` sites in `codegen/rust/emit.py`. Reaching for it there
means using another module's private helper or promoting it, which is a
small decision rather than an obvious edit -- so this is recorded with its
reproduction rather than fixed in passing.

## What the Rust sweep found that belongs to 0062

Reported by the worker that ran it, verified by me only where noted, and
recorded here so the next person does not re-derive the population:

**0062's duplicate-definition class is eight names in Rust, not two.**
`validate`, `required`, `check_which` and `new` fail `E0592` in every
construct; `extent`, `extent_at`, `nesting` and `nesting_at` fail it only
for a variable-extent or recursive struct, so four constructs cannot see
them. 0062 lists `validate` and `required`. All 48 Rust keywords are
clean, including the three `r#` cannot carry.

**`as_ref` and `bytes` are one mechanism with two names**, and it is a
different one. Confirmed by reading `rust/emit.py:8053`, which is

    re.sub(r"self\.(?!as_ref\(\))(?!bytes\b)", "self.as_ref().", text)

-- two negative lookaheads, one to avoid rewriting into
`self.as_ref().as_ref()` and one to leave the private data field alone.
**A member's own accessor can match either**, so the rewrite is skipped
and the expression resolves to the wrong thing. That is this entry's own
shape -- a rewriter's guard matched by generated text -- in a third place.

**`into` is std's blanket `Into` impl winning over the inherent getter**
(`E0282`). The worker states the resolution order as the cause and says
plainly it did not read the emitter site that spells the receiver, so the
mechanism is theirs and unverified.
