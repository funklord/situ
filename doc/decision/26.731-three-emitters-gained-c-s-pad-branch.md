# 26.731: three emitters gained C's pad branch

Status: recorded -- 26.692's open item is closed
Date: 2026-10-29
Source: `project.md` section 26

C has had a `pad_to` branch in `_required` since 26.265 and the other
three had none, so a `pad_to` member reached a length expression that
answers an array count a pad has not got, the expression answered None,
and the struct was declined. The consequence was 26.692: five structs the
shared `frameable` called frameable and three backends would not define a
`required` for, so their frame layers emitted a `Reader` calling a
function that was not there and did not compile.

26.729 took three of those five out -- they held a `tlv` region and no
backend should have framed them. **This closes the other two**, and with
them the last entry in every backend's frame holdout set.

## What decided it, having been parked wrongly once

The previous run parked this as depending on the open question of whether
`required` should read every readable length, on the ground that C's pad
term was loose. `project.md` settles it in one sentence:

> **Four backends over one layout**, and the claim that matters is that
> they agree [...] four backends that disagreed would mean a schema means
> four things.

A faithful port makes them agree; the looseness was a separate recorded
question. **And the looseness turned out to be a safety fault** (26.730),
so the parking was wrong twice over -- it deferred a port *and* left the
fault that made the port look unattractive. A wrongly-deferred question
is caught by nothing, which is exactly what `working-practice.md` says
about it.

## The port

`situ_pad_to_u32`, `situ_rt::pad_to` and `pad_to` -- the UNCLAMPED
padding, which is the form 26.730 left rather than the clamped one that
stood there. C++ shares C's runtime and had it; the Rust and Python
runtimes gained it, each defined once and used by `align_up` so the
clamped and unclamped forms cannot drift. That is how `situ.h` has always
had it.

Three things the branch has to get right, and the comment in each emitter
says so:

- **The alignment is taken at the pad's own base**, not at `at`. `at` is a
  running total whose constant includes every fixed member, the ones after
  the pad included, so aligning `at` for `u16 used; u8 data[used];
  pad_to(4); u16 trailer;` aligns `2 + n + 2` and answers 4 where the
  truth is 6. That is 26.265's own trap.
- **It is not clamped**, which is 26.730.
- **The cursor advance is omitted where nothing reads it**, because Rust's
  `-D warnings` refuses a dead store outright. The `ahead` form the other
  branches already use handles it.

Where there is no cursor the three decline rather than guess: C falls back
to a static base expression and they have none. No schema in the tree
reaches it -- `framing_gaps` gives a cursor for all three pad structs --
and declining is what they did for every pad until now.

Measured, all four identical on `pickle_string` with `used = 1`, where a
whole one is six bytes:

    have=1  truncated need=4
    have=2  truncated need=6
    have=3  truncated need=6
    have=4  truncated need=6
    have=5  truncated need=6
    have=6  COMPLETE  need=6

## The construct, and what it found

`test/schema/padded.situ` gains `trailing_pad` -- `u16 used; u8
data[used]; pad_to(4);` -- the shape 26.730 needed and the schema had
not: both of its pad structs carry a `u16 trailer`, which is why they are
the two arrangements in which that fault cannot be seen.

**It found a second thing on arrival**, which is what putting a construct
in the corpus keeps doing. It is the first struct in the tree whose LAST
member is a pad, so the first whose offset-cache plan ends with an
`align` step after the final capture -- and `resolve_offsets` emitted

    at = situ_rt::align_up(at, 4, self.bytes.len());

as its closing line, with nothing below it to read `at`. Rust's
`-D warnings` makes `unused_assignments` an error, so the materialized
crate would not build. The other three backends accept the same dead
store in silence, so this is trimmed in the Rust emitter rather than
treated as a fault in them: every step after the last capture is dead by
construction, because `at` is read by a capture or by a later advance.

That is the third time in two runs that this backend's compiler has
reported something the other three take quietly, and the argument for
having written it.

## What is left of 26.692

Nothing. Every backend's frame holdout set is empty. They are kept rather
than deleted, with the history in their comments, because the mechanism is
live: the frame layer asks the shared `frameable` and each emitter's
`_required` then applies its own conditions, so the next construct one
backend gains before the others puts a schema back in them.
