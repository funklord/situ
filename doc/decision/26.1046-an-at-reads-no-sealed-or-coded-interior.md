# 26.1046: an `at` reads no sealed or coded interior

Status: recorded
Date: 2026-11-17
Source: openmlx4's FS2 schema, measured while landing 26.1041

**An `at` that reached into a nested struct's `sealed` region crashed
`situc build`:**

    struct section {
        u8 n[12];
        sealed body(ae, nonce = n) { u8 next; u8 len; }
        tag u8[16];
    }
    struct s { section one; hdr there at one.next; }

    situc.names.UnknownName: 'one.next'

What the message holds there is ciphertext, so no reader could have
placed anything by it, and a discriminant may not read it either -- it
is out of scope. It is refused by name now, for `sealed` and `coded`
alike, on a plain located member and on a located variant arm.

## What was refused first, and why it is not

The first version of this refusal also took `authenticated` regions,
and it refused openmlx4's committed `fs2.situ`, whose `gph_chain` places
each section by `section.hdr.next`, inside `gph_section`'s `authenticated
body`. Its premise was that "a variant may not switch on a field inside a
nested struct's region", so `at` should not read one either. **That does
not hold for `authenticated`**, measured: `variant rest switch (one.next)`
with `next` inside `section`'s `authenticated body` builds, and so does a
length naming it. What refused the two-level `one.h.next` was the
discriminant's scope, which reaches one level down, not the region.

And it should not hold. `authenticated` is plaintext covered by a tag, and
a format has to read such bytes to find the tag at all -- a record's
length sits in the AAD it authenticates. Section 14.3's gate, no view
before the tag verifies, is a `sealed` region's. Verifying FS2's CRC
before following `next`, as fs2.c does, is the caller's
`situ_gph_section_crc_check`, because `validate` computes no checksum
(0051). A version that ran that check inside the located accessor was
built and set aside for that reason: it changed what `validate` means
for one construct, and the C walker, which computes no checksum, could
only decline such a struct.

The holder had chosen to land the first version on its stated premise
and to tell openmlx4, whose `make check` it turned red. This version
refuses nothing in `fs2.situ`.

## Measured

`test_wellformed.py`: `hdr there at one.next` with `next` inside a sealed
`body` is refused ("reads into `section`'s sealed region `body`"), and so
is the same read from a located arm; with `next` inside an authenticated
`body` it builds, and so does a read of a field beside the sealed region.
With the region lookup made to answer nothing, both refusal tests fail.
openmlx4's `src/fs2.situ` and all 63 schemas in this tree build.
