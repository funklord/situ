# 26.928: a pad is part of an element

Status: recorded
Date: 2026-11-07
Source: a RIFF schema written to see whether one could be

**A pad the data places measured as nothing.** With

    struct chunk { u8 id[4]; u32 size; u8 data[size]; pad_to(2); }

C's extent summed `0u` for the pad, so a chunk of odd size ended a byte early and the
next was read from its pad: wrong, silently. Python had no `_extent` and raised
AttributeError out of `validate`, and C++ and Rust did not build. WAV, AVI and WebP
are all this shape. Nothing in the corpus had a pad behind a variable member inside a
run: `required` had handled one since 26.730, in its own loop.

**`_content_length_expression` answers for a pad now**, in all four, as what reaches
the next multiple from where it stands. The offset chain already knew how.

**Clamped.** The first draft took `required`'s unclamped form, and the walkers
disagreed, rightly: 26.578 settled that a pad past the frame is as many bytes as are
there, and every backend's own pad check clamps. A WAV that drops its last pad byte
reads, which is what readers of them do. `required` still asks for the byte, as it
says what a whole one needs.

`example/riff` is ffmpeg's: `-write_bext 1` with a coding history of two bytes makes a
605-byte chunk with `data` behind it, and Python's `wave` module, which knows nothing
of this project, finds the same twenty frames.
