# 26.1167: a known tlv value holds its type

Status: recorded; built in the four backends, declined by both walkers
Date: 2026-11-23
Source: openmlx4 (inbox 20261123T1138Z), measured on situ b55f6812

## The finding

openmlx4's FS2 image-info region names its items' types:

    known = {
        1 : { name = fw_version,    type = u8 },
        2 : { name = fw_build_time, type = fw_build_time },
    }

and nothing held a value to its type. A date whose binary year the
struct refuses (`07 E1` where BCD wants `20 17`) verified inside the
region; an 8-byte struct verified in a 3-byte value; `type = u32`
verified with 2 or 10 bytes. openmlx4 asked which `type` means: one value
of the type, or an element type filling the length.

## What `type` means

**The element type filling the item's length.** That was already the
code's and the corpus's reading, which the first answer sent to openmlx4
got backwards and then corrected: example/protobuf declares
`2 : { name = username, wire = 2, type = u8 }` over a length-delimited
string, and `type = T[]` says the TAG may repeat (`tlv_single_tags`,
26.740), not that one value holds a run. So 16 bytes of a date are two,
and 16 bytes of `type = u8` are a string.

## What is held

`traverse.tlv_typed_tags` names the tags whose element is a struct of
fixed size taking no arguments (a scalar was here too; see the correction
below). Each backend's `_whole` -- the check `validate` runs over the
region (26.737) -- refuses, for an item with such a tag, a value that is
not a whole number of elements (CONSTRAINT), and runs a struct element's
own `validate` over each element, whose refusal is the region's.

Left out, each for a reason:

- **A byte-wide scalar** divides every length; there is nothing to check.
- **A scalar whose wire rule already fixes a multiple of its width** --
  protobuf's `f32` on wire 5 is four bytes by its rule. Naming it would
  only make the walkers decline a region they can answer for.
- **A varint, an enum, a struct of varying extent** -- no width to divide
  by; left as before rather than given a rule of their own here.

## The walkers

The image carries neither the tags nor the element type, so the region's
row gains bit 3 and both walkers decline it (`cannot-say`), as they do
for `ordering`, `unknown = error` and `duplicate_tags` (26.738-26.741):
never `0` for a value the four refuse.

## Found on the way

C and C++ read a three-byte length or tag as its first byte alone, and
openmlx4's region is `length_type = u24`; fixed first, in its own commit
(4cb44215).

Held in `test_a_known_tlv_value_holds_its_type.py`: eleven hand-worked
verdicts in all four backends, the struct declared after the region so
C and C++ must name its validator ahead of its definition, and both
walkers declining. The test fails with any one backend's check removed.

**Corrected (2026-11-23): a scalar `type` is held to nothing.** Gate g35
refused example/coap's committed `content` vector in all four: CoAP's
uint options are `type = u16` over a value of 0 to 2 bytes (RFC 7252
3.2), an integer of at most the width, where openmlx4's HwDevsId is
`type = u32` over a run of them. The corpus reads a scalar `type` both
ways, and neither may be refused on the other's account, so
`tlv_typed_tags` names only a struct of fixed size; the scalar half of
openmlx4's report (`u32` in 2 or 10 bytes) stays accepted. A way to say
which reading a schema means is a language question this does not
answer.

**Amended (2026-11-23): `form` says which reading.** The language
question the correction left is the schema's to answer, so a known tag
may say it: `form = run` holds the value to a whole number of its scalar
type (openmlx4's HwDevsId, `type = u32, form = run`), `form = number` to
one integer of at most its width (CoAP's `content_format`, `type = u16,
form = number`). Unstated, a scalar `type` is held to neither, as since
the correction; on a struct `type` `form` is refused, a struct value
being a run of whole structs already. In the wire signature as
`form=run`, in all four backends, and the walkers decline such a region
as for every typed one. Eight hand-worked verdicts in all four.

**Shown as well as held (2026-11-24).** The dissector named no item:
each was a row of its bytes. A `known` item's row now carries its name,
and a value whose `type` is a struct (one taking no parameters) is that
struct's subtree under it, as a member placed by `at` is (26.978); an
unknown tag stays its bytes. Held in tshark itself.
`situc doc` gave the region one row and no size; it now writes how an
item is read (the tag, its parts, how a value is sized, the policies)
and a table of the known tags: name, value -- a struct, `a run of u16`,
`one u16, in as few bytes as it needs`, bytes -- and whether it may
repeat.
