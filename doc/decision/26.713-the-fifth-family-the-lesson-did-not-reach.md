# 26.713: the fifth family the lesson did not reach

Status: recorded -- fixed; the same lesson's fifth and last family
Date: 2026-10-28
Source: `project.md` section 26

    codec c { kernel = polynomial(width = 16, init = 0x0000); }
    impl c derived;

generates nothing, and says:

    /* No implementation for `c`: a polynomial kernel is described but not
     * yet generated. Its properties are derived and correct; bind an
     * `impl c extern "..."` to supply the code. */

**Add `poly = 0x1021` and the same build emits 152 lines of CRC**, lookup
table and all. So the message sends an author off to write by hand a thing
the compiler will write for them, over one missing argument, and blames
the generator for it.

## It is a lesson this tree already learned four times

`_what_is_generated` exists for exactly this and its docstring says why:

> The message above says a kernel is "not yet generated", and on its own
> that reads as though the whole family were unimplemented. It was read
> that way: decision 0017 recorded that `stuffing` "returns no
> implementation for any input at all", when three codes generated then
> and five do now.

It then records that the fix **"reached one family of four"** and was
widened to `table`, `linear_block` and `permutation`. Polynomial is the
fifth and kept the bare sentence -- measured: `_what_is_generated` returns
`[]` for every polynomial kernel, complete or not, where a `table` kernel
with no `code` gets the eight names it could have used.

So this entry is not a new class. It is the same class, found by asking
which families the earlier fix had reached.

## The condition is neither `poly` nor `field`

The family generates **two** ways and both work:

    polynomial(width = 16, poly = 0x1021, init = 0)       152 lines
    polynomial(field = 256, n = 255, k = 223, ...)        309 lines

A CRC from `width` and `poly`; a Reed-Solomon code from `field`, `n` and
`k`. Keying the note on a missing `poly` alone would have put it on every
Reed-Solomon codec in the tree, which is why both controls are asserted
and why one of them is the RS form.

`width` alone is enough for the properties and not for the code, which is
`permutation`'s position in the same helper -- a bare `span` gives the
extent and not the mapping -- so this branch reads like its sibling
deliberately.

## What it is not

**No silently-wrong implementation.** This was the hazard worth checking
first, and it does not occur: the generator declines rather than inventing
a polynomial, so nothing like `KERNEL_REQUIRED_FOR_DERIVED`'s recorded
case -- *no seed -> generated with 0xFFFF, a different keystream* -- is
happening here. The cost is a misdirected author, not a wrong CRC.

That is also why this is a message and not a refusal.
`KERNEL_REQUIRED_FOR_DERIVED` lists `SHIFT` and `ONES_COMPLEMENT` and
could not express this one: the requirement is per FORM, not per family,
and a flat tuple would refuse the Reed-Solomon shape. The sparse map is
right; what was missing was the sentence.

## How it was found, and the lens

Derived from this run's own four bugs, which share a shape: a fact
recorded in one place and read in another with nothing checking they
agree. The probe was to omit each argument of each family from a working
declaration and see what happened -- 7 families, 30 omissions. Most are
refused by the family's own derivation; the survivors were `table` without
`code`, `linear_block` without `standard_form` or `code`, `stuffing`
without `unit` or `code`, and **`polynomial` without `poly` or `init`**.
Of those, only polynomial's reaches a family whose message says nothing
about what does generate.

## Proofs

The new sentence appears for the incomplete form and for neither complete
one, both asserted. Corpus-neutral: `gen-derived` output is byte-identical
over all 46 schemas, because all ten CRC declarations in the tree carry
`poly` and both Reed-Solomon ones carry `field`. The finding test fails
against `git archive HEAD`; both controls pass on both trees, which is
what a control for an over-broad note should do.
