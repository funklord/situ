# 26.1082: both walkers test a token in a named value

Status: recorded
Date: 2026-11-18
Source: 26.1079's "not yet", made a blocker by 0070's walked registry

**A named value that tests a token was the backends' alone.** 26.1079 let
`let u64 seconds = count * ((unit == time_unit.d) * 86400 + ...)` compile
in all four backends, and the image had no operation for "this member
spells that arm": the packer recorded such a `let` as one it could not
encode, and both walkers answered nothing for it. A walked registry reads a
duration's seconds and a flag's value exactly that way, so the gap blocked
step 4 of 0070.

## The rule

- `spells` (0x0D): a placement, a flags byte (bit 0 folds ASCII case), the
  arm's length and its bytes; 1 where the member's span is that arm,
  compared whole, else 0. `!=` is `spells`, then `^ 1`.
- The arm's bytes are the operand, so no table is needed and a `default =
  pass` set reads as any other -- the membership rows the packer writes
  for a `default = error` set are not what this reads.
- A span the frame does not hold spells nothing, as each backend's `which`
  over its clamped pointer and length answers no arm.
- The C walker's load callback carries the operand's offset in the code
  section as its `base`, `SITU_WALK_ASK_SPELLS`.

## Measured

`test_a_named_value_reads_a_text_number` holds both walkers to the four
backends' `seconds` and `daily` over seven duration frames, where it held
them to answering nothing; a Python walker that inverts the comparison
fails it on `14d`.
