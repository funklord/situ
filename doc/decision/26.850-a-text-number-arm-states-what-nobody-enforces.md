# 26.850: a text number in an arm states what nobody enforces

Status: recorded -- fixed in all six readers for the FIXED-WIDTH form; the
delimited sibling is 26.423's documented decline and is named below
Date: 2026-11-03
Source: 26.848's lens -- "a check family the member path asks and the arm
path does not" -- run a second time, immediately after the reserved field
it found first

## The construct

    struct arms {
    	u8 kind;
    	variant body switch (kind) {
    		case 1:  decimal u32 code[3] [min = 200, max = 599];
    		default: u8  other;
    	}
    	u8 tail;
    }

A fixed-width decimal number as a variant arm. Three constraints are
declared on it: the span is three decimal digits, the value is at least
200, and it is at most 599.

## What the six readers do with them

**Nothing.** Measured through the Python backend, whose `validate` is the
one that can be driven without a toolchain:

    kind = 1, "200"   accepted   (correct)
    kind = 1, "199"   accepted   -- below the declared minimum
    kind = 1, "600"   accepted   -- above the declared maximum
    kind = 1, "ABC"   accepted   -- not digits in any base

The same field OUTSIDE the arm, same attributes, same backend:

    "199"   ConstraintError: arms.code is 199, min 200
    "600"   ConstraintError: arms.code is 600, max 599
    "ABC"   ConstraintError: arms.code is not 3 digits in base 10

So the member path asks all three questions and the arm path asks none.
The other three backends emit no comparison either -- grepping their
whole output for the two numbers and for either comparison finds zero
sites in `c`, `cpp`, `rust` and `python` alike -- and the packer's arm
pass cannot write a row for one, ending as it does with

    if kind is not traverse.Check.CONSTRAINED:
    	continue

which `traverse.Check.TEXT_NUMBER` does not survive. So both walkers have
nothing to read, which makes it six readers and not four, exactly as
26.848 turned out to be.

## Why this is worse than a gap

**C publishes the bounds as constants.** Its header carries

    #define SITU_ARMS_BODY_CODE_VALUE_MIN 200u
    #define SITU_ARMS_BODY_CODE_VALUE_MAX 599u

beside a member nothing holds to them, so a caller reading the header is
told the range is contract.

**And THREE of the four state the digits check in a docstring** -- which
this entry first said was all four, corrected by generating the fourth and
reading it. C emits no helper for the construct at all, only the two
`#define`s above and the decline; C++, Rust and Python each emit the
infallible `_value` helper the offset arithmetic after the arm needs, and
document it in these words:

    `arms.body.code`, where an error cannot be returned: the offset
    arithmetic after it is not fallible, and `validate` refuses a frame
    whose digits are not digits.

`validate` does not. The comment is not decoration -- it is the argument
for why the helper may be infallible, and it rests on a check that is not
there.

So the four readers are wrong in two different ways, and C's is the
quieter one: three publish a promise they do not keep, and C publishes a
RANGE as two macros with no reader holding anything to it. A caller
reading that header is told the bounds are contract by the only thing the
header says about them.

Section 14.5 is what the compiler itself says about this shape, in the
error it raises for an attribute in a position nothing reads: "a schema
that states what the generated code does not enforce is worse than one
that states nothing". Here the schema states it, the header republishes
it, a docstring promises it, and six readers are silent.

## And the harness could not pose the question

Found while writing the gate: **`situc diff`'s driver generator names a
getter no backend defines**, for this exact construct. `_arms` in
`situc/codegen/differ.py` matches each arm shape to the accessor the four
backends emit for it -- a delimited arm to the span probe, a run of wide
values to the element probe, and so on -- and a fixed-width text number
matched none of them, so it fell through to the scalar probe:

    cc: implicit declaration of function `situ_arms_body_code_get`;
        did you mean `situ_arms_body_other_get`?

All four drivers do it, in their own spellings: `view.body_code(held)`,
`view.body_code()`, `view.body_code`. The C one fails to compile, which
is the good outcome -- and what it means is that **the construct could
not be compared four ways at all**, so no differential could have said
anything about the gap above. A harness built to find exactly this kind
of disagreement was unable to reach the construct that had it.

`_arms` skips a fixed-width text number now, naming the decline it is
matching. Output-neutral over the corpus and measured as such: 172
drivers -- 43 schemas in four languages -- byte-identical with the skip
and without, because the corpus's one text-number arm
(`edges.wide_delim_arm.held.code`) is delimited and was always taken by
the span branch. `test_a_text_number_in_an_arm.py` is the gate, and it
asserts that the question can be PUT rather than what the answers are,
so the fix below will not have to rewrite it.

## What the fix needs

The same five places 26.848 needed, and one reader question more:

- the four `_arm_member_checks`, which handle a pinned run, a delimiter, a
  run's span, a scalar's bounds, an enum's membership and now a reserved
  policy. A text number is none of those: its branch returns before the
  scalar path, which is the same route by which `decimal u32 code[] until
  " " [min = 200]` reached no backend as a MEMBER until that was fixed --
  so this is that defect in the other position.
- the packer's arm pass, which needs `Check.TEXT_NUMBER` to survive the
  `CONSTRAINED` test, writing the digits row, the minimal-spelling row and
  the value rows the member path writes a few hundred lines above.
- **and a reader for the digits row on an arm.** The value kinds already
  work for one, which is what made 26.848's walker half a row rather than
  a mechanism; `DIGITS_VALID` and `DIGITS_MINIMAL` are member-path kinds
  in both walkers, and neither `report._arm_constraints` nor C's
  `arm_constraints` switch renders them. That is the one genuinely new
  piece.

## Fixed

Five places, and one of them needed a reader rather than a row -- which is
where this differs from 26.848:

- **The four `_arm_member_checks`**, each reading the span inline. There is
  no accessor to wrap: all four decline the member, so the check parses
  the bytes itself, and the frame question is asked first and separately
  (a struct's minimum is its shortest arm's, and Python's slice CLAMPS
  rather than refusing, which would hand `parse_uint` two bytes of a
  three-digit field).
- **The packer's arm pass**, letting `Check.TEXT_NUMBER` through with the
  spelling row, the digits row and the value rows -- in that order, which
  is the member path's and has to stay: a field of non-digits that is also
  padded is a `[minimal]` failure before it is a parse failure.
- **Both walkers' arm readers**, which is the new piece. The value kinds
  were already there, but a failed READ was answered BOUNDS -- and for a
  text number the read IS the parse, so `ABC` came back `1` where the four
  backends said `2`. Both walkers make the member path's distinction now.

**Two of the four clauses were in the wrong place first, in a way that
reads as working.** The C++ port emitted nothing: `decimal u32 code[3]` is
a run of wide values by the test of the branch above, so that branch
claimed it, found no `[encoding]` to check, and returned -- a clause after
a branch that already claims the construct is a clause that never runs.
C's own first test is the same trap from the other side: a text number has
a count, so it left with the spans on the function's second line.

### And two of the four controls were vacuous until the case had an edge

Neutralising each half and watching the gate fail found that the
`DIGITS_VALID` comparison in BOTH walkers was unfalsifiable as first
tested. A fixed-width field's ceiling is derived from its own digits --
`decimal u32 code[3]` holds 0..999 -- so no three-digit spelling can
exceed it and the row is a tautology. The sabotage passed, which is the
signal.

`decimal u8 code[3]` has a ceiling of 255, which three digits CAN spell,
so `"999"` is the input with an edge: with it in the gate, cutting either
walker's digits comparison fails that case and nothing else. The four
controls now read: the emitter clauses fail both four-backend cases; the
packer's rows fail both walker cases; each walker's digits comparison
fails the narrow one.

## The delimited sibling, which is 26.423's decline and not news

`decimal u32 code[] until " " [min = 200, max = 599]` is the same
construct with a scan instead of a width, `edges.wide_delim_arm.held.code`
is in the corpus, and its terminator is checked while its digits and its
range are not -- by all six. **That one is documented**, in
`python/emit.py`'s `_delimiter_check` and in 26.423: all four decline it
together, deliberately, because "a partial port is the one outcome worse
than the gap" and an arm's property of that name answers its BYTES where
the member's answers a number.

The obstacle named there is now answered -- the fixed-width clauses parse
the span rather than reusing a parsed property, which is exactly what the
delimited form needs -- so this is the next piece of work rather than a
standing decline. It is left out of this pass on 26.423's own reasoning:
the half that was undocumented is now fixed in all six, and extending
scope to the half that is agreed and written down would risk the
four-of-six state both entries warn about.

## The lens, which is the entry's real content

26.848 was found by putting a construct in the corpus that nobody had
written. **This was found by asking the same question again rather than
moving on** -- what else does the member path ask that the arm path does
not? -- and it answered on the second try, in a construct the corpus also
does not carry.

**And what separates a gap from a decline is worth stating, because two
of the candidates checked at the same time turned out to be declines.**

- A **`tlv` region as an arm** is legal, gets no `_whole` accessor and no
  check -- and all four backends say so in the generated file: "`opts` is
  not a shape this backend reaches into yet." Named, in four languages,
  with nothing in the header claiming otherwise. **Not a finding.**
- A **pad inside an arm** is 26.848's, declined in agreement by all six.
- A **varint arm** is refused outright (26.433).
- A **nested variant with `default: error`** reaches the nested struct's
  own `validate` through `_arm_validation`, which asks its discriminant;
  `edges.versioned_arm` carries the top-level form already.

So the text number is the one of the four that is not a decline, and the
reason is exactly what makes it worth fixing: the construct is REACHED.
Its `_value` helper is emitted, its bounds are `#define`d, and its
docstring argues from a check that does not exist. **A decline the
generated file names costs a reader nothing; a promise it does not keep
costs them the thing they relied on.**
