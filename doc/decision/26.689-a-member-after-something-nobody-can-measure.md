# 26.689: A member after something nobody can measure

Status: recorded -- fixed in the lattice, in C's notes, in the Python
backend and in the gate that compares the four
Date: 2026-10-25
Source: `project.md` section 26

bbq-predictor's fifth item, reported 2026-10-25 and left open by 26.688:
`explain` calls a member after a non-seekable coded region `Dynamic` and
offers "move the variable-length member after this one", while the
generator emits "its offset cannot be resolved". Their reading was right
and it is the useful half -- nothing in the bytes says where such a region
ends, so no generator can place what follows it.

Closing it found five more faults, each one construct over, and the last
three were found by the first two rather than by looking -- the last of
them by putting the shape in the corpus, where it broke five consumers
that had never met a member no backend can place.

Six things in all, then, and a seventh that is not one of them: a walker
divergence this pass did not cause and that the corpus addition exposed
by re-dealing a seeded draw. It is listed below with the three like it,
and the counts in this record mean the six unless they say otherwise.

## The lattice said the member was reachable at parse time

`Dynamic` is "arithmetic over values already read" (`doc/capability-axes`),
and that is exactly what this member's offset is not: a bounded or
unbounded expansion publishes a worst case, so nothing before the member
says how many bytes the region took. The generic `dynamic-predecessor` row
said it anyway, with a blame line reading "`columns` has size Bounded(0,
65621), so the bytes before this field vary" -- which invites counting
bytes that cannot be counted -- and a remedy that treats the region as an
ordinary variable member.

`coded-predecessor` is the row now, suppressing the generic one for the
same reason `_is_bounded_size` excludes the constructs that own their
mutate effect: both would meet to the same values and the specific reason
is the product.

What carries the cost is the STAGE axis, which is the lattice's own
vocabulary for this and needed no new value:

    offset  Dynamic        wherever the decoder stopped
    stage   TransformTime  the region has to be decoded first

The precedent is `versioned-member`, which weakens the same axis because
whether its bytes are there at all is a value in the data. `Dynamic` stays
as the offset value because the position does exist once the decoder has
run and no weaker value says anything truer -- `DataPlaced` is one read and
an addition, `Scanned` is a search.

**The remedies are the three that were measured**, because a remedy nobody
ran is the fault this record is about. A `coded` region takes no length
clause -- the grammar admits `until` and nothing else -- so the shapes
that work are a delimiter (`until "\xC0"`, which generates a real
accessor through the region's own `_span` scan), a closed-form expansion
(`ratio_exact(2, 1)` generates one by arithmetic), and the region last
(`AbsoluteStatic(0x02)` for the member that was after it).

The predicate is one authority rather than two. `CLOSED_FORM_EXPANSION` is
in `layout.py` beside `_expand`, which classifies the forms, and
`traverse.region_extent` gates on it -- so the question "can this region be
measured" is answered in the same place for the extent and for the
diagnostic about everything after it.

## A delimited region was not telling anybody it ends in a search

Found while verifying the first remedy. `place_field` has recorded a scan
cause since 8.6.1 -- a delimited member means reaching anything past it is a
search that can fail, which is `Scanned` and not `Dynamic`, and
`Walk.scan`'s own comment says why the two are different claims.
`place_coded` was not recording it, so a member after a delimited REGION
reported `Dynamic` while the generated accessor called the region's `_span`
scan. The capability map said one thing and the code did another, which is
the one thing the map must never do.

One question, two constructs, one of them wired -- the twelfth instance of
that shape this year.

## C's note was true for one of the three shapes that reached it

`_unresolvable_offset` names the blocker and explains it, which is more
than the other three backends do: they write "its offset cannot be
resolved" and stop. Its last branch says

    codec `X` has no closed-form expansion

where `X` is `blocker.type_name`, and that is a codec only where the
blocker is a region. Measured across the corpus and then with a schema
written to reach it:

- a region -- `codec stuffed_apart has no closed-form expansion`, true;
- a varint inside a sealed region -- `codec edge_varint has no
  closed-form expansion`, where `edge_varint` is a varint type and the
  real reason is 26.440's: its length is in its own bytes and from
  outside the region those bytes are the codec's output;
- a variant no arm chain can measure -- `codec variant has no
  closed-form expansion`, taking the literal word for a codec name.
  Fourteen lines of schema reproduce it.

Two branches now, each naming what is actually there. The function's
counted-run branch already existed for this reason and its docstring
says so in as many words -- "a note naming one for a struct is a
diagnostic that is simply false" -- so this is that rule finishing its
own sweep.

**A false explanation is worse than no explanation**, which is why this is
worth a fix rather than a note: the bland sentence leaves the reader to
look, and the false one sends them to change a codec that is not there.

## The gate comparing the four backends could not see three of them

`test_the_backends_refuse_the_same_members` reads each backend's output and
reports any member one of them declines and another emits. Its `REFUSALS`
list held `"cannot resolve"` and the phrase C++, Rust and Python all write
is "its offset cannot be **resolved**" -- the two differing by a passive
voice, which no substring match bridges.

So the commonest decline in three of the four backends was invisible to the
gate that exists to compare declines. It surfaced the moment the corpus
gained a member after a region with no closed-form expansion: C was
reported as the lone refuser and the other three as emitting an accessor
that is nowhere in their output.

With the phrase added, the gate immediately found a real divergence it had
never been able to see.

## Python emitted an accessor that cannot run

`piece recs[kind]` in a variant arm. C, C++ and Rust all decline the member
after it, because an arm is emitted by a family of its own that reaches a
scalar, a byte run, a run of wide values and one fixed-size struct, never a
run of records -- Rust's comment says "the gap is one gap in four backends
rather than four answers to one schema", and Python was the fourth and was
never wired.

It answered instead, naming `body_recs_span` where the arm family defines
`body_recs_extent`. Five references, no definition: a getter, a setter and
`required` all raising `AttributeError` on first use. C would not have
compiled; Python runs until somebody reads the field.

The guard is `arm_of` and `is_counted_run`, and it is narrower than the one
C, C++ and Rust carry, which was measured rather than copied: those three
also exclude a delimited run and a `while` run in an arm, and this
backend's arm family does reach both. Copying their condition made Python
the lone refuser of `delimited_arm.after`, `separated_arm.after` and
`wide_delim_arm.after`, three members it gets right.

## And all four frame layers read a `required` nobody writes

The C frame layer is the only one a test compiles, and it refused:

    edges_frame.h:3014: implicit declaration of `situ_unwalkable_arm_required`

`frame.py` is guided by `traverse.frameable`, which said yes, while every
backend's emitter declines `required` for the struct and says so in the
same file. That is slip's fault exactly -- 26.260 recorded it as "the
reader was emitted and called `situ_frame_required`, which nothing
defines" -- with a different blocker, so the shared predicate had been
fixed for one cause and not for the class.

`frameable` returns False for a variant arm holding a counted run now.
The proof is the count rather than the predicate reading itself: 32
structs in the corpus were unframeable before and 33 after, the one
being the struct this pass added. A guard that refuses more than its
reason is how a backend stops emitting something it was right about.

C++, Rust and Python all name the struct in their frame layers too, so
this was a four-backend fault that one compiler caught. It is worth
saying plainly: **three of the four frame layers are emitted and never
compiled**, which is why the test that found this is the one worth
extending rather than the fix.

## Five consumers assumed every member has an accessor

Three structs went into `edges.situ` and `make check` reported ten
failures in five gates, none of them in the code above. Every one is a
consumer that had never met a member no backend can place, because the
corpus had never held one:

- **the differential's driver generator** named `_after_get`, `_after_set`
  and a region's `_ptr` and `_len`, so four drivers stopped compiling. It
  already guarded the narrower `since` case and said why -- "a driver
  naming one is a compile error rather than a comparison" -- and the
  general case was missing. `traverse.offset_unresolvable` is that
  question asked once, for the three layout-level blockers, and the driver
  generator and the propagation table both read it.
- **the map's own writability gate**: `mutate=InPlaceFixed` on a member no
  backend emits a setter for, which is the map claiming a property the
  code does not have. `coded-predecessor` weakens `mutate` to `Immutable`
  where a codec is the blocker -- a member nothing can locate is a member
  nothing can write.
- **the packer** cannot encode such a region's size program, correctly, and
  `test_pack` asserted that nothing in the tree is unencodable. The one
  exception is named in the test rather than filtered by its reason text,
  so a second shape arriving under the same sentence still fails.
- **the Rust subtraction floor** moved 132 to 133, in the arm accessor for
  `body.recs`, three lines under its own bounds guard. That gate's own
  comment says a floor on a total cannot tell "the emitter regressed" from
  "there is more to generate", and this is the fourth time it has been the
  second one.
- **the arm-shape census**, for the eleventh time.

**Where the lattice cannot say it, and that is the open question.** The
`mutate` fix reaches the codec blocker because the layout names it on the
placement -- `dynamic_cause_codec`, and `expansion_open` on the region
itself. It does not reach a variant with an arm no backend walks: the
arm's element layout is not reliably available when the variant is placed,
and a flag that silently fails to fire is worse than none, so the
propagation table has no signal for it. No corpus member reaches that case
now, so the gate stays strict and will fail -- correctly, and pointing
here -- for the next schema that has one. An exemption with no instance is
a hole nobody can see.

The real gap is that **no axis says "unreachable"**. `offset` says
`Dynamic` because the position does exist once the decoder has run;
`stage` says `TransformTime`; `mutate` says `Immutable` and `access`
says `Sequential` where a codec is the blocker. Nothing says "no accessor
exists at all", which is what all four backends emit a comment about.
Whether an axis should is a question for whoever owns the axes, and it is
not one to answer while fixing a diagnostic.

**`access` was the one this pass got wrong**, and bbq-predictor caught it
on 2026-10-26: it read `Random` while the generator wrote "its offset
cannot be resolved" and emitted nothing, so the axis that says how a
field is reached disagreed with the code about this member. `Sequential`
is the honest value and needed no new one -- reaching the field means
running the decoder from the start of the region, which is a walk and not
an addition, for the same reason `codec-needs-decode` weakens the axis
for the region's own interior. Two axes of six were right the first time,
which is the measure of how far the lattice is from being able to say
this in one.

## And then `validate` reported a malformed message as valid

The struct that kept paying out is the one that is no longer in the
corpus. `unwalkable_arm` -- a counted run of variable records in a variant
arm -- made the walker and C disagree, which is what the differential
exists for:

    unwalkable_arm, validate:  walker 1, C 0
    buffer: 01 e4 1d a0 ... (47 bytes)

`kind` is 1, so the arm holding the run is selected, the run's one `piece`
declares 0xe4 = 228 content bytes, and 46 bytes follow. The message is
malformed and the walker says so. C says `SITU_OK`.

Its `check` is three lines: the struct's minimum length, and `return
SITU_OK`. Every other counted run gets a `_fits` predicate and a call to
it; a run in an arm gets neither, because there is no walk to measure it
with, so the one check that would have caught this is the one shape it is
not emitted for.

**That is not a diagnostic, and it is not this pass's to settle.**
`validate` being sound is what every framing argument in this project
rests on -- 26.684 closed a framing fault on exactly that ground, that "a
caller who validates is safe and a caller who frames is not". Two answers
are available and they are different decisions:

- **`validate` is absent where it cannot check every member**, which is
  this project's own rule about operations it cannot support, and which
  costs every caller of such a struct the operation entirely;
- **an arm gets a walk**, which closes the gap the other four findings
  above all trace back to -- no backend walks a run in an arm -- and is a
  change in four emitters.

So `unwalkable_arm` came back out of `edges.situ` rather than being
carried with a known-unsound `validate` and nothing saying so. What covers
the fixes it found is named where each one is: the Python guard in
`test_codegen_python.py`, the frame layers and the predicate's variant
branch in `test_relations.py`, both with inline schemas. **The corpus is
the poorer for it** -- that shape is the one that found four faults in an
afternoon -- and putting it back is the first thing to do once the
question above has an answer.

## A seventh, exposed by the corpus moving rather than by any change

The gate at `0b803f1` failed one test, and not for anything this pass
wrote. `test_the_two_walkers_agree_about_which_check_refused` draws two
packets per struct from a fixed seed, in struct order -- so two new
structs ahead of `varint_driver` handed it two different packets, and
these are the first that reach a hostile length.

Measured on both sides, on
`a685a8d4978dcc3f48024c8e8b59f0c49c9860082203798427d5291bc7`:

    python   verdict 1, placement[156], fits_frame
    C        verdict 1, placement[156], no check identity

Both refuse and both say BOUNDS; only the name of the check differs. C's
placement guard is the wider one and refuses before any named check runs,
which `c_why` renders as "bounds" because the id is outside
`CHECK_NAMES`. That is the fourth instance of the shape `IDENTITY_APART`
holds -- after `png.chunk`, `pickle_wstring` and `oob_inner` -- and the
first with the length declared by a varint rather than a fixed-width
field.

**So `varint_driver` has very likely been divergent since it was written**,
and what found it was luck re-dealt. That is a finding about the detector
rather than about either walk: two packets per struct from a fixed seed
finds this class only when the deal happens to be hostile, and the deal
changes whenever somebody adds a struct. The reconciliation raised at the
third instance stands as the answer, and nothing here is a reason to
decide it differently -- which walk is right is a question about both of
them.

It is listed rather than fixed for that reason, with the measurement
beside it, which is what the three before it did.

## The corpus had none of these shapes, which is why nothing executed them

Measured across all 45 readable schemas in `test/schema`, `example` and
`std`: zero placements after a region with no closed-form expansion, and
zero after a delimited region. `externally_stuffed` is the corpus's only
delimited region and it is its struct's only member, so nothing had ever
asked what a region does to the member AFTER it.

`edges.situ` gains two of the three structs this pass wrote --
`stuffed_then_field` and `stuffed_opaque_tail`, the third being the one
the section above sends back out -- and `stuffed_apart` was already
there, an `extern` codec whose stuffing kernel gives
`ratio_bounded(2, 1)`. 26.688 declined a fixture for its own arithmetic
because the corpus's codecs are derived or exact; this needed no new codec
at all, which is worth knowing about the next shape somebody wants to add.

That is 26.675 for the third time: every dynamic check here is driven by
the corpus, so a shape no example contains is a shape nothing executes.
Three of the six findings above were found by adding the shape, and one of
them -- the gate's blind spot -- could only have been found that way.

## What this is worth beyond the fixes

**A diagnostic is code, and an unexercised diagnostic is unexercised
code.** Three of the six are explanations rather than
behaviour: a vector claiming parse-time reachability, a note naming a
codec that is not there, a gate blind to the phrase it was built to
compare. None of them would fail a test, none would crash a caller, and
each one sends a reader to change the wrong thing.

The cheap test for the class is the one bbq-predictor ran by accident:
read what the tool says about a shape nobody in the tree has, and ask
whether a reader acting on it would get anywhere.

## 26.688's own case, which this pass owed

`test_codecs.py` has the arithmetic case 26.688 recorded as the next
pass: `ratio_bounded(1001, 1000) + 20` over a 446411-byte interior,
asserted on all three surfaces -- the region's extent, the struct's and
the generated `SIZE_MAX` macro -- because each could disagree about which
way the division went while looking plausible alone. Reverting
`_whole_bytes` gives 3575020 bits where 446878 whole bytes are wanted,
which is the figure bbq-predictor reported, so the control is the
reporter's own number.

## Found on the way, and not fixed: 645 records have no readable date

Noticed while citing 26.260, whose header reads

    Date: @ -21417,0 +21418,56 @@ where they parted, twice, in the half-...

A diff hunk header spliced into the `Date:` field. It is not one record:
**645 of the files in `doc/decision/` match `^Date: @`**, all of them from
the bulk move of 2026-10-17, `1670624` ("doc: move 190 more cited entries
to their own records") and its siblings. A record in this directory opens
with `Status:` and `Date:` -- that is the shape every one of them claims to
have -- so it is broken in 645 places by a tool nobody checked the output
of. A mechanical change over many files has to carry a proof: state what
must not change, check it in the tool, and refuse to write when the check
fails. This one wrote 645 files and checked nothing.

The dates are recoverable and the method is known:

    git log -S"### 26.260 " --format=%ad --date=short --reverse -- project.md

gives 2026-09-05 for 26.260, and the commit it names is
`a25eb6b "fix: frame a delimited coded region, and compile rung 4 in the
suite"` -- which is this record's own subject, five weeks earlier.

Not done here, for two reasons. It is 645 files and belongs in its own
commit with its own proof -- every rewritten line matching
`^Date: \d{4}-\d{2}-\d{2}$`, nothing else in the file touched, and no date
later than the move that lost it. And per-record `git log -S` costs about
nine seconds each, so the cheap form is one reverse walk of
`git log -p -- project.md` collecting every added `### 26.N` heading rather
than 645 separate queries. The lookup path is `grep -l '^Date: @'
doc/decision/`.
