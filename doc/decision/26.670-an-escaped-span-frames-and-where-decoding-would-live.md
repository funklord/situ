# 26.670: An escaped span frames, and where decoding would live

Status: recorded
Date: 2026-10-21
Source: `project.md` section 26, from `suggestion/netcfgd.md`

`netcfgd` names one thing that stops it adopting situ, and it is not
academic there: **its hottest member carries whole configuration files.**
`config_put` and `probe_put` each send a `text` member holding the
literal contents of a file an operator wrote, and the example config in
that tree holds 374 double quotes across 172 lines. A reader whose
string scan ends at the first escaped quote fails on the first drop-in
anybody stores.

They quote situ's own comment as the evidence:

> Escapes are the reader's to interpret -- situ frames the span and does
> not decode it, and a `\"` inside the content ends this scan early.

**That sentence was already stale when it was quoted.** It was
`example/json`'s own bill, describing a gap in the SCHEMA rather than in
situ, and 26.299 closed it by putting `[escape = "\\"]` on `text.chars`
-- the extent of `{"a":"say \"hi\""}` went from 13 of 18 bytes to 18. So
the failure they describe does not happen. Their report is right about
everything except which side the gap was on, which is this queue's
recurring shape.

## The question they ask, and the answer

> the question I would ask of it is whether it frames or decodes

**It frames.** Over `"a\"b"` the span comes back as `a\"b`: four bytes
with the escape still in them.

**And nothing pinned that.** The existing coverage asserts the scan's
length, its terminated flag and `validate` -- every one of which a
DECODING reader would satisfy while handing back different bytes. The
property a consumer builds on was inferable from the emitter and
asserted nowhere, which is `evidence.md`'s "assert the relationship, not
either value" pointed at a span.
`test_an_escaped_span_is_framed_and_not_decoded` asserts the bytes now,
over an escaped delimiter, a doubled escape and `say \"hi\"`; sabotaging
it to expect the decoded form fails it.

## Where decoding would live, which is not "the reader does it"

A transform over a span is a codec, and a `coded` region already
generates one:

    situ_err_t situ_S_body_decode(situ_view_t view, uint8_t *out,
                                  uint32_t cap, uint32_t *len);

into a caller's buffer, with a capacity check that reports rather than
truncating, and no allocation -- which is section 20's rule satisfied
rather than bent. **Escape-stuffing is one of the seven kernel families**
(13.4), and a JSON string's single-character escapes are exactly that
shape. What is missing for them is a CODE rather than a mechanism, which
is the gap `linear_block` had until a schema could state its matrix
outright (0064).

**The numeric escape is a different thing, and it is the part their CVE
point is really about.** Six bytes in, one to three UTF-8 bytes out, with
surrogate pairs to join: not stuffing in any form, and `stuffing`'s own
derivation would mis-report it. That is a kernel of its own or a tier-1
`extern`, and tier-1 is where situ puts a decoder whose work needs a
buffer.

So the division on today's situ is: situ frames; situ can decode the
stuffed half through a codec once one is named; the numeric half stays
the consumer's or becomes a kernel.

## The holder's question

**Should situ ship a JSON-string codec?** It would be a `stuffing` code
for the single-character escapes plus either a kernel or a documented
tier-1 binding for the numeric ones, and it would move the part with the
CVEs in it from every consumer's hand-written reader into one generated
one. Against it: 13.4's survey is an argument for keeping the family
count small, and a code that decodes only half of JSON's escapes is a
code whose name promises more than it does -- which is the
classification fault 26.139 recorded for 8b10b.

Not raised as a gap, because what `netcfgd` needs to know is answered:
framing works, it is asserted, and the boundary is where their own
reader already sits.
