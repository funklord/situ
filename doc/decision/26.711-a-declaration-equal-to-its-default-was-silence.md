# 26.711: a declaration equal to its default was silence

Status: recorded -- fixed; 26.493's four axes were one cause
Date: 2026-10-28
Source: `project.md` section 26

26.493 recorded four codec axes that could be declared and silently
dropped. **They are one cause**, and it is in the one line that decides
what the author wrote.

## The cause

`_explicit` recovered the written set by comparing against a bare
signature, and its own docstring defended that:

> Recovered by comparing against a bare signature: the parser does not
> record which properties were written, and a property equal to its own
> default was not worth arguing about anyway.

That last clause is true only when the DERIVED value also equals that
default. Where the two defaults differ, **a declaration equal to the
decl's default cannot be told from silence**:

    deterministic    CodecDecl False    Derived True

So `not deterministic` sets False, equals the decl default, is invisible,
and is dropped. `seekable = none` and `granularity = stream` are the same
shape against a kernel deriving LINEAR and bit(1), and
`length_preserving` is the costly one -- a claim about offsets, replaced
by a CRC kernel's +32 bits. All four at rc=0, against seven live controls
on the same axes.

**The declaration was never lost**, which is what makes this the check's
fault and not the parser's: `not seekable; seekable = linear;` has always
been refused as *"seekable is given twice"*, so the words were already
recorded for that.

## The fix records property NAMES, not the author's words

`CodecDecl` carries a `written` frozenset and `_explicit` returns it,
intersected with `DERIVED_PROPERTIES`. The parser accumulates it as each
branch assigns, and **names rather than words is the load-bearing
choice**: one word can set more than one property, and the forms differ.

    expansion = +5 bits         expansion, expansion_add
    expansion = ratio_exact(8, 9)   expansion, ratio
    granularity = block(16)     granularity, granularity_size

A map from the word `expansion` to all three would make the `+N` form a
declaration that `ratio` is None, so a kernel deriving a ratio would
disagree with a claim the author never made -- **a refusal invented by the
bookkeeping**. A test asserts the three sets above for that reason.

## Provenance does not outlive the question it answers

`written` is cleared once signatures resolve, which makes
`resolve_signatures`' own sentence -- *the lattice reads nine properties
and never asks where they came from* -- an enforced fact rather than a
convention. A test asserts it over every corpus schema.

**That is not tidiness; it is what keeps the round-trip comparator
whole.** `test_examples._without_spans` walks EVERY dataclass field on
purpose, and its docstring says what the alternative cost: *ten AST
fields were dropped on the round trip across fifteen schemas and the
comparison saw none of them*. Excluding provenance from it would weaken
the property those ten paid for. With the set cleared there is nothing to
exclude -- `unparse` emits the derived values, a reparse records them as
written, and the resolution clears both sides.

**The clear was in the wrong function first, and the corpus said so.**
Putting it in `apply_to` fixed eleven of the thirteen round-trip failures
and left two: `apply_to` sees only the kernel-bearing codecs, and
`std/codecs.situ`'s AEADs have no kernel, so they kept what they were
parsed with. It belongs in `resolve_signatures`, which sees every codec,
and that is one site rather than two.

A fixture would not have found this. The two survivors were kernel-LESS
codecs in the one corpus file whose codecs are all unbound signatures,
which is the opposite of the case the fix was written for.

## Why this could not be measured before fixing it

Twice I tried to measure what corpus codecs write and both instruments
were wrong, which is worth recording because the first error is the same
one the defect is:

- **Comparing a parsed decl's properties against the defaults answers
  nothing.** `_check_derived` REPLACES those fields with the derived
  values, so a parsed `CodecDecl` never shows the author's text. That is
  also why the parser is the only place that can answer.
- **A regex for the codec body overran it.** Every codec body in this
  corpus is a one-liner, so `codec X \{(.*?)\n\}` ran past it into the
  following struct and reported two `authenticated` hits that were
  `authenticated` REGIONS in a struct.

Brace-counted bodies with comments stripped give the answer: **none of the
56 kernel-bearing codec bodies writes any derived property at all.** So
the fix refuses nothing in the corpus -- 46 of 46 schemas still map and
every map is byte-identical -- and the corpus cannot cover it either,
which makes the tests the only coverage and is why they carry the four
diagnostics rather than deriving them.

## Proofs

All four axes refuse now, each with its own diagnostic, and the control is
the same axes declared at a value the kernel AGREES with -- `deterministic`
and `seekable = linear` over the table kernel -- which stay accepted,
because saying a thing twice is redundant rather than wrong. Against `git
archive HEAD` five of the six new cases fail and the one that passes is
that control.

The expected fragment is carried in the table rather than built from the
property name: `_render` spells a false bool `not deterministic` and an
enum `seekable = none`, so the four are four shapes, and an assertion
built from the name alone passes for the wrong reason or fails for a
reason that is not the code's. Mine did the second, once.
