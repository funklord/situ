Source: fuzznet (inbox 20261120T1231Z, item 6): "a relayed exchange
(inner and outer ids, resent together)". The last of its six network
items not built or declined: (1)-(3) are 26.1123, 26.1122 and 26.1120,

## What fuzznet does by hand

`relay_carry` in fuzznet's `node/daemon.c` (its secs 622, 754, 756)
seals the request for the target under the target's session as `msg`,
wraps it in a relay head, and sends that to the relay under the relay's
session as `outer_msg`. Two replies can then end the one exchange:

- the target's answer, routed back by the relay, under the target's
  session and `msg`;
- the relay's own refusal, under the relay's session and `outer_msg`.
  The relay's `ok` under the same message is waited past.

A resend re-seals the inner request as the same `msg` and the outer as
the same `outer_msg`. Today fuzznet holds the second key itself
(`via_set`, `via_key`, `via_msg` beside its caller), which is the part
the drive machine cannot say.

## The shape proposed

One exchange id held under more than one (peer, key), every one ending
with it:

    <drive>_track_also_from(drive, peer, <the key's values>, id)
    <drive>_track_also_key_from(drive, peer, key, id)

adds another way the exchange `id`, already live, may be answered. It is
refused (CONSTRAINT) where no exchange `id` is live, so it cannot start
one, and answers BOUNDS where the table is full, as `_track_from` does.
It holds no bytes and starts no timer: the exchange keeps its one
deadline and retry count, and a resend still reaches the caller once, by
`id`, so fuzznet re-seals both layers as it does now.

Whichever key a reply matches through `_on_message_from` ends the
exchange, and with it every key held for that id; expiry and `_end` do
the same. A reply under the other key afterwards is unmatched, as a
duplicate is. The relay's `ok` is the caller's to wait past: `_peek_from`
says which exchange it names without ending it (26.1122), and only a
refusal goes to `_on_message_from`.

The one change to what exists: the conversation table's `forget` stops
at the first slot holding the id. It would end every slot holding it,
which is the same for every table that has never held two.

Python, Rust and C++ the same, under their spellings of `_track_key_from`.

## Rejected

- **A relation naming both layers** -- `relation relayed(...)` with an
  inner and an outer key. The outer reply is a different session's
  message of the same kind, so it is one relation read under two peers;
  a relation of two keys would state in the schema what is a routing
  choice made per send.
- **Tracking the same id twice with `_track_key_from`.** Each call is a
  first send to the drive machine: two deadlines and two retry counts for
  one exchange, and the first to expire would end it under the other.

## Put for review (answered below)

- Whether the relay's refusal is read as a reply of the same relation as
  the target's answer -- a sealed reply naming the message it answers --
  so one key layout serves both. If it is a different message, the
  second key needs that relation's layout and the call takes it.
- Whether the relay's `ok` should push the exchange's deadline (fuzznet
  waits "past" it -- under the deadline it already had, or a new one).
- Whether more than two keys per exchange are ever wanted (a relay of a
  relay). Nothing in the shape limits it; the table's capacity does.

## fuzznet's answers (inbox 20261121T1300Z)

Read from its node/caller.c receive path, relay_carry and node/relay.c:

1. **One relation.** The relay's answer is the same sealed frame, opened
   under the relay's session key, one piece, its `head.msg` the relay's
   outer number where the target's carries the target's. So the key
   layout is the relation's own, and only the value and the peer differ.
2. **The wait stays under its deadline.** Nothing in fuzznet moves it when
   the relay answers. Today fuzznet takes the relay's one-piece answer,
   whatever it says, as the answer and disarms the relayed way; peeking a
   forwarding relay's `ok` and waiting past it is behaviour it would gain.
3. **Never more than two keys.** node/relay.c refuses a second hop. The
   shape is left unlimited, which costs nothing.

## Built (2026-11-21)

- C: `<drive>_track_also_from(drive, request, peer, id)` and
  `<drive>_track_also_key_from(drive, key, peer, id)`. **The key comes
  before the peer**, as in `_track_key_from`, rather than the
  `(drive, peer, key, id)` written above: one order for every call taking
  both. `forget` ends every slot holding the id; `_on_message_from` calls
  it after a match, and expiry and `_end` already did. Each key is a slot
  of `drive->pending`, which `_init` sizes one per exchange, so a caller
  holding relayed exchanges re-initialises it with a larger array
  (`<table>_init(&drive->pending, keys, key_cap)`) straight after `_init`.
- Python: `track_also(request, id, *, peer)` and `track_also_key(raw, id,
  *, peer)`, the other keys held apart from the live exchanges so `step`
  resends once; `on_message`, `peek`, `end` and expiry read and clear them.
- Rust and C++: `track_also_from` and `track_also_key_from`, the second
  key a slot marked `also` that carries no timer; `step` skips it and
  clears one whose exchange gave up, and `part_held` ignores it.

Held by `test/unit/test_a_relayed_exchange_is_awaited_under_two_keys.py`
in all four: the relay's answer ends the exchange and the target's late
one is unmatched, and the other way round; the second key holds its own
peer; expiry after the one resend and `end` take both keys; `also`
never starts an exchange. Each backend fails it when a match ends only
the matched key.
