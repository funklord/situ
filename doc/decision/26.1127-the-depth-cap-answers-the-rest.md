# 26.1127: at the depth cap an extent answers the rest of its view

Status: recorded; built in all four backends 2026-11-21
Date: 2026-11-21
Source: libFuzzer on `example/cbor`'s C harness, the run after 87bba626
stopped the nesting probe at its first too-deep answer.

## What was found

An odd run of `0xbf` -- open maps, each the key of the one around it --
ending in a byte string whose length runs past the buffer:

    bf bf ... bf 5b bf bf bf bf bf bf bf bf

Every reader refused it, and every reader took time growing with each
byte to do so:

    item validate, 1610 bytes     before      after
    C, -O1                        6.9 s       0.00 s
    C++, -O1                      5.3 s       0.00 s
    Rust, -O                      0.96 s      0.00 s
    Python, 70 bytes              20 s        0.07 s

and `open_array`'s count and indexed accessor over 3.2 KB of the same
shape, 86 s in C. Under the fuzzer's sanitizers 115 bytes took 7 s.

## Why

A struct's extent past `[depth]` answered 0 -- "`[depth]`/`[limit]`, not
the frame". A pair is a key and a value; when the key is a map measured at
the cap, its 0 put the value at the key's own offset, and the value was
measured again from there. Two descents a level, and the cap of 65 struct
levels is sixteen CBOR levels, so one extent near the cap cost on the order
of 2^16 -- and the nesting probe, the count and each `_at` measure their
elements from depth zero, so every one of them paid it again: linear in the
message with a constant of about 4 ms a byte.

The probe's early return (87bba626) could not reach it: the probe stops at
a too-deep answer, but each answer it waits for is an extent.

## The rule

**At the depth cap an extent is the rest of its view.** Nothing behind a
struct that cannot be measured is read from inside it: the members after it
sit at the frame's end and measure in constant time, and a run holding it
ends with it.

**Two things moved with it, and the gate found both.** A message one turn
too deep now refuses as too deep (CONSTRAINT) in all four where it read
BOUNDS: the run's fit walk had taken the cap's 0 for an element the frame
does not hold -- the wrong error 26.676 already names for a depth-capped
message. And the extent one turn past the bound is the message's whole
length rather than the bytes above the cap (`test_recursion.py`'s table:
27 -> 30, 19 -> 23, 9 -> 11). A third was a fault it exposed: the nesting
probe in C and C++ read a struct's fixed prefix unguarded, unreachable
while the parent stopped short and reached once it did not, so the probe
now returns its depth on a view shorter than the struct's fixed bytes, as
the extent's own guard does (`test_a_walk_reads_nothing_past_its_view`,
under ASan).

One line per backend, in both of its extent shapes (`_extent_at` and the
cursor form): `view.limit` in C, `raw_.limit` in C++, `self.bytes.len()` in
Rust, `self._len` in Python. The walkers needed nothing: both already let
the ceiling travel as a refusal of the walk rather than a short answer.

## Rejected

- **A run whose element overruns spans to the frame's end.** 26.342's
  break -- "one running past the limit was never in this frame" -- ends a
  run short when an element claims more than is left, and the parent then
  reads its next member from inside that element: the same overlap. Changed
  in the generated C alone, it made both shapes above instant too. But it
  is every run kind's walk in six readers (some forty sites) against one
  line in four, it changes the span a valid-looking run reports where the
  cap leaves all of those alone, and with the cap answering the rest a run
  that overruns below the cap re-descends at most to the cap, where it
  stops. Four minutes of libFuzzer at a one-second limit on the cap-only C
  reader found nothing; if a shape below the cap turns up, this is the
  change to make.
- **Memoising extents.** The overlap is a pure function of (struct,
  offset, depth), so a cache would remove it without changing an answer.
  Generated C holds no state between calls, and a reader that allocates to
  measure is the wrong trade for one hostile shape.
- **A lower cap.** Each level of the cap is a factor in the cost, but the
  cap is the format's `[depth]`, not a tuning knob.

Held by `test/unit/test_a_cbor_map_is_judged_inside_its_bytes_and_in_time.py`:
C (item and the open-array walk), C++ and Python each fail it on the old
code by timeout; Rust's case holds it rather than telling the two apart.
