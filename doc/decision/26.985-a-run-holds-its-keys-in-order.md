# 26.985: a run holds its keys in order

Status: recorded
Date: 2026-11-13
Source: hull's `store/pack.situ`, whose header lists "that the index's
digests ascend, each once" among what the schema cannot say, so
`store/pack.c` checks it by hand

`index_entry index[count] [ascending = digest]` states it, and `u32
offsets[n] [ascending]` states it of a run of integers. Each key must be
above the one before. That is strict on purpose: it is what `ordering =
ascending` holds a `tlv` region's identities to under `duplicate_tags =
error`, its default (26.740, 26.741), so the language has one meaning for
"ascending", and it is hull's "each once". A non-strict order has no
consumer yet and would be a second spelling, `[ascending]` beside an
attribute allowing repeats, when one asks.

A byte key compares byte by byte, first byte first -- a digest or a name
sorts that way -- and an integer key as the number its bytes say, in the
byte order it is written in: `-1` before `1` in a little-endian `i16`,
where the bytes alone would say otherwise.

**The shape is a counted run of elements of one size**, with the key a
whole-byte member at one place in each: one stride, so each key is a
constant distance after the last, which is the shape a sorted index takes
and what all four backends compare without walking. A run to the frame's
end, a `while` or delimited run, a run of variable elements, a key that is
not an integer of 1, 2, 4 or 8 bytes in a stated order, or not a run of
bytes, is refused at `resolve` with the reason. Widening it is the same
comparison with the walk each backend already has; nothing has asked.

`validate` checks it after the run's own checks, so every key read is one
the frame holds, and names the run in `which`. `traverse.run_ordering`
answers for all four what the stride and key are, so they cannot disagree
about which bytes are compared. C and C++ compare a byte key in a loop, the
runtime header carrying no `string.h`; Rust compares slices through `get`,
so it cannot panic; Python compares `bytes`.

The walkers' image carries no ordering program, so the packer marks such
a struct as one they cannot validate, and both say `cannot-say` rather
than pass a run out of order -- as for a `tlv` region's ordering. The
signature publishes it (`ascending=digest`), and `situc wire --check`
reports gaining it as a receiver that may refuse what an old sender
produced. The dissector shows the run and says nothing about its order.

`test_a_run_holds_its_keys_in_order` asks the four over twelve messages --
a byte key decided by its last byte and by its first, a key twice, a
big-endian `u16` across a byte boundary, a little-endian `i16` across zero,
a run of bytes -- has both walkers abstain, refuses five shapes, and builds
the Rust under `-D warnings`. All of it fails with the change reverted.
