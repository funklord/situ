# 26.847: a fuzz harness that needs no fuzzer

Status: recorded -- `gen-fuzz --target python`, driven over 42 schemas and
RUN by this repository's own gate rather than skipped
Date: 2026-11-03
Source: 26.846, which dissolved the reason this was parked

## The shape, and why it is better than what was parked

26.846 established that nothing forbade generating an `atheris` harness:
decision 0001 constrains what `situc` imports, not what a generated file
expects of the consumer, and `--target c` already emits a libFuzzer entry
point `situc` does not depend on.

**But the dependency turned out not to be wanted at all.** `--target c`
keeps `LLVMFuzzerTestOneInput` separate from a `SITU_FUZZ_STANDALONE`
`main` that reads stdin, and says why: "so the harness can be built and
run without a fuzzing engine. This is what keeps it from rotting between
runs."

The same split in Python gives `one_input(data)` plus a stdin `__main__`,
and that buys something the parked design could not have: **this
repository's own gate RUNS the harness** instead of skipping where a
fuzzer is absent. An engine is two lines on top:

    import atheris, <name>_fuzz
    atheris.Setup(sys.argv, <name>_fuzz.one_input); atheris.Fuzz()

The first byte selects a struct, so one corpus drives every parser in the
schema rather than needing a harness each -- again the C target's
arrangement.

## What it exercises, and how that is known

Acquire, `validate` on arbitrary bytes -- the first thing a parser runs
and the last thing an attacker controls -- then read every field, so a
getter that indexes outside its own claim is reached rather than merely
compiled.

Driven over the corpus: **42 schemas, 16800 random inputs, no crash.**

A fuzz run that finds nothing is exactly the result that needs a second
measurement, because a harness that crashes on nothing and a harness that
does nothing are indistinguishable from outside. `sink` is where every
read goes, so patching it counts them: **814 field reads over 200 inputs**
on `test/schema/header`, about four per input, one of its two structs
being selected each time. The gate counts them on every schema and
refuses a run that read nothing.

## The driver was the vacuous one

Written with `rng.randrange(0, 80)` first, and `example/cpio` read
**nothing**: its struct needs 110 bytes, so every input fell short of the
harness's own length guard and it returned before touching an accessor.

A fuzz driver whose inputs cannot reach the minimum is a driver that tests
the length check and nothing else -- and it reported success, because the
harness did not crash. The gate sizes its inputs from the harness's own
guards now (`if len(data) < N`), to twice the widest plus slack.

**That is the third instrument fault of the day**, after a vacuous-pass
guard that matched by substring (26.845) and a check whose two guards
backed each other up (26.843). The pattern is worth more than any of
them: **when a measurement comes back clean, the thing to suspect first is
the measurement** -- and the cheap way to suspect it is to ask what it
would have had to see.

## Where zero reads is the true answer

`example/protobuf` is a bare `tlv` region and `example/slip` is framing,
so neither has a plain scalar field and the harness carries `pass` where
the reads would be. The gate asks for a read only where the harness has
one to perform; demanding otherwise would be demanding a getter the schema
does not describe.

## What remains

`--target rust`, which has the same shape available -- `pub fn
one_input(&[u8])` and a stdin `main`, with `cargo-fuzz`'s `fuzz_target!`
three lines on top. That would bring both halves of section 1's "test
scaffolding" to all four languages.
