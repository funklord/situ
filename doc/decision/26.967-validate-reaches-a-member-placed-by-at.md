# 26.967: validate reaches a member placed by `at`

Status: recorded
Date: 2026-11-12
Source: describing a whole TIFF, whose first directory sits at `ifd_offset`

**Every backend's `validate` got a member placed by `at` wrong, each a
different way, and both walkers got it right.**

    struct d { u16 a; u16 b [max = 9]; }
    struct t { u32 off; u16 w at off [max = 9]; d first at off; }

C and C++ did not compile: `check` called the located accessors with the
view alone, and they take the message first. Rust compiled and compared
`self.bytes` at a fixed offset in its own frame, which is not where the
member is. Python raised: `self.w > 9` compared a `memoryview` with an
integer, and `self.first.validate()` called a method bytes do not have.
A located struct the data sizes was worse -- its length named a
`<member>_extent` helper no backend emits for a located member, so C,
C++, Rust and Python all failed to build. Nothing in the corpus had a
constraint on a located member or a located struct, which is why none of
it had run; the walkers, reading the whole message, checked both.

The walkers are the reference: a located member is read where the
message places it, a constraint it breaks is CONSTRAINT, and a member the
message does not reach is BOUNDS -- a located struct validated through
its own validator. Each backend reaches the message the way it already
can:

- **C** through the view's `owner` (26.306), and the located view now
  sets `owner` on what it hands back, so a struct placed by `at` can
  reach a member of its own placed the same way.
- **C++** through its raw view's `owner`; the located struct, handed back
  as bytes, is taken as a view over them with the same owner.
- **Python** through `_msg`, reading `<name>_value` and taking the struct
  over the bytes its accessor returns.
- **Rust**, whose views hold only their bytes, through a message
  argument, as its located accessors already take one: a struct whose
  checks reach a located member gets `validate_in(msg)` and
  `check_which_in(msg, which)`, and `validate()` is `validate_in` over the
  view's own bytes -- the message, for a view acquired over the whole of
  one. Delegation passes `msg` down. That follows C's choice in 26.306
  for the parameter Rust already used, rather than growing every Rust
  view by a second slice.

A located struct the data sizes is measured where the message puts it,
by its own extent (C) or `required` (the other three) over the message
from `at` on.

**The C walker skipped a located struct it could not measure**, under a
clamp meant for a byte run too wide to count in bits (bmp's
`image_size`). A struct starting at the message's end measured as a
failure and was skipped, so the message validated; `walk.py` refused it.
A located struct the message does not hold is BOUNDS now; a byte run
keeps the clamp.

Only a value the backends can read is checked: a constrained located
scalar with a `<name>_value` getter (26.959's plain integers). An enum or
bit field placed by `at` with a constraint is still checked by the
walkers alone.

## Verified

`test_a_located_member_is_validated.py`: a fixed and a sized located
struct, a constrained located scalar, verdicts worked out by hand, in all
four backends and both walkers.
