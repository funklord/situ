# 26.660: The literal-only builder, and a writer that could ship what its reader refuses

Status: recorded
Date: 2026-10-19
Source: written as a record

The last item on 26.636's list: *"whether a struct with nothing for a
caller to supply gets a builder. json's `true`, `false` and `null` are
refused as entirely literal, which is accurate and was deliberate; an
adopter composing a document then hand-writes those bytes, and situ
emits no constant for them to use."*

**It gets no builder, and the refusal's own reasoning is right** --
`_encode` of a constant is not a builder. The route is the owned form,
and the recorded gap was half false and half worse than stated.

## The population, and the stronger example

Four entirely-literal structs in the corpus, in two schemas:

	json.situ   yes, no, nothing     `u8 word[n] [must_eq = "..."]`
	png.situ    png_signature        `preamble u8[8] = "\x89PNG\r\n\x1a\n"`

PNG's is the better case: an adopter writing a PNG hand-writes the
eight-byte magic, where a typo is easy and the schema already states
the bytes.

## Half false: a preamble is already written

`situ_png_signature_encode` writes them itself, and says so:

	(void)in;		/* every member is a preamble */
	{
		static const uint8_t want[] = { 0x89u, 0x50u, ... };

		memcpy(data + 0u, want, sizeof want);
	}

So the adopter calls `_encode` and gets the magic, bounds-checked. No
constant is needed and no builder is missing.

## Half worse: a `must_eq` field was not written, and not checked

The pinned-literal write above sits INSIDE `if placement.kind ==
"reserved"`. A preamble is reserved so it reaches it; `u8 word[4]
[must_eq = "true"]` is a FIELD, so it fell through to the generic copy
-- although `pinned_runs` deliberately answers for both spellings.

Measured by compiling, not by reading:

	encode  SITU_OK
	wrote   flse
	decode  SITU_ERR_CONSTRAINT

**The owned writer could emit a message its own reader refuses**, which
is exactly what `build.py` says the builder avoids by refusing instead:
*"it cannot ship a wrong message, only no builder at all."* The scalar
spelling had it too: `u16 magic [must_eq = 4660]` copied `in->magic`.

Fixed by asking the decision layer rather than the member's kind.
`traverse.stated_scalar` is `pinned_runs`' sibling for a scalar, and is
deliberately narrower than `checks._required_pattern`: that answers what
a BASELINE may hold, folding in `min` and an enum's smallest member,
neither of which the schema states. A writer that wrote the smallest
satisfying value would be choosing rather than recording.

	must_eq run       writes the literal
	must_eq scalar    writes the stated value
	preamble          writes the literal
	an ordinary u16   copies from `in`

## And the round trip was passing on two errors that cancelled

The fix broke `test_decode_then_encode_returns_the_same_bytes[tiff]`,
and the regression was not in the fix.

`tiff_header [endian = from(byte_order)]` has `u16 magic [must_eq =
42]`. **The owned emitter bakes ONE byte order**: it decodes `magic`
with a static `situ_get_be16` and encodes with `situ_put_be16`. So a
little-endian TIFF hands back 10752, and validates anyway, because
`_decode` delegates its constraints to `_validate` -- which is the
VIEW's and reads the marker properly.

The round trip could not see that, because the same wrong order ran both
ways and the two errors agreed. Writing the correct 42 broke the
symmetry, so the suite reported a correct write as the regression.

**So the scalar branch leaves a marker-governed field alone**, which
restores the cancelling pair rather than pretending it is right. That is
the honest split: the fix stands where it is sound, and the byte-order
defect is its own finding, needing the owned form to resolve order at
runtime as the view form already does.

## What this item cost in wrong measurements

Five, before one was right, each reporting confidently:

- `parts_of` does not exist, and a `hasattr` fallback reported every
  struct as unbuildable;
- `refusals(resolved)` with no `Shape` reported `yes` as *"neither a
  scalar nor a struct of this schema"* -- a plausible sentence about a
  struct that is plainly both, because the lookup table was empty;
- two probe builds failed on mismatched generated basenames;
- and the round trip above, green for a cancelling pair.

Only the fifth -- `refusals` with a real `Shape` -- showed that `value`
HAS a builder and that `as_true` is not refused, which is what made the
arm builder's `(bytes, len)` signature the thing to look at and the
whole question tractable.
