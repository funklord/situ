# 26.685: The framing total was used as the element offset

Status: recorded -- fixed in all four backends
Date: 2026-10-23
Source: `project.md` section 26

Found while sizing 26.684's fix, by reading what `_framing_walk` passes as
an offset. **Fixed in all four backends**, with 26.686 and the prefix
sweep that found both; 26.684 remains open.

**This is the more serious of the two**, because the shape is ordinary: a
counted run followed by any fixed member -- a trailer, a checksum, a
terminator -- which is most length-prefixed formats.

## The fault

`_required`'s own docstring is exact about what `at` is:

> `at` starts at the sum of *every* fixed member, including the ones after
> the variable member being measured, and grows by each variable length as
> it is resolved.

So `at` is a running TOTAL. It is also passed as the element's OFFSET:

	e = situ_one_required(data + at, situ_remaining_u32(have, at), &part);

The two coincide only when no fixed member follows the run. Put one after
it and every element is read from the wrong place.

Measured 2026-10-23, C, on

	struct one { uvar v; }
	struct withtail { u8 n; one d[n]; u16 t; }

`at` starts at 3 -- one byte of `n` plus two of `t` -- while `d` starts at
byte 1. With `02 81 01 05 00 00`, a whole message of six bytes:

	have=1  err=7 need=3   (truth 6)
	have=2  err=7 need=3   (truth 6)
	have=3  err=7 need=5   (truth 6)
	have=4  err=7 need=5   (truth 6)
	have=5  err=0 need=5   (truth 6)
	have=6  err=0 need=5   (truth 6)

**It answers complete at five bytes of six.** A stream reader consumes
five, parses them as a whole message, and resynchronises one byte into the
next one -- on every message, which is 26.265's failure exactly, reached
by a different route.

Reproduced identically in a worktree pinned at `b186326`, so it predates
the varint-run work rather than following from it.

## All four backends have it, so nothing could see it

	cpp:    std::uint32_t at = 3u;   ... One::required(data + at, ...)
	rust:   let mut at = 3;          ... One::required(&data[at..])
	python: at = 3                   ... one.required(data[at:])

The four-way differential compares the backends against each other and
they agree, and the six-reader comparison has four witnesses here -- the
four that share the arithmetic. The same shape as 26.683: agreement is not
corroboration when one hand wrote all of it.

**This record first said neither walker frames, and that is wrong.**
`walker/session.py`'s `Reader` frames, which its own docstring says in as
many words -- "framing needs no framing section: `struct_extent` already
measures one instance from its own bytes" -- and it is built on the
quantity 26.684 is about. Measured 2026-10-23 over every prefix, and it is
the worst-behaved framer in the tree: for `col { uvar count; one
d[count]; }` it hands out a whole message at ONE byte of five, and again
at two, three and four, each time reporting a different length. `lastrun`
the same at one and two bytes.

The mechanism is 26.684's exactly: `struct_extent` shrinks when the bytes
run out, and `Reader.next` admits a message when `need <= len(buffer)`, so
a shrunken need passes the test that was meant to refuse it.
`withtail` escapes only because a fixed member after the run adds two
bytes the collapse cannot remove -- luck, not a guard.

So 26.684's fix has a walker half, and the walker's is the more urgent of
the two: a compiled `framed` over-reports a frame a caller then validates,
while `Reader.next` hands back a View that nothing re-checks.

## The fix

**Separate the offset from the total**, which is the whole of it. The walk
has a cursor of its own now, initialised to the expression the accessors
already use to place the member and advanced by each element's `part`;
`at` grows by the same `part`, so the conservatism the docstring describes
is unchanged. Both the element's `required` call and the delimiter scan
read from the cursor.

Measured after, over every prefix of a six-byte `withtail`: 3, 3, 6, 6, 6,
complete at 6 -- exact from the point the message determines it, where it
had answered complete at 5. `col`, whose run has nothing after it, is
unchanged at 4, 5, 5, 5, complete at 5, which is the control that shows
the cursor and the total still coincide where they should.

The pad branch three screens above already knows this. Its comment says
"`at` is a running TOTAL, not a running offset: the constant it starts
from is every fixed member, including the ones AFTER this pad", and it
takes `_base_expression` for exactly that reason -- a `pad_to(4)` behind a
2-byte length and in front of a 2-byte trailer otherwise answers 4 where
the truth is 6. **The knowledge was in the file, one branch away from the
code that needed it.**

## What the two open framing faults have in common

26.684 adds a quantity that shrinks as bytes go missing; this one reads
content at a quantity that is not an offset. Both make `required` answer
"complete" for an incomplete message, and neither is visible to a
differential, a fuzzer over whole messages, or a test that asks a framing
function about a complete buffer.

**The probe that finds this class is to ask about every PREFIX**, and it
found both within an hour of being written down. It is three lines:

	for (n = 1u; n <= sizeof b; n++) {
		uint32_t need = 0u;
		situ_err_t e = X_required(b, n, &need);
		printf("have=%u err=%d need=%u\n", n, (int)e, need);
	}

**One test did, and this record first claimed none did.** `test_codegen_
rust.py::test_every_prefix_of_a_real_request_answers_honestly` has swept
every prefix of a real HTTP request since 26.32, asserting the same three
properties -- never complete early, the bound above what is in hand, and
never above the whole message. The claim here was written from a grep for
the loop's shape and not from asking what each framing test does, which is
`evidence.md`'s manufactured absence: the pattern was mine and the test
spells it `for i in 0..whole`.

What was true is narrower and still the gap: **it existed for one backend
and one schema.** Rust and `example/http`, which has no counted run of
records with a fixed member after it and no varint at all -- so the shape
that carries three of these four faults was outside it, and the suite that
would have caught them never ran them. `test_required_answers_every_
prefix.py` is the general form, over four shapes and pinned per prefix.

The lesson survives the correction, so it is worth keeping: a framing
function has one answer per prefix length, and a test that asks it about a
complete message asks the one input that cannot fail.
