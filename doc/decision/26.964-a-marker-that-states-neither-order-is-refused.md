# 26.964: a marker that states neither order is refused

Status: recorded
Date: 2026-11-12
Source: describing a pcap file (26.961), whose nanosecond variant read

**Every reader asked a marker one question -- is it the `little`
literal? -- and read big-endian otherwise.** The backends' `is_little`,
both walkers' `marker_order`, and now the dissector's `_little` all
compare against `little` alone, and `validate` checked nothing about the
marker itself: `classify_check` sent a placement of kind `marker` to
`NOTHING`. So a header naming no order at all read as a big-endian one.
A TIFF starting `XX` with a big-endian 42 behind it validated; so did a
pcap file carrying the nanosecond magic `a1 b2 3c 4d`, every record read
with `ts_usec` holding nanoseconds -- a wrong reading that looks like a
number, which is the failure 26.576 is about.

Section 8.3 says exactly one encoding is valid given the marker. A third
value is no marker, so `validate` refuses it as a constraint:
`classify_check` answers `MARKER`, each backend compares the marker with
both literals, and the packer gives the walkers the row an enum that
rejects an unknown value already writes -- membership in a set of two --
so neither walker gained code. Each backend names the marker as the
member that refused.

Reading is unchanged: a governed member still reads big-endian under a
third value, because a read is not a verdict, and `validate` is where a
caller learns the message is not one.

## Verified

`test_a_marker_names_one_of_its_orders.py`: the nanosecond magic in
either order and a zero magic are `validate 2` in all four backends and
both walkers, the two real orders `validate 0`; a TIFF header marked
`XX` is refused by both walkers and `II` and `MM` are not.
