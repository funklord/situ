# 26.687: The image did not say what a varint's bytes mean

Status: recorded -- fixed in the image and both walkers
Date: 2026-10-24
Source: `project.md` section 26

Found while implementing 26.683's run of varints, by asking what the
walkers answer for a `svar`. Recorded then as two gaps beside that work
and fixed here.

## The fault

**The packer wrote three fields and one flags byte per varint member, and
the flags byte stated two things of which the image read one.** Bit 2 is
`be128`; bit 1 is `minimal` and `image.py` never looked at it; the
transform had no bit at all.

So a varint's bytes reached both walkers with their *parameters* and
without their *meaning*, and two divergences followed. Measured
2026-10-23:

- **A `svar` came back as its raw groups.** The walkers answered 1 and 6
  for a two-element run where all four backends answered -1 and 3: the
  zigzag transform, which the backends apply in the accessor and the
  walkers could not know about.
- **A padded encoding was accepted.** Four backends refuse one with
  `SITU_ERR_CONSTRAINT`, because `minimal` says exactly one byte sequence
  encodes a value; both walkers took it.

**Neither was exercised by anything.** `edges.situ` declared one varint
type, `be128` with no transform and no `minimal`, so the four-way
differential and the two-walker differential both passed over a certain
divergence -- `evidence.md`'s vacuous pass with six witnesses, which is
the same reason 26.683 went unseen in six readers at once.

## The fix

Bit 4 for the transform, and bit 1 finally read. Both as sets on the
image rather than fields of the rules tuple, because neither is a decode
PARAMETER: the decoder reads groups either way, and these decide what the
groups mean and whether the encoding is admissible.

**And a zigzag varint member is marked SIGNED.** A varint has no `scalar`
for the flag's own branch to ask -- its width is in its own bytes -- so
the flag was clear, and a reader printing through it showed -1 as
18446744073709551615 while the backends, whose accessor returns
`int64_t`, printed -1. The BITS agreed; only the signedness anybody would
print them with did not, which is the kind of divergence a differential
reports as a value mismatch and a reader diagnoses as arithmetic.

## Where the fact lives, which the fixture decided

**The transform is a field on the PLACEMENT now, beside
`varint_minimal`.** The first version read it from the declaration at
each point of use -- twice in the packer, and nowhere else could -- and
the fixture found the consumer that proves why that is wrong.

`codegen/differ.py` generates the differential's own four drivers from a
RESOLVED schema and no `ast`, so it had no way to ask whether a varint
was zigzag and printed every one with `%llu`. On the first random buffer
over `edges.varint_signed`:

    walker:  v len=1 value=-39
    C:       v len=1 value=18446744073709551577

Same bits, different reading. Rust and Python were already right, their
accessors returning a signed type -- so C and C++ were disagreeing with
their own siblings as well, and nothing had ever asked them to agree.

`Placement` has carried `varint_minimal` since varints landed, which is
the same kind of fact wanted in the same places. `varint_signed` sits
beside it, the layout solver derives it once, and the packer now reads
that field rather than looking the declaration up a second time: two
readings of one declaration are two things to be wrong about.

That is the eleventh consumer of "what do this member's bytes mean" to be
found by the failure it produced rather than by anyone enumerating them
-- 26.683's own list names nine, and this makes eleven with the differ's
printing and the layout fact itself.

## Where the refusal goes, which the first draft got wrong

**`minimal` is the getter's refusal and nothing else's.** The first
version checked it inside the shared decode, which the WIDTH path also
calls -- and the width path answers a refusal as a zero width, so every
member after the varint was placed on top of it. Measured:
`varint_canonical { edge_canonical v; u16 tail; }` over `85 00 00 00` put
`tail` at offset 0 and read `0x8500` as its value, where the truth is 0
at offset 2.

The four backends draw the line exactly: `_len` answers the encoded
length whatever its minimality, and only `_get` refuses. So the walkers
apply the transform in the shared decode -- harmless, the width being a
byte count -- and ask admissibility at the read sites only.

## The measurement that closes it

`edges.varint_signed` and `edges.varint_canonical`, four cases, all six
readers:

    zigzag 1   backend -1          C walker -1          python -1
    zigzag 6   backend 3           C walker 3           python 3
    minimal 5  backend 5, tail 0   C walker 5, tail 0   python 5, tail 0
    padded 5   backend CONSTRAINT  C walker refused     python refused
               tail 0              tail 0               tail 0

The fixtures are the point rather than the fix. A value divergence moves
nothing in the frame, which is why this one needed a schema written for
it: 26.683's run was found because a wrong WIDTH moves the member after
it, and a wrong VALUE is invisible to every structural check there is.
