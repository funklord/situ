# 26.645: The clamp on the count path, and the C cast that hid it

Status: recorded
Date: 2026-10-14
Source: `project.md` section 26, where it was written

26.644 named the fix and said the walker needed none. Applied: the count
path in all four generated backends now bounds its leaves and clamps
once, which is what the length path beside it has always done.

What each emits for the cell `varint-arith-vrec-after-varint-in-frame-since`,
whose run is counted by `n + 1` over a varint:

    C       return (uint32_t)situ_nonneg_u32(situ_leaf_u64(situ_s_n_value(view)) + 1);
    C++     return ::situ::rt::nonneg(::situ::rt::leaf_u(n_value()) + 1);
    Python  return nonneg(leaf(self.n_value) + 1)
    Rust    situ_rt::nonneg(situ_rt::leaf_u(self.n_value() as u64) + 1)

#### What proved it, which is not the sweep

`tool/sweep.py --only varint-arith-vrec-after-varint-in-frame-since`
reports `agreed` both before and after the change, and that is not
evidence: with `HELD_BACK = False` nothing asks a struct run for its
count, so the sweep could not see this path at all. I wrote the sweep
line into this entry first and it would have read as a gate.

The control is the probe turned on, and it was run in both directions:

    probe on, clamp in all four         agreed
    probe on, C's clamp reverted        DISAGREE, count=1364443823
                                        against count=2147483648 x3

So the fix is proved by a check that fails when it is removed, which is
what `evidence.md` asks of a guard, and the sweep's verdict with the
probe off is a vacuous pass -- that file's first rule, met in my own
write-up of the fix for it.

It also corrects the numbers in 26.644. Those -- 637019603631 three
ways -- were measured with no backend clamping. With three clamped and
C not, the three answer 2147483648: the leaf saturated at
`SITU_LEAF_MAX` and then incremented. `situ_nonneg_u32` and its
siblings guard the low end; the leaf bound is what caps the high one,
and it is applied before the arithmetic rather than after.

**No `* element_bytes` on this path**, which is the one place it differs
from the length path it copies. A length is bytes and the clamp belongs
after the multiplication; this is a count of elements, and the clamp
belongs on the count -- multiply after clamping and the product leaves
the domain again.

#### The cast was the reason C looked right

Worth keeping because the appearance was the opposite of the fault. C
was the only backend whose number was inside `uint32_t`, so a reader
comparing the four would take C for the one obeying the rule and the
other two for the ones overflowing. It was the reverse: C's
`(uint32_t)` cast truncated 637019603631 to its low 32 bits and
produced a plausible count out of an implausible one. The two large
numbers were honest.

That is 14.2b's own text arriving a second time -- *"clamping the low
end alone left `(LEAF_MAX + 1) * 2` truncating to zero on the cast to
`uint32_t` -- the same failure one step along"* -- and the transferable
part is narrower than the rule: **a narrowing cast is not a bound, and
it is the one that makes a wrong number look like a right one.** An
unclamped count in C++, Python or Rust announces itself by being
absurd. In C it does not announce itself at all.

#### What it unblocks

26.641 held the struct-run count probe back on two obstacles: the C
macro for `edges.pieces.two[2]`, closed by narrowing the probe to runs
with no `array_count`, and this one. Both are closed, so `HELD_BACK` in
`situc/codegen/differ.py` can come on -- in its own change, gated
separately, because turning it on is what reproduces the red gate if
anything about either obstacle was wrong.
