# 26.789: `validate` validates every element of a run of structs

Status: recorded -- decided by the copyright holder, implemented for runs
outside a variant arm
Date: 2026-10-31
Source: the holder's direction ("validate the elements of a run"),
answering the question 26.786 left

    struct piece { u8 len [max = 4]; u8 body[len]; }
    struct s     { u8 n; piece r[n]; }

## What it replaces

No implementation validated a run's elements. C's `validate` said why:
"that is a loop on every parse, and a caller who wants it should walk the
elements". The other three backends and both walkers followed. So a DNS
label, an HTTP header field, a netlink attribute, an id3 frame and an MQTT
subscription were each checked when validated as a struct of their own, and
never as an element of the run carrying them. Measured over the corpus, 21
of 26 runs of structs hold an element with checks of its own. `validate`
called a message clean while a record inside it broke a rule the schema
states, and the cost argument is the holder's to weigh, not the generator's.

## What it does

- **Every element, through its own `check`.** Each element is what the
  run's own walk steps over, at the extent that walk gives it. So a record
  the frame does not hold ends the run, as it always did (26.680), and is
  not validated. One loop per run shape: a count (literal, a field or
  arithmetic), `[remaining]`, `while` and a terminator.
- **In order.** An element is validated in the run's own place in
  `validate`, after the run's frame checks and before the members after it.
  So `{ u8 k; kv recs[] until "\n"; u16 after; }` over a `kv` whose value
  has no `;` now answers CONSTRAINT where it answered BOUNDS for `after`.
- **A refusal is the element's own code and names the run.** That is what a
  nested member's refusal already did. `which` is the run's check id, and
  the walkers record the run as the failing member.
- **A run whose element can refuse nothing gains no id.** Otherwise a run
  of plain records would get an id nothing can report, shifting every id
  after it. Where the element can refuse, the run may gain an id it did not
  have (a `while` or delimited run had none), and the ids after it in that
  struct move by one. They move the same way in all four backends, since
  each numbers its own groups.

## Not yet

- **A run in a variant arm.** The arm family has its own walk (26.779 to
  26.786) and is the next piece.
- **A recursive element**, which needs a depth `check` does not carry.
  This covers json's members and elements, sexpr's items and edges'
  `nest_group`.
- **An element taking arguments.**
- **An `indexed` region's elements** (sqlite's cells).

`situc verify` still names these in its "except inside arrays" note. It
no longer names a run it validates.

## What it found

- **id3 refused every padded tag.** `frames[] while (identifier_0 != 0)`
  ends after the element failing its test. So the first ten bytes of the
  padding were the run's last frame, and that frame's identifier fails
  `[min = 0x30]`. The schema's comment admitted the run took padding as a
  frame. That was harmless while elements went unvalidated. 3.1's rule is
  about the byte where a frame would start, which is `until "\0"`, so the
  run is now that. The tag's minimum falls from 20 to 11, and the
  mutagen oracle now checks that no frame is padding.
- **The C walker's hook first returned on a verdict an earlier member had
  set.** The member loop carries one forward while a check that outranks
  it runs. So the hook keeps its own verdict.
- **The walkers did not hold an element to its struct's minimum** when the
  element is variable-size. Every backend's `check` asks that first, and
  edges' `kv_block` over `03 c3 a9` showed it. The nested member's
  26.577 check is now asked of each element too.

## Tests

`test_a_run_validates_its_elements.py`: six run shapes, a bad element
first, last or not at all, in all four backends and both walkers.
`test_checks.py`, `test_verify.py` and `test_an_ended_run_in_an_arm.py`
are updated where they pinned the old answer.
