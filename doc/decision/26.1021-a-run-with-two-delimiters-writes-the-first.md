# 26.1021: a run with two delimiters writes the first

Status: recorded
Date: 2026-11-14
Source: the goal gap -- builder refusals over the example schemas

**An HTTP field line could not be built**, and so neither could a request
or response head. `u8 value[] until "\r\n" | '\n' [trim]` was refused in
all four: "ends at any of 2 delimiters, so which byte to write after it is
not stated".

**The protocol states it.** RFC 9112 section 2.2: a sender MUST generate
CRLF, and a bare LF is what a recipient MAY also accept -- which is why the
schema lists both, CRLF first. A writer is a sender, so it writes the
first alternative. Where the reader then stops depends on the content as
well -- `a\nb` holds no CRLF and still ends at the LF -- so the run is
checked afterwards, as a span its expression sizes is (26.1016): the
reader's own length for it, once the message is whole, must be what the
caller passed. Several delimiters with an escape stay refused, since which
of them the escape protects is not stated.

**Measured**: `Host:example.com\r\n` from C and Python, with `a\nb` and
`a\r\nb` refused; the agreement test builds `header_field`,
`request_head` and `response_head` alike in all four. The other schemas
naming several delimiters list `end` as one of them and generate the same
code as before.
