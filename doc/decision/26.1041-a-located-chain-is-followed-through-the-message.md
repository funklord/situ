# 26.1041: a located chain is followed through the message

Status: recorded
Date: 2026-11-17
Source: openmlx4's FS2 report, measured as f715cd8c

    struct chain [depth = 8] {
        hdr   head;
        u8    data[head.size];
        chain following at head.next;
    }

**`situc build` accepted this and no backend's output compiled.** C called
a `_following_extent_at` and a `_following_offset` it never emitted, C++ and
Rust a `following_count` and an `extent`, and Python's depth probe read a
count that did not exist -- the crash `situc verify` used to render as a
verdict on the bytes. All four had treated the located member as though it
followed `data` inside the frame.

## The rule

A located member is reached from the start of the message, so none of its
bytes are this instance's. The layout already said so -- the struct's
minimum is 8 here, not 16 -- and `traverse.extent_parts` now agrees, so the
extent and `required` no longer walk it. That was wrong outside recursion
too: `required` for `struct s { hdr head; u8 data[head.size]; tail t at
head.next; }` asked for `tail`'s bytes right after `data`, where nothing put
them.

The depth probe follows a located member through the message, as `validate`
already reached it: C and C++ through the view's owner, Python through the
member's view, and Rust, whose views hold no message, through a
`nesting_in_at(msg, depth)` that `nesting_at` hands its own bytes, as
`validate` hands `validate_in` its own. Depth is counted along the chain as a
nested member's is, so a chain whose `next` loops back is refused as
CONSTRAINT once it passes `[depth]` rather than followed for ever.

## What is still open

**A way to say the chain stops.** FS2 ends at `next == 0xFF000000`, and
without a way to say so no such chain validates: its last `next` points
somewhere, and outside the message that is BOUNDS. The spelling the grammar
already has is a located arm -- `case 0xFF000000: nothing none; default:
chain following at head.next;` -- since that is how PES and JSON write an
optional member. It was refused by name ("`at` on a variant arm member is
not implemented") and is allowed for one struct since 26.1044.

A located run, `chain following[head.next != K] at head.next`, is not the
route. A located run of structs built and did not compile in C, C++ or
Rust (C called `_fits` and `_offset` functions it never emits), and every
accessor ignored the count; it is refused by name now, as a located
variant arm was.

## Found beside it

**Nothing else that reads a frame may name a located member, and three
things did.** A `when` reading `following.head.next` crashed `situc build`
with an unknown name in all four backends; a length, a rule or an offset
reading one built output that read the wrong frame byte (`u8 d[h.n]` read
byte 2, inside `d`) or did not compile (`u8 d[v]` called a `_v_offset`
nobody emits); and a relation's `must` reading one built a `_converse.h`
calling a `_v_get` no located member has. Each is refused by name now. No
schema in the tree did any of them. A checksum's `covers()` already refuses
anything but a region, and the edit and frame layers compile over every
located shape here.

## Measured

`test/unit/test_a_located_chain.py`: five chains -- one looping to itself,
three and six sections ending outside the message, twelve in a line, and
three looping back -- give the same verdict and nesting in C, C++, Rust and
Python: CONSTRAINT with nesting saturated at 10 for the three past the
depth, BOUNDS with nesting 2 and 5 for the two that end outside. With the C
probe's located branch switched off, the C case fails. Python's output
passes `mypy --strict`.

`test_verify_reports_a_compiler_fault_as_one` was pinned on this chain's
crash and now injects the fault instead, since the crash it relied on is
gone.
