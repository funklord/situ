# 26.892: A JSON string is a stuffing code

Status: recorded
Date: 2026-11-06
Source: 26.670's question, and the holder's rule that a sane protocol's need is
ours

26.670 asked whether situ should ship a JSON-string codec, and named what stood
against it: a code that decodes only the one-letter escapes promises more than
it does. So this one decodes all of it. `json_string` in `std/kernels.situ` is
the inside of a string, RFC 8259 section 7: the one-letter escapes, `\uXXXX`
to UTF-8, a surrogate pair as one character, in C, Rust and Python.

`stuffing` holds it, though 26.670 thought the numeric half might not fit.
What `stuffing` promises is a bounded expansion and a decoder that takes bytes
out, and both hold: six bytes for one is `\u0000`, and decoded text is never
longer than its wire form, so the wrapper's buffer is the right size.

## What it refuses

An unknown escape, an escape cut off, a raw quote or control byte, a `\u` that
is not four hex digits, and **either half of a surrogate pair alone**. RFC 8259
lets the text exist and Python's `json` accepts it, handing back a string no
UTF-8 encoder will take. This refuses it, which is where the oracle and this
code part on purpose.

A refusal answers zero. Every valid escape yields a byte, so zero from a
non-empty input is unambiguous, though the decoded-region accessor does not yet
turn that into an error of its own: `Ok(0)` there means malformed for this code.

Bytes above 0x7F pass through both ways. That text is UTF-8 is the reader's to
check.

## Held against

Python's `json`, which nobody here wrote: `ensure_ascii` for every `\uXXXX` and
pair, plain `dumps` for the encoder's exact bytes, over 306 strings, in all
three languages. C++ takes C's.
