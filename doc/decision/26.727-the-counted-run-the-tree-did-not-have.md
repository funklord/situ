# 26.727: the counted run the tree did not have

Status: recorded -- the construct is in `test/schema/edges.situ`
Date: 2026-10-29
Source: `project.md` section 26

26.724's record closed by asking for this and said why: of the 46 schemas
this repository builds, **exactly one has a counted run of variable-size
records** -- `example/ble`'s `adv_report` -- and **not one has an element
whose length carries a declared minimum**. `ble`'s `data_length` is
`[max = 31]` with no `[min]`.

That is not a gap against an ideal. It is measured: 26.725's sweep, pointed
at every schema, **passes on an export of `a176c43`**, the commit where
26.724's fault is present and unfixed. The tree could not see it.

## The construct

    struct floor_element {
            u8  len  [min = 3, max = 32];
            u8  body[len];
    }

    struct floor_run {
            u32            stamp;
            u16            count  [max = 4096];
            floor_element  items[count];
    }

in `test/schema/edges.situ`, which exists for exactly this -- *"a construct
the language offers and nothing exercises is a construct whose generated
code has never run"* -- rather than in `example/`, which carries worked
protocols and whose rule is that every constant is read out of a real
source and cited by line. This shape is not a protocol and inventing one to
hold it would be a claim about a format nobody read.

Two properties, because the week's two faults needed one each:

- **`[min = 3]` makes `floor_element`'s `SIZE_MIN` four where its
  STRUCTURAL minimum is one**, and that three-byte gap is 26.724. The
  committed map says so: `struct floor_element size=4..33`.
- **The count sits at offset four behind a six-byte prefix**, which is
  26.723. `u32` and `u16` rather than two bytes, because a count in the
  first byte is the arrangement every shape in
  `test_required_answers_every_prefix.py` has and the one in which neither
  fault can appear.

## A construct is not a population until something drives it

**The first three fills could not reach it, and that is the finding worth
keeping.** 26.725's sweep fills each prefix with one repeated byte -- 0x00,
0xFF, 0x5A -- and a uniform fill makes a `u16` count either zero or
enormous. So the run either never starts or never finishes an element
inside 48 bytes, and the arithmetic 26.724 lives in is the step where an
element AHEAD completes while the next one reports its own short bound.
That step was unreachable.

A fourth fill of `0x01` gives a count of 0x0101 and elements of two bytes,
so the step happens every other prefix. Measured against the `a176c43`
export: `floor_run`'s `need` falls from **1032 to 1029 at eight bytes**
under that fill, and at no prefix under the other three.

So the blind spot took the construct *and* an input chosen for it. **A
population is not only which schemas are swept but which bytes they are
swept with**, and the first three fills were chosen for the memory half of
that sweep rather than for the arithmetic. The same question is worth
asking of every corpus-driven check here: the schemas are counted and the
inputs are not.

## What it cost

The committed map and wire signature are regenerated and the diff is
**purely additive** -- the two new structs and nothing else moved, which is
the thing to check when a schema grows, because added rows fail no gate.

`edges.situ`'s packed image goes from 45,538 bytes to **46,106** against
26.722's `DRIVER_IMAGE_MAX` of 65,536: headroom 1.42x where it was 1.44x,
and room for about thirty more structs of this size before the guard that
record added has anything to say.
