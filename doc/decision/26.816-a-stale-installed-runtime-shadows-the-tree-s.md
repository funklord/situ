# 26.816: a stale installed runtime shadows the tree's, and nothing says so

Status: recorded -- fixed by an ABI serial the generated headers assert
Date: 2026-11-02
Source: `project.md` section 26; reported from fmake 2026-11-03

**A consumer compiling this tree's committed tests got twelve signature
errors and read them as "your generated tests are out of step with
situc".** They were not. The header they compiled against was
`/usr/include/situ.h`, from `libsitu-dev`, and it is byte-identical to
`runtime/c/situ.h` at `af50443` -- 2026-09-08, nearly two months stale.

    $ grep -n situ_view_check /usr/include/situ.h runtime/c/situ.h
    /usr/include/situ.h:155: situ_err_t situ_view_check(const situ_msg_t *msg,
                                                        situ_view_t view)
    runtime/c/situ.h:181:    situ_err_t situ_view_check(situ_view_t view)

    $ gcc -c test/generated/test_runtime.c -I/usr/include
    error: incompatible type for argument 1 of 'situ_view_check'
    ... and eleven more

    $ gcc -c test/generated/test_runtime.c -Iruntime/c
    (clean)

`test/generated/*.c` use `#include "situ.h"`, and a quoted include
searches the including file's own directory first and then the `-I`
path. Nothing is beside them, so which runtime they get is entirely a
property of how the caller spells `-I`. This tree's own
`test/generated/Makefile` names `runtime/c`; a build system reading an
unannotated tree cannot know to.

## Why nothing could detect it

Both headers say the same thing about themselves:

    #define SITU_VERSION_MAJOR	0
    #define SITU_VERSION_MINOR	1

The ABI changed -- `situ_view_check` lost a parameter, and the file grew
from 1443 lines to 1940 -- and the version macro did not move. The
package version cannot distinguish them either: `libsitu-dev` is `1.0`
installed and the tree's `VERSION` is `1.0` now.

So a consumer has no way to ask "is this the runtime that generated
header was built against", and the first thing it learns is a cascade of
type errors in whichever function the ABI touched. **The failure names
the wrong file**: the errors point at the test, and the fault is on the
include path.

## The fix: an ABI serial, asserted by the generated code

An integer that increments whenever the runtime's C ABI changes in a way
generated code can see. It is additive, so a stale header fails the
`defined()` arm rather than needing the old header to have been right
about anything:

    #if !defined(SITU_RUNTIME_ABI) || SITU_RUNTIME_ABI != 1
    #error "..."
    #endif

One source for the number, and a gate for the copy. situc holds it as a
Python constant because situc is what emits the requirement, the runtime
header carries the `#define`, and a test asserts the two agree -- the
same shape as every other fault in this week's run: **two places
answering one question must read one text.**

## What this does not fix

- **`SITU_VERSION_MINOR` is still 0.1 over an ABI that has changed.**
  Moving it, and moving `VERSION` and the package version with it, is a
  release decision rather than a code one, and it is the holder's. The
  ABI serial is deliberately a separate number so that the fix did not
  need that answer.
- **Python has the same shadowing hazard by a different route**:
  generated modules `import situ_runtime`, and an installed copy earlier
  on `sys.path` wins exactly as an installed header does. Rust does not
  -- `mod situ_rt` names a file.

## Measured, on this machine

The installed header is byte-identical to `runtime/c/situ.h` at
`af50443`, found by walking the last twenty commits that touched the file
and comparing each with `cmp`. It is 1443 lines where the tree's is 1940.

Before the guard, the real scenario -- a generated header in a directory
with no `situ.h` beside it and `/usr/include` on the path -- gave twelve
type errors, the first naming `test_runtime.c`. After it, one:

    edges.h:15:2: error: #error "the situ.h on the include path predates
    SITU_RUNTIME_ABI, so it is older than this generated header. An
    installed libsitu-dev shadows a tree's own runtime/c/situ.h whenever
    it comes first on the include path."

The quoted include is why the scenario needs setting up carefully: a
generated header with `situ.h` copied beside it finds that one first,
whatever `-I` says, so a probe that copies the runtime in cannot
reproduce this and will report the guard untriggered. That is how the
first attempt at this measurement came back clean.

## Verified

- All four backends generate; the C compiles under the project's flags,
  the C++ under `-Wall -Wextra -Werror`, the Rust under `rustc -O`.
- `test_a_generated_header_names_its_runtime.py` holds the serial's two
  copies to each other and preprocesses a generated header against three
  stand-in runtimes: one predating the serial, one with a different one,
  and the tree's own as the negative control -- without which two tests
  pass over a guard that refuses everything.
- The drift gate was sabotaged by moving the runtime's `#define` to 2,
  which fails naming both numbers and which to move.

## What it does to `deb-check`

`deb-check` extracts the freshly built packages, has the installed
`situc` generate a header, and compiles it with
`-I$(DEB_DIR)/root/usr/include` -- the installed runtime. Both halves
come from the same build, so the serial agrees and nothing breaks. What
changes is that the target's closing claim, *"the installed situc built a
schema against the installed runtime"*, is now checked rather than
asserted: before the serial, a package whose `situc` and `libsitu-dev`
were out of step would have compiled clean whenever the drift happened to
miss the schema in question.

Nothing else in the tree reaches for the installed header.
`test/generated/Makefile` and `test/cross/Makefile` both default
`RUNTIME_INC` to the tree's `runtime/c`, which is the right answer and is
why the tree's own gates never saw this.
