# 26.1173: a run of varints has a cursor

Status: recorded; built in the four backends. Extends 26.1172, whose "Not
covered" left a run of varints without one ("yes, build the varint
cursor", holder, 2026-11-26).
Date: 2026-11-26
Source: the holder asked whether the shapes 26.1172 left out were likely
to come up. A census of the generated C found no consumer schema with
either; the formats situ is for have plenty of varint runs.

## Why now, with no consumer asking

Measured 2026-11-26 over generated C, every walking `_at` without a
`_next`: situ's 60 schemas had four, all runs of varints (quic's HTTP/3
settings, wasm's function section type indices, two in edges); the 83
schemas of fuzznet, raidcfgd and openmlx4 had 53 walked runs, every one
with a cursor, and no varint run. So no consumer needs it today.

What decided it is the formats. A run of varints is how SQLite states a
record's column types, how protobuf packs a repeated scalar, how
WebAssembly writes every vector of indices, how DWARF and QUIC write
theirs. An element's offset is the sum of the lengths before it, so `_at`
walks from the start (`access=Sequential`, 26.683) and a loop over the
run is quadratic -- and unlike a run of structs, no schema can avoid it:
there is no stride to declare and no struct to wrap it in.

A run that is a variant's arm stays without one: putting the run in a
one-member struct, as `example/json` does with `members` and
`elements`, gives it a cursor today, so that shape is a spelling and not
a gap.

## The rule

Every run of varints -- counted, or sized by the frame -- has `_next`
beside `_at`, with 26.1172's types and contract: a zeroed cursor starts at
the first element, and the k-th call answers what `_at(k - 1)` answers,
the value or the refusal (`bounds`, or `constraint` for a padded element
of a `minimal` varint).

    C      situ_S_R_next(view, &cursor, &value)   -> SITU_OK / SITU_ERR_*
    C++    s.R_next(cursor, value)                -> err::ok / err::*
    Rust   s.R_next(&mut cursor)                  -> Ok(value) / Err(..)
    Python s.R_next(cursor)                       -> value / BoundsError

## Derived from `_at`, and how it differs from a struct run's

As in 26.1172, each backend rewrites the lines of its own `_at` and emits
nothing when one keyed line is not there exactly once: `at = <base>`,
`n = <count>`, `seen = 0`, and the yield at `seen == index`.

A run of structs re-reads the element handed out last, because a `while`
run asks of that element whether it ended the run. A varint is whole once
decoded and nothing asks about it again, so the cursor keeps where the
NEXT element starts (`at + used`) and resumes there with `seen = index`.
No element is read twice.

A run sized by the frame (`uvar v[remaining]`) counts by walking to the
frame's end (26.742). Kept, that count would make every `_next` call a
walk of the whole run. It is left out: the walk stops on exactly the
conditions counting stops on -- the frame's end, or an element the frame
cuts short -- so the bound adds nothing. Python's message names the count
as `index`, which is the count wherever such a walk stops, since every
element before it was whole.

## How it is held

`test_a_cursor_walks_a_run_as_its_index_does.py`: the per-schema counts
gain quic's one, wasm's seventh and edges' two, equal in the four
backends; the differential runs quic and wasm too and compares values,
and asserts how many varint runs each backend's probe asked
(`VARINT_RUNS`), because the Rust and Python probes first looked for
`x(i)` -- a struct run's spelling -- and skipped every varint run while
the struct runs beside them passed. Sabotaged twice: a C cursor resuming
at the element's start, and Python's frame-sized bound one short; each
failed its differential.
