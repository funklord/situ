#### What the next session should pick up

**The lens, not the corpus.** `python3 tool/sweep.py --writer --all` runs
the planner over 9000 composed cells in 77 seconds and asks the claim
gate's question of every refusal. It is green now (13356 plans, 5544
claimed refusals, no crash, no silent cell, no false claim), and it is
where the next writer fault will show, because every one so far was in a
shape the corpus lacks. The suite carries a 400-cell sample of it.

**The compile half of that lens is `sweep.py --writer --compile`**, and
it does not wait on the readers' warnings: warnings are on, `-Werror` is
not, and a diagnostic counts only where the filename blamed is the
WRITER's header. A lens that stopped at the reader's header would be
measuring somebody else's code -- and the reader's warnings are recorded
below with the measurement that says they are cosmetic.

150 cells compiled with nothing blamed on the builder. The lens was seen
to FAIL before that was believed: an undeclared identifier added to the
scalar emitter was reported for 8 of 12 cells, by name and with the
line.

**What it did not do is hold the reader to `-Werror`.** That was measured
rather than deferred: the one warning class with a value behind it is a
mixed-signedness comparison in a counted run's loop bound, where the
count is rendered as a C `int` and compared against a `uint32_t`. The
composition space spells that count only as `field + 1`, so it cannot go
negative, and the four-way differential agrees on every `arith-vrec`
cell sampled -- six of six. Making the comparison unsigned-safe is
therefore a change of generated output in every backend for a warning
whose value is cosmetic today, and it would change behaviour only for a
SUBTRACTIVE count the space cannot express. That is a reader decision
with a measurement attached rather than a fix somebody should slip in.

#### Open, and whose

**~~The readers' count accessor for a dynamic nested run.~~ Fixed in
26.638, and it was never a decision.** Ten minutes of measurement -- the
element is `SIZE_FIXED` and has its own `_required` -- made it one bug
with one answer in four renderings. What is open is the half that let it

reported the cell as `agreed` while C answered zero and Python answered

branch beside it was fixed. That is the coverage piece, and it is the
first thing a session with budget should write.

**~~0056's open question~~ -- what a canonical decimal spelling is --
is settled by 0063.** It stays refused, and not as a deferral: the
construct's one asker is json's `number`, JSON is the format whose
canonicalisation is published, and RFC 8785 defines it through an
IEEE-754 double this construct deliberately does not have -- requiring a
JSON string above 2^53, so 99 per cent of an `i64` significand's range
has no canonical JSON number form at all.

The measurement that shrank the prize to one struct is what made the
question answerable: with one asker, "what is a canonical decimal
spelling" stops being abstract and becomes "can situ declare THIS field
canonical", which has a published answer.

**Whether a struct with nothing for a caller to supply gets a builder.**
json's `true`, `false` and `null` are refused as entirely literal, which
is accurate and was deliberate; an adopter composing a document then
hand-writes those bytes, and situ emits no constant for them to use.

**0043 against the parser**: the record says `pad_to(n) [preserve]` is
the escape for padding that carries data and the front end refuses the
attribute there. The parser's refusal is what makes every pad
`must_be_zero`, which is what let the pad branch be total.
