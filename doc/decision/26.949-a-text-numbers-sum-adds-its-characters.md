# 26.949: a text number's `sum` adds its characters

Status: recorded
Date: 2026-11-10
Source: `example/ustar`'s header checksum, left open by 26.948
Supersedes: 26.948's "the header checksum is read and not checked"

**`sum(x)` over a fixed-width text number adds the bytes it is written in.**
A text number's width is digits, not elements (8.6.2), so its elements are
its characters: `sum(mode)` over `octal u32 mode[8]` is eight bytes added.

## What was wrong

26.896 made `sum` a size builtin over a table of lengths, and refuses a
text number there. A `when` was never held to that rule, and every backend
read a text number's `[8]` as eight elements of its scalar: `sum(mode)`
added eight `u32`s, 32 bytes out of an 8-byte field. Nothing used it until
ustar's checksum, which every tar reader verifies: the sum of the header's
512 bytes with `chksum`'s own eight counted as spaces. Most of those bytes
are digits.

`traverse.summed_width` answers the element width once, a byte for a text
number, and the four backends, both walkers and the dissector ask it. The
C walker counts a text number's characters itself, `situ_walk_count`
declining a text number's bracket as no count of elements.
`test_sum_adds_a_text_numbers_characters.py` holds all six; with the
width rule removed the four backends refuse the right sum.

## The checksum

`example/ustar` states it:

    when ustar_header.chksum != sum(ustar_header.name) + sum(ustar_header.mode)
        + ... + 256 + ustar_header.typeflag + ... + sum(ustar_header.prefix)
        refuse checksum_mismatch "...";

GNU tar's header passes, and a flipped bit in the name, a digit of `mode`,
`typeflag` or `uname` is refused, in all four backends. POSIX's sum is
unsigned; archivers that summed signed bytes are refused where a name has
a byte above 0x7F, the stricter of the two.

## What it cost the generated checks

The check generators build a fixture by writing what each member needs
into zeros, and ustar's rule refuses that fixture: the digits it writes add
up to something and `chksum` reads 0. Three backends' suites failed on it.
A fixture a rule refuses would make every check built on it assert the
wrong thing, so the baseline now declines where a `refuse` rule might
refuse it -- each rule evaluated over the fixture's values three ways, a
`sum` being unknown, and anything short of false declining. cpio's rule
opens `check != 0 &&`, false over zeros, so it declines nothing there:
cpio, rtp and `edges` generate exactly the checks they did, counted. The
rules reach the generators as `ResolvedSchema.refusals`.
