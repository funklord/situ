# 26.714: a declared width is not a width the frame has

Status: recorded -- fixed in C; C++ followed in 26.715
Date: 2026-10-28
Source: `project.md` section 26

    ==22379==ERROR: AddressSanitizer: heap-buffer-overflow
    READ of size 1 at 0x5020002921d8
        #0 situ_parse_uint         runtime/c/situ.h:1018
        #1 situ_text_driver_moved_n_get  gen/edges.h:9280
        #2 fuzz_text_driver_moved  gen/edges_fuzz.c:2732

    0 bytes after 8-byte region [0x5020002921d0,0x5020002921d8)

A generated text-number getter passed the schema's **declared** digit
width to `situ_parse_uint` with nothing checking the frame had those
bytes:

    if (situ_parse_uint(situ_s_n_ptr(view), 4u, 10u, 9999u, &value) != 0)

`situ_parse_uint` is correctly bounded by the `len` it is given, so the
fault is entirely at the call site.

**Pre-existing.** Generated from `f5ea3c2`, before the corpus gained
`negotiated_signed`, the same eight calls in `edges.h` are unguarded; the
emitter has always done this.

## The construct that reaches it

    struct text_driver_moved {
            edge_varint   lead;          /* length the message chooses */
            decimal u32   n[4]  [max = 4];
            u16           tail;
    }

A varint of message-chosen length in front of four digits, so the digits'
offset is a sum the message chose and `offset + 4` can exceed the frame.
`edges.situ` carries this because it is the file for constructs no worked
example has, and that is exactly what it earned here.

## The file already promised the bounds check

`_text_value_helper`'s own comment:

> `validate` is what makes this safe -- it refuses a frame whose digits
> are not digits, so a validated frame always parses here. An unvalidated
> one reads zero, **which is the same bargain every other accessor makes
> with the bounds check it did not do.**

The scalar getters keep that bargain. These read past the frame instead.
A claim nothing keeps, which is this tree's worst-rated shape.

## Refused, not clamped

`min(width, remaining)` would parse the digits that ARE there and hand
back a different number: `"1234"` with two bytes left is 12, not an
error. **A length field quietly reading 12 instead of refusing is worse
than the over-read**, because nothing downstream can tell. So the
fallible getter returns `SITU_ERR_BOUNDS` -- the digits are not wrong,
they are absent, and every other accessor here distinguishes those -- and
the non-failing one returns zero, which is the bargain it already states.

## The first fix was too broad, and the project's own convention said so

Guarding unconditionally put **39 always-reached branches into
`example/cpio`'s header**, whose text offsets are all constant. That is
stricter than the scalar getter beside it:

    static inline situ_protocol_t situ_ipv4_header_protocol_get(situ_view_t view)
    {
            return (situ_protocol_t)((uint8_t)(situ_base(view))[9u]);
    }

-- no check at all. `_fits` carries the reason: *a statically placed
member is inside the frame by the bounds check that acquired the view
(20.2), which is the argument that makes every constant-offset access
unchecked.*

So the guard is **asked of `_fits`** rather than added, and the answer is
`None` for a constant offset and for a delimited field, whose length is
its own scan's answer and already compared against `situ_remaining_u32`.

Found by looking at what a plain scalar getter actually emits, after
noticing the 39. The same shape as yesterday's clear-in-`apply_to`: a fix
in the wrong place, caught by asking the corpus rather than by reading the
patch.

## Scope, measured

Of the 51 `situ_parse_*` call sites in the generated corpus, **45 pass a
literal width** -- cpio 39, edges 4, smtp 2 -- and 8 pass a scan-bounded
length (http's delimited fields). After the fix none of the 45 is
unguarded where `_fits` says the question arises.

**The corpus changes in one file**: `test/schema/edges.h`, 8 lines. No
worked example changes, because no worked example puts a text number
after a variable-length member.

`c/owned.py` needs nothing and that is worth saying, because a sweep over
every `situ_parse_uint` would have added 39 dead checks to cpio's owned
decode. It reads constant offsets after one check at the door --
`if (len < SITU_CPIO_HEADER_SIZE_FIXED) return SITU_ERR_BOUNDS;` -- which
is the same 20.2 argument one level out.

## Proofs

**Two-sided, on the artifact the fuzzer wrote.** A harness built from the
unfixed generator crashes on it with the ASan report above, exit 1; the
fixed one runs it clean, exit 0, with the guard verified present in the
rebuilt header first -- because a replay against a binary the build did
not rebuild proves nothing.

## The UBSan lens, run and empty

This was found while running a lens for something else. The fuzz harnesses
build with `-fsanitize=fuzzer,address`, so **ASan has always been gated
and `undefined` never has**, and for a compiler whose output is bit and
byte manipulation UBSan is the sharper instrument: shift exponents from
schema widths, offset arithmetic, `situ_base(view) + offset`, and the
alignment the capability map claims.

The first pass stopped at this crash after 2 of 45 harnesses, so it
reported nothing because it had barely run. Rerun after the fix:
**43 harnesses, zero UBSan reports, zero ASan errors** (two schemas have
no parseable struct). So the lens is complete and empty, and the empty
result is the point -- recorded so the next session does not spend the
hour again.

## What is not done here

**C++ has the identical shape** --
`situ_parse_uint(situ_base(raw_) + (0), 4u, 10u, 9999u, &value)` -- and is
left to its own change, which wants its own control: `fuzz-cpp` exists and
is the instrument for it. Rust and Python are safe by language, slicing
rather than pointing.
