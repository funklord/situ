# 26.665: A tlv region had no byte order, and four backends disagreed

Status: recorded
Date: 2026-10-20
Source: `project.md` section 26

Found while fixing 26.664, one layer under it. Fixing the width of a
scalar tag raised the next question -- in which byte order -- and the
answer was four answers.

**A `tlv` placement carried `endian = None`.** Every other placement
takes `scope.endian`; this one was constructed with `None`, which reads
as "this member has no scalar of its own" and is true of the region and
false of the numbers it reads. The tag and every `prefixed(T)` length
are read in *some* order, and the placement said nothing about which.

**So each backend answered from its own default, and the defaults
disagree.** Both helpers are documented, and documented as the default
for a field that has no order:

    python  _byte_order(None)  -> "little"   # '"big"' if BIG else '"little"'
    rust    _reader(None)      -> read_be    # read_le if LITTLE else read_be

Measured on a `u16` tag with `endian big` in the schema: Python emitted
`int.from_bytes(data[at:at + 2], "little")` and Rust
`situ_rt::read_be(self.bytes, at, 2)`. One schema, two meanings, in the
four backends whose agreement is the whole claim.

**It was invisible, and the reason is worth more than the fault.** Every
scalar read inside a `tlv` region in this tree is **one byte wide** --
`tag_type = u8` and the `prefixed(u8)` arms -- and a one-byte read has
no byte order to get wrong. So the disagreement could not be observed by
the differential, by the five-reader comparison, or by the two walkers,
all of which were green throughout. A difference that only a width
greater than one can expose, in a tree whose every instance is one byte,
is a difference nothing in the harness can reach.

**The fix is the placement, not the helpers.** The region carries
`scope.endian` now, so `None` never arrives from a `tlv` region and the
question is answered by the schema rather than by each backend's guess.
The helpers keep their defaults, which are correct for what they
document.

**What is still unreachable.** No corpus schema has a multi-byte scalar
tag or a `prefixed(u16)`, so the four backends' agreement about the
order is asserted by reading the emitted text rather than by running
anything. A schema with a `u16` tag would make it a behavioural
comparison; adding one is a corpus decision rather than part of this
fix, and `edges.situ` already carries the one scalar-tag region the tree
has.
