# 26.814: a divided run's `_count` took no argument

Status: recorded -- fixed in C; the other three were already clean
Date: 2026-11-02
Source: `project.md` section 26

**A legal schema whose generated C does not compile under this project's
own flags**, and the element here takes no argument at all -- which is
what makes it a shape of its own rather than another instance of 0068
step 5. Three lines:

    struct beacon { u16 seq; u8 flags; }
    struct relays_on_divided {
            parameter u8  block [stream];
            u8            head[block];
            beacon        rest[remaining];
    }

`_count` has four branches, decided by how the run's length is written: a
literal count is a macro with no function at all, `[remaining]` over
elements of one size is a DIVISION, `[remaining]` over elements with no
single size is a walk, and a counted run is an expression. The division
branch wrote

    static inline uint32_t situ_relays_on_divided_rest_count(
                    situ_view_t view)
    {
            const uint32_t base = arg_block;
            ...
            return (situ_remaining_u32(view.limit, base)) / 3u;
    }

-- a fixed signature over a body that names the argument:

    error: 'arg_block' undeclared (first use in this function)

and, at the call site, `too many arguments to function` as well, because
the caller asked the member's own length expression (which does name the
argument) while the definition asked nothing. Two halves of one function
disagreeing, which no assertion about either half can see.

## Why nothing reached it

The division branch is the only one of the four where the ELEMENT is not
argued. Every argued construct in the corpus had the argument on the
element, so `_child_args` was non-empty and the threading that exists for
the other three branches carried it. Here the argument reaches the
function only through `base` -- the run's offset, which `head[block]`
makes dynamic -- and nothing in the branch looked at `base` to decide
what the function takes.

The corpus had no `[remaining]` run of fixed elements behind an argued
member, so the four compile gates could not fail on it. `beacon` is three
bytes and was already in `edges.situ`; the construct is two lines.

## The fix

The branch derives its signature from its own body text, as the counted
branch beside it already did:

    f"(situ_view_t view{self._argument_tail_in(struct, base)})"

`_argument_tail_in` reads the text it is given and declares a parameter
for each argument that appears in it, so the signature and the body
cannot disagree: they are one string answering for both.

## The shape, which is the week's fifth instance

**Two places answering one question from different text.** The
definition asked `base`; the call asked the member's length expression.
Both are true statements about the member and they are not the same
question, so the two sides drifted the moment a schema made them differ.
The remedy is the same every time: name the text once and let both sides
read it.

Siblings: 26.812 (a signature from base+length, a body from
base+length+`_child_args`), 26.813 (`(void)view` gated on "has no
variable member" where the question is "does the body name `view`"),
26.708 (`_sig_covered` fixed over a body naming `arg_block`).

## Verified

- `edges.situ` gained `relays_on_divided`; all four backends generate it,
  and the generated C compiles clean under
  `-Wall -Wextra -Werror -Wconversion -Wsign-conversion` where before the
  fix it gave the two errors above.
- The control is a `git archive HEAD` export with the same struct
  appended: two errors, so the fault is this branch's and not something
  the surrounding work introduced.
- C++ and Rust compile; Python generates.
