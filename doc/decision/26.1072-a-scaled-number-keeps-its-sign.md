# 26.1072: a scaled number keeps its sign, and the walker reads text numbers

Status: recorded
Date: 2026-11-18
Source: the measurement after 26.1069 of what C's driver answers and the
walker's listing omits -- text numbers were the next class

**The walker answered no text number.** Every backend's driver prints
`name ok= value=` for a text number -- cpio's header is thirteen of them,
HTTP's and SMTP's codes, `edges.measured` -- and `_scalars` leaves them out
as digits rather than bits, with no other list taking them. `_text_numbers`
does now, through the walk's own `parse_digits` and `parse_scaled_digits`.

**Its first comparison found three backends accepting a negative number in
an unsigned member.** `edges.measured.positive` is `scaled u16 ... until
" "`; over `-75 ` C, C++ and Rust answered `ok=1 value=65461`, Python and
the walker `ok=0`. `situ_parse_scaled` built the magnitude's ceiling as
`(uint64_t)(-(min + 1)) + 1`, which for a minimum of zero wraps to zero;
`ceiling - digit` then wrapped as well, so the per-digit bound passed every
digit, and nothing checked the range afterwards. C++ calls C's. Rust's
`parse_scaled` is the same arithmetic, which in a debug build is an
overflow panic on hostile input rather than a wrong value. The four-way
compares all four on every draw and would have caught it; its seeded draws
never held a minus sign before a scaled unsigned member, and the walker's
did.

The same subtraction wrapped wherever the ceiling is below a digit -- and
`situ_parse_uint`, under every fixed-width and delimited integer text
number, had it too: `value > (max - digit) / radix`, which for a `max`
below fifteen admits any digit at all. `9` read into a `decimal u3` and
`F` into a `hex u2` in C, C++ and Rust, and `validate` passed the message;
Python refused both. No corpus schema holds a text number that narrow, so
no sweep had asked.

## The rule

- In C's and Rust's `parse_scaled` a minus sign before an unsigned member
  leaves a ceiling of zero, admitting `-0` alone -- the spelling Python and
  the walkers already read as zero -- and each digit is checked against
  the ceiling before the subtraction that could wrap; `parse_uint` checks
  the digit against `max` the same way.
- The walker lists every text number that is a member: `ok=1 value=N`, or
  with `exp=` for a scaled one, and `ok=0 value=0` where the digits are not
  a number or the number is outside the member's range -- the
  `DIGITS_VALID` row's ceiling, which `validate` already read and the
  listing did not: put in the corpus, `edges.narrow_text` showed the walk
  reading `4` into a `hex u2` once the backends refused it.
- `edges.narrow_text` holds a `decimal u3` and a `hex u2`, so every sweep
  draws digits past their range.

## Measured

`test_a_scaled_number_keeps_its_sign` puts `-75`, `-0`, `7`, `75.5` and
`65536` to all four; with C's runtime reverted it fails on `('c', '-75 ',
['value ok=1 value=65461 exp=0'])`, with Rust's on the same line for
`rust`. `test_all_four_refuse_a_digit_wider_than_its_member` holds the
narrow case, failing on C's runtime with the old check. The walker sweep then agrees with C on every text number over 60
schemas.
