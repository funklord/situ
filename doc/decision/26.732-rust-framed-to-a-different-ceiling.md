# 26.732: Rust framed to a different ceiling

Status: recorded -- fixed, and the comparison that found it is in the suite
Date: 2026-10-29
Source: `project.md` section 26

**The framing layer had no cross-backend witness at all.** 26.725 measured
that `situc/codegen/differ.py` -- the differential comparing all five
spellings of the accessors over the corpus, and the source the C++ fuzz
harness is built from -- mentions neither `required` nor `framed`. And the
two corpus prefix sweeps check each backend against PROPERTIES rather than
against the others: two backends can both be monotone, both progress, and
still disagree about the number.

Seven of this function's records in two weeks are a quantity computed in
two places from two things, and nothing was asking whether the four places
agreed.

## What it found, first run

    pickle.situ      `pickle_wstring`   fill 0xFF  have=4
    png.situ         `chunk`            fill 0xFF  have=8
    sqlite.situ      `table_leaf_cell`  fill 0xFF  have=18
    edges.situ       `oob_inner`        fill 0xFF  have=4
    edges.situ       `varint_driver`    fill 0xFF  have=9

      C = 4294967295   C++ = 4294967295   Python = 4294967295
      Rust = 8589934594

`4294967295` is `UINT32_MAX`, and the other three saturate there
**deliberately**: 26.651 is that a `u32` length of `0xFFFFFFFF` once
answered `0x80000004`, two gigabytes a caller can actually satisfy and
then be handed a body truncated from the four declared. Saturating at the
type's maximum makes the answer a recognisable refusal rather than a
plausible one.

Rust carries the running total in a `usize`, and `saturating_add`
saturates at `usize::MAX`. `oob_inner` is the arithmetic in one line:
`4 + 0xFFFFFFFF` is `0x100000003` in a 64-bit `usize`, which is
`4294967299`.

**And the divergence depends on the pointer width**, which is worse than
either answer. On a 32-bit Rust target `usize` is 32 bits and this would
have agreed with the other three, so a schema means one thing on an
embedded target and another on a desktop -- in a backend chosen for
freestanding work.

## The fix

`situ_rt::need` and `situ_rt::need_mul`, mirroring `situ.h`'s
`situ_need_u32` and `situ_need_mul_u32`: saturating, with the ceiling at
`u32::MAX` rather than at `usize::MAX`. Every `saturating_add` and
`saturating_mul` in the framing emitters' output becomes one of those, so
the four spellings line up literally rather than nearly.

`usize` stays the carrier type. Narrowing `Framing::Need` to `u32` is a
public-interface change and nothing needs it: what the four have to agree
on is the number, not the width of the box it travels in.

## The comparison

`test/unit/test_four_backends_frame_alike.py`, parametrized per schema:
every struct whose `required` takes bytes and nothing else in all four
backends, four fills, prefixes 0 to 32, with each backend's answer
sequence read back and compared token for token. 40 of the 46 schemas
contribute, 221 structs and 884 (struct, fill) sequences.

It is deliberately NOT a second copy of the property sweeps:
`test_required_over_the_corpus.py` owns the exact-size allocations and the
sanitizers, which is where a missing bound is caught, and this owns
agreement. **Two backends agreeing wrongly is what this cannot see**, and
the properties are what see it. The two together are the pair.

`test_a_counted_run_is_framed.py` holds a third and different claim --
that each backend HAS a framing walk, structurally, over one hand-written
shape. This asks what they answer, over the corpus, numerically.

## The instrument lied first, which is now four runs in a row

The first version reported **zero differences over zero sequences**. The C
symbol is `situ_<name>_required` and the C++ class is `<name>`, so the
intersection of the two name sets was empty, every loop body was skipped,
and the summary line said what a clean run says.

That is why this file's non-vacuity companion counts schemas, structs AND
sequences rather than asserting the mismatch count is zero. A count of
zero mismatches is what both a correct tree and a broken detector print.
