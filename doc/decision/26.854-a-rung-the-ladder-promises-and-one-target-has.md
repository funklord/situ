## What the walk measured

Section 1 says how much of a schema becomes code is the consumer's choice:
`situc build --layer` runs from `view` up to `drive`. Asked of the CLI and
then RUN -- six rungs against four targets, `example/dns` at each --
the output sizes are:

| layer | c | cpp | rust | python |
|---|---|---|---|---|
| `view` | 12458 | 11823 | 10078 | 8467 |
| `edit` | 17839 | **11823** | **10078** | **8467** |

| `drive` | 31710 | 21061 | 19373 | 15252 |

Every rung grows every target except one: **`edit` adds nothing to C++,
Rust or Python.** Not approximately nothing -- the directories are
byte-identical to `--layer view`'s, file names included, which
`test_a_rung_absent_for_a_target_says_so.py` now asserts.

## Why, and the half that is not a gap

Rung 2 has two halves and only one is lopsided.

**The read half is symmetric.** `edit.py` exists in all four backends and
emits owned decode against caller backing; for `dns` it emits nothing in
all four alike, every member having to be fixed-size for it. No asymmetry
and nothing to report.

**The write half is C only.** `situc/codegen/c/build.py` is the
append-only builder of 26.610 and has no sibling under `cpp/`, `rust/` or
`python/`. `cli.py` guards it with `if args.target == "c"` and says why in
a comment: "the write half of the same rung, and C only so far."

## The finding is the silence, not the scope

That comment states the principle the dispatch applies one struct at a
time: *a rung is absent rather than defaulted where the schema states
something it cannot hold to*. `cli.py` prints "no builder for `x`" and "no
owned form for `x` at any rung" for exactly that reason -- a caller who
asked and found their struct missing would conclude the generator was
broken.

**The TARGET's absence is the same sentence about a different subject, and
it was the one left silent.** A Rust consumer typed `--layer edit`, got
rung 1, and had no way to tell a rung they were given from one that does
not exist for their language.

So the notice names the rung, the target, and where to read: decision 0032
for the ladder and 26.610 for the builder's shape. The gate asserts the
notice, asserts C does NOT get it -- a notice printed for every target
would pass the first half and say something false about C -- and asserts
the CLAIM the notice makes, by comparing the two directories file by file.
That last one fails the day a backend gains a builder, which is the point:
a notice is a claim about generated code, and this tree has had to correct
three unchecked claims in a week.

**Control**: with the notice neutralised, the three naming tests fail and
the four others pass.
