# 26.762: An encoding source is not a nested namesake

Status: recorded -- fixed
Date: 2026-10-30
Source: `project.md` section 26

    struct inner { other_charset says until ";"; }
    struct s {
        inner             h;
        document_charset  says  until ";";
        u8                body[]  until "\0"  [encoding = from(says)];
    }

`wellformed` resolves `from(says)` against the members `s` declares
before `body`, which reach into a region or an arm and never into a
nested struct's type. All four backends found the source by matching the
LAST path component over every entry, and `s.h.says` comes before
`s.says` in layout order. So they took `other_charset`, found no arm
spelled `us-ascii`, wrote no check for it, and accepted `x;us-ascii;`
followed by `c3 a9` -- a body that is not ASCII under a declared ASCII --
in all four. With the field renamed the same message is refused.

The packer looks the source up by its path, `<struct>.<source>`, so the
image and both walkers were right. Four agreeing backends hid it, which
is why the walkers exist.

`traverse.encoding_source` is now the one lookup: the entry of that name
that is not under a nested struct's type or a run's elements. Each
backend asks it.

Found by the lens 26.760 gave -- a lookup keyed on one component of a
path -- applied to the emitters' other path-component lookups. The rest
were sound: a register's fields are flat, and the same match in the
emitters' other places names nothing a nested struct can shadow.

## Tests

`test_an_encoding_source_is_not_a_nested_namesake.py` holds the three
verdicts all four give. With the nested-struct exclusion removed, the
non-ASCII body is accepted again and the test fails.
