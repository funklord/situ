# 26.963: the dissector follows a byte-order marker

Status: recorded
Date: 2026-11-12
Source: describing a pcap file (26.961) and looking at it in the dissector

**Every member an `endian_marker` governs was shown big-endian, whatever
the marker said.** A little-endian TIFF -- most of them -- showed `magic`
as 10752 where the file says 42; a little-endian pcap file showed
`version_major` as 512. Lengths read the same way, so a pcap record's
`data` was sized by a byte-swapped `incl_len` and the rest of the file
was shown as one raw run. The four backends and both walkers have
followed the marker since 26.576; the dissector was the one reader left,
and `_tlv_number` said so in a docstring ("which this does not follow")
while every other site said nothing.

The comparison against the walker could not see it: it draws random
packets, and a random marker almost never equals the `little` literal,
so both read big-endian and agreed.

**`_little` answers the question once.** `true` or `false` where the
schema decides; where a marker does, a Lua expression reading the marker
big-endian -- as every reader reads one -- against its literal, or, for a
struct handed its order (26.961), the argument against it. Every site
that chose `add`/`add_le`, `le_uint`/`uint` or a `situ_uint` order now
asks it, and a member shown with a marker's order picks its method as it
is shown. Where the marker is somewhere a site cannot read -- an element
walked backwards from its end, a TLV tag -- the site declines as it does
any read it cannot make.

## Verified

`test_the_dissector_follows_a_byte_order_marker.py`: a TIFF header and a
pcap file in each order, through the harness, values worked out by hand;
and a little-endian pcap file inside a capture through real tshark,
whose two records' `incl_len` read 14 and 4 -- the handed argument
reaching the nested dissector, which the harness calling each function
itself cannot show. All three fail with the change reverted.
