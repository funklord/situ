# 26.681: A declared cap was not checked after a dynamic member

Status: recorded
Date: 2026-10-23
Source: `project.md` section 26

Reported by bbq-predictor as item 4: `u8 t[remaining] max 2` accepts a
four-byte `t`.

Decision 0059 is explicit about what a cap means -- "such a cap restates a
bound the enclosing format guarantees, so a message exceeding it is
malformed" -- so a longer frame is REFUSED rather than truncated. The
refusal was not emitted.

## The fault

**The struct-level maximum was read as discharging the cap, and it does so
only where the two numbers coincide.** Every backend emits
`view.limit > SITU_X_SIZE_MAX` for a struct with a declared maximum, and
for a `[remaining] max N` run at a STATIC offset that guard is exactly the
cap: the struct's maximum is the fixed prefix plus N.

Put anything variable in front of the run and the two part company:

	struct x { u8 n; u8 d[n]; u8 t[remaining] max 2; }

`SIZE_MAX` is 1 + 255 + 2 = 258, so a six-byte frame passes the struct
guard, `n` is 1, `d` is one byte, and `t` is four bytes against a cap of
two. The guard is not wrong -- it bounds the FRAME, which is a different
quantity from the run.

**bbq's framing of it was right and situ's first reading of that was
wrong.** The report said "after a dynamic member", and this tree's first
answer was that the cap is enforced as a struct-level `SIZE_MAX`. Both are
true; only one of them is an answer, because the question is whether the
struct bound implies the run bound, and it does not.

## The fix

The run's own length against its cap, prepended to the `run_fits` block in
all four backends:

	if (situ_remaining_u32(view.limit, <base>) > Nu) {
		return SITU_ERR_BOUNDS;
	}

`situ_remaining_u32` rather than a subtraction, for 26.675's reason: the
base is a sum of lengths the message chose and may exceed the view.

Gated on `sized_by == "remaining"`, which is the bare form -- the only one
that carries a `remaining_cap`. Asked that way in all four, rather than
through `_count_expression`, which returns a `str` in C and `str | None`
elsewhere: the first spelling of this guard was dead in C alone, for
exactly that reason.
