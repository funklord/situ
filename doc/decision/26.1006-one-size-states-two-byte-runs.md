# 26.1006: one size field states two byte runs

Status: recorded
Date: 2026-11-13
Source: the goal gap -- builder refusals over the example schemas

**ARP could not be built.** `hardware_length` is the length of both the
sender's and the target's hardware address, and every builder refused
`arp_generic` as "`hardware_length` is the stated size of both ... so one
value cannot say both". It can, where the two runs are as long as each
other -- which is exactly the claim the field makes. The refusal guarded
the right thing, two lengths with one field and the last planned winning
silently, and the answer is a check rather than a refusal.

**Now, for two byte runs**: the field is computed from the first, the
second is a span the caller hands over as before, and all four builders
refuse it as a constraint violation unless it is as long as the first.
Runs of wider elements or of structs sharing one count stay refused --
git's pack index counts 20-byte names and 4-byte CRCs with one `count`,
which is a count of elements, not a byte length, and wants its own work.

**Measured.** RFC 826's request for Ethernet and IPv4, "who has
192.168.1.1, tell 192.168.1.2", built byte for byte in Python and C, and a
target address one byte short refused in both. `test_the_four_builders_agree`
reaches `arp_generic`.
