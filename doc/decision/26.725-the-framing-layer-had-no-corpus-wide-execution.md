# 26.725: the framing layer had no corpus-wide execution

Status: recorded -- the sweep is in the unit suite
Date: 2026-10-29
Source: `project.md` section 26

`required` has **seven** decision records against it in two weeks -- 26.683,
26.684, 26.685, 26.686, 26.693, 26.723, 26.724 -- and two of them arrived
from a consumer's fuzzer rather than from here. This asks why, and the
answer is not the one 26.723 and 26.724 wrote down.

## Nothing in the corpus ever called it

Measured 2026-10-29: **`situc/codegen/differ.py` does not mention `required`
or `framed` anywhere.** That file is the differential -- the thing that
compares all five spellings of the accessors over every schema in the corpus
-- and it is also the source the C++ libFuzzer harness is built from
(`situc/cli.py`, `differ.generate(..., "cpp", ...)`). So neither the
corpus-wide comparison nor the corpus-wide fuzzing has ever reached the
framing layer.

What had run this function, in full:

- `test_required_answers_every_prefix.py`, over seven hand-written shapes;
- one `test_every_prefix_of_a_real_request_answers_honestly` per backend,
  over `example/http` and nothing else.

Seven shapes and one real schema, for the function that frames every
message situ describes.

## The buffer was the whole of it, and 26.723 said otherwise

**26.723's and 26.724's records both blame the population, and for 26.723
that is wrong.** `example/ble`'s own `le_advertising_report` reproduces it:

    uint8_t *p = malloc(1);
    le_advertising_report::required(p, 1, need);   /* reads p[3] */

    ERROR: AddressSanitizer: heap-buffer-overflow ... READ of size 1
      #0 situ::le_advertising_report::reports_count()  ble.hpp:620
      #1 situ::le_advertising_report::framed()         ble.hpp:770
      #2 situ::le_advertising_report::required()       ble.hpp:807

at `97d1343`, clean at `a176c43`. **The corpus had the shape all along.**
`num` sits at offset 3 behind a four-byte prefix, and `adv_report` is a
counted run of variable-size records -- the construct `example/ble`'s own
README entry says it exists for.

So nothing was missing from the population. What was missing was ever
handing this function a buffer whose end was real. The one sweep there was
walks every prefix of a real HTTP request out of a `const char req[]` **on
the stack**, where an over-read lands inside another object, answers from
whatever is in it, and reports nothing.

That is the transferable half, and it is `evidence.md`'s shape rather than
this function's: **a bound is only tested by an input whose edge exists.**
A test of a length check that supplies the length from a buffer with slack
behind it has checked the arithmetic and not the bound. The sweep was
right, the population was right, and the allocation was the defect.

## The sweep

`test/unit/test_required_over_the_corpus.py`, parametrized per schema:
every class in the generated C++ whose `required` takes only bytes, every
prefix from 0 to 48, three fills, each prefix in a `malloc` of exactly its
own length, under `-fsanitize=address,undefined
-fno-sanitize-recover=all`.

Measured: 32 schemas swept and 4 skipped for emitting no such `required`,
**14,259 calls of which 7,238 answered truncated**, in 26 seconds.

Two properties are asserted beside the sanitizer, and they are the two a
synthetic buffer can carry honestly: a truncated answer must exceed what
arrived, and `need` may not fall while a message is still incomplete. Not
asserted: that no prefix is reported complete early, because a fill is not
a message and there is no length to compare against --
`test_required_answers_every_prefix.py` owns that over shapes whose whole
message is written out.

**The C++ backend, and that is a choice rather than convenience.** Its
accessors are the only ones that are not lax: a static offset reads
straight through `situ_get_be16` on the invariant that a view has passed
`view()`'s `length >= size_min` guard, and `required` is the one caller
that builds a view without it. So C++ is where a missing bound is a memory
fault rather than a wrong number, which is why 26.723 was C++ only and why
a sanitizer has anything to find. The arithmetic is identical in all four
and Python holds it in the other file.

**Which classes to call is read back out of the header** rather than
derived from the schema a second time, by scanning for the signature that
takes bytes and nothing else. A predicate written in the test would be a
second opinion about which structs are frameable, and the opinion that
matters is the emitter's.

## What it catches, and what it still cannot

Both measured on exports rather than argued:

| commit | the sweep |
|---|---|
| `97d1343`, before 26.723 | **fails on `ble.situ`**, ASan abort |
| `a176c43`, after 26.723, before 26.724 | **passes** |
| here | passes |

So it would have found 26.723 on its own, from the corpus, without
bbq-predictor's report. And **it is blind to 26.724**, which is the useful
half: that fault needs an element whose length carries a `[min]`, and no
corpus schema has one. `ble`'s `data_length` is `[max = 31]` with no
minimum, and it is the corpus's only counted run of variable-size records.

That is now a measured gap rather than a suspicion, and the next piece of
work: `example/` wants a real format with a counted run of records whose
element length carries a declared minimum. A standard MIDI file is the
candidate -- `ntrks` at offset 10 of a 14-byte header, then that many
`MTrk` chunks whose data length is at least three bytes, because a track
must end with the End of Track meta event.

## What this does not claim

It sweeps one backend and one layer. The differential's silence about
`required` is recorded above as a fact and not fixed here: teaching the
corpus differential to compare framing answers across all five spellings
is a larger piece of work than this sweep, and it is the thing that would
make the framing layer as well witnessed as the accessors already are.
