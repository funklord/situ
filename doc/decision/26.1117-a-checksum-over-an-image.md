## What FS2's image CRC is

Measured from openmlx4's `src/fs2.c` (`fs2_verify_walk`, `verify_boot2`,
`verify_section`), a port of mstflint's `Fs2Verify`: one CRC16 over

- the 56-byte image header, with the CRC's own sixteen bits (bits [15:0] of
  the big-endian dword at 0x20) read as `0xFFFF`;
- BOOT2, its stored CRC dword included -- BOOT2's successor is computed,
  `offs + size * 4 + 16`, so it follows the header directly;
- every section the chain reaches, in chain order: its 16-byte header, its
  data, and its CRC dword (the computed one, equal to the stored one in a
  section that verifies). A section's successor is a POINTER read from its
  header (`gph[3]`), so nothing in the format says the sections are back to
  back.

checked only where an image-info section carries a MicVersion tag, and
waived when the GUIDs are blank -- policy, which stays openmlx4's (14.1
puts the decision to check with the caller; a `when` can state it).

## The three parts, each gated

**A. Its own bytes read as a constant other than zero. Already built.**
Decision 0029's `[self_as = N]` carries a value, not a flag, because tar's
header sum reads its own bytes as spaces. FS2's slot is `u8 crc[2]` at
0x22 with `[self_as = 0xFFFF]`. Nothing to build, nothing to read.

**B. A tag inside a nested struct covering bytes outside it. Go, in the
shape that passes the cost gate -- see "Part B, measured" below.** Other
formats need it: GPT's header carries the CRC32 of a partition-entry array
that lives elsewhere on the disk; U-Boot's legacy image header carries the
CRC32 of the payload that follows the header. Both are, like FS2, a header
struct holding a check over bytes its parent places. Today a tag covers
members of its own struct, or `before` it; a schema can only describe these
by flattening the header into its parent, which loses the header as a
type. The readable form is a tag declared where both ends are in scope --
in the nearest struct holding the header and what it covers -- naming the
nested field that stores it, the way an `invariant` already names paths
across structs. Cost: a tag whose storage is a nested path, in the four
backends, both walkers, `verify` and the editor's recompute, held to one
another by the differential harnesses as every tag is.

**C. Coverage gathered link by link along a chain placed by `at`. Not
yet: only FS2 is known to need it.** No other format in the corpus, in
openmlx4's or fuzznet's, or that this record's author knows, sums along a
linked list of sections. And it may not be needed for FS2 either: if real
images keep their sections back to back, the chain covers one span from
the header to the end of the last section, and B with a span says it. That
is a measurement on real firmware images -- openmlx4 has them, situ does
not -- so it is asked of openmlx4, and C is built only if a real image has
a gap the CRC skips.

## Part B, measured

Mapped across the tree before building: EVERY layer scopes a tag's
coverage to the struct that declares it -- `covers` names regions of that
struct, the layout keys coverage by the tag's owner, the image's tag row
restricts `first`/`last` to the owner's placements, C++, Rust and Python
emit a tag's helpers only in the struct that owns it, and both walkers, the
editor and the dissector measure the span within one struct's view. A tag
naming members of an enclosing struct would rework all of them: it fails
the cost gate.

One clause already reaches past its struct, and every layer carries it:
`covers(before)`, every byte of the MESSAGE ahead of the tag (26.1050) --
message-relative, not member-relative. Its two twins say what the formats
above need, at the cost of a second branch beside `before`'s at its 33
sites:

- **`covers(after)`**: every byte of the message from the end of the tag's
  own struct to the message's end. U-Boot's data CRC, stored in a nested
  header and covering the payload that follows it.
- **`covers(message)`**: every byte of the message, the tag's own read as
  its `[self_as]` (which is then required). FS2's image CRC, from byte 0,
  if real images keep their sections back to back (part C's question);
  `[self_as = 0xFFFF]` is part A.

The message's end is the caller's frame, as `before`'s start is the
message's first byte: a file with bytes past the image is framed by the
caller (`--length`, a view's limit). GPT's partition-array CRC, over bytes
at another place on the disk, is not described by either and stays out.
Readability: one word in the clause `before` already uses.

## Part B, built

In the parser, wellformedness (`message` needs `[self_as]`; `after` needs
its struct to have a fixed size, refused in `resolve`), the layout's
staling (a `message` tag is staled by every member of every layout holding
it, an `after` tag by the members placed behind its struct), the image's
tag row (flag bits 3 and 4; an older reader sees them and declines), both
walkers (`report.message_span`, and `situ_walk_sum_prefixed` with the
struct's own extent), all four backends' `covered`, `compute` and `check`
(Rust's `_in(msg)` form, as `before`'s), the differential's asks, and the
editor, which recomputes a header's `after` or `message` CRC when a byte of
the parent it covers is written. Every reader's span and sum is held to
zlib's value in `test_a_checksum_covers_after_and_the_message.py`, and
restoring the C walker's old flag mask fails its two cases.

The dissector declines both, as it declines a prefixed checksum: its
checks mark a span by the members it passes, and these have none. It
shows the field and does not say whether it holds.

## Not decided here

The `when` that gates the check (MicVersion present, GUIDs not blank) is
FS2's policy and already expressible; nothing here changes it.
