# 26.848: the placeholder that reached three consumers

Status: recorded -- the name mismatch of 26.839 is fixed at its source,
and so is the defect it was hiding: a reserved field inside a variant arm
is enforced in all six readers now. One thing beside it is left and said
so below -- a PAD inside an arm, declined in agreement by all six
Date: 2026-11-03
Source: 26.839, which recorded this as a layout decision left unfixed, and
`test_a_refusal_says_what_the_member_is` on `edges.situ`

## What changed the calculus

26.839 found that the layout records an anonymous arm member as
`s.body.arm` while the placement it creates is `s.body.<reserved0>`, made
both `gen-checks` backends decline such a field rather than emit a check
about bytes nobody had selected, and left the mismatch alone: a
placement's name is a layout decision with consumers beyond `gen-checks`.

**The third consumer is what moved it.** With `arm_holder` in the corpus,
`test_a_refusal_says_what_the_member_is` fails:

    arm_holder.arm: the message names `arm_holder.body.arm`, which is
    not a member of `arm_holder`

A diagnostic citing a member the struct does not have, shown to the
author. `_arm_name`'s own docstring had already called the fallback "a
placeholder reaching a user-facing artifact, which invariant 16 is the
general form of: a label is not an identifier, and neither is a
fallback" -- and then returned `"arm"` for the one arm form it did not
know about.

So: three consumers, each wrong differently. `gen-checks` emitted a check
for bytes nobody had selected; the variant-arm census counted the arm
nowhere; a refusal named a non-member. **The third is the one a user
meets, and that is what makes it a layout fix rather than a guard.**

## The fix

The arm's member is read from the placement the layout creates, after
`arm_extent` has created it, rather than predicted:
`<reserved{n}>` is numbered as the layout walks, so guessing `n` at the
recording site would be a second answer to a question the layout already
answers.

All three consumers came right at once, which is what a root fix looks
like: the refusal names `arm_holder.body.<reserved0>`, `enclosing_arm`
finds the arm, the census gained the one scalar arm its annotation had
**predicted** it would gain, and `gen-checks` selects the arm and emits
the check it had been declining.

`traverse.inside_an_unresolved_arm` stays as the backstop it now is. Of
the corpus's placements it still answers true for six, and **every one is
an array element** -- the arm names `recs` and the placement is `recs[]`
-- which the emitters name more precisely, so the array branch is asked
first and the arm branch keeps no input of its own.

## The defect it was hiding

With the arm selectable, `gen-checks` emits the check -- and **the check
fails**:

    raw[0] = 0x01        # select the arm
    view.validate()      # passes
    raw[1] = 0xff        # break the reserved field
    view.validate()      # does NOT raise

**A reserved field inside a variant arm is not enforced by any of the four
backends.** `validate` carries the bounds check and nothing else: Python's
body is two lines, and C's `situ_s_check` likewise. Measured for all four.

**And by ONE mechanism in six places, which is not what this entry first
said.** It claimed three backends drive validate from `own_entries` and
need the loop widened, with the discriminant guard as "the real work".
Both halves were wrong, and re-measuring before fixing is what found it:
all four backends already have an `_arm_member_checks`, reached through
the variant rather than through the validate loop, and it already carries
the guard -- the arm's own accessor refuses `VERSION` for the arm that is
not present, which is the gate. What it asks is the enum's membership and
the attribute bounds. **It does not ask the reserved policy**, and in C
the reserved branch of `_checks_for` sits BELOW the dotted-path test that
sends an arm to that builder, so it cannot fire for one.

**And the sixth reader is the packer, which makes it six and not four.**
Both walkers read their checks from the image, and the image is written
in two passes: a member pass over `own_entries`, and a second narrow pass
over `rstruct.entries` added by 26.418 for exactly this case, which
writes "the two families the four backends check on an arm and nothing
else" -- a pinned run, a delimiter, a run's span, a scalar's bounds, an
enum's membership. Reserved is not among them, and the pass ends
`if kind is not traverse.Check.CONSTRAINED: continue`, which a reserved
placement does not survive. Measured directly against both walkers:

    struct arms { u8 kind;
                  variant body switch (kind) {
                      case 1:  reserved u8 [must_be_zero];
                      default: u8 other; } }

    01 ff   walker (python) 0   walker (c) 0

...and with the same field OUTSIDE an arm, the same two walkers answer 2
(Constraint) for the same byte. So the gap is not that the walkers do not
enforce reserved; it is that the image carries no row for one an arm
selects. **The guard is already the reader's**, which that pass says in
as many words, so the walker half is a row rather than a mechanism.

**The population, measured across the corpus**: ten reserved members sit
inside a variant arm, in four schemas. Nine of them are inside a STRUCT
arm -- icmp's `frag`, six of id3's `present`, mqtt's `connect` and
`connack` -- and every one is enforced, through that struct's own
`validate`, which `_arm_validation` calls. The tenth is the only reserved
FIELD arm in the tree, `edges.arm_holder`, added for this. That is why
nothing had found it: the construct the gap needs did not exist until the
day the gap was named.

Section 8.8 says what that costs: reserved bits are malleability control,
not pedantry, and a receiver that ignores them lets a sender vary bytes
the format calls fixed -- a bypass primitive in anything authenticated.
Here the bytes are free in every language situ generates.

**Four steps were each necessary to see it**, and that is the entry's
lesson rather than the defect: a corpus construct nobody had written, a
name mismatch that made the arm unnameable, the fix that made it
nameable, and only then a check that could be built at all. Any one of
them missing and the gap stays invisible -- which is why the construct
went into the corpus in the first place, and why a decline is worth
writing down rather than leaving as silence.

## Fixed, and what the fix had to stop short of

One clause in each of four `_arm_member_checks`, one row in the packer's
arm pass, two kinds added to the C walker's `arm_constraints` switch, and
one shared `reserved_want` so that five derivations of `must_be_one`'s
width do not become five answers. The Python walker needed nothing: its
`_arm_constraints` already read `MUST_BE_ZERO` and `MUST_BE_ONE` from the
rows, kept there deliberately as "one copy of the member path's decision
rather than a second one that has to be kept in step with it" -- so a
decision taken for tidiness turned out to be the half that was already
right.

**Three controls, each neutralised and watched to fail**: the packer's row
alone fails the two walker tests and leaves the four backends green; the
four emitter clauses together fail the two backend tests and leave the
walkers green; the C walker's two switch cases fail the two walker tests.
Six readers, two policies -- `must_be_zero` and `must_be_one` on the same
byte under two arms of one variant -- in
`test_a_reserved_field_in_an_arm.py`.

Across the corpus the change is one site per backend, all four in
`edges.arm_holder`, and one image longer by sixteen bytes: 43 schemas
packed before and after differ in `edges` alone, and `edges.situ.map` and
`edges.situ.wire` are byte-identical.

### A pad arm, which is where it stops

`pad_to(4)` is legal inside an arm and all four backends checked it the
moment they asked the policy at all -- and the check was **worse than
silence**. The pad spans three bytes; the arm's accessor reads ONE,
`self._read(1, 1, ...)`, while bounds-checking three. So the comparison
caught a nonzero first byte, missed the other two, and `01000001` was
accepted by all four. The packer meanwhile excluded pads, so both walkers
said nothing -- four readers half-checking and two silent, which is the
disagreement the differential exists to find, introduced by the fix for
the gap beside it.

`reserved_want` declines a pad now, for the reason the packer's member
path already gives in as many words: "the scalar `must_be_zero` reads a
fixed byte and would check one the empty pad does not own". The run form
that WOULD answer is the packer's kind 13, which scans the aligned span,
and porting it to an arm needs a reader for it in both walkers -- neither
`_arm_constraints` nor C's switch renders a span kind for an arm today.
**So a pad inside a variant arm is unchecked by all six, deliberately and
in agreement**, and the test asserts that agreement rather than today's
answer, so that teaching four backends without the other two goes red.

**And the one-byte read is its own defect, recorded and not fixed**: an
accessor that names `<pad>` and hands back one byte of it is wrong for any
caller, not only for a check, and the bounds test one line above it knows
the span is three. It is an accessor shape with consumers beyond this, and
the corpus has no pad arm to catch it -- which is this entry's own lesson
arriving a second time.

### What the first version of this entry got wrong, twice

It named `own_entries` in three emitters and called the discriminant guard
"the real work"; both were wrong, and the guard already existed. Then the
fix's own first draft asserted in a comment that no backend checks a pad
arm, at the moment its sibling clause had taught all four to. Two
confident claims about what other code does, a day apart, in one entry --
and both were cheap to check and expensive to carry.
