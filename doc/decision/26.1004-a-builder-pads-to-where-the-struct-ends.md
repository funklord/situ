# 26.1004: a builder pads to where the struct ends

Status: recorded
Date: 2026-11-13
Source: the goal gap -- the builder refusals over the example schemas,
re-tallied after 26.1003

**A netlink attribute and a tar entry could not be built.** Both end in a
pad whose length is an expression of fields before it --
`align_up(nla_len, 4) - nla_len`, `align_up(header.size, BLOCK) -
header.size` -- and every builder refused it: the expression calls
`align_up`, so it cannot be run backwards to solve for a field.

Nothing needs solving. When the writer reaches the pad, every byte before
it is down, so the struct's own `_required` -- the reader's framing --
says where the struct ends, and the pad is zeros to there. That is a role
of its own, `FRAMED`, in all four builders, each calling its own
language's `required` over what it has written.

**Only a trailing pad, in a struct that frames itself.** `_required`
measures the whole struct, so its answer is this pad's end only where
nothing follows it; cpio's pad, which a data run and a second pad follow,
stays refused. And only a pad the policy lets be zero.

**Measured against outside truth.** Netlink attributes of payloads 0 to 8
bytes: `nla_len` counts header and payload, and the attribute is padded to
`NLA_ALIGN(nla_len)` (netlink.h:1319) with zeros. A ustar entry for data of
0, 1, 511, 512 and 513 bytes is byte-for-byte what Python's `tarfile` writes
for that member, header included. C under the strict warnings, and a short
capacity refused. `test_the_four_builders_agree` now reaches `nlattr` and
`ustar_entry` and the four agree.
