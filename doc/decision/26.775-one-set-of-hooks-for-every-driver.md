# 26.775: One set of hooks for every driver

Status: recorded -- built in all nine drivers
Date: 2026-10-31
Source: `project.md` section 26; asked by the holder

The holder asked whether the scheduler tier -- the nine drivers of 0033 --
has enough callbacks and insertion points to be used fully without
standing in a situ user's way, and whether equivalent callbacks carry the
same names in every form of driver. The names did agree: `on_reply` and
`on_expired` in all nine, `on_done` in Qt. What they carried did not
serve the user, measured on `example/dns`:

- **`on_reply` passed the caller's handle and not the reply.** The driver
  received the datagram, matched it and discarded the bytes -- a stack
  buffer the drive machine keeps nothing of. A user learned that query 7
  was answered and could not read the answer without writing their own
  loop.
- **Everything that was not a correlated reply vanished.** A datagram too
  short for the reply's view, a duplicate, a reply after its exchange
  expired, one nobody asked for: dropped, with no hook.
- **Every failure was `SITU_ERR_BOUNDS` with `errno` gone**; io_uring
  reposted a failed receive forever and tokio swallowed one, where the
  readiness drivers ended the loop.
- **The C drivers could not be stopped**, and Qt's `stop()` disarmed
  without completing, so `on_done` never fired and `qt_*_run`'s pump was
  never deleted.
- **Every receive buffer was 2048 bytes and nothing checked for
  truncation**, so a 4096-byte EDNS response was parsed cut short.

## The hooks

The same six names, the same order, the same meaning in every driver:

| hook | when | carries |
|---|---|---|
| `on_reply` | a reply answered an exchange | the caller's handle, and the reply as a view |
| `on_unmatched` | a reply answered nothing waiting | the view, and what `on_message` said |
| `on_malformed` | a datagram that is not a reply | the bytes, and the view's refusal or BOUNDS |
| `on_expired` | exchanges ran out of retries | the count |
| `on_error` | the loop is ending on a failure | the result, and the system's reason |
| `on_done` | the loop is over | the result -- exactly once, on every path out |

and `stop`, which ends the loop at the top of its next turn with success,
leaving what is still in flight in the drive machine for a later run.

Each language spells the container its own way, because each has an idiom
the others lack: C a `situ_drive_hooks_t` of function pointers with `user`
and a `volatile int stop`, shared by all six C drivers; C++ a
`qt_<relation>_hooks` of `std::function`s, with `stop()` on the pump;
Python a `<relation>_hooks` class whose methods default to nothing, with a
`stop` attribute; Rust a `<Relation>Hooks` trait with default methods and
`stop()`, implemented for `()`. The reply is the backend's own typed view
where it has one (`dns_header`, `EchoMsg`), and `situ_view_t` in C. It
views the driver's buffer, valid for the call: copy what you keep.

## Decisions

- **One C type for six drivers, generated and guarded**, beside the
  generated `situ_io_t` it accompanies -- not in `runtime/c/situ.h`, which
  carries no driver type, and not one typedef per facility, which is how
  the names could have drifted. Guarded by `SITU_DRIVE_HOOKS_T` because it
  is spelled `situ_` and two driver headers may meet.
- **The receive buffer is the largest datagram, not the reply's size.**
  The reply struct can describe only the front of a datagram --
  `dns_header` is twelve bytes of a DNS response -- so it bounds nothing.
  65536 bytes, and a datagram longer than that is reported through
  `on_malformed` rather than read: `recvmsg` and `MSG_TRUNC` in the five
  readiness drivers and Qt, `MSG_TRUNC` as the receive flag in io_uring
  (whose result is then the whole length), and a full buffer in Python's
  `recvmsg` flags and Rust's receive.
- **A failed receive ends the loop in all nine**, through `on_error` with
  the system's reason. io_uring and tokio now agree with the other seven.
- **The fd drivers share one loop.** `driver.loop` holds the stop check,
  `step`, the receive, the delivery and the single exit that calls
  `on_error` and `on_done`; each of the five supplies only its setup, its
  wait and its teardown. The hooks agree by construction rather than by
  five copies agreeing.
- **The drivers remain optional.** A program with its own event loop calls
  the drive machine directly -- `send`, `on_message`, `step` -- which owns
  no socket and no clock (0033). The hooks are for the program that wants
  situ to own the loop, not a replacement for that.

This changes every driver's public signature. Nothing outside this tree
calls a driver: hull uses situ's C accessors, not its drivers.

## Tests

`c_driver_harness.py` puts one set of cases to all six C drivers over a
real socketpair, and `test_qt_driver.py`, `test_asyncio_driver.py` and
`test_tokio_driver.py` put the same cases to theirs: a reply after
retransmissions read back through its view, an expiry, an unmatched
reply, a short datagram, an oversized one (not over UDP, which cannot
carry it), `stop` from a hook, and an unusable descriptor where the
facility can see one -- each reaching its hook, and `on_done` once. With
the truncation check removed the oversized case fails. The tokio test
skipped on any build failure, so a driver that stopped compiling read as
an offline machine; it now skips only when the crate cannot be fetched.
