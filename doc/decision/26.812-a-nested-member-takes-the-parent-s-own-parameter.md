# 26.812: a nested member takes the parent's own parameter

Status: recorded -- built for a single nested member; a run is still refused
Date: 2026-11-02
Source: `doc/decision/0068-a-parent-supplies-a-child-s-arguments.md`

0068 step 5 is an argument that hands on one of the parent's OWN
parameters, rather than a constant or a parent field. Its open list said
it "was not started" and named the cost. This builds the half where the
member is a **single nested struct**; a run of them stays refused, with
the refusal narrowed to exactly that.

## Why a parameter is different from a field

A parent FIELD is read out of the view, so every helper that measures the
child already had what it needed. A parent PARAMETER is not in the
message: C carries it as a trailing function parameter, so it has to be
threaded into each helper that measures or places the child, and into
every call to one.

C++, Rust and Python needed nothing -- the parent's argument is already a
member of the view they emit -- and all three were checked rather than
assumed, because four backends that disagreed would mean a schema means
four things.

## The defect, which is the week's shape for the fourth time

**The signature and the body were decided from different text.**

`_member_reads_arguments` asks the member's base and length expressions.
The bodies whose signature it decides are built from those AND
`_child_args`. For

    struct relay { parameter u8 block [stream];
                   negotiated(block = block) one; u8 after; }

the base is `0u` and the length is a call into
`situ_relay_one_extent_from`, so neither names `arg_block` -- the
argument appears only INSIDE that helper, through `_child_args`. The
predicate said no, the signature took no tail, and the body embedded
`arg_block` anyway:

    error: 'arg_block' undeclared (first use in this function)

twice. That is the compile error `_argument_tail`'s own note promises
instead of a wrong byte, and it is worth saying that the note lists the
shapes still spelling `situ_view_t view` alone -- a run of variable
structs sized by an argument, and a delimited or `while` run's stride
helpers -- and **this pair was not on the list**. The list was a true
statement about what had been looked for.

## Two wrong fixes, kept because both looked right

**Widening `_member_reads_arguments` to read `_child_args` too.** It
fixes `_view` and breaks `_count`: the predicate is shared with the
member's other accessors, and a run's `_count` reads the count field
rather than the argument, so widening made its call sites pass a tail
`_count` does not take -- three `too many arguments to function` errors.
A predicate shared by functions with different bodies cannot answer for
all of them.

**Asking that same predicate at the nested-extent call site.** It
recursed until Python ran out of stack: the predicate renders the length
expression, a nested member's length expression renders a call into
`_extent_from`, and deciding that call's tail asked the predicate again.

So `_hands_own_argument` answers only what the three helpers need --
whether what this member hands its child names one of this struct's
arguments -- from `_child_args` alone. It is cycle-free by construction,
because it never asks the length renderer, and `_handed_tail` and
`_handed_call` are its paired signature and call-site forms so the two
cannot disagree.

## Measured

In C, on a five-byte message with `block = 3`: the child's extent is 3,
`after` is placed at 3 and reads 0x7F, and the child's own view has
limit 3. Python answers the same through `relay.at(msg, 0, 5,
arg_block=3)`. C++ and Rust compile clean, Rust under `-D warnings`.

`edges.situ` carries `relays_on`, and the grown header compiles under
`-Wall -Wextra -Werror`.

## What is not built, and why it is still refused

A RUN of such members. Its `_count`, `_at`, `_span_from` and `_fits`
reach the argument through a second set of helpers; `_child_args` has 21
call sites in C's emitter. The run case was written into `edges.situ`,
measured to need them -- one `arg_block undeclared` and one `too many
arguments` in each of three functions -- and taken back out rather than
shipped half done. The gate refuses exactly `member.array is not None and
_reads_a_parameter(...)` now, so an unplumbed path is a `situc build`
refusal rather than a compile error in somebody's project.

A struct naming itself, and one that can contain itself through any
chain, are the other half of step 5 and are unchanged: a recursive child
is measured with a depth, and handing arguments down that path is its
own piece of work.
