# 26.673: A truncated checksum cannot verify, in any of the four backends

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

Found while verifying `example/id3`'s bill for 26.672. The bill is sound
and is dated; the probe written to test it compiles a schema no example
contains, and that schema generates a check which cannot pass.

## The reproduction

    endian big;
    bit_order msb_first;

    codec crc32 {
            kernel = polynomial(width = 32, poly = 0x04C11DB7,
                                init = 0xFFFFFFFF, xorout = 0xFFFFFFFF,
                                reflect);
    }
    impl crc32 derived;

    struct frame {
            authenticated s {
                    u16 count;
                    u8  body[8];
            }
            checksum u8  sum[1] covers(s) is crc32 [truncated];
    }

All three adopter gates pass -- `map --check`, `wire --check` and the
committed map are current -- and all four backends generate. The C
round trip, compiled and run:

    compute rc=0 want=0x6d1b11a6
    stored byte=0xa6
    check rc=8 (0=OK)

8 is `SITU_ERR_CHECKSUM`. The message was computed and stored by the
generated API and is then rejected by the generated API.

**It is unsatisfiable rather than mismatched**, which is the part that
matters: no byte the caller could store makes it true.

    return (uint32_t)situ_base(view)[crc_at] == want

The left side is at most 255 and `want` is the full 32-bit CRC. C++ and
Rust generate the same widening compare (`std::uint32_t{raw().base[...]}
== want`, `u32::from(held) == want`); Python spells it differently and
does the same thing --

    stored = int.from_bytes(bytes(self.sum), "big")
    found  = self.sum_compute()
    if stored != found:

Four emitters, one behaviour, so this is a missing concept rather than
four slips: nothing in the layout carries "the stored width is less than
the codec's, so compare only that much."

## Where it comes from

0038 made truncation *sayable*. It added `tag_bytes`, made a narrow field
an error unless it carries `[truncated]`, and put the attribute on a tag
field "and nowhere else" -- where `ast.TagField` is both `tag` and
`checksum`, as `wellformed.py` says in as many words: "only a `tag` or
`checksum` has a width a codec has an opinion about".

Its consequences list is entirely about the compiler check. **Codegen was
never revisited**, and a checksum is the one member of that family whose
comparison situ generates itself -- an authenticated `tag` is compared
inside the codec, which knows its own truncation. So the gap is exactly
where 0038's reasoning did not reach.

## The second half: the width guard's "cannot tell" branch

`checksum u7 sum covers(s) is crc32` -- seven bits for a 32-bit CRC --
compiles with **no `[truncated]` at all**, which is the typo-versus-
deliberate distinction 0038 exists to force, not forced. Its map says
both halves out loud and does not mind:

    codec crc32 derived expansion=+4 ...
    frame.sum   ... size=Fixed(7bit) ... mutate=Immutable

`check_codec_sizes` skips when `_declared_byte_width` returns `None`, and
that helper returns `None` when `bits % 8`. Its docstring names the three
cases it means by `None` -- an array sized by an expression, a
`[remaining]` run, a type whose width is not in its name -- and `u7` is
none of them. Seven bits is knowable, and it is knowably narrower than
32.

This is `evidence.md`'s shape with the guard pointed at itself: a skip
branch for "the compiler cannot see the width" that also swallows a
width the compiler can see.

## The decision, which is not this record's

Two questions, and both are the copyright holder's because both are
language rather than implementation:

- **Which bits does a truncated checksum keep?** Leading or trailing is a
  per-format choice; OSCORE's truncation, which 0038 cites, keeps the
  leading bytes of a MAC. A fix has to pick one or make it sayable, and
  picking silently is how a generated comparison becomes wrong in the
  other direction instead.
- **Is `[truncated]` meaningful on a `checksum` at all?** `std/kernels.situ`
  already carries `crc5_usb`, `crc7_mmc`, `crc15_can`, `crc24_ble` and
  `crc40_gsm` -- narrow CRCs as their own codecs, which is how formats
  actually specify a short check field. A truncated wide CRC may be a
  mistake in a way a truncated MAC is not, in which case the fix is to
  refuse it and name the narrow codec. That contradicts 0038's placement
  table, so it is a decision rather than a correction.

What is not in question either way: **a check that cannot pass must not
be generated.** Whichever answer the first question takes, the present
behaviour is wrong under both.

## Cost of the delay

No example truncates a checksum, and no vector or corpus case exercises
one -- which is why 48 random buffers per schema never saw it. So nothing
in the tree is broken today and no consumer can have hit it. It is a trap
set for the first adopter who writes the attribute the language offers
them.
