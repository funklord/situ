# 26.675: `validate()` read past the buffer, and why nothing caught it

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

Reported by `bbq-predictor` through `.git/cc-inbox/`, from an evaluation of
situ for a public binary format its clients parse from the network.
Reproduced here at `f9fa599` on their input, nine bytes: `01 c8 01 02 03
04 05 06 07`.

    ERROR: AddressSanitizer: heap-buffer-overflow
    #0 situ_get_le32 runtime/c/situ.h:329
    #1 situ::pc::extent() const
    #2 situ::el::c_extent_from(unsigned int) const
    ...
    #8 situ::top::validate() const

**`validate()` is the function that read out of bounds**, which is the
worst place for it: a server calls it precisely because it does not trust
the bytes.

## The mechanism: two faults, and the second is why it was memory-unsafe

    std::uint32_t at = 0;
    at += 1;                                      // past `n`
    at = situ_advance_u32(at, n, raw_.limit);      // CLAMPED to 9
    at += 2;                                      // -> 11, unclamped
    ...
    situ_view_t{ situ_base(raw_) + at, raw_.limit - at, ... }   // 9 - 11

- **Clamping each term is not clamping the sum.** `situ_advance_u32` keeps
  `at <= limit` as an invariant; a bare `at += 2` breaks it at exactly the
  point where the term before it saturated. The C++ emitter clamped only
  the *dynamic* terms, on the reasoning -- written at the call site -- that
  "a term is a length the message chose". A constant term is not, and that
  is true and beside the point.
- **`raw_.limit - at` wrapped to 4294967294**, and the sub-view was
  brace-initialised with it. A brace-initialised view is a limit nobody
  checks, so every `situ_in_bounds` below it passed against four billion.
  This is the fault that turned a wrong offset into a read past the end.

**The C backend was clean on the same bytes**, and it is the model for the
fix: it builds sub-views through `situ_view_sub`, which re-validates the
extent and refuses a wrapped one, and it clamps *every* term including the
constants. Its own call site says why, citing 26.27: "a wide length field
is worse than out of range ... so every term stops at the view."

Rust was memory-safe by a guard before the slice, and gave a different
answer: `c_extent` of 0 where C said 4.

## Why nothing here caught it

Three gaps, measured, in the order they would have caught it.

**1. No corpus schema had the shape, and that is the primary miss.** The
composition is a fixed-width member *between* a dynamic member and a nested
struct whose extent is read from the bytes, inside a run. Scanning the
generated C++ for all 43 corpus schemas, the emitted pattern -- a fixed
advance after a clamped one -- appears in **one** function, `samples_offset`
in `edges.situ`, and that is an offset accessor rather than an extent chain
feeding a sub-view.

Every dynamic check here is corpus-driven: the four-way differential, the
walkers, the golden vectors, and `make fuzz`, which does build C++ under
libFuzzer and an address sanitizer. None could reach the path however many
bytes it was given. `bbq-predictor`'s harness came from situ's own
`gen-fuzz --target cpp` and found it in seconds -- the tool was right and
had never been pointed at a schema with this shape.

`test/schema/edges.situ` exists for exactly this. Its own header says it
carries "constructs the example protocols happen not to use", found by
mutation testing "because no schema in the tree reached the code path at
all". The shape it was missing was a memory-safety one.

**2. Nothing compared the backends' use of the saturating helpers.** The
differential compares *answers*, which is the weaker question: it cannot
see one backend bypassing a guard while the answers agree. Here the answers
did not agree -- C 4, Rust 0 -- so the differential would have reported it,
given gap 1 closed. But a divergence found that way arrives as "two numbers
differ", not as "one backend built a view from unchecked arithmetic".

**3. `make fuzz` is not part of `make check`.** `check` is `style typecheck
lint test cross-test`. The sanitized, libFuzzer-driven target that 26.27
built -- including `fuzz-cpp` -- is a separate target no push depends on.
Raising rather than changing: putting it in the gate is a cost decision
about every push, and the holder's.

**And five tests asserted the vulnerable spelling.** `at += 3;` and
`(raw_.limit - (1))` were pinned as expected output in
`test_codegen_cpp.py` and `test_codegen_c.py`. So the unsafe arithmetic was
not merely unnoticed, it was *held in place*: changing it broke tests, and
nothing recorded that the spelling was the hazard. 26.27 found the same
thing in its own round -- "two tests were pinning the bug rather than the
behaviour" -- and said the sentence this round needed: an assertion that
records what the code does is not a test of what it should do.

## What was changed

- **The C++ emitter builds extent sub-views through `situ_view_sub`** with
  `situ_remaining_u32`, and returns 0 when it refuses -- which is what the
  C emitter has always done. The two defences are independent: the
  subtraction cannot wrap, and if it did the sub-view would refuse it.
- **Every offset term clamps, in C++ and in Rust.** Rust had the same
  incompleteness twice in one function: its dynamic term had been fixed
  with a comment saying the plain one "was left plain when that was fixed
  ... which is what an incomplete fix looks like from outside", and the
  constant term beside it was still plain.
- **No generated code in C, C++ or Python computes a length by subtracting
  from a limit.** 46 sites in the two emitters, including 80 in C that were
  safe because `situ_view_sub` refuses a wrapped extent: converted anyway,
  because a guard three lines up is a guard somebody moves.
- **Rust's 136 remaining sites are pinned by a floor**, not fixed. They are
  a different hazard -- a wrapped `usize` panics on the slice, which 26.27
  already records as a denial of service rather than a mitigation -- and
  sweeping them wants a `situ_rt::remaining` that does not exist yet.

## The tests, and what each would have caught

Both were run against the parent commit, which is the only way to know
they bite:

- **`test_a_generated_length_never_wraps.py`**, static, over every corpus
  schema in four backends: **31 failures** before the fix. It closes gap 2
  and needs no schema to have the shape and nothing to be executed.
- **`test_validate_does_not_read_past_the_buffer_on_a_hostile_length`** in
  `test_codegen_cpp.py`, under ASan and UBSan: **aborts** before the fix.
  The behavioural half, asserting the reduced reproduction directly.
- **`edges.situ` gains the shape** -- `oob_inner`, `oob_element`,
  `oob_run` -- which closes gap 1, so the differential, the walkers and
  `fuzz-cpp` all reach the path from now on.

**The first draft of the static gate was wrong in a way worth keeping.** It
asserted "no bare `at +=`" and C passed with zero hits -- by spelling the
same operation `at = at + size`, three lines below a guard proving it safe.
A count inherits its detector. The property that survived is the narrow one
whose remedy is spelling-independent: the subtraction is gone, replaced by
a helper, and the behavioural half is a separate test.
