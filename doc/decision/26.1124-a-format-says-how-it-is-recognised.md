# 26.1124: a format says how it is recognised

Status: recorded; the first tier built
Date: 2026-11-20
Source: the holder, 2026-11-20 (`project.md` open register, *File
identification*): identification inside the schema, made of evidence that
names the format's own members; each item sufficient, required or
supporting; an extension a hint or a proof; confidence in named levels,
not a score; weak text formats in scope through named built-ins; the cheap
tier run across every format in one pass; magic(5) and shared-mime-info
from the same declaration. Low priority, taken once the rest was waiting
on other trees.

## The shape

    identify png(f: png_head) [media = "image/png"] {
        sufficient f.signature;
        required   f.first.kind == ihdr;
        supporting extension "png";
    }

- **The parameter is a struct laid at the start of the file**, as a
  relation's parameter is a message: the evidence reads through it, so
  nothing restates the layout.
- **A bare path is the member's own constraint**: a `preamble`'s bytes, a
  `[must_eq]`, a closed enum's members, a `[min]`/`[max]`. "This member is
  what the format says it is" is the commonest evidence, and saying it
  again as a comparison would be the duplication the holder ruled out.
- **A comparison is a narrower or looser predicate over a member** --
  `f.version <= 3`, `f.first.kind == ihdr` -- for the "one minor
  difference" without a second copy of the format.
- **`extension "a", "b"`** holds when the file's name ends in one of them,
  case folded. Its role decides what it is worth: `supporting`, a hint; or
  `sufficient`, proof, for a format nothing else can recognise.

## The levels

An item holds or not. Then, for one format:

- a `required` item that does not hold: **no** -- whatever else held;
- otherwise a `sufficient` item that holds: **certain**;
- otherwise, where there is a `required` item and every one held:
  **likely** if a `supporting` item holds as well, **possible** if none
  does;
- otherwise **no**.

**A `supporting` item never stands alone.** The first version let one
lift a format to likely by itself, and a text file named `a.png` came back
"likely PNG" against the PNG schema's own comment that a `.png` without the
signature is not PNG. A hint ranks what the required evidence admitted; a
format with nothing better than its name makes the extension `sufficient`
or `required`, a proof or a gate, by its role -- which is the holder's
"hints or proof".

Within a level, formats rank by how many bits the held items pinned --
`RIFF....WEBP` over a bare `RIFF` -- a tiebreak inside a named level, never
a score across them.

## The cost, and the first tier

The compiler places every item. **The first slice accepts only items at a
fixed offset from the start of the file**, and says the number of bytes
the format needs (`head`): a search tool reads that many bytes once per
file and answers every format from them, with the file's name. An item at
no fixed offset -- past a variable-length run, in a container member, a
text heuristic -- is refused naming why, so that the cheap tier cannot
quietly grow a walk; those are the later tiers, built when a format needs
one.

## What it generates (first slice)

- `situc identify SCHEMA... -- FILE...`: each file's best format and its
  level, from the first tier of every schema at once.
- `situc identify --magic SCHEMA...`: the items magic(5) can say -- byte
  strings and numbers at fixed offsets -- as `file(1)` rules, `!:mime`
  from `media`, `!:ext` from the extensions. A required item becomes a
  continuation line of the sufficient one; `possible` and `likely` have no
  magic(5) spelling and are left out, said in a comment.

Built so: `situc/identify.py` compiles each item to tests at fixed byte
offsets -- one run of bytes, one of a set (a closed enum, a byte-run
enum's arms), or a number in a range -- and judges by the roles above.
`example/png` declares PNG's: the signature sufficient, the extension
supporting. `test_a_format_says_how_it_is_recognised.py` holds the
levels to cases worked by hand, the refusals to their reasons, and the
magic(5) output to what file(1) says of the same bytes; putting the name
on the first magic line instead of the last fails it, since file(1) then
prints the name with the continuation unchecked.

**The C matcher** (`situc identify --c`): one file holding every given
format's tests as tables and `situ_id_judge(head, length, name,
&chosen)`, answering all of them from one read of `SITU_ID_HEAD` bytes,
for a search tool to include in one translation unit. A name's case is
folded A-Z only, in both matchers, so they cannot disagree over a byte the
other folded. The suite feeds both the same mutated heads and names and
requires the same verdict for each, every level reached and every format
chosen. Its first version passed with the C tiebreak reversed and with
byte order ignored, because no case tied exactly and no little-endian
number was ever compared; an identical twin format and a little-endian
range now make both sabotages fail.

Later: shared-mime-info XML, the built-in text heuristics (UTF-8, line-regular
CSV, JSON's first byte), and the deeper tiers.
