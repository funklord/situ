# 26.863: A walker does not read a `native` tlv tag or length as big

Status: recorded
Date: 2026-11-05
Source: 26.857, the same shape in `pack.py`

The packer wrote a fixed-width tag's and a `prefixed` length's order as "big
unless little", so both walkers read `native` big while the four generated
readers read it as the host does. On a little-endian machine a `u16` tag of
0x0702 read as 0x0207, and a valid message came back BOUNDS.

An image is one file for every host, so the packer cannot settle `native`.
Bit 2 of `tag_flags` and `len_flags`, `TLV_NATIVE`, leaves it to the reader,
and each walker does what it does for a `native` member: Python answers as
the machine it runs on and C declines for more than one byte, since a capture
does not record which machine wrote it. The bit is new and bit 1 stays clear,
so a walker older than it reads `native` little.

**A region the C walker cannot walk is now a verdict it cannot give.**
`validate` asks `tlv_walk` of every placement and passes UNSUPPORTED through,
since a placement that is no region answers that. So the first version of
this fix answered OK for the bytes it declined. It now passes only where no
tlv row exists, which also closes a region whose selector did not encode.

`test_a_native_tlv_tag_is_read_natively.py` holds all six on a tag and a
length, laid out in the host's own order.
