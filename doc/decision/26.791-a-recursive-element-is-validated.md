# 26.791: A run of a recursive element validates its elements

Status: recorded -- fixed
Date: 2026-10-31
Source: 26.789's "not yet"

    struct node [depth = 4] { u8 n [max = 3]; node kids[n]; }
    struct top  { u8 k; node recs[k]; }

26.789 left a run of a recursive element unvalidated: json's members and
elements, sexpr's items, and edges' `nest_group`. Two things looked like
they needed a depth `check` does not carry. Neither did.

- **The descent is already bounded.** A recursive struct's `check` opens
  with its nesting probe (26.284), which refuses a tree deeper than
  `[depth]` before any member is read. So an element's `check` called from
  a run recurses no further than the cap allows, in all four and in both
  walkers.
- **What did not terminate was the generator.** "Can this element refuse
  anything" asked the element's check groups, and a recursive element's
  groups hold its own run's element walk, which asks again. Each backend's
  `_element_refuses` is memoised now, and a struct already on the path
  answers yes, as `has_computable_extent` cuts the same question with
  `seen`. The rule is the same in all four, so the ids agree.

The walkers' `[depth]` exclusion goes with it.

## Two walker faults it exposed

- **The C walker's `validate_deep` gave up one level early.** 26.288 moved
  `struct_extent` and `while_walk` to `depth > ceiling`, since `[limit =
  N]` counts edges and admits N + 1 structs, and left this guard at `>=`.
  Nothing reached it until a run's deepest element was validated. Then
  nine nested nodes inside `[limit = 8]` were `cannot-say` in C and clean
  in Python and the four. It is `>` now.
- **Both walkers overran a member with a lead by the lead.** The bounds
  check on a fixed member at a dynamic offset, and the run frame check,
  added `offset_bits` (already past the member's lead) to `size_bits` (its
  span, which counts the lead again). That was invisible while a frame had
  bytes after the member. An element's view ends exactly at it, so
  sexpr's `kind` after whitespace was BOUNDS in both walkers and clean in
  the four. They now add the content width, which is what the backends'
  `in_bounds(offset, size)` asks.

## One answer the tests change

A `while` run is never empty, so `node { u8 more; node kids[] while
(more != 0); }` is two bytes at least. The leaf every test message of that
shape ends on is one byte, `00`, with its run cut off by the frame.
Validated as an element of its parent's run, it is short of its own
minimum and refused, as a nested member already is (26.577). That shape
therefore no longer has a valid message, and `test_recursion.py` and
`test_walker_c.py` say so. The nesting count still pins the bound.

## One answer differs from the recursive struct's own

A tree past `[depth]` inside a run answers BOUNDS. `node` validated
directly answers CONSTRAINT, as 26.284 has it for a too-deep message. The
element is measured with the cap, so its view stops short of the tree, and
its `check` finds the kids outside that view. Both are refusals, and the
walkers answer `cannot-say` past their own ceiling, so nothing compares
them. Answering CONSTRAINT would need the run's walk to tell a capped
extent from a short one, which `_run_fits` declines to do for the reason
26.676 gives.

## Tests

`test_a_run_validates_its_elements.py` gains the shape. An element over
its `[max]`, a second one, and a kid of the first are refused by all six.
A five-level tree is clean, and a six-level one is BOUNDS in the four.
