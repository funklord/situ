# 26.741: `ordering` meant nothing, and made a region canonical

Status: recorded -- decided by the copyright holder 2026-10-29 and fixed
Date: 2026-10-29
Source: `project.md` section 26

Found by the lens 26.738 and 26.740 handed on: a policy the schema
declares, which reached the capability map, and which nothing that reads
a message enforced. This one was worse than an unenforced default.

`tlv items (..., ordering = banana)` parsed. The parser recorded only
that an argument called `ordering` was present, any value at all, and
that presence cleared `tlv-unordered-items`. The region read Canonical,
so `require canonical(o)` passed. No section of this document defined an
order, and no backend checked one: items in any order validated. A
schema author could sign messages believing there was one encoding of
each. And the advisor recommended the construct -- "declare an ordering
rule on the region, which is what makes a tag-based format signable at
all" is the remedy `situc explain` prints for `example/protobuf`.

So the lattice, which section 0 calls the core of the project, claimed a
capability the generated code did not uphold.

## The decision

Asked rather than guessed, because it is capability propagation (section
0, rule 4). The holder chose:

- **`ordering = ascending` is the one value**: each item's identity --
  the part `tag_identity` names (decision 0023), or the raw tag -- is no
  lower than the one before. Any other value is an error naming this one.
- It clears `tlv-unordered-items`, as the bare argument did.
- **`tlv-unordered-duplicates` applies whether or not an order is
  declared.** Ascending order fixes items of different identities and not
  the order among equal ones, so with `duplicate_tags = allowed` two items
  tagged 1 can still swap. It used to be suppressed by any `ordering`. Its
  remedy is now `duplicate_tags = error`, the default.

## The fix

- The parser accepts only `ascending`.
- Each backend's `_whole` (26.737) keeps the last identity and refuses a
  descent with CONSTRAINT, in the same walk 26.738 and 26.740 use.
- The walkers decline: bit 0 of the TLV row's flags, which already meant
  "ordered" and was documented nowhere, now joins bits 1 and 2 in the
  mask both validators decline on. The image carries no identity program
  to compare.
- The rule table in 11, the 14.5-adjacent policy table, 9.5's sentence
  and the protobuf cause list say the same.

`test_ambiguity.test_duplicates_allowed_with_ordering_is_canonical`
asserted the old rule. It became
`..._is_still_not_canonical`, beside a test that `ordering = banana` is
refused.

## Verified

`test/unit/test_a_tlv_region_is_validated.py`: ascending, equal
identities in a row, a descent, and a descent after a repeat, asserting
the exact verdict in all four backends and `cannot-say` from both
walkers. Controls: with the emitter half stashed the four answer
`validate 0` for a descent; with either walker's mask set back to 6 it
gives a verdict where it must decline. All 46 committed capability maps
are unchanged -- no schema in the tree declares an `ordering`, which is
how this went unseen.
