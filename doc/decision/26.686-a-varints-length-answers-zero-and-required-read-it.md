# 26.686: A varint's length answers zero, and `required` read it

Status: recorded -- fixed in all four backends
Date: 2026-10-23
Source: `project.md` section 26

The fourth instance of 26.683's sentence, found by the same prefix sweep
and in the shape that makes it worst: a struct holding nothing but a
varint.

## The fault

**A varint's `_len` answers ZERO for one it cannot read.** That is
deliberate and right for the offset chain -- the lax-reader convention
this tree uses everywhere, so that a truncated varint does not drag every
member after it out of the frame, and only the getter refuses. It is wrong
for `required`, which added the zero and reported a complete message.

Measured 2026-10-23 on `one { uvar v; }` with the single byte `0x81`, a
continuation byte with nothing after it:

    one::required([0x81])  ->  SITU_OK, *need = 0

**And it compounds through a run.** `col { uvar count [max = 100]; one
d[count]; }` frames its run by asking each element's own `required`, so
with `03 81` it read a count of three, asked `one` about one byte three
times, was told OK with zero each time, and answered:

    col have=2  err=0 need=1    (the whole message is 5 bytes)

A `need` of 1 for a 2-byte buffer: below what had already arrived, so a
caller asking "how many more" is told to read minus one. Reproduced
identically in a worktree at `08b9470`, so it predates this week's work.

## The fix

`required` asks for ONE BYTE MORE than has arrived where the varint
cannot be read:

    if (situ_one_v_len(view) == 0u) {
        *need = situ_need_u32(have, 1u);
        return SITU_ERR_TRUNCATED;
    }

That is what the delimiter branch two screens down already answers, and
for the same reason, which its comment states: how much more a
continuation byte promises is a question only the sender can answer, so
the honest lower bound is to read again and ask again.

A RUN of varints is a separate case and already had one, `_span_min`
(26.683) -- **which this pass found loose in the same way.** It credited
one byte to the element the walk stopped INSIDE, so a single truncated
element whose first byte had arrived was counted as satisfied: a run that
is the last member of its struct read as complete. It now answers every
byte present plus one, and then one for each element it never started,
which is exact for every prefix measured.

## What the four instances have in common

- **26.683**: a run's `_span` shrinks when an element is truncated.
- **26.684** (open): a nested member's extent shrinks the same way.
- **26.686**: a single varint's `_len` collapses to zero.
- **26.685** is the odd one -- not a shrinking quantity but two quantities
  confused, the running total passed as the element's offset.

So three of the four are one sentence: **a framing function may never read
a quantity that gets smaller as bytes go missing.** Every quantity
`framed` and `required` sum is a candidate, and the test is three lines --
ask about every prefix rather than about the message.

`test/unit/test_required_answers_every_prefix.py` is that test. It pins
the sequences and asserts the three properties a framing answer needs:
never complete before the message is, never going backwards, and always
exceeding what has arrived while incomplete. Each of this pass's three
fixes was reverted in turn and fails it, in its own shape and on the
safety property.
