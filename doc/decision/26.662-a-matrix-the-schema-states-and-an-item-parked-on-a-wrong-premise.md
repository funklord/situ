# 26.662: A matrix the schema states, and an item parked on a wrong premise

Status: recorded
Date: 2026-10-20
Source: `project.md` section 26

The construct and the alternatives are decision 0064. This records what
the work found that the decision does not need.

**The item was parked for 43 days on a premise nobody checked.** 26.218
wrote `linear_block` knowing one code as needing "the generator matrix
expressible in a schema, which is a language addition rather than a
table entry", and 26.144 carried it unchanged. A language addition is
the holder's, so the sentence was not merely wrong -- it was the reason
the item never moved. It took one parse to falsify: a kernel argument is
an `expr`, arguments may repeat, and `table` had been taking its map
outright as repeated `symbol` arguments since before the item was
written.

**The sibling was the cheapest source of the answer and nothing pointed
at it.** `working-practice.md` says a working sibling explaining itself
beats the document, and here the sibling is one family over in the same
`dict`: `KERNEL_ARGUMENTS[TABLE]` carries a comment saying `symbol`
"gives the map outright rather than by name" and that a sweep looking
for `argument("x")` missed it, which is the form question answered in
full, in the file the new argument had to be added to.

**So the shape to hold is not "check a premise".** It is that **an item
whose deferral names an expensive mechanism is the one to re-derive
first**, because the expense is what stops anybody testing the claim.
Four of 26.144's eleven live items say "language addition", "data model"
or "convention change"; one of them was none of those things.

## The defect the gap was hiding

The emitters gated on the code's name and read `n` and `k` from nowhere,
so this schema generated Hamming(7, 4)'s tables:

    codec c { kernel = linear_block(n = 15, k = 11, standard_form,
                                    code = hamming_7_4); }
    impl c derived;

A seven-bit codeword, a 16-entry encode table and an 8-entry syndrome,
under a capability map saying `ratio_exact(15, 11)`. 13.4 names exactly
this as the case it does not allow -- "A convolutional code declared as
a shift register is not honest, because [...] a consumer sizing a buffer
from the map would under-allocate" -- and listed `linear_block` among
the honest ones in the same paragraph.

**Nothing could have caught it from the test side**, which is why it is
worth more than its fix. The suites assert the code's properties by
executing what was generated -- systematic, the weight distribution,
every single-bit error corrected -- and all of those hold of the tables
that came out, because they are Hamming(7, 4)'s tables and it is a
correct Hamming(7, 4). The fault is only visible by comparing the
implementation against the *signature beside it*, and no test did that
for this family. A named code carries its dimensions now and a mismatch
declines with the reason.

## What the equivalence test is for

The `parity` form's whole claim is that two routes describe one code, so
the test asserts the relationship rather than either side: the numbers
generated from `code = hamming_7_4` and from its rows stated outright
are identical, in all three backends.

**It would have passed before the form existed, for the worst reason** --
nothing generated from the rows, so both sides would have been the same
empty absence. It carries a second assertion that the named side
produced a table at all, and the sabotage that proves it: with
`linear_code` made to decline a named code, the test fails naming the
vacuity rather than the inequality. Three sabotages in all -- reversed
rows, a hard-coded check count, a declining name -- each failing the
test it was aimed at and leaving the others green.
