# 26.1008: a deadline survives the clock wrap

Status: recorded
Date: 2026-11-13
Source: fuzznet, `suggestion/fuzznet.md` 2026-11-13, "rung 6 against
fuzznet's caller -- one bug, three gaps"

**Rung 6 compared deadlines as plain integers.** `deadline_ms = now_ms +
timeout_ms` wraps at 2^32, and `now_ms >= deadline_ms` then holds at once.
fuzznet reproduced it on the generated DNS driver: sent at `0xFFFFFFFF -
1000`, an exchange waiting 5000 ms spent both retries and expired one
millisecond later. A daemon passing milliseconds since boot meets it after
49.7 days, which a router running fuzznetd does. Rust's driver did not get
that far: its `+` panicked at the wrap in a debug build.

**Serial arithmetic now, modulo 2^32, in all four.** A deadline is due when
`(now - deadline) mod 2^32 < 2^31`, and the soonest is the one with the
least `(deadline - now) mod 2^32` -- the two comparisons `step` makes. Rust
adds and subtracts wrapping; Python, whose integers do not wrap, takes the
same arithmetic explicitly so that a caller passing a 32-bit clock gets the
same answer from it as from the other three. The contract this states: a
timeout is under 2^31 ms, about 24 days.

**Measured** by fuzznet's case in each driver: sent 500 ms before the wrap
with an 800 ms timeout, three steps one millisecond later neither resend nor
expire and report the wrapped deadline, 299, and a step at 299 resends. All
four fail with the change reverted, C and C++ at the first step; Rust is
built with overflow checks on.

**fuzznet's three gaps are not taken here**: `submit` told which exchange it
sends (to reseal under a fresh nonce), `expired` saying which, and a
non-taking `match`. Each widens rung 6's interface in four languages, and
fuzznet has said it is not blocked.
