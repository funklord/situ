# 26.1066: the walkers sum a pseudo-header they are handed

Status: recorded
Date: 2026-11-18
Source: the goal gap, walked in /go run 3 -- 26.1058 left TCP's and UDP's
sums declined in both walkers and compared as refusals in the sweep

**The two independent readers never checked TCP's or UDP's checksum.**
Since 26.872 the four backends sum a `prefix(...)` they are handed --
`<tag>_compute(view, prefix, prefix_len, &out)` in C, a byte slice in the
other three, held to `PREFIX_BYTES`. Both walkers declined such a sum
before reading a byte (26.1058), and the differential did not ask it, so
the most widely deployed checksums situ describes were compared by
nobody but the backends against each other.

The reason given was that no message holds the prefix (14.2a). That is
true and is not a reason for a reader to decline when the caller holds
it: the backends take it from the caller, and so can the walkers.

## The rule

- **The image carries the prefix's size.** The tag row's flag word gains
  bit 2 and bits 8-31: the size in bytes of the struct `prefix(...)`
  names, where that struct is fixed-size. A reader older than this sees
  bits it does not know and declines, as it did.
- **Both walkers take a pseudo-header**: `derived.compute(..., prefix=)`
  and `report.listing(..., prefix=)` in Python, `situ_walk_sum_prefixed`
  in C (`situ_walk_sum` is it with none), and `--prefix <hex>` on both
  command lines. It is summed ahead of the covered bytes, the tag's hole
  measured against the two together, as every backend's `_spans` does.
  A wrong length is refused (BOUNDS, `refused`), as the backends refuse
  it; a prefix of no fixed size, or none handed over, is declined as
  before. A tag that names no prefix ignores one, so a caller may hand
  one pseudo-header to every tag in a message.
- **The differential asks it.** `differ.handed_prefix(n)` is the
  pseudo-header every reader is handed -- not zeros, which RFC 1071's sum
  cannot tell from no prefix -- and `schema_prefix` the one for a
  schema. Each driver bakes it into its `SUM` ask; the walker sweeps hand
  the same bytes to the listing and to `situ_walk_sum_prefixed`. A sum
  whose prefix is another size than the schema's first is not asked,
  since a walker takes one prefix per message.

The dissector still declines: its pseudo-header would come from the IP
layer below it, which a generated dissector does not know how to find
from this schema. That is a separate question, not this one.

## Found on the way

Comparing TCP's sum found a walker fault that predates it (cb6ce2ac):
both walkers checked only where the LAST covered member ends, so
`options[(data_offset - 5) * 4]` running past the frame, followed by a
`payload[remaining]` placed back inside it, was summed by both walkers and
refused by all four backends.

## Measured

UDP's segment `1234 5678 000c 0000 deadbeef` from 10.0.0.1 to 10.0.0.2
sums to `0xE589` in both walkers, as RFC 1071 written out in the test
computes it; a 23-byte TCP SYN with an odd length the same. One byte
short refuses in both, no prefix declines. Six readers over 68 UDP and
TCP messages each, with UDP lengths planted: 8 UDP and 47 TCP sums as
values, the rest refusals, no disagreement once cb6ce2ac is in.

Sabotage: either walker summing without the prefix fails the UDP and TCP
published values; Rust's driver handed the pseudo-header reversed fails
the four-way sweep on TCP. Not on UDP, whose random lengths never fit, so
every UDP sum there is a refusal -- the published vector is what holds
UDP's value, as PNG's holds its CRC.
