# 26.650: The last unclamped sum, and a reachability claim I got wrong twice

Status: recorded
Date: @ -31306,0 +31307,82 @@ reproductions, in a file that was not its own.
Source: `project.md` section 26, where it was written

26.648 left `preserving` open as *"a sum in 32 bits, which is safe for
one clamped term and not for two"*, and 26.649 repeated it. **Both
statements were wrong, in opposite directions, and measuring took one
command.**

Across all 45 schemas in the tree, every `coded` and `sealed` region:

    kind=preserving  variable members=0   x4
    kind=preserving  variable members=1   x5
    kind=ratio       variable members=0   x1
    kind=ratio       variable members=1   x1

**No region anywhere has two variable members**, so the condition I
named cannot arise. And one variable member is not safe either, because
`inner` is `constant + (length)` and four of the five carry a nonzero
constant:

    keystore.situ  keystore            constant=32  plaintext, stride 1
    packet.situ    packet              constant=22  body,      stride 1
    edges.situ     sealed_run          constant= 2  vals,      stride 2
    edges.situ     sealed_self_sized   constant= 2  n, a varint's own bytes

A length that has saturated to `UINT32_MAX` makes `32 + length` wrap to
31 in `uint32_t`. So the danger is a nonzero constant and ONE term, not
two.

**Then the third measurement contradicted the second.** For a term to
reach `UINT32_MAX` it has to be a saturating product, and none of these
can be:

- a stride-1 run's length is the clamped count itself, at most
  `SITU_LEAF_MAX`, and `32 + 0x7FFFFFFF` fits;
- `sealed_run` is the only stride-2 case, where `count * 2` could reach
  `0xFFFFFFFE` and `2u +` that is exactly 2^32 -- **but its driver is
  `u8 n [max = 4]`**, so the term tops out at 510;
- `sealed_self_sized`'s variable member is a varint measured by its own
  bytes, at most 9.

So the sum is **structurally able to wrap and unreachable in this
corpus**, and it is one schema edit from being reachable: widen
`sealed_run`'s `n` to a `u16` and it is live.

#### The lesson is about the shape of the claim, not the arithmetic

Three successive statements -- safe with one term, unsafe with one term,
unreachable with one term -- and only the third was measured. The first
two were derived from reading the code, which is exactly what makes them
convincing: each followed correctly from the line in front of me, and
each was answering a question about the CORPUS that the line cannot
answer. `evidence.md`'s *a claim about another tree is a measurement you
did not take* is usually read as being about other repositories. The
same thing happens one function away.

What the measurement cost was one script over 45 files. What publishing
the unmeasured version cost was two entries and a paragraph to the
holder that had to be retracted.

#### Fixed anyway, and why that is not inconsistent

`preserving` now clamps where it has a variable term, in all four
backends, although nothing reaches it. Two reasons, and neither is
tidiness:

- It was the last arithmetic in `_region_length` outside the clamp.
  *An exception wider than its reason is how a rule stops being
  enforced* -- `code-style.md`'s sentence about an ASCII check, and the
  shape is the same here.
- The gap is a `u8` away. A finding whose reachability rests on one
  attribute of one test schema is not a property of the design.

**And the same pass found a real gap in the fix of 26.646.** C++ and
Rust built their wide form as `static_cast<std::int64_t>(inner)` and
`((inner) as i64)` -- a cast applied to the whole sum, which widens a
value the 32-bit addition has already wrapped. The `ratio` instance
that was measured had `constant = 0`, so it could not show this. Each
term is widened on its own now. That is the same rule failing one step
earlier than where it was fixed, which is the third time this session
that *a clamp bounds only the arithmetic it encloses* has located a
defect -- and the first time it did so in my own patch.
