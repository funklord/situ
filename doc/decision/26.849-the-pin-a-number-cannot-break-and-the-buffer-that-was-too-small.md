# 26.849: the pin a number cannot break, and the buffer that was too small

Status: recorded -- the pinned-run body ported to `--target python`, which
closes 26.840's named gap for one of the four; C++ and Rust still decline
Date: 2026-11-03
Source: 26.840, which measured the gap at 18 of 67 pins and left it

## What it does

A pin on a byte RUN cannot be broken by adding one to anything: `"BM"` has
no integer to increment, and a schema admitting several alternatives needs
a byte outside every one of them. So the first byte of each admitted pin
is collected and a byte beginning none of them is written at the run's
start -- wrong for every pin the schema admits, and still wrong for one
nobody has written yet.

`--target c` records why that beats writing all-ones: all-ones is right
for `\r\n` by luck and vacuous for a preamble pinned to 0xffff.

11 of the corpus's 18 run pins are checked now, taking `must_eq` from 40
checks to 51; the other 7 are declined by name -- an arm this cannot
select, a schema admitting every first byte, or no satisfiable baseline.

**The control**: neutralising the emitter's own pinned-run check fails
exactly those 11 across 7 schemas, and nothing else.

## The buffer was the minimum and needed to be the maximum

The first run over the corpus failed on `example/cpio`, and not in the
check:

    situ_runtime.BoundsError: cpio_entry.<reserved0>: declared length
    does not fit

raised by `view.validate()` **on the baseline**, before anything had been
broken. The control arm failing is the control arm doing its job, and what
it caught was the extent.

A baseline writes the value every driving member must hold, and a driving
text number's smallest admitted value can still declare a length the
minimum extent does not reach. `cpio_entry` is thirteen text numbers
around one pinned magic, so over its minimum the baseline is not a valid
message at all.

`--target c` has used the struct's MAXIMUM since its checks were written
-- `buf[65536u]` stands in cpio's C suite to show it -- and the other
three backends took `layout.size_bytes` and were going to meet the same
wall one struct at a time. `buffer_size` is in `situc/codegen` now, with
the ceiling beside it, which is the eighth thing to move there today.

**And the obvious form of that fix lost checks.** Written as
`extent = buffer_size(...)` with a `return []` when it answers None, it
took `must_eq` from 51 to 46 and the enum kind from 39 to 36: a struct
with no computable maximum went from some checks over its minimum to none
at all. A wider buffer is an improvement where one can be had, and the
narrow one was never wrong -- only sometimes too small. So the minimum is
the fallback rather than the alternative.

That is the day's recurring shape once more, in a form worth naming
separately: **a fix that is right about the case it was written for can
still subtract from the cases that already worked.** The counts are what
caught it, which is why the kinds report them.

## What remains

`--target cpp` and `--target rust` still decline a run pin, so their
`must_eq` kind is 18 pins short of what the corpus holds and their
constraint kinds still size a buffer from the minimum. Both are the same
two changes made here, and the second is the one that will bite first:
cpio is in every corpus run.
