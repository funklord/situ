# 26.684: `framed` reads an extent, and an extent shrinks

Status: recorded -- fixed in all four backends and in the walker's framer
Date: 2026-10-23
Source: `project.md` section 26

Found while closing 26.683, which is the same fault one function over, and
reported independently by bbq-predictor as the surviving half of its item
2.

**Fixed, and the route took three obstacles rather than the one this
record first named.** The delegation was written, measured correct, and
set aside twice -- because it needs each member's BASE and the obvious
way to get one is a call that `required` cannot make. What unblocked it
was deriving the offset instead, which is the first section below; the
other two are a cycle's prototype and a dead store Rust refused.

The code in the `git stash` this record once pointed at was never used:
every call site moved when `required` gained the running offset, which
is what the pointer's removal predicted. The design was the durable
half, and it was enough.

## The fault

**`framed` adds a nested member's EXTENT, and an extent walk stops early
when the bytes run out.** So the quantity it adds gets SMALLER as a message
gets shorter, and `framed` reports a complete frame for anything that has
the fixed prefix.

Measured 2026-10-23, C++, on

	struct one { uvar v; }
	struct col { uvar count [max = 100]; one d[count]; }
	struct outer { u8 h; col c; }

with the five bytes `AA 03 01 01 01` offered a prefix at a time:

	have=1  outer: err=7 need=2  | col alone: err=7 need=0
	have=2  outer: err=0 need=2  | col alone: err=7 need=4
	have=3  outer: err=0 need=3  | col alone: err=7 need=4
	have=4  outer: err=0 need=4  | col alone: err=7 need=4
	have=5  outer: err=0 need=5  | col alone: err=0 need=4

`outer::required` answers OK at two bytes of five, and at three, and at
four, each time echoing `have` back as `need`. **Once the fixed prefix has
arrived it can never report truncation again.** `col::required` asked
directly is right throughout.

A stream reader using this would parse every partial message as a whole
one. `validate` refuses them correctly, so a caller who validates is safe
and a caller who frames is not -- and framing is what runs first.

## It is not about variants

bbq's reproduction put the run inside a variant arm, and situ's first
reading took the variant to be the subject:

	col alone:  validate=1 framed=7 need=4
	in variant: validate=1 framed=0 need=3

The plain nested case above has it identically, which is the measurement
that matters: a variant contributes `at = need(at, x_c_extent())` and a
nested struct contributes `at = need(at, c_extent())`, and the fault is the
word `extent` in both. Narrowing it to variants would have fixed one
spelling of two.

## Why `validate` does not have it

**`validate` delegates and `framed` does not.** `validate` emits, for a
nested member and for a selected arm alike, a sub-view and a call to that
struct's own `validate` -- the generated comment says so in as many words:
"the arm the discriminant selects carries its own constraints, and its own
validator is what knows them". `framed` reaches for a number instead of
asking the same question one level down.

## The walker had it too, and worse

`walker/session.py`'s `Reader` frames a stream by asking
`struct_extent` -- its docstring says framing needs no framing section
because that function "already measures one instance from its own bytes"
-- and then admits a message when `need <= len(buffer)`. The extent is
the quantity this record is about, so a shrunken need passes the very
test meant to refuse it.

Measured 2026-10-23 over every prefix, with `col { uvar count [max =
100]; one d[count]; }` and a five-byte message:

    have=1  complete=1     <-- a whole message, one byte long
    have=2  complete=1
    have=3  complete=3
    have=4  complete=4
    have=5  complete=5

Four of the five prefixes are handed back as whole messages, each with a
different length. `lastrun { u8 n; uvar v[n]; }` does the same at one and
two bytes. `withtail`, which has a fixed member after its run, escapes --
because those two bytes are in the extent whatever the collapse does,
which is luck rather than a guard.

**The walker's half is the more urgent.** A compiled `framed` that
over-reports hands a caller a frame they then `validate`, and `validate`
is sound; `Reader.next` hands back a View that nothing re-checks.

## The fix, and the machinery is already there

`_framing_walk` does exactly the right thing for a RUN -- it calls the
element's own `required` per element and propagates `at + part` as the
need, with `situ_need_u32` saturating. A nested struct wants the same
thing without the loop:

	if (have < at) { *need = at; return SITU_ERR_TRUNCATED; }
	e = <nested>_required(data + at, situ_remaining_u32(have, at), &part);
	if (e != SITU_OK) {
		*need = situ_need_u32(at, part);
		return SITU_ERR_TRUNCATED;
	}
	at = situ_need_u32(at, part);

gated on `traverse.frameable`, falling back to the extent where the nested
struct cannot frame itself. A variant arm is the same call per arm, under
the discriminant test `framed` already emits -- and only where EVERY arm
can be accounted for, a fixed one by its size and a struct one by its own
framing, because a chain handling some arms would report the rest as zero
bytes.

Measured with it applied, over every prefix of a six-byte message, with
`outer { u8 h; col c; }` and the same shape behind a discriminant:

    outer  2, 5, 6, 6, 6, complete at 6
    arms   2, 5, 6, 6, 6, complete at 6

Identical in all four backends and identical to each other, which is the
point: the discriminant costs a byte and changes nothing else about the
framing. bbq-predictor's own reproduction answered
`in variant: validate=1 framed=7 need=5` where it had said `framed=0
need=3`.

## What kept it out of the tree: two ordering obstacles

This section was headed *Why it is not in the tree* and kept that heading
after the fix landed, so the record contradicted its own `Status:` line
for a reader who scanned the headings -- which is what a reader does.
Rewritten rather than appended to, because a reader who finds both
believes the one that sounds more careful and the stale one always does.
Everything below is the history of the obstacles, in the past tense it
should always have been in.

**The delegation needed the member's own base, and `_base_expression`
answers it with a function call.** That is correct for an accessor, which
is emitted where the call resolves, and wrong in `required`, which is
emitted earlier in the header and for members whose accessors may not
exist at all. Measured across the corpus with the delegation applied, 14
of 1618 tests fail, in two groups:

- **A mutual cycle.** `json`'s `element` nests `value`, and `value` is
  emitted after it, so `situ_value_required` is an implicit declaration.
  Also `sexpr` and `edges.nest_group`. The remedy exists: 26.679 added
  `validate` and `check` to `_recursive_prototypes` for exactly this
  reason, one function earlier, and `required` is the next in that list.
  It needs the gate 26.679's did -- a prototype for a function the
  emitter then declines to define is `-Werror`, which is the trap that
  record is about.
- **An accessor that is never emitted.** `mqtt`'s `connect_body.will`
  sits at a dynamic offset behind an optional member, and there is no
  `situ_connect_body_will_offset` in the header at all -- so the base
  expression names a function that does not exist, rather than one
  declared too late. No prototype can fix that.

**So the base is arithmetic now rather than a call.** `traverse.
framing_gaps` gives the fixed bytes before each variable member, and
`required` already accumulates the lengths -- so the offset comes for
nothing, and the dependency on accessors is gone. `_framing_walk` takes
the same cursor, which also removes 26.685's latent exposure: its own
base call survived only because every corpus run happens to sit where
its accessor exists.

**The proof, because a mechanical change carries one.** `framing_gaps`
checks internally that its gaps plus the trailing fixed bytes are the
constant `extent_parts` reports, and declines rather than guessing if a
gap is not a whole number of bytes. Measured across the corpus: gaps
derived for all 107 structs that have an extent, and the 100 cases where
the layout already knows a first variable member's static offset agree
with the derived base exactly. Generated `required` bodies call zero
offset accessors in `edges`, `json` and `mqtt`.

**The cycle, which the first attempt met second.** `json`'s `element`
nests `value` and `value` is emitted after it, so the delegation's call
was ahead of its declaration -- also `sexpr` and `edges.nest_group`.
`required` joins the cycle prototypes beside the verdict pair 26.679
added, gated on `_frames_itself`: that renders the function and looks for
its signature, because the decline has many causes and a prototype for a
`static inline` the emitter then declines to define is the `-Werror`
trap 26.679 is about.

**And a dead store, found by the one backend that refuses them.** The
cursor's advance after the LAST variable member is never read. Rust's
`-D warnings` rejected it outright, then rejected the `mut` that became
unnecessary; C, C++ and Python accept both in silence. The advance is
gated on a later member reading it, in all four, because it was dead in
all four and dead arithmetic reads as arithmetic somebody meant.

**A variant chain also needed closing.** With no `default:` arm the
chain matches nothing for an unexpected discriminant, and `len_` is
never assigned -- which Rust refuses as possibly-uninitialised and
Python would have met as a NameError at run time. Zero is what C and C++
already answered, being what `_length_expression`'s own chain opens
with: no arm matched, so no bytes are claimed, and `validate` is what
refuses the discriminant.

## The walker's half, and what it needed

**`Reader.next` cannot be fixed by the same delegation**, because the
walker has no `required` to delegate to -- that is what its docstring
means by "framing needs no framing section", and it is the claim this
fault falsifies. `struct_extent` is correct for its own purpose and is
the wrong question here: it measures what is THERE.

**Fixed: `frame_min(view, depth)` sits beside `struct_extent` now**, and
`Reader.next` asks it before taking the extent -- two questions, which
is the distinction the fault turned on. `frame_min` says whether a whole
one has arrived; `struct_extent` says how long THIS one is, and that is
what the caller consumes. They agree for a complete message.

The per-member rules, as implemented:

- fixed: its size;
- a varint: its length, or the bytes present plus one where it cannot be
  read (26.686);
- a run of records: each element's own `frame_min`, plus a minimum for
  every element the count still promises;
- a run of varints: `_span_min`'s rule -- bytes present plus one, then
  one per element not started (26.683);
- a nested struct or a selected arm: its own `frame_min`;
- delimited: the scan, or the bytes present plus one.

It had to agree with four backends, which is what the walker exists to
check -- so the prefix sweep compares `Reader` against the generated
`required` for every shape rather than testing the walker's own
numbers. `test_the_walker_frames_the_same_prefixes` is that comparison,
and reverting `Reader` to `struct_extent` fails it on five of the six
shapes.

Measured after, over every prefix: `col`, `withtail`, `lastrun`,
`outer` and `arms` all report nothing until the whole message has
arrived, and then its exact length. Before, `col` handed back a whole
message at one byte of five and again at two, three and four.

**The C walker needs nothing**: it has no framer at all. `session.py` is
Python-only, which is why this is one function in one file rather than
the two-walker change the rest of 26.683's work was.

## The general rule, which is what this is worth

**A framing function may never read a quantity that gets smaller as bytes
go missing.** 26.683 met it as `_span` versus `_span_min` and fixed one
instance; this is the same sentence about extents, and the two together say
it is a class rather than two bugs. Every quantity `framed` and `required`
sum is a candidate, and the test that finds them is cheap: ask the
function about every PREFIX of a message rather than about the message. A
framing function tested on a complete message is tested on the one input
that cannot fail.
