# 26.1105: an arm's member may name its bytes too

Status: recorded
Date: 2026-11-19
Source: 26.1099's refusal of `[chars]` in a variant arm, whose reason --
that C could not dispatch a `default` arm for the check -- was the route
that check took, not a limit of the readers

**26.1099 refused a class on an arm's member**, reasoning that C's
`_arm_guard` answers nothing for a `default` arm, so a class there would be
enforced by some readers and skipped by others. Measured before changing
it: a `[max]` on a default arm's member is enforced by all four backends,
through the arm ACCESSOR, which answers VERSION where another arm is
selected. The class had simply taken the member path rather than that one.

## The rule

A class may sit on an arm's member, named or default. Each backend reads the
arm through its own arm accessor -- C's `_ptr` with its error, C++'s
`err`-returning form, Rust's `Result`, Python's property raising
`VersionError` -- and checks nothing where another arm is selected. The
packer writes the arm's four rows into its arm checks, and both walkers
apply them in their arm-constraint path over the selected arm's span. A
sealed or coded interior is still refused: neither reader has an accessor
for it on the struct's view.

## Measured

`test_a_run_may_name_its_bytes`: a named arm with a class, one without, and
a default arm with one, through four backends and both walkers on six
frames; with the packer's arm rows removed the walker test fails.
`edges.classed_arm` carries the shape through every edges reader.
