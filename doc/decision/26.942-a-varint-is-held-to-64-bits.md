# 26.942: a varint's value is held to 64 bits by every reader

Status: recorded
Date: 2026-11-08
Source: the dissector's signed varints (26.941), which disagreed with the walker on one message

**Every reader keeps the low 64 bits of a varint's value.** A ten-byte leb128 number puts
its last group at bit 63, where one bit of it fits, and a be128 number of ten groups is
seventy bits. C's `uint64_t`, C++ on the same runtime, Rust's `u64` and the C walker keep
the low 64 bits and lose the rest; the Python backend's runtime and the walker used
Python's integer and kept everything, so `80 80 80 80 80 80 80 80 80 7f`, zigzag-decoded,
read 585684124340278263808 -- a number past 2^64 that no other reader has -- where the
rest read 4611686018427387904. Both are masked to 64 bits now.

Wrapping rather than refusing, because four of six readers already wrapped and the C
runtime's `situ_varint_get` says so in its shape; refusing a number past `max_bits` is a
different rule, for every reader at once, and nothing asked for it.

Found by the dissector, which reads varints by the walker's rules in Lua 5.4 integers
and so wrapped where the walker did not. Held across the four backends, the walker and
the dissector by values worked by hand; the walker's test fails unmasked.
