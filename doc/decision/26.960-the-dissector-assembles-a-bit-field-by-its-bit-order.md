# 26.960: the dissector assembles a bit field by its bit order

Status: recorded
Date: 2026-11-12
Source: the dissector run against the walker over this session's sweep schemas

**An MSB-first bit field in an `endian little` schema was assembled
little-endian by the dissector.** Every backend loads a bit-packed scalar
by its bit order -- `endian` orders whole-byte scalars -- and so do both
walkers; the bit-field sweep of 40 straddling layouts found them all
agreeing. The dissector chose `add_le` for any member of a little-endian
schema unless the member was LSB-first (26.375's fix), so in a
little-endian, MSB-first schema every straddling field of five layouts
showed a number no other reader gave:

    endian little; bit_order msb_first;
    struct s [allow_straddle] { u3 f0; u13 f1; i7 f2; u9 f3; u8 k; }
    b7 20 9a bf 55   walker: 5 5920 -51 191   dissector: 5 183 ...

A bit-packed scalar is assembled by its bit order now, as the backends'
loads do (`scalar.is_bit_packed`), and the other forty agree. Real tshark
reads `b7209abf55` as 5, 5920, -51, 191 -- the walker's numbers.

## How it was found

Every sweep this session compared six readers and left the dissector out.
Running `test_dissector.compare` over the 267 sweep schemas the compiler
accepts -- text numbers, varints, delimiters, bit fields, variants, byte
enums, TLVs, placed members -- found this, and three schemas it could not
compare at all: a `[padded]` number's label carried the message's own
bytes (26.948's `situ_padded_text`), which the harness's strict UTF-8
read raised on and whose tabs and newlines broke its line format. The
label shows the digits and `?` for any other byte now, the harness
tolerates bytes it cannot decode, and the three compare with no
difference; tshark still shows ustar's `0000644`. Nothing else differs.
`test_a_bit_field_is_assembled_by_its_bit_order.py` holds the layout above
and fails without the fix.
