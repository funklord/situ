# 26.948: a `[padded]` text number's digits stop at a NUL or a space

Status: recorded
Date: 2026-11-10
Source: the copyright holder's answer to the open entry on ustar's numbers -- "digits end at a NUL or space"; `suggestion/hull.md` section 19
Supersedes: the "What it does not do" half of 26.756

**Under `[padded]`, a fixed-width text number's digits stop at the first
NUL or space, and every byte after them to the end of the width is a NUL
or a space.** 26.756 made `octal` a radix and left this open: a fixed width
was digits to the last byte, so ustar's `0000644` and a NUL was refused,
and `until "\x00"` ended where the digits did and moved every member after
a short field.

## What it means

    octal u32 mode[8] [padded];

| the eight bytes | value |
|---|---|
| `0000644` NUL | 420 |
| `0000644` space | 420 |
| `644` and five NULs, or a NUL then spaces | 420 |
| `00000644` | 420 -- no terminator, all digits |
| eight NULs | 0 |
| `64` NUL `4` ... | refused: a digit after the padding |
| a space then `0000644` | refused: no leading space |

**A field that is all padding is zero.** "No digits is not the number zero"
is the runtime's rule everywhere else, and is kept everywhere else: here
it would have refused GNU tar 1.35's own ustar output, which writes an
unused `devmajor` and `devminor` as eight NULs each, and GNU tar, Python's
`tarfile` and Go's `archive/tar` all read that as 0. Measured on the
archive in `example/ustar/ustar.vectors`.

**No leading space.** POSIX's ustar writes leading zeros; v7 archivers
right-justified with spaces, and GNU tar skips them. The holder's answer
says where the digits end, not where they begin, so the stricter reading
is taken and a leading space is refused. Widening it later accepts more
and breaks no reader.

## Why an attribute, and not every fixed width

The answer could have been read as the rule for every fixed-width text
number. Measured over the corpus, those are cpio's thirteen `newc` fields,
SMTP's reply code and two fields in `edges`. cpio writes every digit, and
an SMTP reply code is exactly three digits: `25 ` is not one, and a global
rule would have accepted it. So it is opt-in, on the member whose format
writes it, and cpio and SMTP read exactly what they read before.

It is placed only on an unsigned integer of a literal width with no
`until`: a delimited number's digits already stop at its delimiter, and a
sign or a point would need the padding threaded through a grammar ustar
does not have. `[minimal]` beside it is refused -- one spelling and
several.

## What it costs

**`canonical = NonCanonical`**: the three spellings above are one value.
**No owned form**: `decode` then `encode` is byte-exact in that mode, and
cannot be when the writer has to pick one of three. The setter writes
every digit, zero-padded, as it does for any fixed width; every tar reader
measured accepts that spelling.

## Where it lives

One function per runtime with `parse_uint`'s signature --
`situ_parse_uint_padded`, `parse_uint_padded` -- so each generated parse
site changes the name it calls and nothing else. Both walkers cut the
digits the same way; the image carries the flag in `text_flags` value 2,
which is `[trim]` on a delimited member and read by neither walker, the
flag byte being full. The dissector's `situ_digits_padded` does the same
for a padded length.

`example/ustar` is the header and an entry, with vectors GNU tar wrote.
It found two older faults on the way: the unparser had no `octal` keyword
and wrote one back as a binary `u32[8]`, and C++ wrote a `u64` text
number's limit with no `u` suffix, which `-pedantic-errors` refuses --
neither had a schema to fail on before.

`test_a_padded_text_number.py` holds all four backends, both walkers, the
placement refusals and the map; with either the C runtime's cut or the
Python walker's removed, it fails.

## Still open

GNU's base-256 numbers, a first byte with its high bit set, are a second
spelling of `size` this refuses rather than misreads. The header checksum
is read and not checked: it sums all 512 bytes with its own eight read as
spaces, which is not a rule the language states.
