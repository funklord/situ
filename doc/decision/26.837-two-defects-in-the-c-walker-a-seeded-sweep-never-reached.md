# 26.837: two defects in the C walker a seeded sweep never reached

Status: recorded -- both fixed; the discovery mechanism is the part worth
keeping, since neither defect is in anything this session set out to change
Date: 2026-11-03
Source: `test_walker_c.py` on `edges.situ`, after 26.833 added three structs
to it

## How they were found, which is not by looking

26.833 added `marked_tag`, `marked_entry`, `marked_index` and
`marked_prefix` to `test/schema/edges.situ` to ask a question about byte
order. `test_walker_c.py` sweeps every struct in a schema against buffers
from a **seeded** draw, so adding structs renumbered the shapes and the
sweep began asking pairs it had never asked. Two of them disagreed.

Neither defect has anything to do with byte order, markers, or anything
else 26.833 touched. **A seeded sweep is a fixed sample of its corpus, and
changing the corpus resamples it** -- so a corpus addition is a lottery
ticket on every latent disagreement the old sample missed, and the shape to
expect after adding one is a failure somewhere unrelated.

Both failures were confirmed to predate the change by reverting the 26.833
fix and watching them fail without it.

## The first: a value read wider than the member

`situ_walk_read` ended in

    return read_at(message, len, &held, offset, held.size_bits, out);

`size_bits` is the row's own figure, and for a member whose extent the
message decides it is the **maximum**. `edges.blocked_arg.one` is a
`negotiated(block = block)` whose row says 40 bits; with `block = 0` and
`kind` selecting the error arm it occupies 32. So C read five bytes where
it reported a width of four -- taking a byte belonging to the member after
it, and at the end of a frame reading past the frame, `read_at`'s bound
being computed from the width handed to it.

Measured: C answered `0x3339350000` and the Python walker `0x33393500`,
over the same buffer, while **both reported a width of 4**. A reader whose
value and whose width disagree is the cheapest possible tell and nothing
was comparing them.

The remedy is `content_bits_deep`, which the text-number path in the same
function already asks and which answers `size_bits` for an ordinary scalar,
so nothing else moves.

**The comment four lines above it describes this exact mistake** -- "Reading
`size_bits` gave the delimiter's width and answered `"GET "` as 0x47" -- and
answered it for delimited members alone, by refusing. The class was left.

**And the tree had the gap written down.**
`test_walker_c.py::test_they_agree_about_a_nested_variable_struct` asserted
both halves of it on purpose:

> The two still differ about the struct-typed member ITSELF -- C reads one
> byte and answers 3, `walk.py` reads four and answers 0x03616263 -- and
> that is a separate path from the extent this fixes, unchanged by it and
> disagreeing before it. Asserted here so the gap is recorded where somebody
> comparing the two will meet it.

That is the one test the fix breaks, and breaking it is the proof: the
assertion pinning C at 3 now reads 56713827, the same as Python. Pinning a
known disagreement is a good habit and this is what it buys -- the next
person to close the gap cannot do so by accident, and the record cannot go
stale without a test going red.

## The second: descending into a truncated struct

The nested-member path checked the member's measured extent against the
frame (26.800) and never the nested struct's **minimum** against that
extent. So a `negotiated` measuring 32 bits with a minimum of 40 was walked
into, and the variant inside it answered `VERSION` -- a verdict about what
the message says -- for a message that is merely short.

Five readers disagree with that. The Python accessor says it in as many
words:

    BoundsError - negotiated needs at least 5 bytes; 4 given

and the Python walker, which has made this check since 26.577, answers
BOUNDS. `report.py`'s own comment at that check says it is "the check every
backend makes and this could not until the image carried the number" -- the
number was added to the image for the Python walker and the C walker never
read it. **A fix that reached one of a pair of readers**, which is this
tree's recurring failure and the reason the two walkers are compared at all.

The row carries it at offset 16, guarded on `struct_stride >= 20` because
the row grew the field at 26.577 and an older image does not have it.

## What both have in common, and it is the third instance today

Each is a correct fix applied to the case that produced it and not to the
class: the delimited member but not the argument-sized struct, the Python
walker but not the C one. 26.836 was the same (a tag but not a length) and
so was 26.833 (one of two placements, and a two-branch predicate with three
answers).

Four in one day is no longer a coincidence worth noting individually. The
cheap counter-measure is the one that caught all four: **two readers of the
same artifact, compared over a corpus** -- and the expensive part is that
the comparison only asks what the corpus contains, which is 26.836's
lesson arriving from the other direction.
