# 26.921: a first byte can say how wide the number is

Status: recorded
Date: 2026-11-07
Source: re-reading 26.919's "nothing asks yet" against the holder's "anything theoretically a need"

**BER's length could not be described**, and that length sizes everything in X.509,
SNMP and LDAP. Nor could Bitcoin's CompactSize or MySQL's length-encoded integer. A
struct with a `variant` on the first byte reads each one, and cannot hand it to
`u8 body[...]`, as each arm is a different field. All three are one shape: a first
byte below a threshold is the value, and above it a marker for how many bytes hold
it.

    encoding = der;          below 0x80; 0x81 to 0x88, one to eight, high first
    encoding = compactsize;  below 0xFD; FD, FE, FF: two, four, eight, low first
    encoding = lenenc;       below 0xFB; FC, FD, FE: two, three, eight, low first

**One read, and a table for each.** The holder's worry about a builder for each
combination is this question one level down, so the decoder, the length and the
writer are written once and take a table, and a fourth form is a row. `ast.MARKED`
names them. A byte in no row is no number: BER's indefinite `0x80`, which DER
forbids, and MySQL's NULL at `0xFB`. `max_bits` chooses the widest marker the type
admits and `max_bytes` is refused, as for `quic`.

**The table is not in the image.** It names a form by a code in the byte a last
group's bits would have, 200 and up, past anything eight bits of group can be, and
each walker holds the three rows. The rows would need a section and a reader for
what is a published constant, and `tlv`'s by-value parameters have three bytes.

**A schema cannot write its own table.** Rejected for now: a format with a fourth
shape is a row and a release, where declaring one would make the table a language
feature in five readers, to be read from a message nobody has yet.

The witnesses are not this tree's. `example/x509` is a certificate `openssl` wrote,
and `openssl asn1parse` states the 370 the test expects. `example/bitcoin` is the
genesis coinbase, whose double SHA-256 is the published transaction id, which the
test recomputes. The lenenc values are by hand from MySQL's protocol documentation,
and no capture backs them.

**The Bitcoin example found three faults of its own**, being the corpus's first
counted run of records of no one size that each hold a varint length. Python's
`required` summed such a run past 2^32 where the other three saturate. Both walkers
refused a varint length cut short where the backends' `_value` reads zero, so a run
ended an element early and what followed it landed elsewhere. And both held a count
to 2^32 where the backends hold it to the leaf bound of 2^31.

The dissector's plain-Lua stand-in showed such a transaction's `u64` value as
negative. The generated dissector is right: real tshark shows the unsigned number,
and the stand-in now does too.

**Not here.** A tag number past 30 in BER takes more octets of its own, in base 128:
`tag_type = be128` is close and its first byte's five bits are not. HPACK's integer
(RFC 7541, 5.1) begins in the low bits of a byte shared with flags, and CBOR's head
puts a major type above its marker. Each wants a number that starts inside a byte,
which is no varint this tree has. All three are since 26.922.
