# 26.661: A marker decides the order, and the owned form had baked one

Status: recorded
Date: 2026-10-19
Source: written as a record

26.660 found this and left it, being larger than the item that uncovered
it. `endian = from(marker)` is decided by bytes in the message, and the
owned emitter picked an order when the code was generated.

One line, shared by both sides:

	end = "le" if placement.endian is ast.Endian.LITTLE else "be"

A marker-governed field has `placement.endian` of None -- that is what
"the marker decides" means -- so both fell through to big-endian.

## What it cost, in the numbers

`tiff_header [endian = from(byte_order)]` over a little-endian header:

	out->magic       10752       which is 42 byte-swapped
	out->ifd_offset  134217728   which is 8 byte-swapped

And `_decode` returned `SITU_OK`, because it delegates its constraints
to the view's `_validate` -- which reads the marker properly. So the
owned form handed back wrong numbers for a message it had just certified
as valid.

## Why every existing check was green

**The round trip is symmetric, and the two errors cancelled.** `_read`
baked big-endian and `_write` baked big-endian, so
decode-then-encode returned the same bytes for any document, in either
order, with the values wrong in between. 101 cases of
`test_decode_then_encode_returns_the_same_bytes` could not see it, and
neither could `test_owned_code_compiles_under_the_same_warnings`.

It surfaced only because 26.660 made the encoder write a `must_eq`
field's STATED value: writing the correct 42 broke the symmetry, and the
suite reported the correct write as the regression. That is the inverse
of the usual reading and the reason this took a commit to separate --
the first response was to exclude marker-governed fields from the stated
write, restoring the cancelling pair.

## The fix, and the test that can see it

Both sides ask the marker at runtime, using the view's own test spelled
over `data`:

	out->magic = (uint16_t)((situ_get_be16(data + 0u)
	    == SITU_TIFF_HEADER_BYTE_ORDER_LITTLE
	    ? situ_get_le16(data + 2u) : situ_get_be16(data + 2u)));

Encode writes the marker first and reads it back from `data` to order
what follows, so both halves are literally the same expression. Sound
because a marker must precede the fields it governs -- otherwise the
view form could not read them either -- and it keeps the two from
drifting apart, which is the hazard this file's own comments name twice
for bit order.

**`test_a_marker_decides_the_order_the_owned_form_reads` is asymmetric
on purpose**: decode a little-endian TIFF and look at the number.
Demonstrated in three states, which is what makes it a control rather
than a case:

	both sides static      round trip PASSES, the value is wrong
	the read side static   both tests fail
	both fixed             both pass

## Scope, measured

	4  marker-governed whole-word scalars in the corpus
	0  sub-byte
	2  at a dynamic offset -- `edges.marked`, not owned-eligible

Of the four, `edges.marked.n` and `.pad` are in a struct the owned form
does not own, so the population it can reach is exactly tiff's `magic`
and `ifd_offset`. The fix covers everything in range and the measurement
is what says so.

And 26.660's exclusion is gone with its reason: the stated-value write
no longer skips a marker-governed field, because `_write` handles the
order now.

1060 passed over the owned, codegen, checks and endian suites, mypy
clean over 250 files.
