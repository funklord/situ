# 26.734: a counted run of fixed-size records was framed as one

Status: recorded -- fixed in all four
Date: 2026-10-29
Source: `project.md` section 26

Reported by bbq-predictor 2026-10-29, five minutes of their framing fuzz
case against `1605cd8`, and **it is the unsafe direction**: complete
before the message has arrived.

    struct index_body {
        station_id   station;          // variable, 10 bytes here
        i64          generated_utc;
        u16          count  [max = 2400];
        index_entry  months[count];    // fixed 42 bytes each
        u8           trailing[remaining] max 0;
    }

104 bytes with `count = 2`, which `validate` accepts whole:

    have=104  ok  need=62
    have=62   ok  need=62
    have=63   ok  need=62
    have=103  ok  need=62

62 is `20 + 42`: the fixed prefix and **one** entry of the two, held as
the answer to the last byte. A caller trusting it stops reading 42 bytes
early. Their fourth invariant fired -- if the whole input validates, the
`need` bytes validate too -- and their note that it is not a regression
is right: `601fa96` answers the same 62.

## Reproduced in nine lines

    struct ent  { u16 month; u8 digest[40]; }        // fixed, 42
    struct body { u16 count [max = 2400]; ent months[count]; }

`count = 2`, so a whole one is 86 bytes:

    have= 2  truncated  need=44
    have=44  COMPLETE   need=44   <-- 42 bytes short
    have=85  COMPLETE   need=44
    have=86  COMPLETE   need=44

and the generated C says what it did, in its own comment: *"body.months:
a nested `ent` frames itself."* Python answered 44 too.

## The one shape every guard let through

`_nested_framing` delegates to a nested struct's own `required` rather
than adding its extent, because an extent walk stops early when the bytes
run out (26.684). Each of the four emitters guarded it with the same four
conditions: not delimited, not a `while` run, not `is_run`, not
`is_counted_run`.

**An array of fixed-size structs is none of those four and is not one
struct either.** `is_counted_run` excludes a fixed-size element on
purpose -- its docstring says so, *"there is no stride to multiply"* is
the case it exists for -- because such a run wants arithmetic rather than
a walk. So `ent months[count]` fell past every condition and arrived at
the branch for a single nested member.

The fix is one line of condition, and the right place for it is not any
of the four: `traverse.nests_one_struct` folds all five questions into
one, and the four emitters ask it. **Third time this week that the fix
was to make several places ask one question** -- 26.728's frame-layer
predicate against each emitter's own, 26.729's `frameable` against C's
`_required`, 26.733's `gen-checks` against the emitter.

Once declined, the ordinary length path takes it and answers
`count * 42u` -- exact, O(1), and the right answer from the first prefix
at which the count is readable:

    have= 2  truncated  need=86
    have=85  truncated  need=86
    have=86  COMPLETE   need=86

## Why nothing here saw it

**The corpus C output did not change by one byte**, measured by sha256
over header and source for all 46 schemas before and after. No committed
schema has a counted run of fixed-size records inside a FRAMEABLE struct
-- `message.situ`'s `record recs[hdr.rec_count]` is the same construct
and the struct ends in `trailer[remaining]`, which makes it unframeable,
so nothing ever reached the branch.

That is the fourth fault in two days found only from outside or from a
construct deliberately added, and the second this week whose corpus
witness was blocked by one member elsewhere in the struct.

`test/schema/edges.situ` carries `counted_fixed` now, so the C and C++
prefix sweeps and the four-way comparison all see it, and
`test_required_answers_every_prefix.py` pins the shape's answers --
`[5, 5, 5, 5, complete]` for a five-byte message of two rows. On a
`git archive HEAD` export `test_no_prefix_is_reported_complete
[counted_fixed]` fails, which is the safety property by name.
