# 26.744: A run counted by arithmetic was framed as one record

Status: recorded -- fixed
Date: 2026-10-29
Source: `project.md` section 26

26.734's fault again, by the one spelling its fix did not test.
`traverse.nests_one_struct` decides whether `required` frames a member by
delegating to ONE nested struct's own `required`. Its comment names three
ways to spell MANY: a literal `ent e[4]`, a field `ent e[count]`, "or an
expression over one". The condition tested two:

    return placement.array_count is None and placement.sized_by is None

`rec run[a + 1]` carries its count in `size_expr`, so it read as one
nested `rec`. **All four backends ask this predicate, so all four were
wrong the same way:**

    u32 a; rec run[a + 1]; u8 tail;      a = 1: two records, 11 bytes
    required() 5 5 5 5 8 8 8 8 *8 *8 *8 *8      in C, C++, Rust and Python

The message was called complete at eight bytes of eleven. A caller
trusting that parses three bytes that have not arrived, which is the
one-sided property `required` exists to keep.

## How it was found, and why agreement could not find it

It surfaced while checking 26.743's second lens, unsaturated arithmetic in
`required`, by asking all four about `rec run[a + 1]` with `a` at the
`u32` maximum. The answer was 8 where the message claims four billion
records. The corpus differential compares the four with each other, and
four answers from one predicate agree. That is the class the differential
is blind to, and the reason this record is pinned as an exact number
rather than as agreement.

The composed sweep has the shape -- `form = arith`, `element = rec` -- and
passed it for the same reason.

## The fix

`and placement.size_expr is None`. After it, the run falls to the length
path every counted run of fixed records already takes: 11 for the honest
message, and 4294967295 for the hostile count, in all four.

`test_the_differential_frames.py` asserts the eleven-byte answer
sequence, and fails with the condition removed.
