# 26.984: a relation names a constant

Status: recorded
Date: 2026-11-13
Source: the words-by-contexts sweep, carried into relations

`must response.k == kind.ack && response.seq == request.seq + STEP` was
"`kind` is not a message this relation was given": every name in a
relation was read as a path into one of its two messages, so a reply's
kind could be compared with the request's and not with the constant that
names it. A `when`, a bound and a size all fold a `const` and an enum
member.

The parser folds them in a relation's body, in `Parser.finish` before
`wellformed`, so the 26 readers of `Schema.relations()` -- the four
backends' relate, converse and drive layers, the packer, the fuzz
harness, the dissector's conversation key -- are handed numbers rather
than each taught a name. A parameter shadows a constant of its name:
`kind.seq` is a path where `kind` is a parameter. A `must` that reads one
message after folding is still refused as a `when`'s job.

The rest of the sweep through relations found the commands agreeing:
`size`, `count`, `offset`, `sum`, `popcount` and `min` leave a relation
ungenerated, as `relation._check` has always said, in every command
alike, and nothing crashes.

`test_a_relation_names_a_constant` has the four emit it with
`--refuse-ungenerated`, the Python backend and both walkers agree on four
pairs, and checks the shadowing; all eight fail with the fold removed.
