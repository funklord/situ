# 26.961: a struct takes its byte order from its caller's marker

Status: recorded
Date: 2026-11-12
Source: a pcap capture file, described while walking the goal gap

**A whole pcap file could not be described.** Its header's magic says
which byte order the file is in, and every record after it is in that
order. An `endian_marker` governed only its own struct's members, so a
`record` struct -- needed for `record packets[remaining]` -- had no way to
read in the header's order: without a file-level `endian` it was refused
for having none, and with one it read the wrong order half the time. A
TIFF's directory entries are the same shape. 26.833 named the question
("nothing says a marker reaches across" a named struct) and left it.

**The order is handed in as an argument.** A `parameter` may be typed by
a marker, and `[endian = from(m)]` may name one:

    struct record [endian = from(order)] {
        parameter magic order [stream];
        u32 ts_sec; u32 ts_usec; u32 incl_len; u32 orig_len;
        u8  data[incl_len];
    }
    struct pcap [endian = from(magic)] {
        endian_marker magic; ...
        record(order = magic) packets[remaining];
    }

Chosen over letting a marker reach into every struct nested in its own,
for two reasons. That would change what existing schemas mean -- a nested
struct under a file-level `endian` reads in that order today, and
`edges.situ`'s `marked_entry` relies on it -- and it says nothing at the
nested struct about where its order comes from. An argument says it in
the schema, and the parameter machinery already carries one through all
four backends and both walkers: C as a trailing `arg_order` on each
accessor that reads it, the other three on the view.

The argument is the marker as the caller read it -- big-endian, the one
reading that does not presuppose the answer -- and every reader compares
it against the marker's `little` literal, as it compares a marker field.
So each backend's marker gained a plain getter for that raw value
(`situ_pcap_magic_get`, `magic()`, `magic`), which the use site hands
on, and the C walker reads a marker field big-endian where it had
declined for want of a stated order.

**It must be `[stream]`.** It decides how `incl_len` reads, so it moves
`data` and everything after; `check_parameters` holds a size expression
to the same rule for the dissector's sake.

## And `from(m)` naming nothing

`[endian = from(nothing)]` was accepted, and so was `from(bo)` naming a
marker TYPE the struct holds no field of. C called an `is_little` nobody
emits and did not compile, and the walker refused every message: a
misspelt marker reached the author as a C compiler's complaint about a
name the schema never wrote. It is refused at the attribute now. No
corpus schema was affected.

## Verified

`test_a_struct_takes_its_byte_order.py`: a pcap file built in each order
reads two records and validates in all four backends; the values read
through the Python backend are the ones the records were built from; both
walkers accept both files and agree on a record whose length runs past
the end. Files written by `text2pcap` (little-endian) and the same file
byte-swapped read identically, and `capinfos` counts two packets in each.

## Not yet

The dissector follows no byte-order marker at all -- a little-endian
TIFF or pcap shows `version_major 512` -- which predates this and is the
next piece of work.
