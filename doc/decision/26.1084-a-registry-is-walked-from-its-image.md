# 26.1084: a registry is walked from its image, in both walkers

Status: recorded
Date: 2026-11-18
Source: 0070, step 4 -- the holder: "both a walker and the compiled
versions", since a schema may be written at runtime by a GUI editor

**The image carries a registry, and both walkers read it.** Two ancillary
sections, declared in `std/image.situ`:

- `image_registry_entry`, sixty bytes per cell: the registry's and key's
  string ids, the cell's struct, family, safe, what its value is (its bytes,
  a `let` row, or a member's placement), the bounds on the value and the
  bytes, and the default, unit and summary as string ids;
- `image_registry_word`, one row per policy word an entry names, as names.

`walker/registry.py` and the C walker's `situ_walk_registry_find`,
`_check`, `_value` and `_safer` read them: a key found exactly or as a
family's one-word instance, a cell walked as a message of its type through
the same `validate` every walk uses, then the row's bounds, then its value.

**The rows are declarative**: nothing in one is a solved offset, only a
struct index, strings and numbers. So a program that writes rows without
the compiler -- through `std/image.situ`'s own generated accessors, over an
image whose types `situc pack` solved -- is read exactly as a packed one.
That is the runtime half 0070 asks for, and step 5 is writing them.

The C walker reads the strings section now, for keys alone, and reaches
for no libc to compare them: it is written freestanding.

## Measured

`test_a_registry_is_walked`: the 33 cases `test_a_registry_is_generated_in_c`
asks the generated C, through the Python walker and through a C probe over
`situ_walk.c`, all agreeing; the rows' policy words. Sabotaged: an
upper-case family word admitted in the C walker is caught.
