# 26.817: a signature that derives its own offset needs the argument

Status: recorded -- fixed for a member, a run and a variant arm; the
transparent block is 26.818
Date: 2026-11-03
Source: `project.md` section 26; decision 0068 step 5

**Four legal schemas that situc accepted and whose generated C did not
compile**, three of them now fixed and the fourth recorded open. All are
0068 step 5 -- a parent handing on its own parameter -- and none was a
construct anybody had written: they came out of a decision table that
asks one argued child against every parent context.

## What the table is, and why it found these in seconds

For one argued child, every parent context, each case asserted to be in
one of two states:

- **refused** by `check_parameter_nesting`, which is how an unbuilt
  context stays honest -- an unplumbed path in C is a `situc build`
  refusal rather than a wrong byte in somebody's program;
- **generated, and the C compiles** under this project's flags.

The third state -- generated, and the C does not compile -- is what the
table forbids, and it is the state this week met four times already
(26.812, 26.813, 26.814, 26.815). Fifteen cases: ten compile, four are
refused at 0068's stated frontier, and one is refused for a reason of its
own (`positional` declines a dynamic member, which predates arguments
entirely). No case is broken.

Nothing in the corpus asked these questions because **step 4 and 26.811
both used a parent FIELD**, and a field needs none of the plumbing a
parameter needs. Every one of the four was answerable in a few seconds
once the question was asked.

## The fault: one question asked where there were two

`_hands_own_argument` (26.815) asks whether the text handed to the CHILD
names one of this struct's arguments, and its docstring explained that
the base "arrives as a parameter". That is true of `_extent_from` and
false of `_extent` beside it, which derives its own offset -- and
`_base_expression` renders an offset call with the struct's WHOLE
argument list, unconditionally, because that keeps one call site in step
with one definition.

So a body that embeds an offset call names every argument the struct has,
whatever the member hands its child. The schema that shows it hands a
constant:

    struct kid { parameter u8 b [stream]; u8 body[b]; u8 mark; }
    struct p {
            parameter u8 b [stream];
            u8 head[b];                 /* this makes the offset dynamic */
            kid(b = 2) k;               /* and this hands no argument */
            u8 z;
    }

`_hands_own_argument` says no on both sides and says it correctly. The
body reads `arg_b` under a signature declaring nothing:

    static inline uint32_t situ_p_k_extent(situ_view_t view)
    {
            return situ_p_k_extent_from(view, situ_p_k_offset(view, arg_b));
    }

**All three of a plain member, a counted run and a variant arm were wrong
the same way**, which is what said the fault belonged to the predicate
rather than to any one emitter.

## The fix: two predicates, one per shape of body

`_reaches_own_argument` is the wide question -- the handed text OR the
member's own offset -- and `_hands_own_argument` stays narrow and keeps
its name's meaning. Both are cycle-free, and the wide one for a
structural reason worth stating: a member's offset is a sum over the
members BEFORE it, so asking for it cannot reach this member's own
length, and the unbounded recursion that `_hands_own_argument` exists to
avoid cannot form.

Which helper gets which was settled by reading each body rather than by
rule, and the answers are not what the shapes suggest:

- **narrow**: `_extent_from` alone. Its body is `situ_view_sub` over the
  base it was handed, then the child's extent call -- no offset call, no
  count call.
- **wide**: `_extent`, `_extent_at`, the walking `_at`, `_remaining_count`,
  `_run_fits`, the arm's extent helper, and all four `_span` forms. The
  last is the one that reads oddly: `_span_from` takes a start, so it
  looks narrow, and its walk condition calls this run's `_count`, which
  takes the wide tail -- so the body names the argument through that
  call. **A `_from` is not narrow because it takes a start; it is narrow
  if nothing in its body derives anything.**

Each call site moved with its definition, which is what the error
messages walked through one at a time: `arg_b undeclared` where a
definition was short, `too many arguments` where a call site was ahead of
it, and `unused parameter` where one tail served three functions and
over-declared for the one that takes its base.

## The fifth site, which no predicate decides

`_required`'s variant-arm plan called the child's `_required` with no
arguments at all:

    e = situ_kid_required(data + pos,
                    situ_remaining_u32(have, pos), &part);

The other four `required` call sites in the emitter have always passed
`_child_args`, and this one dropped it -- a missing argument rather than
a wrong signature, so no amount of deciding tails would have found it.
The plan now carries the handed text alongside the call it plans.

## The transparent block, closed by 26.818

This record was written with a sixth case still broken and said so here.
It is fixed, and the entry is rewritten rather than appended to because a
reader who finds both believes the one that sounds more careful, and the
old one always does.

    struct p {
            parameter u8 b [stream];
            authenticated body { kid(b = b) k; }
            tag u8 mac[16] covers(body);
    }

What this record said about it was right as far as it went -- the parent
flattens the child's members into its own stale-marking setters, and
`situ_p_k_mark_set` called a `situ_p_k_mark_offset` nothing defines. What
it missed is that the same walk had also emitted `situ_p_k_b_set`, a
writer for a `parameter`, storing at the nested member's base. Byte zero
of `kid` is `body[0]`.

So the compile error was hiding a wrong-byte bug, and anything aimed at
the error message would have shipped it. 26.818 has the two carve-outs
and the corpus measurement that chose between them.

## Verified

- The table is `test/unit/test_a_generated_argument_reaches_its_signature.py`,
  which records a verdict per case rather than asserting "nothing is
  broken" -- the Rust census's reason, from
  `test_a_generated_length_never_wraps.py`: a claim about a whole cannot
  tell a regression from growth. A case that improves fails the test
  with "good news", which is the prompt to move its row.
- `edges.situ` is unchanged by this and all 92 committed images match a
  fresh generation, so the fix changes no output for any construct the
  corpus already had.
- All four backends generate `edges.situ`; the C compiles under
  `-Wall -Wextra -Werror -Wconversion -Wsign-conversion`.
- `make style`, `make typecheck` and `make test-c` pass.
- **The bytes, not just the signatures**, read back against a
  hand-computed layout through C and through Python independently. A
  compile proves a signature agrees with its call; it cannot see a wrong
  offset, which is the fault 26.819 found behind a refusal and 26.818
  found beside one.

  The variant arm at `b = 2`, five bytes: `t`, the arm's extent of 3,
  `z` at offset 4, `required` asking 5, and the child's `body`, its
  `mark` at 2 and its value.

  The base-only spelling with the parent's argument and the child's
  constant deliberately DIFFERENT -- parent `b = 3` sizing `head`, child
  handed 2 -- so a confusion between them is a wrong byte rather than a
  coincidence. Seven bytes: `head` of 3, `k` at 3, its extent 3 (from the
  child's 2, not the parent's 3), `z` at 6, `required` asking 7, and the
  child's own reads. `_extent_from` takes no argument here and `_extent`
  does, which is the narrow and wide pair doing exactly what they were
  split for.

## The lens, which is the transferable part

Three of this week's five faults were *two places answering one question
from different text*. This one is the next turn of that: **one question
asked where there were two.** A predicate named for what a member hands
its child was used for every signature in the family, including the ones
that reach an argument by another route entirely -- and its docstring
stated the assumption that made it wrong, confidently, in a sentence that
was true about the one function its author was looking at.

So when a predicate is shared, the thing to check is not whether it is
right but **how many questions its callers are actually asking.** The
table is what makes that answerable rather than arguable.
