# 26.722: The image ceilings beside the message ones

Status: recorded -- the drivers assert the blob fits before compiling and
`situ-walk-c` refuses an image larger than it reads
Date: 2026-10-28
Source: `project.md` section 26

26.718 and 26.719 are one question asked of two message buffers: where
does a bound quietly substitute one input for another? The image buffers
sit immediately beside them in the same four programs, read the same way,
and were never asked.

    const size_t n = fread(img, 1, sizeof img, f);

Three drivers in `test/unit/test_walker_c.py` and `walker/c/main.c` pass
what they got to `situ_walk_open` without asking whether the file had
more.

## The drivers are the real half, and the headroom is 1.44

`edges.situ` is the largest image in the corpus, and the figure depends
on which form a test packs:

    31202 bytes   `image_for`, which packs without metadata -- the four
                  corpus sweeps
    45538 bytes   `pack(..., metadata=True)` -- what the tests that need
                  struct names by name use

Against `img[65536]`, that is a factor of **1.44**, not the 2.1 the
metadata-free figure suggests. And `edges.situ` is the file this
project's own practice grows: it exists for constructs no worked example
carries, so a struct lands in it per construct, and
`put-the-construct-in-the-corpus` is the standing instruction that puts
it there.

**The failure when it runs out is 26.718's, exactly.** A driver handed a
truncated image fails at `situ_walk_open`, exits 1, trips
`_run_driver`'s assertion -- and all four sweeps catch that and
`continue` under a comment reading "no driver can acquire this shape". So
the first schema to outgrow the array would drop out of the comparison
silently, and then its neighbours as the file grew.

The guard is therefore on the **Python** side, in `_build_driver`, where
the blob is in hand and an assertion is a test failure rather than an
exit status somebody catches:

    assert len(blob) <= DRIVER_IMAGE_MAX

A refusal written in C would land in the same `except AssertionError`
that hid 26.718 for eleven weeks, which is the whole reason this is not
done in the drivers. `DRIVER_IMAGE_MAX` is a claim about C living in
Python, so `test_every_driver_reads_the_image_size_the_guard_asserts`
reads the three `static uint8_t img[...]` declarations back and compares
them: a driver whose array shrank below the figure would read a
truncated image with nothing saying so, which is the thing the assertion
exists to prevent.

## `main.c`'s half is a diagnostic fault rather than a silent answer

Its ceiling is a megabyte, thirty-three times the largest image, so the
margin is not the point. What it did with a file past the ceiling is:

    situ-walk-c: malformed

That is a reader's ceiling reported as a fault in the file -- measured,
not supposed: an image padded to `IMAGE_MAX + 1` says exactly that on the
commit before this one. For a program whose whole job is to say what is
wrong with some bytes, misattributing its own limit to the data is worth
four lines, and it is the same shape as 26.719 in the same function's
neighbourhood: read the whole of it or say you did not.

It refuses by asking whether anything is left rather than by comparing
sizes, because `got == sizeof image_bytes` is true for a file of exactly
that length too:

    const int more = (got == sizeof image_bytes) && (getc(held) != EOF);

## Honestly, this one found nothing

No corpus image exceeds either ceiling, so unlike the three findings
before it this record closes a hole rather than a fault. It is here
because those three were the same shape found after the fact, because the
measurement that makes it worth doing is a factor of 1.44 on a file that
grows by instruction, and because the drivers' failure mode is the one
that already cost eleven weeks of a differential comparing nothing.
