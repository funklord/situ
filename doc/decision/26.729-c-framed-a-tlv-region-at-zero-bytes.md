# 26.729: C framed a TLV region at zero bytes, and the Reader looped

Status: recorded -- fixed in `traverse.frameable`
Date: 2026-10-29
Source: `project.md` section 26

Found by the C arm of 26.725's prefix sweep, on its first run, through the
**non-vacuity assertion rather than through a property**:

    protobuf.situ: 196 calls and not one truncated answer

196 is one `_required` over four fills and forty-nine prefixes, and not one
of them was told the message was incomplete. The function is:

    static inline situ_err_t
    situ_proto_message_required(const uint8_t *data, uint32_t have,
                                uint32_t *need)
    {
            uint32_t at = 0u;
            ...
            { const uint32_t len = (uint32_t)0u; at = situ_need_u32(at, len); }
            *need = at;
            return have >= at ? SITU_OK : SITU_ERR_TRUNCATED;
    }

**`SITU_OK` with `*need = 0`, for every input including an empty buffer.**

## What that costs, in the generated Reader

    situ_proto_message_reader_next(...)
    {
            situ_proto_message_reader_advance(reader);   /* returns at once
                                                            for ready == 0 */
            err = situ_proto_message_required(reader->buf, reader->have,
                                              &need);   /* OK, need = 0 */
            ...
            reader->ready = need;                        /* 0 */
            return SITU_OK;
    }

The header tells the caller *"call `next` until it answers
SITU_ERR_TRUNCATED"*. It never does. **A caller doing exactly what the
documentation says loops for ever, handing back zero-length views**, on an
empty buffer.

That is the hazard `frame.framed_structs` excludes a zero-byte struct to
prevent, in its own words -- *"a zero-byte struct would frame an unbounded
number of empty messages out of an empty stream"* -- reached by a route its
`is_fixed_size and size_bytes == 0` test cannot see, because
`proto_message` is not fixed size.

## The cause: a `tlv` region has no extent to sum

`proto_message.fields` is a `tlv` region. TLV is schema-free by
construction -- items arrive tagged and the region holds whatever was sent
-- so how far it reaches is not a sum over what precedes it. That is the
same statement `frameable` already makes about an `indexed` region, in a
comment two lines away: *"the region reaches wherever its furthest element
ends, which is not a sum over what precedes it"*.

`extent_parts` puts the tlv placement in `variable`, and C's length
expression for it is the literal `(uint32_t)0u`. So C framed every such
struct at the length of its **fixed** members:

| struct | fixed bytes | what C answered |
|---|---|---|
| `protobuf.proto_message` | 0 | complete at 0 -- the loop |
| `coap.coap` | 4 | complete at 4, options split off |
| `edges.tagged_options` | 1 | complete at 1, likewise |

Three structs in the whole tree, and **they are three of the five that
26.692 and 26.728 recorded as "C is the widest"**. C was not wider about
them; it was answering a question that has no answer. C++, Rust and Python
declined all three, and were right to.

## The fix, in one branch of the shared layer

`traverse.frameable` refuses a `tlv` placement, beside the `indexed`
branch it parallels. And C's `_required` **asks `frameable`** rather than
applying its own conditions, which is 26.728's root problem met head on:
the predicate deciding whether to emit a Reader and the one deciding
whether to emit what the Reader calls were different predicates, and now
there is one.

C's own comment at that site already named this case without being able to
see it -- *"True of a bare `tlv` region and useless to say"* -- because its
test is `constant == 0 and not variable`, and `variable` holds the tlv
placement, so the struct fell through to a walk whose only term is zero.

**Measured blast radius: C loses exactly three `_required` functions**,
`situ_coap_required`, `situ_proto_message_required` and
`situ_tagged_options_required`, and gains none. 226 before, 223 after.
Nothing else in the corpus holds a tlv region in its extent.

## What this says about the sweeps

**A property sweep would have passed this, twice over.** 26.725's two
properties are that a truncated answer exceeds what arrived and that
`need` never falls -- and `need` never fell and was never below `have`,
because it was never anything. The assertion that caught it is the
per-schema non-vacuity floor: *this schema answered N calls and not one
truncated*.

That is the fourth time in this run that the thing which found a fault was
a count of what a check asked rather than the check itself, and it is the
argument for writing the companion every time: **a sweep that cannot say
how much it asked cannot tell a sound answer from no answer.**

It also says the C arm earned its place immediately. 26.725 swept C++
because that is where a missing bound is a memory fault; C is where the
widest `required` lives, and the widest one was the one answering about a
region nobody can measure.
