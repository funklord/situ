# 26.1000: COBS adds two, not one

Status: recorded
Date: 2026-11-13
Source: 26.999's lens -- a bound measured only on the input its comment
names -- turned on the other stuffing codes

**COBS declared `ratio_bounded(255, 254) + 1`**, the `+ 1` being the frame
delimiter (0048). Every COBS block also opens with a code byte, and the
ratio's floor adds nothing below 254 bytes, so the encoder writes
`n + n / 254 + 2`: an empty payload is 2 bytes, one byte of content is 3.
Measured with the generated encoder over every length to 2000: the declared
bound is one byte short at 2247 of the 4000 cases, and never over. The C
encoder's own comment already said `len + len/254 + 2`; the signature, the
bounds table and `std/codecs.situ` said one less.

**What it cost.** A consumer sizes an encode buffer from the signature,
which `std/codecs.situ` spells out as `len * 255 / 254 + 1` -- one byte
short for almost every frame. No builder writes COBS (26.998 left it out),
so situ's own generated code was not exposed; a caller sizing by the map
was.

**Why the oracle missed it, again.** `test_differential_oracle` fed 254
nonzero bytes, the comment's worst case. A block that fills exactly needs
no further code byte, so 254 encodes to 256, which `+ 1` happens to
predict. It now feeds 253, where the bound is tight, and `+ 2` is the only
constant that passes. The bound is safe at 254 too, one over.

**Now `+ 2`** in `kernels.STUFFING_BOUNDS`, `std/codecs.situ` (with its
comment) and both std maps. `json_string`, `slip`, `ppp_async`, `hdlc`
and `usb` were measured the same way and hold.
