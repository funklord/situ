# 26.719: The program walked a message nobody gave it

Status: recorded -- `from_hex` refuses what it cannot read whole, and
`main.c` has tests
Date: 2026-10-28
Source: `project.md` section 26

`situ-walk-c` is the embedded walker as a program: what a person runs to
see that `situ_walk.c` works, and the C half of the pair decision 0026 is
argued from. It read its message off the command line with

    static uint8_t message_bytes[MESSAGE_MAX];
    ...
    const uint32_t len = from_hex(argv[2], message_bytes, MESSAGE_MAX);

and `from_hex` took the cap and honoured it in silence:

    while (text[0] != '\0' && text[1] != '\0' && len < cap) {

So three different arguments made it answer about a frame the caller had
not described, and in each case `bin/situ-walk` -- the other walker, same
command line -- answered about the right one:

- **A capture past `MESSAGE_MAX`.** Measured against `example/udp` with
  5000 bytes: the Python tool reads a `length` of 5000 in a frame of 5000
  and validates clean, while this one truncated to 4096 and read the same
  5000 in a frame of 4096. One tool's message is well formed and the
  other's is not, from one line of shell.
- **An odd digit count.** The loop stops needing a pair, so the last
  nibble is dropped; `bytes.fromhex` raises.
- **A digit that is not hex.** `strtoul("zz", NULL, 16)` is 0, so `zz`
  reads as a zero byte; `bytes.fromhex` raises.

All three are one fault. **Two readers of one image are the whole of this
project's claim, and they cannot be compared at all if they are reading
different bytes** -- so a reader that quietly substitutes a message is
worse than one that refuses, and worse in a way no answer it prints
reveals.

## The fix is a refusal, because this program allocates nothing

`from_hex` lexes each pair and reports which of the two things went wrong;
`main` prints it and exits non-zero. `MESSAGE_MAX` and the static buffer
stay, and the comment that chose them stays true -- "a ceiling rather than
an allocation, this program having none". The differ's drivers answer the
same question with an exact-sized allocation (26.317) and the drivers in
`test_walker_c.py` now do too (26.718), but that is an instrument's
answer: it buys sanitizer visibility of a read past the frame, and this is
a program a person runs rather than something anybody fuzzes.

So the ceiling is kept and only the silence is removed. A message at
exactly the cap still reads, which is what makes the new behaviour a
boundary rather than a ban, and the test asserts that case beside the
refusal.

## `main.c` had no test of any kind

Nothing under `test/` compiled it. Every other test of this walker drives
`situ_walk.c` through a driver `test_walker_c.py` writes itself, so the
library is held to the Python walker over the whole corpus on three
questions -- and the program a person actually runs was outside all of it.
That is how a truncation lives for eleven weeks: not because the check was
weak but because the file was not in the population.

Two tests now exist, and the second is the one that matters:

- `test_the_program_refuses_a_message_it_cannot_read_whole`, over the
  three arguments above and the control at exactly the cap. It reads
  `MESSAGE_MAX` out of `main.c` rather than copying the number, so a build
  that raises the ceiling does not leave the test asserting about a figure
  nobody uses.
- `test_the_program_reads_what_the_python_walker_reads`, which maps the
  program's own rendering onto the driver's -- a line carrying `= value`
  is an answer and a line carrying `-- ` is a refusal -- and compares it
  with `python_answers`. It passes on the commit before this one, by
  design: it pins the agreement rather than the bug, so that the next
  change to `main.c` has something to break.

The refusal test fails on the commit before this one, where the program
answers about 4096 bytes of a 4097-byte message and says nothing about the
difference.

## The lens, which is the transferable half

This was found by asking a question the previous two findings had already
earned: **where does a bound silently substitute one input for another?**
26.718 is the same question about the differential's driver, found on the
same day, and 26.317 is the same question about the differ's and the fuzz
harnesses' buffers.

Counted across the tree afterwards, there are five hex decoders. The
differ's C and C++ drivers size exactly, these two walker drivers did not
until 26.718, and this one capped. **The decoder that silently truncated
was the only one in a program somebody runs**, which is the opposite of
where attention had gone.
