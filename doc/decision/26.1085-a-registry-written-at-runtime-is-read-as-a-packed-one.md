# 26.1085: a registry written at runtime is read as a packed one

Status: recorded
Date: 2026-11-18
Source: 0070, step 5 -- the holder: a registry "would need to be written
dynamically at runtime in some cases. As there might be a schema editor in
GUI."

**The cell types are solved once and the registry is written by the
program.** `situc pack` over a schema of structs alone gives the base
image; a program writes the registry's rows -- `image_registry_entry` and
`image_registry_word`, with a strings section of their own -- and attaches
them beside it:

- Python: `walker.registry.build_rows(base, name, cells)` from a list of
  cells (`key`, `type` by name, and the bounds, default, unit, summary,
  safe, window and policy words), and `attach(base, rows)`;
- C: `situ_walk_registry_attach(&image, rows, len)`, the rows written by
  any program -- `build_rows`, or `std/image.situ`'s own generated
  accessors. The rows keep their own string pool, so the walker allocates
  nothing to read them.

**What a cell is worth is read from the base image alone**: its type's
`let value`, found by name, or its one member where that is a text number.
So an editor names a type and never an index. A binary member is not
offered: from the image alone a scalar and a byte run of its width are not
told apart.

`situ_walk_open` now reads its sections through a helper the attach shares,
and asks for the core tables after -- which rows have not got.

## Measured

`test_a_registry_is_written_at_runtime`: rows built at runtime over a base
image packed with no registry answer the 33 cases the generated C answers,
in the Python walker and through a C probe that attaches them; and they
are, field for field and string by spelling, the rows `situc pack` writes
for the same registry. Sabotaged: a value lookup that misses `let value`
fails two; an attach that keeps the base's string pool fails the C probe.
