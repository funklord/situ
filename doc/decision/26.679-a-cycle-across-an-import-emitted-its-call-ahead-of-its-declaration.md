# 26.679: A cycle across an import emitted its call ahead of its declaration

Status: recorded
Date: 2026-10-23
Source: `project.md` section 26

hull's entry 18, reported 2026-10-15 and reproduced here. A three-line
schema that imports a mutually recursive pair and names one of them
generates C that does not compile:

    import "canonical.situ";
    struct holder { form value; }

    one.h:612: error: implicit declaration of function 'r_list_validate'
    one.h:1015: error: conflicting types for 'r_list_validate'

`form`'s `check` calls `list`'s `validate` -- a variant arm is a struct,
and validating the arm is validating that struct -- and `list` is emitted
after `form`.

**The pair alone compiles**, which is what says it is the emission order
rather than the pair: an importing schema emits the two in the order that
puts the call ahead of the declaration. hull's diagnosis said exactly this
and was right about both symptom and cause.

## The fix was a gap in a mechanism that already existed

`_recursive_prototypes` has declared a cycle's `extent`, `extent_at` and
`nesting_at` ahead of their definitions since 0054, with a comment saying
why: "there is no order that puts both above the other, which is what a
prototype is for". The verdict pair was not in that list. It is now,
spelled `static inline` to match the definitions -- which is the form a
recursive struct's `validate` and `check` take, where a non-recursive
one is declared non-static in the header and defined in the `.c`.

So hull's suggestion -- declare every validate and check ahead -- was the
right shape, and narrower than it needed to be: the cycle's members are
the ones that need it, and the mechanism for that was three lines away.

## A second fault, found by asking the other three backends

C was reported; C++ failed too, and differently. With `--prefix r` it
emitted `::situ::list` where every other site in the same header said
`::r::list`:

    one.hpp:646: error: 'list' is not a member of 'situ'

Seven sites in the C++ emitter hardcoded `::situ::` for a GENERATED type
instead of the configured namespace. They are invisible without a prefix,
because the default namespace is `situ` and the wrong spelling is then
the right one -- so every schema in this corpus compiled while any
consumer passing `--prefix` got a header that would not build. hull passes
one.

The mechanical change carries its own proof: 7 generated-type namespaces
moved and **288 `::situ::rt::` runtime references did not**, which is the
property that distinguishes them. The runtime namespace is always
`situ::rt` whatever the prefix.

Rust and Python were clean on the same schema with the same prefix.

## Why no sweep could reach it

This corpus had an import fixture and a recursion fixture and never the
two together. `test/schema/shared.situ` carries constraints on purpose,
its own comment explaining that `check` and `validate` are the two
functions with external linkage and that a shared type with nothing to
check could not show that fault -- so the file was built for precisely
this family and stopped one ingredient short.

**That is 26.675's finding in a second place**, a day later: every dynamic
and compile check here is corpus-driven, so a composition no fixture
carries is a composition nothing exercises. `shared.situ` now carries a
`branch`/`twig` pair and `importer.situ` names it, which puts the shape in
front of the compile gates, the differential and both walkers.

And the prefix half says something narrower that is worth keeping: **a
default that happens to be correct hides every site that ignores the
setting.** `--prefix` is exercised by tests that pass one, and the corpus
sweeps do not, so seven sites could ignore it for as long as nobody
looked. A setting whose default makes wrong code right needs a fixture
that sets it.
