# 26.819: 0068's region refusal is load-bearing, measured

Status: recorded -- a measurement of the frontier, no code change
Date: 2026-11-03
Source: `project.md` section 26; decision 0068 step 5

0068's open section lists three shapes still refused for an argued
member: a `coded` region's member, an `indexed` region's element, and a
struct naming itself. It lists them as unbuilt and says nothing about how
far from built they are. **Measured, by lifting the refusal in a throwaway
export and reading what came out.** The answers differ per region and one
of them is the reason the refusal exists.

The lifting was deliberately crude -- admit any region's interior to
`wellformed._transparent_members`, which is the obvious route and the one
26.811 took for `positional` and `authenticated`:

    elif hasattr(member, "members"):
            found.extend(member.members)

## `sealed`: compiles, and reads the wrong byte

This is the finding. With the refusal lifted the header compiles clean
under the project's flags, and the parent emits a full gated family for
the region's interior -- `situ_p_body_open`, then
`situ_p_body_k_extent`, `..._k_body_len`, `..._k_mark_get`. `k.body` is
right, at offset 0 with length `arg_b`. `k.mark` is not:

    static inline uint32_t situ_p_body_k_mark_offset(situ_view_t view,
                                                     uint8_t arg_b)
    {
            uint32_t offset = 0u;
            offset = situ_advance_u32(offset,
                     (situ_p_body_k_extent_from(view, offset, arg_b)),
                     view.limit);
            offset = situ_advance_u32(offset,
                     ((uint32_t)situ_nonneg_u32(situ_leaf_u64(arg_b))),
                     view.limit);
            return offset;
    }

It advances by `k`'s WHOLE extent and then by `body`'s length -- so
`2b + 1` where `mark` sits at `b`. For

    struct kid { parameter u8 b [stream]; u8 body[b]; u8 mark; }
    struct p {
            parameter u8 b [stream];
            sealed body(sealing) { kid(b = b) k; }
            tag u8 mac[16] covers(body);
    }

at `b = 2` that is offset 5 where the answer is 2, and 5 is inside
`mac`. `situ_in_bounds` passes, because the frame is 19 bytes. So a read
of `p.body.k.mark` returns a byte of the authentication tag.

**The arithmetic treats a member INSIDE `k` as a sibling after it**,
which is what the transparent route asks for: a transparent block holds
the struct's own members, so summing the extents in front of one is
right. For a nested member's interior it is not -- the interior is placed
against that member's own view, which is what `kid`'s own accessors do
and get right.

`_transparent_members`' docstring already said so: *"A sealed or coded
region's interior is a transform's input and is not among them."* That
sentence is the reason the refusal exists, and this is it confirmed by
measurement rather than by reading.

## `coded`: compiles, and emits nothing

No `situ_p_body_k_*` family at all -- the parent exposes nothing for the
region's interior, so a caller goes through the region's view and the
child's own accessors, which take the argument and compute correctly.
Safe by omission rather than by design, and the honest reading is that
the lifting bought nothing here rather than that it worked.

## `indexed`: one missing argument

One error, and it is the shape 26.817 closed four of:

    error: too few arguments to function 'situ_kid_extent'
      in situ_p_cells_at

The indexed `_at` emitter calls the element's extent without
`_child_args`, exactly as `_required`'s variant-arm plan did. Nothing
about the offsets is wrong.

## `self reference`

Still refused by the cycle check rather than by the nesting rule, so the
lifting does not reach it. 0068 rule 6 states the intent -- a struct
naming itself writes its own arguments out -- and a recursive child is
measured with a depth, so this is its own piece of work.

## What this changes

Nothing in the code. What it changes is the frontier's description:

- **The `sealed` refusal is load-bearing and the obvious lifting is
  wrong.** Whoever builds it must place the interior against the nested
  member's own view rather than admit it to `_transparent_members`, and
  the test is a byte and not a compile.
- **`indexed` is a one-argument fix** behind a refusal.
- **`coded` is undecided rather than nearly done**: the lifting produced
  no accessors, so there is no evidence either way about what it should
  produce.

Whether to lift any of them is not this record's to say -- the
`_transparent_members` docstring is a stated rationale, and changing a
decision with one is the holder's. What is recorded here is the cost of
the obvious answer, so that the next pass does not spend the measurement
again.

## The lens

**A refusal lifted that compiles is the most dangerous outcome, not the
most encouraging one.** Two of the three compiled at once, which reads as
"already plumbed" and was wrong for the one that matters. The run that
made this measurement had closed 26.818 an hour earlier on the same
lesson -- a compile error hiding a wrong-byte bug -- and the general form
is the same from the other side: **the compiler cannot see a wrong
offset, so a gate lifted on the strength of a clean build has been
checked by an instrument that cannot answer the question.**
