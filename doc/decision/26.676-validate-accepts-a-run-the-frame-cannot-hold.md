# 26.676: `validate` accepts a run the frame cannot hold

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

`bbq-predictor`'s item 2, confirmed here and in three backends rather than
one. On their `validate_oob` input -- nine bytes, one element, `n = 200`,
so the element claims 203 -- every backend says the message is fine:

    C   validate=0        (SITU_OK)
    C++ validate=0
    rust validate=Ok(())

This is a worse fault than 26.675 for the use case situ was being evaluated
for. That one read past the end *inside* the gate; this one is the gate
returning the wrong answer, and a caller who does everything right is told
a hostile message is well-formed.

## The mechanism

The run's span walk is memory-safe and discards the one fact `validate`
needs:

    while (n < e_count() && at < raw_.limit) {
            ...
            const std::uint32_t size = element.extent();
            if (size == 0 || at + size > raw_.limit) {
                    break;          // and the span SO FAR is returned
            }

With `size = 203` the loop breaks and `e_span()` returns 0. `check` then
asks

    if (situ_remaining_u32(raw_.limit, 1) < e_span())

which is `8 < 0`, false, so the verdict is OK. **Breaking out of the walk
is right for safety and wrong as an answer**: it throws away "an element
declared more bytes than the frame holds", which is precisely the
malformedness `validate` exists to report.

project.md is unambiguous that this is a bug rather than a choice.
Section 14 on readers: "**`validate` calls the strict one.** A field that is
meant to be a number and is not is a malformed message, and that is exactly
what `validate` is for." And section 14.2a calls `validate` answering OK
for a message every backend refuses "the walker's worst shape".

26.27 settled the same question for lengths and stated the rule in two
halves: **the accessor clamps**, so a caller who skips validation is
memory-safe, and **`validate` reports `bounds`**, so a caller who does not
skip it learns the message is malformed. Clamping alone "silently turns a
lie into a truncation". The walk does the first half and drops the second.

## The fix that was tried, and why the gate refused it

**Still open.** A one-line change per backend was tried and is reverted:
a run whose declared count could not be walked returned `UINT32_MAX`, so
`check`'s `remaining < span` was true and the verdict became `bounds`. All
four backends refused the reported input and agreed on the element extent.
Then the full gate failed ten tests, and the two reasons are both the
record's original instinct being right.

**`_span` has four consumers, and the fourth sums it.** This record listed
three -- `check`, the indexed accessor, and the offset of whatever follows
the run -- and missed the enclosing struct's `_extent`, which is literally
`3 + span`. So `3 + UINT32_MAX` is 4294967298 in Python and wraps to 2 in
C: **a sentinel that participates in arithmetic is the same class of bug
as the one being fixed.** Measured, where 27 is pinned:

    AssertionError: ('counted', 9, 4294967298)
    assert 4294967298 == 27

**And `n < count` cannot tell a frame that is too small from a message
that is too deep.** At a `[depth]` cap `extent_at` returns 0 -- with a
comment that says exactly this, "`[depth]`/`[limit]`, not the frame" -- so
the walk's `size == 0` guard breaks for a legitimate reason and the count
falls short with nothing wrong with the frame. The contract is pinned in
`test_recursion.py`: `"counted": {8: (27, 8, True), 9: (27, 9, False)}` --
one level too deep keeps its extent and is refused by the NESTING check,
not by bounds.

## Design 2, in the four backends

Taken on the holder's instruction after the first attempt was reverted:
**the walk reports why it stopped**, as a predicate `check` asks and
nothing else does.

    static inline int situ_top_e_fits(situ_view_t view)
    {
            const uint32_t total = situ_top_e_count(view);
            uint32_t at = 1u, n = 0u;

            while (n < total) {
                    if (at >= view.limit)                  return 0;
                    if (situ_view_sub(...) != SITU_OK)     return 0;
                    size = situ_el_extent(element);
                    if (size == 0u)                        return 1;
                    if (size > situ_remaining_u32(...))    return 0;
                    at = at + size;
                    n  = n + 1u;
            }
            return 1;
    }

Two properties make it right where the sentinel was wrong. **`_span` keeps
its one meaning**, so the enclosing `_extent` that sums it is untouched --
which is what broke last time. And **a zero extent answers yes**, because
it is a `[depth]` cap or a degenerate element rather than a short frame:
`check`'s nesting guard already refuses the first, before this, in the same
function. Treating it as a short frame is what made the first attempt
refuse `[depth]`-capped messages with the wrong error.

Measured on the reported input in all four:

| backend | verdict | `el.c_extent` |
|---|---|---|
| C | `SITU_ERR_BOUNDS` | 4 |
| C++ | `SITU_ERR_BOUNDS` | 4 |
| Rust | `Err(Bounds)` | 4 |
| Python | `BoundsError` | 4 |

`test_recursion.py` passes, all 36 including the four `four_agree` cases,
so the `[depth]` contract the first attempt broke is intact.

## The enumeration, which is the part that was owed

**This verdict has six implementations, not four.** The two walkers are the
other two, and they hold their own copy by construction -- 0026 forbids
importing `situc`. With the backends refusing and the walkers not, measured:

    FAILED test_the_walker_agrees_with_the_compiled_backends[ble/ble.situ]
    FAILED test_the_walker_agrees_with_the_compiled_backends[schema/edges.situ]
    E  + validate 0

So `walker/walk.py` and `walker/c/situ_walk.c` are outstanding. Both carry
the same loop and the same `at + size > limit` the backends no longer use,
and the hook in `walker/report.py` is beside the `FITS_FRAME` check, which
is the walker's form of the comparison this record is about.

**That is the third enumeration failure in this one entry.** The record
first listed three consumers of a run's span and missed `_extent`; it then
said four implementations of the verdict and missed the walkers. Both were
found by a gate or a test rather than by looking, and both were cheap to
look up -- the walker directory is named in `project.md` as one of six
descriptions of every schema. **The lesson is not "enumerate carefully",
which nobody disagrees with. It is that an enumeration written from memory
reads exactly like one written from the tree**, and this entry now has
three instances of the difference.

## The walkers, and the fourth enumeration miss

Both walkers carry the predicate now -- `counted_run_fits` in
`walker/walk.py` and in `walker/c/situ_walk.c`, asked from each one's
`validate` beside its `FITS_FRAME` answer. Three things had to be learned
by being wrong, and the third is the one worth keeping.

**The hook belongs OUTSIDE the `FITS_FRAME` branch.** Asked inside it, the
walker still answered OK for `segments`, which carries no such constraint:
which runs carry `FITS_FRAME` is the packer's to say and is a different
question from which runs are counted runs of variable-size elements. The
predicate decides the second for itself and answers yes for everything
else, so it is asked of every member.

**A refused element is the frame's doing.** `struct_extent` raising
`Refused` was first treated as "cannot say", which left the walker
accepting `oob_run` where every backend refused. `walk.py`'s own walk
treats the same exception as a reason to stop. `TooDeep` and `Unplaceable`
genuinely are "cannot say" and answer yes -- the second because the
generated predicate is emitted only where the element has a computable
extent, so refusing there would be the walker answering a question the
other five do not ask.

**And the definition and the call were keyed on different conditions**,
which is the fourth enumeration failure in this entry and the subtlest.
The predicate was emitted for any counted run of elements with a computable
extent, and called only from the branch that handles a member declaring its
own length. `pieces.two` is `piece two[2]` -- a LITERAL count, which
declares no length of its own and is not fixed-size, so it reached none of
the branches and got no check at all. C emitted
`situ_pieces_two_fits` and never called it.

**Nothing in the four backends could have found that.** A dead `static
inline` in a header raises no warning, the four-way differential does not
compare verdicts (measured: the four `four_agree` recursion cases passed
with the predicate in C alone), and no test asks whether an emitted
function is reachable. What found it was the *walker* refusing where C
accepted -- the disagreement arriving from the fifth implementation, about
a shape the first four all got wrong together. That is the argument for six
descriptions in one sentence: they do not merely cross-check each other's
answers, they catch a question four of them forgot to ask.

The call is computed at the top of each backend's check function now and
prepended to whatever its branches decide, so the definition and the call
read from one condition.

A fourth thing, which cost only minutes but is the kind that costs hours:
the local `fits` collided with an existing `fits` in three of the four
emitters, so `return fits` returned `None` and `fits + [...]` concatenated
a string with a list. It surfaced as a `TypeError` during generation rather
than as wrong output, which is the lucky shape of that mistake.

## A third instance of a guard-width divergence, raised not fixed

Adding `oob_inner` to the corpus made
`test_the_two_walkers_agree_about_which_check_refused` fail on it: the two
walkers agree the message is refused and disagree about which check said
so -- C at a placement guard with no check identity, the Python walk at
`fits_frame`, same member, both answering BOUNDS.

**It is not this entry's verdict and not the new predicate.** Placement 286
is `u8 payload[len]`, a byte run sized by a field, so `counted_run_fits`
declines it at its first guard. What the struct did was reach a divergence
that was already there.

`IDENTITY_APART` is the sanctioned list for exactly this, and its test's
docstring describes the class in these words: "one guard was wider than the
Python walk's, refusing a message-sized run at a placement check where the
other reaches `fits_frame`". Its two existing entries are the same shape as
the new one -- a run whose length a `u32` declares:

| entry | the run |
|---|---|
| `png.situ` `chunk` | `u8 data[length]` after `u32 length` |
| `pickle.situ` `pickle_wstring` | `u16 data[length]` after `u32 length` |
| `edges.situ` `oob_inner` | `u8 payload[len]` after `u32 len` |

So `oob_inner` is listed, which is the mechanism working rather than an
ignore rule: it is provably the shape the list was made for, and it is new
to the corpus rather than newly divergent.

**But three of one shape is a finding.** A list of accepted divergences is
a record of something not reconciled, and at one entry that is a footnote
while at three it is a pattern: whenever a `u32` sizes a run, the two walks
refuse at different guards. Which of them is right is a question about both
-- C's placement guard may be too wide or the Python walk's too narrow --
and that is not a judgement to make while landing something else. Raised
here; the next instance should not be listed without it being answered.

## The two designs, and what each costs

- **`check` refuses on `n < count`, with `_span` untouched.** Small, and
  the extent contract survives. The cost is a wrong diagnosis: a message
  whose bytes are all present but which nests too deeply would be reported
  as a frame that cannot hold the run, and the depth case already has its
  own error. situ is fastidious about diagnostics, so this is a real cost
  rather than a cosmetic one.
- **The walk reports WHY it stopped**, and `check` refuses only on
  frame exhaustion. Correct, and it touches every caller of `_span` and
  `_span_at` in four backends -- all four listed above -- because the
  signature or a companion changes.

The second is what this record first asked for. **It said "a contract
change rather than a patch", and the patch was tried anyway.** That is the
transferable part, and it now has two instances in one session: both times
a quick multi-backend change passed four targeted suites and was caught by
the full gate, and both times the cause was the same -- the change altered
a path whose other callers had not been enumerated. The enumeration is the
work, and it is the half that feels like preamble.

## What was kept

The second wrap found while attempting the fix, which is independent and
correct: `at + size > limit` wraps where `size` comes from `extent` and a
`u32` length field makes it large, and a wrapped sum is smaller than the
truth, which admits the element it was meant to reject. 21 sites across
four backends ask `size > remaining(limit, at)` instead -- two were already
spelled that way and are where the form came from -- and Rust gained
`situ_rt::remaining` for it.

So the memory-safety hole of 26.675 is closed ON THE VALIDATE PATH and
the verdict is not. **Not on every path**: `framed` and `required` still
read past the buffer, which 26.678 records -- bbq-predictor's item 1(c),
reported while this was being written and reproduced at the pushed tip. A
caller must still treat `validate() == ok` as "the bytes are structurally
reachable", not as "the declared runs fit".
