# 26.676: `validate` accepts a run the frame cannot hold

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

`bbq-predictor`'s item 2, confirmed here and in three backends rather than
one. On their `validate_oob` input -- nine bytes, one element, `n = 200`,
so the element claims 203 -- every backend says the message is fine:

    C   validate=0        (SITU_OK)
    C++ validate=0
    rust validate=Ok(())

This is a worse fault than 26.675 for the use case situ was being evaluated
for. That one read past the end *inside* the gate; this one is the gate
returning the wrong answer, and a caller who does everything right is told
a hostile message is well-formed.

## The mechanism

The run's span walk is memory-safe and discards the one fact `validate`
needs:

    while (n < e_count() && at < raw_.limit) {
            ...
            const std::uint32_t size = element.extent();
            if (size == 0 || at + size > raw_.limit) {
                    break;          // and the span SO FAR is returned
            }

With `size = 203` the loop breaks and `e_span()` returns 0. `check` then
asks

    if (situ_remaining_u32(raw_.limit, 1) < e_span())

which is `8 < 0`, false, so the verdict is OK. **Breaking out of the walk
is right for safety and wrong as an answer**: it throws away "an element
declared more bytes than the frame holds", which is precisely the
malformedness `validate` exists to report.

project.md is unambiguous that this is a bug rather than a choice.
Section 14 on readers: "**`validate` calls the strict one.** A field that is
meant to be a number and is not is a malformed message, and that is exactly
what `validate` is for." And section 14.2a calls `validate` answering OK
for a message every backend refuses "the walker's worst shape".

26.27 settled the same question for lengths and stated the rule in two
halves: **the accessor clamps**, so a caller who skips validation is
memory-safe, and **`validate` reports `bounds`**, so a caller who does not
skip it learns the message is malformed. Clamping alone "silently turns a
lie into a truncation". The walk does the first half and drops the second.

## The fix

**A run whose declared count cannot be walked inside the frame returns a
span no frame can satisfy**, which makes `check` report `bounds`. Four
backends, one shape each, conditional on the same declared count the loop
bound is -- a run sized by bytes rather than by a count has nothing to fall
short of, and its walk is what *produces* the count.

    while (n < count && at < limit) { ... }

    if (n < count) {
            return UINT32_MAX;
    }
    return at - start;

**It is 26.556's answer in a second place.** That record fixed `required`
reporting a satisfiable `need` for a length nobody could have sent, and
`situ_need_u32` exists because of it: "saturating makes the answer
UINT32_MAX, which no caller can satisfy, so the verdict is TRUNCATED -- the
honest reading of a length nobody can have sent." The span of a run that
does not fit is the same kind of number.

**The sentinel is spelled 32-bit in all four**, including Rust where
`usize::MAX` was the obvious reach and would have been 2^64-1 against C's
2^32-1. The Rust runtime's own comment names the property that forbids it:
"the two agree about where a member is, and agreeing is the property four
backends over one layout exist to keep." Caught while writing the fix
rather than by the differential, which would have found it the moment
`oob_run` was compared.

**And it is right for the other consumer too**, which was the reason this
record first held the change back. `_span` also places whatever follows the
run, and the old answer put a member after an overflowing run *inside* the
frame, pointing at the wrong bytes -- 26.27's hazard without the wrap. The
saturated span resolves it past the limit, where `situ_advance_u32` clamps
it and the accessor refuses. So the two consumers wanted the same answer
and the worry about `_span` serving two questions dissolved on measurement
rather than being traded off.

**A second wrap in the same walk, found while fixing the first.** The guard
was `at + size > limit`, and `size` comes from `extent`, which for a struct
with a `u32 len` is `4 + len` -- so `size` can approach the whole range and
the sum comes back small, admitting an element that does not fit. It is
`size > remaining(limit, at)` now, which asks the same question and cannot
wrap: 21 sites across four backends, two of which were already spelled that
way and are where the form came from. Rust gained `situ_rt::remaining` for
it, which the pinned sweep in 26.675 also wanted.

## Measured, before and after

Their input, nine bytes, one element declaring 203:

| backend | before | after | `el.c_extent` |
|---|---|---|---|
| C | `SITU_OK` | `SITU_ERR_BOUNDS` | 4 |
| C++ | ASan heap-buffer-overflow | `SITU_ERR_BOUNDS` | 4 |
| Rust | `Ok(())` | `Err(Bounds)` | 4 |
| Python | -- | `BoundsError` | 4 |

The four agree on the extent as well as the verdict, which they did not
before: C said 4, Rust said 0 and C++ read out of bounds getting there.

The regression test in `test_codegen_cpp.py` asserts the verdict now rather
than only that asking for it stays inside the buffer, and `oob_run` in
`test/schema/edges.situ` is what holds the four to one answer from here --
the shape nothing in the corpus had, which is 26.675's finding.
