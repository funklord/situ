# 26.676: `validate` accepts a run the frame cannot hold

Status: recorded
Date: 2026-10-22
Source: `project.md` section 26

`bbq-predictor`'s item 2, confirmed here and in three backends rather than
one. On their `validate_oob` input -- nine bytes, one element, `n = 200`,
so the element claims 203 -- every backend says the message is fine:

    C   validate=0        (SITU_OK)
    C++ validate=0
    rust validate=Ok(())

This is a worse fault than 26.675 for the use case situ was being evaluated
for. That one read past the end *inside* the gate; this one is the gate
returning the wrong answer, and a caller who does everything right is told
a hostile message is well-formed.

## The mechanism

The run's span walk is memory-safe and discards the one fact `validate`
needs:

    while (n < e_count() && at < raw_.limit) {
            ...
            const std::uint32_t size = element.extent();
            if (size == 0 || at + size > raw_.limit) {
                    break;          // and the span SO FAR is returned
            }

With `size = 203` the loop breaks and `e_span()` returns 0. `check` then
asks

    if (situ_remaining_u32(raw_.limit, 1) < e_span())

which is `8 < 0`, false, so the verdict is OK. **Breaking out of the walk
is right for safety and wrong as an answer**: it throws away "an element
declared more bytes than the frame holds", which is precisely the
malformedness `validate` exists to report.

project.md is unambiguous that this is a bug rather than a choice.
Section 14 on readers: "**`validate` calls the strict one.** A field that is
meant to be a number and is not is a malformed message, and that is exactly
what `validate` is for." And section 14.2a calls `validate` answering OK
for a message every backend refuses "the walker's worst shape".

26.27 settled the same question for lengths and stated the rule in two
halves: **the accessor clamps**, so a caller who skips validation is
memory-safe, and **`validate` reports `bounds`**, so a caller who does not
skip it learns the message is malformed. Clamping alone "silently turns a
lie into a truncation". The walk does the first half and drops the second.

## The fix that was tried, and why the gate refused it

**Still open.** A one-line change per backend was tried and is reverted:
a run whose declared count could not be walked returned `UINT32_MAX`, so
`check`'s `remaining < span` was true and the verdict became `bounds`. All
four backends refused the reported input and agreed on the element extent.
Then the full gate failed ten tests, and the two reasons are both the
record's original instinct being right.

**`_span` has four consumers, and the fourth sums it.** This record listed
three -- `check`, the indexed accessor, and the offset of whatever follows
the run -- and missed the enclosing struct's `_extent`, which is literally
`3 + span`. So `3 + UINT32_MAX` is 4294967298 in Python and wraps to 2 in
C: **a sentinel that participates in arithmetic is the same class of bug
as the one being fixed.** Measured, where 27 is pinned:

    AssertionError: ('counted', 9, 4294967298)
    assert 4294967298 == 27

**And `n < count` cannot tell a frame that is too small from a message
that is too deep.** At a `[depth]` cap `extent_at` returns 0 -- with a
comment that says exactly this, "`[depth]`/`[limit]`, not the frame" -- so
the walk's `size == 0` guard breaks for a legitimate reason and the count
falls short with nothing wrong with the frame. The contract is pinned in
`test_recursion.py`: `"counted": {8: (27, 8, True), 9: (27, 9, False)}` --
one level too deep keeps its extent and is refused by the NESTING check,
not by bounds.

## The two designs, and what each costs

- **`check` refuses on `n < count`, with `_span` untouched.** Small, and
  the extent contract survives. The cost is a wrong diagnosis: a message
  whose bytes are all present but which nests too deeply would be reported
  as a frame that cannot hold the run, and the depth case already has its
  own error. situ is fastidious about diagnostics, so this is a real cost
  rather than a cosmetic one.
- **The walk reports WHY it stopped**, and `check` refuses only on
  frame exhaustion. Correct, and it touches every caller of `_span` and
  `_span_at` in four backends -- all four listed above -- because the
  signature or a companion changes.

The second is what this record first asked for. **It said "a contract
change rather than a patch", and the patch was tried anyway.** That is the
transferable part, and it now has two instances in one session: both times
a quick multi-backend change passed four targeted suites and was caught by
the full gate, and both times the cause was the same -- the change altered
a path whose other callers had not been enumerated. The enumeration is the
work, and it is the half that feels like preamble.

## What was kept

The second wrap found while attempting the fix, which is independent and
correct: `at + size > limit` wraps where `size` comes from `extent` and a
`u32` length field makes it large, and a wrapped sum is smaller than the
truth, which admits the element it was meant to reject. 21 sites across
four backends ask `size > remaining(limit, at)` instead -- two were already
spelled that way and are where the form came from -- and Rust gained
`situ_rt::remaining` for it.

So the memory-safety hole of 26.675 is closed and the verdict is not. A
caller must still treat `validate() == ok` as "the bytes are structurally
reachable", not as "the declared runs fit".
