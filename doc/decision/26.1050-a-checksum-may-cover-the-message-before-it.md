# 26.1050: a checksum may cover the message before it

Status: recorded
Date: 2026-11-17
Source: openmlx4's vpd.situ (inbox 20261114T0041Z); the holder's word,
2026-11-17: "if there conceivably exists a protocol that needs a feature,
we do it, and we do it properly"

**PCI VPD's RV checksum could not be stated.** RV is one byte inside a
keyword field, inside the VPD-R resource, inside a list of resources, and
it makes every byte of the image from the first through itself sum to
zero. `covers` names regions of the struct holding the tag, and RV's
bytes are the message's: the field that holds it is wherever the keyword
walk put it. The codec existed (`byte_sum(width = 8, negate)`); the
coverage did not. The question that held it was whether the capability
lattice, which section 0 rule 1 makes authoritative, can say that a
write ANYWHERE ahead of a tag leaves it stale.

## The rule

    checksum u8 sum[1] covers(before) is vpd_sum;

covers every byte of the message ahead of the tag. `before` stands alone
in the list, and not with `prefix(...)`, which no format combines with it.

**The lattice says it as coverage.** Ahead is placement order, which is
message order within one instance of a struct: every member placed before
the tag, in the struct declaring it and in every struct that holds that
one, is `Covered` by it, and its setter marks the tag's bit. A tag under a
run is covered by every member, since an earlier element's members precede
a later element's tag whatever their order in one element. Nothing after
the tag is covered, and the tag is not its own coverage. It is recomputed
last among a struct's tags, its span holding all of theirs. The wire
signature lists the members each copy covers.

**The span is the message's.** In the struct that declares the tag, C's
`covered` answers offset 0 and the tag's position in the message, reached
through the view's owner, as a located member is; C++ through `raw().owner`;
Python through the view's message; Rust, whose views hold none, takes it --
`sum_covered_in(msg)`, `sum_compute_in(msg)`, `sum_check_in(msg)`, as
`nesting_in` does. A view with no message is BOUNDS. An enclosing struct
carries the tag's dirty bit, and its sum is asked of the declaring struct.

## What is still open

The walkers and the dissector do not verify such a tag: the image carries
coverage as a run of members, and this is none, so the packer writes no
coverage row and the dissector declines it, as for any tag it cannot
locate. No reader there claims a wrong sum.

The dissector was tried and set aside. A `byte_sum` kernel in its Lua is
a dozen lines, but a nested struct is dissected over a sub-tvb, so its
offset 0 is the struct's, and Wireshark's Lua gives no way from a sub-tvb
back to the message's own -- which is itself usually a lower layer's
sub-tvb. It needs the message's tvb carried through every generated
dissector, entry and exit, and that is the size of the job.

## Measured

`test_a_checksum_covers_the_message_before_it.py`: an image `tag, field,
field` whose second field is RV. C, C++, Rust and Python answer the span
as bytes 0 to 9, compute RV's value, and check OK, and CHECKSUM with RV
off by one; Python's module passes `mypy --strict`. `image.tag` and
`image.first.kw` are covered by both RV copies, `image.second.kw` by the
second only, and the last tag by nothing; `set_tag` marks the second's
bit. Without the coverage step the two staleness cases fail. `map`,
`advise`, `wire`, `doc`, `gen-checks`, `gen-tamper`, `gen-dissector`,
`gen-fuzz` and `pack` run over the schema.
