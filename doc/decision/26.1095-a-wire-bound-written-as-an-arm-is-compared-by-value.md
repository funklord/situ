# 26.1095: a wire bound written as an enum arm is compared by its value

Status: recorded
Date: 2026-11-18
Source: fuzznet, inbox 20261118T2010Z -- `make schema` failing on an
unchanged `spool/message.situ` since 26.1094

**26.1094 made fuzznet's committed contracts read as breaking against
themselves.** The signature records a bound's value, not its spelling
(0041), so once a bare arm was read as the arm `must_eq=data` rendered as
`must_eq=4`. The comparison read the two as text and reported
`fzn_msg_data[1]: type: must_eq=data -> must_eq=4; no message satisfies
both` -- four BREAKING findings over a file nobody changed, where the same
bytes satisfy both.

## The rule

`compare` resolves a constraint's value against the member's own enum
before comparing, as it already reduced a hex literal to its decimal value
(26.1010). Each side resolves against its OWN signature's enum block, which
every signature carries (`enum NAME ...` and its `arm=value` line), so an
arm renumbered between the two builds is still the break it is.

`wire --check` on such a file still reports a change -- compatible -- and
asks for the contract to be regenerated, which is right: the committed text
is not what situ renders today. What it no longer does is call it breaking.

## Measured

`test_a_wire_bound_by_arm_is_its_value`: an arm against its value is not
breaking, an arm against another value is; with the resolution disabled the
first fails. fuzznet's five affected contracts (`log/gather`,
`node/reconcile`, `notes/sync`, `record/exchange`, `spool/message`) report
"changed compatibly".
