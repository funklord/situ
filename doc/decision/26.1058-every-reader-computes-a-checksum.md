# 26.1058: every reader computes a checksum, and a span refuses what does not fit

Status: recorded
Date: 2026-11-17
Source: the holder's word, 2026-11-17, to make both walkers check
checksums; 0051 keeps a checksum out of `validate`, so this is a probe
beside it rather than a verdict inside it

**Six readers describe a layout, and none compared a checksum.** Every
backend generates `_compute` for a checksum whose codec situ derives
(0053), and the differential asked only whether the tag's bytes were
there. The Python walker could compute one since 26.579 and only
`situ-edit` called it; the C walker read none of the three image tables
that say how. So the one member whose value is a function of the others
was the one member nobody compared.

## The rule

- The differential asks `name.sum <n>` or `name.sum refused` of a tag
  whose codec all three code generators derive, with no prefix, no
  `covers(before)` and a whole-byte width -- each backend's own
  `_compute`. `fourway` links the derived C into the C and C++ drivers.
- The Python walker's listing prints the same line from
  `walker/derived.py`, and the C walker has `situ_walk_sum`, reading the
  tag, codec and kernel-table sections it used to skip. The loop is
  written twice, as `derived.py` already argued; the polynomial is the
  packer's, derived once.
- A sum over a pseudo-header (TCP, UDP) is declined before the bytes are
  asked about, in both walkers: no message can supply its prefix.

**And `_covered` refuses a covered member whose declared length does not
fit the frame, in all four backends.** The first walker comparison found
it: a PNG chunk declaring more data than the message holds. The accessors
clamp a declared length, so C's span ended where the frame ended and
`_compute` returned a CRC of bytes the sender never covered, answered as
if it were the message's; the walker, measuring the declared length,
refused. `validate` already calls such a message malformed with the same
fit checks, and the span now asks them too (`_covered_fits`). A caller
checking a truncated chunk is told it cannot be checked, rather than
told a value that will not match for a reason it cannot see.

## Measured

- Four ways, over the ten corpus schemas with a derived checksum: no
  disagreement. PNG's IEND CRC is `0xAE426082` and RFC 791's header
  `0xB861` in all four, and with C's sum skewed by one, PNG disagrees.
- The Python walker against C's driver over the corpus (`test_walker`),
  and `test_a_walker_checks_a_checksum` pins both walkers to PNG, IPv4
  and ICMP's published values and to each other over 8 schemas -- 84 sums
  compared as values. With the C walker's reflected loop skewed, PNG's
  published CRC fails.
- Random lengths never fit a PNG chunk and TCP and UDP sum a
  pseudo-header, so those three compare refusals in the sweep; the
  published values hold PNG.
