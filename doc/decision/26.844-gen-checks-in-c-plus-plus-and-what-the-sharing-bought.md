# 26.844: gen-checks in C++, and what the sharing bought

Status: recorded -- all nine kinds in `--target cpp`, 1172 checks compiled
and run over 42 schemas, green on the first corpus run
Date: 2026-11-03
Source: 26.838 and 26.842, which moved the arithmetic out of the backends

## The port was the vocabulary, not the logic

`situc/codegen/cpp/checks.py` is about 700 lines and **not one of them
computes which value a member must hold, where its bytes land, which arm a
message carries or what a probe pattern is.** All of that is in
`situc/codegen`, shared with `--target c` and `--target python`:
`PROBE_BYTES`, `placed_bytes`, `required_pattern`, `required_run`,
`digit_pattern`, `selected_arms`, `reserved_policy`, `passes_unknown`.

So the three backends cannot disagree about the question, only about how
each language spells the answer -- and the measurement says so. Inverting
the C++ emitter's byte order fails **129** decode checks across 27
schemas, which is the same 129 the Python backend gives for the same
sabotage of its own emitter. Two backends agreeing is evidence only when
they are not each computing the answer, and that is the distinction
`situc/codegen/differ` exists for one level down.

**That is the return on 26.838 and 26.842 stated as a number**: the first
language's nine kinds took a day and found five defects on the way; the
third language's nine took an afternoon and found two, both of them in C++
signatures rather than in anything the map says.

## What the corpus found, which is the only thing that found anything

**A driving field's setter takes the message.** Writing a field that sizes
another moves where the members after it start, so the write has to bump
the generation and the signature is `set_nla_len(message &, u16)`. The
first version emitted `set_nla_len(1)` and g++ refused it for `netlink`,
`pickle` and `png`. The fix asks `invalidating_members` -- the same
predicate the emitter branches on, so the check cannot drift from the
signature it is calling -- and re-acquires a fresh view after the write,
as the Python kind does and for its reason.

**An empty suite printed a ratio of nothing.** `example/register` is every
struct a bus transaction and `example/protobuf` has none with a minimum,
so both produced a `main` announcing "0 of 0 check(s) failed" -- the
vacuous pass, indistinguishable from a suite that checked everything and
found nothing wrong. The corpus gate refuses that exact string, which is
how it was caught, and the empty case now says which of the two reasons
applies.

Neither was found by review, and neither could have been: one is a C++
signature and the other is a sentence only a gate reads.

## The controls

| sabotage | what failed |
|---|---|
| the C++ emitter's byte order | 129 decode checks over 27 schemas, plus 33 "the baseline does not validate" |
| the C++ store writing 0 | 267 round-trip checks over 34 schemas, and nothing else |

The 33 are the constraint kinds' own control arm firing: each check
requires `validate` to ACCEPT the baseline before breaking a field, and a
wrong byte order makes the baseline invalid. It says so rather than
mis-asserting a refusal about the wrong thing -- which is what that arm is
for, and it is the only reason those 33 read as a diagnosis rather than as
noise.

## And the list itself had already drifted

Written down because it is the day's own shape appearing in the cheapest
possible place. Each backend carried its own tuple naming the nine kinds,
and the two did not agree: `--target cpp` called the sixth "`reserved` is
enforced" and `--target python` called it "`reserved` must be zero". One
kind under two names.

That is 26.839's defect (a layout naming an arm's member `s.body.arm`
where the placement is `s.body.<reserved0>`), 26.836's (a flag read by one
reader and not the other) and 26.841's (a minimum read by one walker and
not its pair), in a tuple of strings. Nothing broke and nothing would
have: a reader comparing the two generated files would simply have
believed there were ten kinds, or that one backend checked something the
other did not.

`CHECK_KINDS` is in `situc/codegen` now and both read it. The lesson is
not about lists -- it is that **the same fault reappears at every scale,
and the smallest instances are the ones nothing is watching.**

## What remains

`--target rust` has no `gen-checks`, and by this entry's argument it is now
the cheapest of the three to add: the arithmetic is shared and the only
open question is Rust's vocabulary for acquiring a view, writing through a
setter and reading a sub-view's offset. The pinned-run body still widens
the `must_eq` kind by the 18 byte-run pins all three backends decline.
