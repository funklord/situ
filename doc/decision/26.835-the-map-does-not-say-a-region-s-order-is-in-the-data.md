# 26.835: the map does not say a region's order is in the data

Status: recorded -- a finding about what a published axis claims, not fixed;
whether `REPR` should carry it is the holder's, because consumers read it
Date: 2026-11-03
Source: 26.833, found while checking what `situc map` says about the three
constructs that entry added to the corpus

26.833 was the generated code reading a region's tag, table entry and length
prefix in a static byte order inside a struct whose order comes from an
`endian_marker`. That is fixed. This is the same omission one layer up, in
the capability map rather than in the accessors.

## What the map says

For a marker-governed FIELD it says so. `example/tiff`:

    tiff_header.ifd_offset  ... repr=ConditionallyConverted(byte_order)

For a marker-governed REGION it does not. `test/schema/edges.situ`:

    marked_tag.opts     offset=AbsoluteStatic(0x02) size=Unbounded
                        repr=MemoryIdentical ...
    marked_index.cells  offset=AbsoluteStatic(0x03) size=Unbounded
                        repr=MemoryIdentical ...

`MemoryIdentical` is the axis saying the bytes are the value as they stand.
After 26.833 the generated readers for both of those consult the marker to
read a tag and an offset entry, so the interpretation of those bytes depends
on another field of the message -- which is exactly what
`ConditionallyConverted` exists to say, and the axis does not say it.

A consumer reading the map would conclude no conversion is involved. That is
the map understating a region, and section 18's whole claim is that the map
is a product rather than a comment.

## Why this is not being fixed here

**It is a question about what a published axis means, and consumers read
it.** A region's `REPR` describes how its bytes relate to its value, and a
TLV region's value is its items rather than a number -- so whether the tag's
conditional order belongs on the region's `REPR`, on a per-item axis that
does not exist, or nowhere at all is a modelling decision and not a
one-line correction.

Two facts that bear on it, both measured:

- **`CANONICAL` already treats a marker specially and `REPR` does not.**
  `tiff_header` reports `canonical=CanonicalGiven(byte_order)`, so the
  propagation does carry a marker onto a struct-level axis; `marked_tag`
  reports a bare `canonical=NonCanonical`. Whatever is decided, those two
  axes disagree today about whether a marker is worth naming.
- **No corpus schema has a multi-byte scalar FIELD inside the same struct
  as a marker-governed region**, so the two cases have never been seen side
  by side in one map until these three structs landed. `marked_index.n` is
  a `u8`, which has no byte order, which is why its `MemoryIdentical` is
  correct and not another instance of this.

## What would settle it

A consumer asking the map whether it may copy a region's bytes between two
messages of the same schema. If the answer depends on both messages' markers
agreeing -- and it does -- then the map has to say so somewhere, and the only
axis that currently can is `REPR`.

Until then this is recorded rather than raised: nothing is blocked, the
accessors are correct, and the map is merely quieter than the code.
