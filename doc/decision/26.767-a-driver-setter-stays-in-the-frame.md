# 26.767: A driver's setter stays in the frame

Status: recorded -- fixed
Date: 2026-10-30
Source: `project.md` section 26

    struct located_tail { u8 n; u8 v[n]; u8 spot; u8 payload[2] at spot; u8 tail; }

`spot` sits after `v[n]`, so its offset is a sum the message chose, and it
drives where `payload` is, so C emits its setter from `_shifting_setters`,
the family that bumps the message generation. That family stored at the
offset with no test that the frame reaches it. With `n = 255` in a whole
three-byte message the offset clamps to the frame's end and the store
lands one byte past it -- ASan, heap-buffer-overflow, on a message the
view accepted. The plain and covered setters have tested this since 26.27,
and C++, Rust and Python's setter for the same field does nothing where it
does not fit; C's driver setter was the one write without it.

It now asks `_fits`, as the covered setter does, wherever the driver's
offset is not a constant. In the corpus `located_tail.spot` and
`negotiated.kind` gain the test; nothing else changes.

## How it was found

The lens 26.765 left: every C setter in the corpus called over buffers of
exactly the struct's minimum, three bytes more and forty more, filled with
00, FF, 41 and 02, with values 0 and all-ones, under ASan and UBSan. One
failure in 45 schemas, this one; the probe schemas of 26.758 to 26.766
gave none.

## Tests

`test_a_driver_setter_stays_in_the_frame.py` writes `spot` in the
three-byte message under ASan and asserts nothing was written. With the
guard removed ASan reports the overflow in `situ_located_tail_spot_set`.
