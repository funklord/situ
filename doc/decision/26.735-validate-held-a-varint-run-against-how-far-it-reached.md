# 26.735: validate held a varint run against how far it reached

Status: recorded -- fixed in all four backends and both walkers
Date: 2026-10-29
Source: `project.md` section 26

Found while reading C's `_varint_run` for the feature 26.733 leaves open.
Its docstring says a run that stops early "lets `validate` report the frame
as short rather than the accessor inventing a length". **`validate` did not.**
Measured on

    struct r { u8 n; uvar v[n]; }

over `{ 3, 0x01, 0x01 }` -- three varints declared, two present:

    count=3 span=2 validate=SITU_OK

The same in C++, Rust and Python, and in both walkers. Six readers agreed,
so neither the corpus differential nor the walker sweeps could see it, and
they agreed on the unsafe answer: a message missing an element called valid.

## The mechanism is 26.676's, one construct along

`check` compared the frame against the run's `_span`. A span is how far the
walk REACHED, and the walk stops at the frame, so `remaining < span` can
never be true and the comparison was vacuous for every varint run. 26.676 is
exactly this for a counted run of RECORDS, and it gave that shape `_fits` in
the four backends and `counted_run_fits` in the walkers. The varint run
(26.683) arrived afterwards with its own walk, and the walkers' predicate let
it through on `type_struct == NONE` -- "no element struct" read as "nothing
to walk".

## The fix

The backends already had the answer: `_span_min`, which `required` asks for
the reason 26.683 gives. It equals the span where the walk completed and
exceeds what the frame holds where it did not. So `check` now holds the frame
against `_span_min` as well, in all four, which refuses the short run and the
run whose last element is cut off, and accepts the whole one.

The walkers had no such function, so each gains the verdict where 26.676's
lives: `walk._varint_run_fits` beside `counted_run_fits`, and in C
`varint_run_bits` reports whether it placed every element through a new
`whole` out-parameter, which `counted_run_fits` passes through. Only the
answer is new. The walk already counted what it placed.

A `[remaining]` run of varints is out of scope here: no backend emits it
(26.733), and the frame has no count to fall short of.

## Verified

`test/unit/test_a_varint_run_short_of_its_count.py` runs the three cases
through the four built backends and both walkers, and asserts the verdict as
well as agreement, because agreement held throughout. Controls: with the
emitter changes stashed the four answer `validate 0` for the short run, and
the Python walker and C walker each fail with their own fix stashed.

## And a driver 26.733 left calling what C stopped emitting

The suites for this change found three walker tests red on master, and red
before it -- confirmed against a `git archive HEAD` export. 26.733 made C
decline `_count` and `_at` for `uvar v[remaining]`, and moved the question
to `traverse.elements_are_countable` so `gen-checks` would ask it too. The
four-way differential's C driver, in `situc/codegen/differ.py`, was a third
asker and was not moved: it went on calling both functions, so every
four-way build over `edges.situ` failed to compile. The run that made 26.733
did not run the walker suites, which are the ones that build it.

`differ.py` asks the predicate now and asks nothing of a member all four
decline. That is the third consumer of the one question, and the rule 26.733
states -- one predicate rather than conditions in several places -- holds
only for the places that were found.

`test_a_run_of_varints_is_walked` counted `_span_min` as having one caller,
`required`. `check` is a second, on purpose, and the test now reads C's
source as well as its header: `check` is in the source, so the header alone
had counted one caller fewer for C than for the other three.
