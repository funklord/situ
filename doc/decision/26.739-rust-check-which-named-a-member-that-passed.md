# 26.739: Rust's `check_which` named a member that passed

Status: recorded -- fixed
Date: 2026-10-29
Source: `project.md` section 26

Found while writing 26.737's Rust check. Rust's `check_which` sets a
member's id on the line before each refusal, and a nested member's check
is a `?;` line -- `self.file()?.validate()?;` -- which counts as a refusal
whether it refuses or not. So on a clean walk the id stayed set. `bmp`'s
`check_which` returned `Ok(())` with `*which` naming `info`, the last
nested member, while its doc comment says `NO_CHECK` where nothing
refused.

And a `when ... refuse` after the members was reported against that
member too. C sets an id only inside the branch that refuses, so its
message refusals report NO_CHECK, and the two backends disagreed about
which member a refusal names.

`*which` goes back to NO_CHECK once every member has passed, ahead of the
message refusals, in any struct whose checks include a `?;` line.
`test_codegen_rust.test_check_which_names_the_member_that_refused` has
no nested member and could not see this; its sibling
`test_check_which_is_no_check_after_a_nested_member_passes` runs a clean
walk, a nested refusal and a message refusal under `-D warnings`, and
fails with the fix stashed.
