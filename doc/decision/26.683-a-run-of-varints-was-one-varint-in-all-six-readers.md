# 26.683: A run of varints was one varint, in all six readers

Status: recorded
Date: 2026-10-23
Source: `project.md` section 26

Reported by bbq-predictor as item 3 of its evaluation: `uvar v[n]` compiles,
emits accessors, and `required` reports 3 bytes for a message holding 5.

`project.md` has documented the construct since it first described the
capability axes -- "`access` of an array of varints is `Sequential`, never
`Random`" -- so this is not a feature nobody asked for. It is a documented
one nobody implemented, and the document's own sentence is what says the
cost of implementing it correctly.

## The fault

**Six readers, all wrong the same way, so they agreed.**

The four backends dispatch a member on the shared classifier or, in C, on
`placement.varint`. Both routes answered "a varint" for `uvar v[n]`:

- **C** dispatched on `varint is not None`, which is true of a run, and
  emitted the SINGLE varint's `_get` and `_len`.
- **C++, Rust and Python** asked `traverse.classify`, where `data_sized`
  claimed the member first and answered `VARIABLE` -- a byte region. They
  emitted the run's bytes with no way to read an element.
- **Both walkers** took the varint branch of `content_bits` and measured
  one element.

So every member after the run was placed on top of it. `_len` is the length
of the FIRST element, and the offset chain is a sum of lengths, which makes
the error compound rather than cancel: with three varints of 2, 1 and 1
bytes, `tail` was placed at the second element rather than after the third.

**And `required` reported a truncated message complete.** That is the half
worth naming separately, because it is the one a network caller acts on.
The span walk stops at a truncated element -- correctly, the lax-reader
convention this tree uses everywhere -- so two bytes of a six-byte message
gave a span of zero, a total of two, and `SITU_OK`. A caller would have
stopped reading and parsed a message missing four bytes.

## The fix

**One predicate, `traverse.is_varint_run`**, because this is exactly the
spelling the backends have twice parted on: `uvar v[n]` is sized by the
data, `uvar v[3]` carries a literal count, `uvar v[(n + 1) * 2]` carries
arithmetic, and all three are runs. `classify` answers `VARINT` for it
ahead of `data_sized`, and the four backends ask the same question.

**Four accessors rather than two**, in each backend:

- `_count` -- the count the message declares, bounded.
- `_span` -- the sum of the elements' own lengths, which places every
  member after the run.
- `_span_min` -- the bytes of the elements that are whole, plus ONE for
  each not yet there. `required` asks this one. A varint is at least a
  byte, so it is a true lower bound and can never report a complete
  message short; it saturates, because a declared count of four billion
  is a need nobody can satisfy rather than a sum that wraps (26.556).
- `_at(index)` -- the value, reached by walking, because an element's
  offset is the sum of the lengths before it. That is the documented
  Sequential cost rather than a shortcut nobody declared.

Both walkers gained the matching span walk, and the element reader each
already had (`situ_walk_element`, `report._element`) gained the branch --
in the existing entry point rather than beside it, so the differential's
`ELEMENTS` ask compares the two walkers on run elements for free.

Measured across all six, on `{3, 0x81 0x01, 0x05, 0x06, 0x77}`: count 3,
span 4, `tail` at byte 5, values 129, 5 and 6, index 3 refused, and
`required` over every prefix answering 2, 5, 6, 6, 6 and complete at 6.

## Two things the first draft had wrong

**It returned the raw value, dropping the zigzag transform.** A `svar` run
would have read -1 as 1 and 1 as -2, with nothing in the frame looking
wrong. The single-element path has always applied the transform; the run
was written from the length accessor rather than from the getter, and
inherited the half that does not decode.

**And `required` asked `_span`.** That is what produced the SITU_OK above
-- the fix for the offset chain, applied unchanged to the one caller for
which a shorter answer is dangerous rather than merely wrong. Measured as
soon as `required` was asked over every prefix length rather than over the
whole message, which is the probe shape worth keeping: a framing function
has one answer per prefix and testing it on a complete message tests the
one case that cannot fail.

## Nine consumers, found one gate at a time

The title says six readers and the fix touched nine things, which is the
part worth carrying forward. **This classification has nine consumers**,
and the first pass wired six:

1. the C backend,
2. C++, 3. Rust, 4. Python -- the four that emit accessors;
5. `walker/walk.py`, 6. `walker/c/situ_walk.c` -- the two that read
   without `situc`;
7. `codegen/differ.py`, which generates the differential's own drivers
   and probed the run for `_len` and `_value`;
8. `codegen/c/build.py`, the forward builder, where the signature came
   from the varint branch and the body from a synthesised walk over the
   element's `_required` -- a struct name taken from the varint TYPE;
9. `codegen/c/fuzz.py`, which told a run of records from a run of bytes
   by `type_name in structs` and so asked for `_len` and `_ptr`.

**Seven, eight and nine were each found by a gate run**, one per cycle, at
roughly an hour apiece. What makes the list worth writing down is that
nothing enumerated it: each consumer was discovered by the failure it
produced, and three of the nine answer "what shape is this member" in
three different spellings -- `placement.varint`, `traverse.classify`, and
`type_name in structs`.

So for the next construct: **ask who dispatches on member shape before
writing the first branch.** `test_codegen_c.py::_c_consumers` names five
C consumers deliberately, for exactly this reason -- "a dict rather than a
guard aimed at one of them, because that is how the question below went
unasked of the rest" -- and it is the nearest thing to the inventory. It
does not include the differ, the builder or either walker.

## Why nothing caught it

**The corpus had no varint run.** `edges.situ` has had a varint DRIVER
since varints landed -- `varint_driver`, where a varint sizes an array of
something else -- and never a varint as the ELEMENT. The differential
compares six readers and cannot see a construct none of them is asked
about, which is `evidence.md`'s vacuous pass with six witnesses instead of
one. `edges.varint_run` is the fixture.
