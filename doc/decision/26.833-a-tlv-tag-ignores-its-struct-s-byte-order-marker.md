# 26.833: a tlv tag ignores its struct's byte order marker, in four backends, differently

Status: recorded -- a defect with a reproduction, four backends affected and
disagreeing with each other; the fix is not yet made
Date: 2026-11-03
Source: 26.832, whose closing section named the shape and said to establish
whether it had an input. It has one.

26.832 fixed a two-branch byte-order predicate in the new conformance check
and noted that the sibling helper in the emitter still had the same shape:

    # situc/codegen/python/emit.py
    def _byte_order(endian: ast.Endian | None) -> str:
        if endian is ast.Endian.NATIVE:
            return '("big" if NATIVE_BIG else "little")'
        return '"big"' if endian is ast.Endian.BIG else '"little"'

A `None` endian means the order is resolved at run time from an
`endian_marker`. There is no branch for it, so it falls into `little`. All
four `None` endians in the corpus sit in `tiff_header`, which has no table,
no TLV and no length prefix -- the three things that call this helper -- so
nothing failed, and that is the arrangement in which the question cannot be
asked rather than evidence that the answer is right.

## The reproduction

    target buffer;
    bit_order msb_first;

    endian_marker byte_order : u16 {
        little = 0x4949,
        big    = 0x4D4D,
    }

    struct marked2 [endian = from(byte_order)] {
        endian_marker  byte_order;
        tlv options (
            tag_type = u16,
            tag_decode = { kind = tag >> 8, length = tag & 0xFF },
            tag_identity = kind,
            value_size = switch (kind) { default: length },
        );
    }

`situc build` accepts it without a warning in every target. What the four
emit for the 16-bit tag:

| target | the tag read |
|---|---|
| Python | `int.from_bytes(data[at:at + 2], "little")` |
| C | `situ_get_be16(situ_base(view) + at)` |
| C++ | `situ_get_be16(situ_base(raw_) + at)` |
| Rust | `situ_rt::read_be(self.bytes, at, 2)` |

**None of the four follows the marker, and they do not agree with each
other.** Three read big unconditionally and one reads little
unconditionally, in a struct whose declaration says the order is
`from(byte_order)`. A file written by the C writer and read by the Python
reader has its every tag byte-swapped.

That is worse than a wrong answer. Section 1's claim is one schema yielding
byte-exact accessors in four languages; here one schema yields two wire
formats, and the disagreement is invisible because no corpus schema puts a
TLV, a table or a length prefix inside a marker struct.

## What makes it a defect rather than an unsupported construct

The same struct's plain field is handled correctly:

    def count(self) -> int:
        return self._read(2, 2, signed=False, big=not self.byte_order_is_little)

So the machinery exists, is correct, and is reached by one consumer of the
byte order and not the others -- **a value with two consumers where only
some are wired**, which is this tree's most productive lens and the shape
26.832 was itself an instance of.

The reader can reach the marker. `_options_read` is an instance method on
the view and `byte_order_is_little` is a property of that same view; the C
and C++ readers take `view`/`raw_`, and the Rust one takes `self`. So
emitting the conditional form is possible in all four, and nothing about the
construct forces a static answer.

## Scope

`_byte_order` has three call sites in the Python emitter -- an indexed
table's entry, a TLV tag, and a size or length prefix -- and none guards
against `None`. The counted-array form `u8 payload[count]` does **not** go
through it: that length is a plain field read, and it is correct. So the
exposure is the three, and the TLV tag is the one with a reproduction so
far; the other two are the same helper and want their own inputs before
anything is claimed about them.

## Not fixed here, and why that is deliberate

Two reasons to record before changing it. The fix touches four backends and
a runtime helper each, which is its own piece of work rather than a rider on
the conformance check that found it. And **the fix wants a differential test
first**: a vector file over this schema with the marker set both ways, read
by all six readers, is what turns "three backends agree" into evidence --
agreement among three that are all wrong is exactly what this entry is
about.

The alternative fix is to refuse the schema, on section 17.0's rule that a
schema stating what the generated code does not enforce is worse than one
stating nothing. That is weaker than reading it correctly when reading it
correctly is available, and it is available, so it is the fallback rather
than the plan.
