# 26.833: a tlv tag ignores its struct's byte order marker, in four backends, differently

Status: recorded -- fixed: three reads, two placements, four backends. The
three constructs are in the corpus and the gate that could not see it now
plants its magics, so it fires without the fix and passes with it
Date: 2026-11-03
Source: 26.832, whose closing section named the shape and said to establish
whether it had an input. It has one.

26.832 fixed a two-branch byte-order predicate in the new conformance check
and noted that the sibling helper in the emitter still had the same shape:

    # situc/codegen/python/emit.py
    def _byte_order(endian: ast.Endian | None) -> str:
        if endian is ast.Endian.NATIVE:
            return '("big" if NATIVE_BIG else "little")'
        return '"big"' if endian is ast.Endian.BIG else '"little"'

A `None` endian means the order is resolved at run time from an
`endian_marker`. There is no branch for it, so it falls into `little`. All
four `None` endians in the corpus sit in `tiff_header`, which has no table,
no TLV and no length prefix -- the three things that call this helper -- so
nothing failed, and that is the arrangement in which the question cannot be
asked rather than evidence that the answer is right.

## The reproduction

    target buffer;
    bit_order msb_first;

    endian_marker byte_order : u16 {
        little = 0x4949,
        big    = 0x4D4D,
    }

    struct marked2 [endian = from(byte_order)] {
        endian_marker  byte_order;
        tlv options (
            tag_type = u16,
            tag_decode = { kind = tag >> 8, length = tag & 0xFF },
            tag_identity = kind,
            value_size = switch (kind) { default: length },
        );
    }

`situc build` accepts it without a warning in every target. What the four
emit for the 16-bit tag:

| target | the tag read |
|---|---|
| Python | `int.from_bytes(data[at:at + 2], "little")` |
| C | `situ_get_be16(situ_base(view) + at)` |
| C++ | `situ_get_be16(situ_base(raw_) + at)` |
| Rust | `situ_rt::read_be(self.bytes, at, 2)` |

**None of the four follows the marker, and they do not agree with each
other.** Three read big unconditionally and one reads little
unconditionally, in a struct whose declaration says the order is
`from(byte_order)`. A file written by the C writer and read by the Python
reader has its every tag byte-swapped.

That is worse than a wrong answer. Section 1's claim is one schema yielding
byte-exact accessors in four languages; here one schema yields two wire
formats, and the disagreement is invisible because no corpus schema puts a
TLV, a table or a length prefix inside a marker struct.

## What makes it a defect rather than an unsupported construct

The same struct's plain field is handled correctly:

    def count(self) -> int:
        return self._read(2, 2, signed=False, big=not self.byte_order_is_little)

So the machinery exists, is correct, and is reached by one consumer of the
byte order and not the others -- **a value with two consumers where only
some are wired**, which is this tree's most productive lens and the shape
26.832 was itself an instance of.

The reader can reach the marker. `_options_read` is an instance method on
the view and `byte_order_is_little` is a property of that same view; the C
and C++ readers take `view`/`raw_`, and the Rust one takes `self`. So
emitting the conditional form is possible in all four, and nothing about the
construct forces a static answer.

## Scope

`_byte_order` has three call sites in the Python emitter -- an indexed
table's entry, a TLV tag, and a size or length prefix -- and none guarded
against `None`. The counted-array form `u8 payload[count]` does **not** go
through it: that length is a plain field read, and it was correct
throughout. So the exposure is exactly those three, and the section below
gives each one its input.

## Three sites, not one, and each had an input

The record first said "the tlv tag is the one with a reproduction so far"
and left the other two call sites to their own inputs. Both have one, so
the scope is three reads times four backends.

| the read | the construct that asks |
|---|---|
| a tlv tag | `tlv opts (tag_type = u16, ...)` |
| an indexed table's offset entry | `indexed(offset_type = u16, count = n)` |
| a `prefixed(T)` value length | `value_size = switch (k) { default: prefixed(u16) }` |

Each was static in all four backends before this, and each reads
conditionally in all four now.

## Two placements, not one, and one omission written twice

**An indexed offset table inside a marker struct is the same defect.** A
`u16` entry was read little by Python and big by C, C++ and Rust, and the
cause is a second copy of the first one: the `indexed` placement is built in
its own place in `situc/layout.py`, and it carries its own copy of the same
comment, from the same earlier fix, missing the same field. 26.665 had
found both placements carrying NO endian at all, set `endian = scope.endian`
on each, and left `marker` unset on each -- so one omission, written twice,
re-entered twice.

That is the lens worth keeping: **a fix applied to two sites can be
incomplete at both in the same way**, and finding it at one says nothing
about the other. Both now take `marker = scope.marker`.

## The fix

`scope.marker` onto both placements, and then each backend's read of a tag
and of a table entry asks `placement.marker` and emits the conditional form
its field reads have used all along -- `_marker_predicate`, which every
backend already had. One predicate per backend, so a reader cannot disagree
with itself about what the marker said.

All four thread the **placement** rather than its endian through the tlv
chain now, where three of them threaded a bare `ast.Endian | None` and so
could not have asked the question at the leaf even had anybody thought to.
One word per concept, four backends.

**And demonstrated at run time rather than read off the emitted source**,
which is the evidence worth keeping. One buffer, four bytes after the
marker, read through the Python accessors with only the marker changed:

    marker=little  tag=0x0201
    marker=big     tag=0x0102

The same two bytes, two values, the marker deciding -- which is what the
schema says and what none of the four backends did before. The offset table
answers the same way, bytes `00 05` through `cells_offset(0)`:

    marker=little  entry=1280
    marker=big     entry=5

Verified beside that: all four generate for each of the three constructs;
the generated C, C++ and Rust compile under the codegen gates' own flags
(`-D warnings` for rustc, which a hand-compile with `-A warnings` does not
show, and which caught an `unused_parens` in the Rust read); the tag, the
table entry and the `prefixed(u16)` length read conditionally in each; the
four-way differential passes over the corpus; `make test-c` passes 2619
tests with `edges_checks.c` regenerated; and `make cross-test` -- whose
schemas are `header`, `tiff` and `edges`, and whose whole subject is the
host marker constant following the build -- passes on aarch64 under qemu
with the big-endian variant compiling clean.

Generating every corpus schema for all four targets before and after the
change differs only in `edges`, purely additively, with no line removed
anywhere: the refactor that threaded the placement through four tlv chains
is output-neutral everywhere the construct does not appear.

## The construct is in the corpus now

`test/schema/edges.situ` already had `endian_marker edge_order` and a
`struct marked [endian = from(edge_order)]`, acquired when a marker-governed
field at a dynamic offset crashed two backends. It held fields and an array
-- **neither of the two constructs that ask this question**, which is why
nothing failed for as long as it did.

`marked_tag` and `marked_index` are there now, and `SCHEMAS` is globbed from
the filesystem, so every sweep in the suite picks them up without a list to
update.

## Why the gate could not see it, and what closed that

**The four-way differential planted no magics**, so it could not have
caught this. `test_backends_agree_under_random_bytes` drew random buffers
and asked all four; `fourway.magics` plants a schema's declared constants
and draws a marker BETWEEN its two literals, with a docstring saying that
is exactly what keeps both branches covered. The differential called `draw`
and not `planted`.

The arithmetic is the point: the little branch is taken only when the first
two bytes are exactly `0x4949`, which random bytes reach about once in
65536, against 48 buffers per schema. So the one test whose job is
cross-backend agreement was, on a marker struct, a test of the big branch
alone. The walker tests do plant -- which is why planting exists at all --
but they compare Python against the image walker rather than the four
against each other.

It plants now. That is strictly a widening by `planted`'s own contract
("additive: this can only reach cases nothing reached before"), and the
corpus stays green under it: 44 passed, 3 skipped.

**And the loop closes, which is what makes any of this evidence.** With the
two `marker = scope.marker` lines reverted, the widened differential
reports *the four disagree* on `edges.situ`; with them it passes. A gate
nobody has watched fail is not a gate, and this one has now been watched
failing on the exact defect it exists to catch.

## One thing not touched

A struct used as an element inside a marker struct keeps the file's declared
order rather than the marker's: `marked_entry.value` resolves to `BIG` under
`endian big` even when reached through `marked_index`. That may well be
right -- a named struct has its own scope, and nothing says a marker reaches
across one -- but it is a question about what `from(marker)` means rather
than a defect, so it is left alone and named here.
