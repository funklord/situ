# 26.715: the same width in the other pointer backend

Status: recorded -- fixed; closes the half 26.714 left
Date: 2026-10-28
Source: `project.md` section 26

26.714 fixed a heap-buffer-overflow read in C -- a text number's declared
digit width passed to `situ_parse_uint` with nothing checking the frame
had those bytes -- and left C++ to its own change, which wanted its own
control. This is that change. **The analysis is 26.714's and is not
repeated**; what is here is the C++ half and what differed.

## It was the same in both places

    if (situ_parse_uint(situ_base(raw_) + (situ_advance_u32(0,
            lead_len(), raw_.limit)), 4u, 10u, 9999u, &value) != 0)

Two sites, matching C's two: the fallible getter and the non-failing
`_value`. C++ has its own `_fits` with the same docstring and the same
20.2 argument, so the fix is the same question asked of the same
predicate -- `bounds` where it answers, nothing where it does not.

Rust and Python are safe by language: both slice rather than point, so a
short frame raises or panics instead of reading on.

## One thing nearly reported that was not there

C++ renders the offset `+ (0)` for a text number at a constant offset,
and the first reading of that took it for the *moved* construct's getter
spelling its dynamic offset as zero -- which would have been a wrong-byte
fault rather than a bounds one, and a much larger finding. It was a
constant-offset sibling in another struct. The dynamic one renders
`situ_advance_u32(0, lead_len(), raw_.limit)` correctly, and there is no
divergence between the backends about where the digits start.

## Proofs

**One file, eight lines**, exactly as in C: `test/schema/edges.hpp`, and
46 of 46 corpus headers compile. No worked example changes, for the same
reason -- none puts a text number after a variable-length member.

**Two-sided, with C++'s own artifact and not C's.** The C crash input
does not reproduce it here -- `gen-fuzz --target cpp` builds a harness
that takes a different input shape -- so the control needed its own:
sixty seconds of `cpp_edges` built from the unfixed generator finds it,

    ==14284==ERROR: AddressSanitizer: heap-buffer-overflow
    SUMMARY: ... runtime/c/situ.h:1018 in situ_parse_uint(...)

and the fixed build runs that artifact clean, with the guard verified
present in the rebuilt header first. Afterwards `fuzz-cpp` reports no
crash in 45 harnesses.

**The C artifact not reproducing it is the part worth keeping.** A
cross-backend fix verified only by the first backend's input would have
looked proved and tested nothing here: the two harnesses are generated
separately and reach the accessor by different paths. Each backend's
control has to come from its own fuzzer.

The test asserts the guard **per method** rather than counting the
header, and that correction is the entry's one methodological note: a
global count said the guard should appear twice and the right answer is
three, because `validate` carries a fits check of its own for the same
member. Counting the file asserted something the test did not mean.
