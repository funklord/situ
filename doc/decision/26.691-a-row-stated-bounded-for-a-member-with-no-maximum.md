# 26.691: A row stated Bounded for a member with no maximum

Status: recorded -- fixed
Date: 2026-10-26
Source: `project.md` section 26

`situc map` on

    varint_type uvar { encoding = leb128; max_bits = 32; }
    struct r { u8 n; uvar v[remaining]; }

died with a bare `AssertionError` out of `propagate._parameterise` and no
diagnostic. Section 17.0 forbids that twice over: the compiler neither
worked nor refused in words.

## Two questions wearing one value

A varint's own extent is one to five bytes, which is where the `varint`
row's `SIZE := Bounded` comes from and it is right about the encoding.
**How many bytes the MEMBER holds is a different question**, and for
`uvar v[remaining]` the frame answers it -- so there is no maximum, and
`_parameterise`, whose job is to render that value's two numbers, had
only one.

The row computes its SIZE effect now, `Unbounded` where the layout found
no maximum, with the reason naming the run rather than the encoding.

**The value was never the symptom**, which is worth saying because it is
what makes this kind of bug survive. `unbounded-size` fires on the same
member and the meet reaches `Unbounded` either way, so the rendered map
would have been right if anything had got that far. What crashed was
rendering the varint row's own `Bounded` before any meet happened. A test
asserting the axis alone would have passed against the broken code.

And the assertion says what it means now. It encodes a real invariant --
a row claiming `Bounded` for a member with no maximum is a bug in the row
-- so it stays an assertion rather than becoming a diagnostic, but a bare
`AssertionError` tells a reader nothing about which row or which member.

## What it uncovered and did not settle

With the crash gone the construct builds, and the four backends split: **C
emits `situ_r_v_count` and the other three decline** with "this backend
cannot resolve how many elements it holds". So `uvar v[remaining]` means
something in one language and nothing in three.

That is a gap rather than the ambiguity this was first reported as. The
reading is not in doubt -- varints until the bytes run out, which is what
C implements and the only thing the spelling can mean -- so there is
nothing here for section 17.0 to refuse. What there is, is three backends
short of a construct, and C alone in answering, which is the arrangement
this tree has been burned by repeatedly: the three that decline fail
loudly and the one that answers is the one nobody checks.

Not implemented here, because three backends gaining a construct is a
feature and this was a crash. `edges.situ` has no such member either, so
`test_the_backends_refuse_the_same_members` cannot see the split -- which
is the same corpus argument 26.689 makes three times over.
