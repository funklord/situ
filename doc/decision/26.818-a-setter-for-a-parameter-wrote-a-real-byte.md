# 26.818: a setter for a `parameter` wrote a real byte

Status: recorded -- fixed in C
Date: 2026-11-03
Source: `project.md` section 26; decision 0068 step 5

**The compile error was hiding a wrong-byte bug, and fixing the compile
error alone would have shipped it.** This is the case 26.817's decision
table recorded as its one BROKEN row, and reading it rather than patching
the signature is what found the second fault.

    struct kid { parameter u8 b [stream]; u8 body[b]; u8 mark; }
    struct p {
            parameter u8 b [stream];
            authenticated body { kid(b = b) k; }
            tag u8 mac[16] covers(body);
    }

A tag's covered members get a setter that marks the tag stale, so the
message refuses to be transmittable until the tag is recomputed. The
emitter walks the covered entries and wrote two of them:

## The loud half

`situ_p_k_mark_offset` is never emitted -- an implicit declaration -- and
the setter calling it takes no argument either. That is what the table
reported, and it is the smaller fault.

## The quiet half

**`b` is a `parameter`. It occupies no bytes.** `kid`'s own emitter
declines to give it an accessor and says why in a comment -- *"No
accessor for `b`: it is a `parameter`, which the caller supplies and
which occupies no bytes"* -- and only this path got it wrong. A parameter
reaches the covered-entry walk with `kind=field` and `offset_bits=0`,
exactly like anything at the start of its struct, so the walk emitted a
writer that stores at the nested member's base.

Byte zero of `kid` is `body[0]`. So `situ_p_k_b_set` writes the first
byte of the payload, named for a value that is not in the message at all.

It is `static inline` in a header and nothing calls it, so no warning
fires and the unit cannot be reached while the header does not compile.
That is the hazard rather than a mitigation: the header's one visible
error is in the function beside it, and a reader who adds the missing
offset function and a tail has a compiling header with a silent
corrupting writer in it.

## The fix: two carve-outs, both measured against the corpus first

The filter that selects covered members already carried three carve-outs
of this shape -- a run's element, an arm inside a sealed region, and a
member whose offset has no function -- each from a defect. These are the
fourth and fifth:

- **A `parameter` is not a field.** Unconditional: there is no byte to
  write.
- **A field inside a nested MEMBER at a dynamic offset.** The `[]` test
  already in the filter is this rule for a run's element; the general
  case is any nested struct, because a struct emits offset functions for
  ITS members and not for the interior of one of them -- that member's
  own type does, against a sub-view. A transparent region is the opposite
  case and must not be caught: `sealed`, `coded`, `authenticated` and
  `positional` hold the struct's own members, so the struct addresses
  them itself.

**The test is the offset rather than the nesting, and that was measured
rather than chosen.** Over the 46 corpus schemas there are 95 covered
scalar fields. Eighteen are inside a nested struct member and work,
because the member is fixed size so the interior sits at a static offset
the parent addresses with constants -- a carve-out on nesting alone would
have deleted all eighteen. Four are at a dynamic offset and work, and all
four are inside a `sealed` region rather than a nested member. **Zero are
inside a nested member at a dynamic offset, and zero are parameters**, so
the two carve-outs together remove nothing the corpus has.

## Verified

- Generated output for all 46 schemas is **byte-identical** to HEAD's
  in all four backends -- 230 files, compared file by file against a
  `git archive HEAD` export. The change removes no accessor any existing
  schema had, which is also why `make test-c` cannot differ from HEAD's
  result: it compiles exactly these bytes.
- The table's `authenticated block` row moves from broken to compiles,
  and the row was moved only after the test failed with its "good news"
  message, which is what that arm is for.
- The flattened setters are gone from the generated header and `kid`'s
  own `situ_kid_mark_set`, which addresses the field correctly against a
  sub-view and takes the argument, is untouched.
- `make style`, `make typecheck` and `make test-c` pass.
- **The reads that survive are right**, checked at byte level rather than
  inferred from the removal: the block case at `b = 2`, nineteen bytes,
  gives `k`'s extent 3, `mac` at offset 3 reading 0xE0 through 0xEF,
  `mac_covered` answering (0, 3), `required` asking 19, and the child's
  own `body` and `mark` -- `situ_kid_mark_set` being the setter a caller
  should use, against a sub-view, taking the argument. The covered span
  is the part worth checking: it is what the removed setters existed to
  mark stale.

## The lens

**A compile error is a reason to read the file, not a thing to silence.**
26.817's table reported this case as one error message; the second fault
was four lines above it and would have survived any fix aimed at the
message. The run that found it had already been warned by its own
record -- 26.814's control existed because a comfortable explanation
that ends an investigation costs more than no explanation -- and the
general form is worth keeping: **when a generated unit does not compile,
read what else that emitter produced for the same member.** It was wrong
about two of three.
