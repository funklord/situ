# 26.1166: a text number's spelling, rule by rule

Status: recorded; built in the four backends, both walkers and the map
Date: 2026-11-23
Source: the holder, relayed by fuzznet (inbox 20261123T1050Z): "Shouldn't
this be programmable in situ?", of leading zeros; and the holder's
direction for this run, that text parsing be specified more granularly.

## What was not the schema's

Leading zeros were already the schema's to allow or refuse, on every
form and in all four backends (project.md 8.6.2, and
`test_a_text_number_spelling_is_the_schemas.py`). Three rules were not:

- **`[minimal]` tied two rules together.** It refuses a leading zero
  and, above radix ten, an upper-case digit. A format whose one spelling
  is upper case -- Intel HEX records, a MAC address as most tools print
  it -- or one that refuses leading zeros and takes either case, could
  not be described.
- **`+7` was refused whatever the schema said.** A sign is one optional
  `-`; formats that write `+` -- CSV exports, FIX, many log formats --
  could not be read.
- **`-0` was refused whatever the schema said.** The integer parse calls
  it a second spelling of zero; the scaled parse accepts it, because
  JSON emits it.

Each refusal was situ choosing for the author, which is what the holder
asked it not to do.

## The rules

On a text number, each one rule and each defaulting to what situ did
before, so no schema changes meaning:

| attribute | says | default |
|---|---|---|
| `[leading_zeros = refused]` / `allowed` | whether `007` is a spelling of 7 | allowed |
| `[hex_case = lower]` / `upper` | the one case above radix ten; the other is refused | either |
| `[plus_sign]` | a leading `+` is a spelling of a non-negative value | refused |
| `[negative_zero]` | `-0` is a spelling of zero (signed only) | refused |

`[minimal]` stays, and is exactly `leading_zeros = refused` with
`hex_case = lower` -- or `upper`, where the schema says so beside it. It
is refused beside `leading_zeros = allowed`, `[plus_sign]` or
`[negative_zero]`: one spelling per value and a second spelling allowed
are a contradiction, and situ says so rather than picking.

**The map follows.** A text number is `Canonical` where it refuses
leading zeros (or has a width), fixes its case above radix ten, and
admits neither a `+` nor a `-0`; otherwise `NonCanonical`, as now.

**The builders write the schema's spelling**: lower case unless
`hex_case = upper`, never a `+` or a `-0`, so what they write every
reader accepts.

**The walkers** read the spelling rules from the image; a number that
admits a `+` or a `-0` is one their parse does not take, and they
decline it (`cannot-say`) rather than refuse a frame the four accept.

## Rejected

- **A free-form pattern** (`[spelling = "[+-]?[0-9]+"]`): a regular
  expression per field is a grammar inside a field, which situ does not
  generate (README, *What it will not do*), and six readers would each
  need one.
- **Changing a default.** `+7` refused and `007` accepted are what every
  schema written so far was checked against.

## Built

`layout.spelling_rules` turns the attributes into the bits the runtime's
new `digits_spelled` takes (1 no leading zero, 2 no upper-case digit, 4
no lower-case one); `traverse.spelling_check` emits the old
`digits_minimal` wherever the rules are `[minimal]`'s, so no schema
written before generates anything new. `parse_uint_plus` and
`parse_int_signs` take a `+` and a `-0` where the schema says so. The
image's spelling row carries the rules above the radix's byte; a number
admitting a `+` or a `-0` makes the walkers decline its struct. `wire`
writes each rule beside `minimal`.

Held by hand-worked verdicts on 21 spellings in all four backends
(`test_a_text_number_spelling_is_the_schemas.py`), the refusals and the
map there, and `[minimal, hex_case = upper]` building `FF,` in all four
builders and passing the Python walker (`test_the_four_builders_agree`).
