# 26.889: Alignment in the holder's coordinates, and radiotap

Status: recorded
Date: 2026-11-06
Source: the holder's yes to 26.667, and `example/radiotap`

    variant channel_field switch (has_channel) {
        case 1:  channel  channel_data [align = 2];
        case 0:  nothing  channel_absent;
        default: error;
    }

Radiotap has two dozen optional fields behind a `present` word, each aligned
to its own size from the start of the header. It was reported as waiting on
a message-relative offset. It was not, and that report was wrong twice over.

## What radiotap needed

**Not the message.** The header's start and the message's start agree only
when the header is at byte 0. Inside a capture record they need not, and a
field must not move because of what stands in front of the header.

**Not a pad inside the arm's struct either.** A struct whose length depended
on where it sits could not be measured by itself, and an arm value (26.881) is
made before it is placed.

**The struct that holds the variant.** A `pad_to` arm already measures from
there. Two variants on one flag, a pad and then the field, read correctly at
a constant offset before this record began. What refused was the builder, and
what broke was a run-time offset.

`[align = n]` is the spelling. On a plain member it is a pad and the member.
On an arm the parser lowers it to a variant of pads on the same discriminant,
`<variant>_align`, where an arm that does not ask aligns by one. Every reader
keeps the shape it has.

## Two variants on one discriminant

26.881 kept this refused for want of a consumer, and the holder's rule since
is that a shape a sane protocol needs is ours: a kind field selecting a head,
then common members, then a kind-specific tail, is one. A second variant on a
discriminant now takes its own arm value, and the builder refuses values whose
tags disagree (`Part.agrees`).

**A variant of pads takes no value at all.** `_fold_pads` gives each of its
arms to the matching arm of the variant directly behind it, as `ArmOf.lead`,
so the caller says `channel` once and the pad comes with the arm. Every
backend reads the same plan, so this cost each of them two lines.

## A pad arm at a run-time offset

Its length depends on where it starts, so it is not a term to add. Every
member after one lost its accessor while `validate` went on calling them:
Python raised `AttributeError`, and the corpus had only ever had one at a
constant offset.

**The obvious fix is the fan-out again.** "Align if the flag is set" repeats
the running offset in both branches, and twenty fields double the text twenty
times. Aligning to one does nothing, so the choice goes in the unit:

    align_up(F, (8 if self.has_tsft == 1 else 1), len)

`F` appears once, and `traverse.arm_alignments` says when this applies. A
variant holding a pad arm beside bytes cannot be both a thing to align by and
a thing to add, at a run-time offset, and is refused with the spelling that
works.

## Two faults found on the way, neither radiotap's

**Bytes after a pad were read from the wrong place, in three backends.** C
kept only the leading bytes as one constant. C++, Rust and Python summed every
fixed byte first and applied the terms after, so a pad aligned a total that
already held the bytes behind it:

    u8 n; u8 a[n]; pad_to(4); u16 x; u8 y;
    y from 03 01 02 03 00 07 09:  C 9, the others 2

The second `validate` was wrong the same way: a nonzero pad passed in those
three and C refused it. `traverse.leading_bytes` is the one rule now.

**Two `pad_to` in one struct did not compile in C.** Both were `<pad>`, one
path, so `situ_p_pad_offset` was emitted twice and `resolved.find` answered
for the first. All of XDR pads after each opaque. The second is `<pad2>`.

`pad_to(n) [preserve]` was documented by 0043 and refused by the placement
table, which is now reachable: radiotap's padding is the sender's.

The differ's Python driver printed a signed arm as -60 where the other three
print its 64-bit pattern, which no schema had reached. So did two generated
checks: C++ compared a `u64` through `int64_t` against a literal past it, which
a little-endian one with the probe's top bit fails, and Python read a `u16[6]`
as a property where it has an indexed getter.

**The walker had the pad arm's cycle.** A pad's size asked for its offset, whose
sum reached the pad's variant and asked for its size. `chain_bits` now takes a
chosen pad arm as an alignment step, and `_arm_bits` measures one from the
variant, so the sum stays linear. Answering the cycle the other way, by asking
each pad for its own walk, would have been a walk from the start per pad.

**And the fan-out reached this tree's own test.** `test_the_four_builders_agree`
tried every combination of arms, which 26.881 left there on purpose as a thing
that was cheap: mqtt has eight. Radiotap has 2^24, and the sweep sat at one test
for 21 minutes before anyone looked. It takes the product up to 64 now, and past
that every arm once and a seeded sample.

## What it does not do yet

A struct holding such a variant has no `required`: framing measures a member by
itself, and a pad's length is where it starts. All four decline together, in
`_variant_is_measurable`. Radiotap ends in a `[remaining]` run, so it has none
to lose, and a format needing both would need the cursor carried into framing.

## What was measured

`example/radiotap`: one builder where a builder per combination would be 2^24,
50 arm constructors. Nine vectors laid out from the specification's table by a
script that knows nothing of situ, read back by tshark field by field, each
rebuilt byte for byte from one value per field. Four languages over the nine
and every prefix of two, 127 packets, none disagreeing.

## Rejected

**Message-relative alignment**, above: wrong for a header not at byte 0.

**A view carrying its origin.** Every sub-view in four languages gains a
field, and a struct's length then depends on its position, which an arm value
cannot know.

**A hidden argument for the offset.** 0068's plumbing would carry it, but a
parent has no expression for "where I am", and the same objection stands.

**A multi-member arm.** It would serve radiotap and asks every arm emitter for
a sequence where each holds one member.
