# 26.716: a gate that prints a finding and passes

Status: recorded -- `undefined` added to both fuzz flag sets, with the flag
that makes it able to fail
Date: 2026-10-28
Source: `project.md` section 26

The fuzz harnesses have built with `-fsanitize=fuzzer,address` since the
target existed, so **ASan has always been gated and `undefined` never
was** -- and for a compiler whose output is bit and byte manipulation
UBSan is the instrument that fits: shift exponents derived from schema
widths, offset arithmetic, `situ_base(view) + offset`, and the alignment
the capability map claims.

26.714 was found running that lens by hand. This makes it permanent.

## The flag that matters is not `undefined`

Adding `undefined` alone gives a gate that **cannot fail**. UBSan's
default is to report and recover, so the harness prints its finding,
libFuzzer carries on, and the target exits 0 -- `make` reports success
over a run that found undefined behaviour.

Measured, on a deliberate `1 << 64` in a ten-line harness:

    -fsanitize=fuzzer,address,undefined               1 report, exit 0
    ... -fno-sanitize-recover=undefined               1 report, exit 1

So `-fno-sanitize-recover=undefined` is the whole of the change's value,
and `undefined` without it would have been the vacuous pass this tree
keeps paying for, dressed as a new gate.

**That is why the sabotage came before the commit.** A green run proves a
gate does not false-positive; it proves nothing about whether it can go
red. The green runs were already in hand from 26.714 -- 43 harnesses,
zero reports -- and they would have looked identical with recovery left
on.

## What it found, which was not what it was aimed at

The first full run after the flags changed went RED, and not on UBSan: ASan
reported a **stack overflow in the C walker** on a zero-byte input, and
`make fuzz` had been failing on it all along. That is 26.717, and it is a
pre-existing fault -- it reproduces under the old flags and with no
sanitizer at all, so this change did not cause it and did not detect it
either.

**What this change did was make somebody run the target.** The walker half
had never been measured under either sanitizer by this session, and
`run-fuzz` stops at the first crash with `|| exit 1`, so one red harness
had been failing the whole target silently. Rebuilding 135 binaries to
check a flag is what put the output on screen.

Worth separating honestly, because the tempting write-up is that a new
sanitizer found a memory bug. It did not. A gate nobody runs is the
finding, and the lens was aimed at the wrong half.

## What it costs

Nothing in findings once 26.717 is in: 135 harnesses build clean under
`-Werror` with both sanitizers and run clean on their corpora. Build and
run time grow with a second sanitizer, which `fuzz` already paid for
`address`.

Both flag sets changed, because `fuzz-cpp` is a separate build and had the
same gap; the walker harnesses take `FUZZ_CFLAGS` and so are covered by the
C half. Forcing the rebuild was necessary to check any of it: flags are not
a prerequisite in this Makefile, so `make` reported *"is up to date"* for
binaries compiled on the old ones -- the stale-artifact trap, in the step
that was verifying a flag change. The binaries carry 22 `__ubsan_handle_*_abort`
symbols apiece, which is the flag visible in the artifact rather than in
the command line.
