# 26.663: Two absences, one item, and a sentence nobody read

Status: recorded
Date: 2026-10-20
Source: `project.md` section 26

The construct is decision 0065. This records what re-deriving item 13's
premise found, which is the half worth more than the feature.

## The item folded two things on opposite sides of its own boundary

26.142's sentence is the one to read: **"situ carries state inside codecs
and nowhere in the layout."** It names a boundary, and then the item
treats both sides of it as one question:

- **8b10b** wants running disparity across symbols, which is state
  INSIDE a transform. situ carries that twice already -- a
  `shift_register` holds a register, and `stuffing` with `unit = stream`
  holds line position. 26.139 lists three candidate shapes and every one
  of them is codec-side: an argument to `table`, a seventh family, or
  leave it tier-1.
- **CoAP's option number** wants a running total across ITEMS, in the
  layout, where situ carries no state at all. New in kind.
- **CoAP's option length** wants a value sized by a part of its own tag,
  which is not state at all and was specified before any code existed.

So the risk the item guards against -- "answering them separately is how
a language grows two spellings for one idea" -- does not bind on the pair
it was written about. A kernel argument and a layout accumulator are
never one spelling, any more than an LFSR's register and a `while`
predicate are. What the item got right is that the two CoAP halves are
independent and either alone blocks the protocol; what it got wrong is
which of its three absences are one question.

Item 13 is narrowed to the one that is: **state between items in the
layout.** 8b10b is 26.139's three shapes and is codec-side; the length
half is built.

## The sentence

Section 9.5 has said since the scaffolding commit of 2026-07-26 that a
value is "sized by a literal, a `prefixed(...)` form, **or an
expression**". The parser implemented the first two of those three. So
the length half was never an open question: it was the code failing to
implement the document, and `code-style.md`'s precedence settles that
direction without anybody deciding anything.

**Nothing in the ordinary course of work brings a reader to that
sentence.** The item was written from the refusal the parser produces,
and a refusal reports what the code does. Three records name this gap
while citing 9.5, and not one of them quotes the sentence three lines
above the thing they cite.

Which is the lesson, and it is the second instance in two days -- item 11
was parked for 43 days on a premise one parse falsified. **A deferral's
stated reason is the thing to check first, and the check is usually to
re-read the document rather than the code.** Both items named an
expensive mechanism, both were wrong about needing one, and in both cases
the cheap evidence was sitting in a file the item cites.

## What the work turned up

**The wire signature would have called a changed extent unchanged.**
`_value_rule` renders a rule for the signature consumers diff in review,
and it printed the kind word plus a size or a length type -- so
`computed` would have been the whole of it, and a change from `length` to
`length + 13` would have produced an identical signature. That is the one
fault that file exists to prevent (26.520's reading of a rename as a
regression is the same instrument working). It prints the arithmetic now,
and `situc wire --check` reports the change as breaking.

**The image row grew by stride rather than by version.** `image_tlv_rule`
gained a program offset, and the reader picks the longer layout when the
section's stride allows it -- which the struct rows already did. A format
version bump would have been the obvious move and was not needed.

**The packer's own warning caught the loop that ignored it.** `pack.py`
carries a note saying `rule` and `kind` are bound in that scope and that
shadowing them "made the whole loop a type error rather than a wrong
image". A loop added there shadowed `rule` immediately; mypy refused it,
which is the note being right twice.

**The corpus addition found a grammar gap of its own, which is the policy
working.** `edges.situ`'s new region ends its argument list with a
trailing comma, and `tlv_args` is the one list production in the grammar
that does not describe one -- `tag_decode`, `value_size` and
`known_tags` all carry `[ "," ]`. The parser has always accepted it. No
corpus schema had written one, so `test/unit/ebnf.py` could not see it,
and the gate refused the schema rather than the grammar: *"cannot derive
edges.situ: line 1686 ... stops before `)`"*.

That is 26.542's class a third time -- an existing spelling in a new
position -- and it arrived through the one mechanism built to catch it.
The fix is `[ "," ]` in both copies, and the control is the gate's own
failure: with the comma dropped from the grammar again, `edges` stops at
the same byte.

**There are two walkers and both hold their own copy of the numbering.**
`walker/c/situ_walk.c` reads the image in C and imports nothing from the
compiler (0026), so a rule kind one walker knows and the other does not
reads as "the count stops here" rather than as an error -- silently, and
in the reader a user is most likely to embed. It has the kind and the
branch now, and `test_they_agree_about_a_tag_sized_value` compares the
two over the same vectors; sabotaging the C side by one byte makes them
disagree, which is what that file exists to catch.

**The five-way test needed a schema of its own.** `example/protobuf` is
the only committed tlv and carries no computed size, so the existing
five-way comparison could not reach the new rule. The new one builds a
CoAP-shaped schema in the test and compares all five columns over
hand-built packets where the length nibble decides each answer -- with
two sabotages run against it, one in the walker and one in a backend,
each failing it in the right column.
