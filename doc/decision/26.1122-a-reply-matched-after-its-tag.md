# 26.1122: a reply matched only after its tag verifies

Status: recorded; built 2026-11-21 after fuzznet's review (inbox 20261120T2130Z)
Date: 2026-11-20
Source: fuzznet (inbox 20261120T1231Z, item 2): "`reply_to`'s key
(`head.msg`) is in the clear head, but a match there lets a forged head end
an exchange its owner still waits on, and two callers may number alike.
Wanted: matching on a verified view -- after a `verify_gated` region opens
-- with a key that may name verified fields (the sender with `msg`). Then
the driver ends exchanges itself and the asks table's matching goes."

## What is there

Rung 5's table (`<stem>_converse.h`, 26.97) matches a reply by the key its
relation's equalities name, read through ordinary getters from a plain
view -- before anything has verified the reply. A sealed region's interior
is reachable only through a GATE value, `<struct>_<region>_t`, which
`<struct>_<region>_open(view, verified, &gate)` hands out only when the
caller says its tag verified (14.3): the doom principle as a type.

## The shape proposed

    relation reply_to(request: fzn_frame, reply: fzn_frame)
            [after = sealed, ...] {
        must reply.head.msg    == request.head.msg;
        must reply.sealed.from == request.head.to;
    }

`[after = REGION]` names a `verify_gated` region of the reply's struct.
With it, the table's `match` takes that region's gate instead of a view --
so the call cannot be written with a reply nobody verified -- and the key
may name fields behind the gate (`reply.sealed.from`), read through the
gate's accessors. The request side is unchanged: a request is the
caller's own and was never in question. Rung 6's driver, which already owns
the receive path, then calls the caller's verify hook (the key is the
caller's, 14.1) and matches with the gate it gets, ending exchanges itself.

## A peer the message does not name (fuzznet's item 5)

fuzznet's item 5 -- one driver over many peers and sockets, the peer part
of the key -- is the same mechanism, read from `node/asks.c`: it tracks
every exchange by id (`_track_by_id_with`) and matches replies itself,
because the relation's key alone would let two peers' equal message
numbers meet. Where the message names its sender, the key above already
separates them (`reply.sealed.from`). Where it does not -- a socket
address, a path -- the caller says it: `_track_from(drive, peer, ...)` and
`_on_message_from(drive, peer, gate, ...)` take a `uint32_t peer` the
caller assigns, held beside the key and compared with it, so an exchange
is ended only by a reply from the peer it was sent to. The first send and
a resend already reach the caller by exchange id (`resend`, 26.1036),
which is how it knows the socket; nothing there changes.

## For review

- Whether the key reaches fields behind the gate by the region's name
  (`reply.sealed.from`) or by the interior struct's.
- Whether a clear field in the key -- `head.msg`, which the tag also
  covers -- is read from the view the gate came from: the gate would carry
  it, so `match` takes one value.
- Whether `after` should also gate the request side for a relation whose
  request is received rather than sent (a peer's ask), or that is a second
  relation.
- Whether a caller-assigned `uint32_t peer` is enough for item 5, or the
  first send should also go through a per-peer `submit`.

## fuzznet's answers, and what was built

fuzznet answered the four points from `node/asks.c`, `node/caller.c`,
`wire/seal.c` and `wire/frame.situ` (its sec 1325):

1. **By the region's name**, `reply.sealed.from`: its interior struct is
   an implementation of the region, not a name a schema reader looks for.
2. **A clear field from the view the gate came from.** fuzznet's head is
   the AEAD's associated data, so once the gate opens every head field is
   as verified as the interior. One value to `match`.
3. **A received request is a second relation**, read in the other
   direction, rather than one relation meaning two things by a flag.
4. **A caller-assigned `uint32_t peer` is enough, provided the peer is
   the VERIFYING CONTEXT** -- fuzznet's session, `fzn_caller_t` -- and
   not the network peer: message numbers are per session, and two
   sessions can talk to one peer, so even the verified sender key with
   `msg` would collide. Reusing a handle is safe once nothing can verify
   under the old session's key: a reply meant for the ended session
   cannot verify under the new one's, so it never reaches the match. No
   per-peer `submit`: first sends and resends reach the caller by
   exchange id already.

Built in all four backends, as reviewed:

- `[after = REGION]` on a relation names a `sealed` region of the reply's
  struct, refused otherwise and on a member. `match`/`take`, `peek` and
  the driver's `on_message` and `peek` then take that region's gate. The
  key reads a member behind it through the gate's accessor and a clear
  field through the view the gate was opened over -- `gate.view` in C,
  `_view` in Python, and a new `view()` on the Rust and C++ gates, which
  is the clear view and nothing the gate did not already reach.
- The predicate, handed two views, cannot read behind the gate and says
  so: the conversation table reads it.
- **`peer`**: every table slot and driver slot holds one. `_record_from`,
  `_match_from`, `_peek_from`, `_track_from`, `_send_from`,
  `_on_message_from` take it (`peer=` in Python, `take_from` and the like
  in Rust and C++); the calls without `_from` hold peer 0, so every
  existing caller keeps its meaning.
- **The rung-6 machine takes the gate rather than calling a verify
  hook**, a narrowing of the shape above: the caller already verifies on
  its receive path, and a gate parameter makes an unverified match
  unwritable with no hook to register. The event-loop drivers own the
  receive path, so they gained a `verify` hook -- appended last in
  `situ_drive_hooks_t`, so positional initialisers keep their meaning --
  answering whether the reply's tag holds. Only then is the region opened
  and the reply matched; without a hook, or on any other answer, it goes
  to `on_unmatched` with a tag error. A relation without `[after]` never
  reads it.

`test/unit/test_a_reply_is_matched_after_its_tag.py` holds each backend to
the same three answers, and the C poll driver to a fourth: a reply whose
`verify` refuses never reaches the match.

## Tracking by the key alone (2026-11-21)

fuzznet's asks table also awaits exchanges it holds no request for -- one
sealed and sent by somebody else, a relay's forwarded question -- knowing
only the key's values (inbox 20261121T0600Z). `_track_by_id_with` holds
no key, so the driver could never match those. C now has
`<table>_key(...)`, the key from its parts' values packed as the table
packs one it reads; `<table>_record_key_from(table, key, peer, id)`; and
`<drive>_track_key_from(drive, key, peer, bytes, len, id, now, policy)`.
`_record_from` is `_record_key_from` after reading the key. The other three
backends track by a request view only; fuzznet's need is C's, and they
gain it when one of their callers asks.

The gate points into the reply's bytes, which must live until
`_on_message_from` returns; the generated comment says so.
