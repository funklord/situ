# 26.989: Wireshark says a run is out of order

Status: recorded
Date: 2026-11-13
Source: the last of the seven readers 26.985 and 26.988 left silent

Six readers refuse a run whose keys do not ascend; the dissector showed
the run and said nothing. It now declares one expert per ordered run,
`<struct>.<run>_out_of_order`, malformed and an error as a `refuse` is,
and raises it after the run is dissected where a key is not above the one
before.

One comparison serves every key: byte by byte from the most significant
-- reversed for a little-endian integer -- with a signed integer's first
such byte's sign bit flipped, so the bytes order as the numbers do. No
64-bit arithmetic, which an older Wireshark's Lua does not have.

`test_a_run_holds_its_keys_in_order` asks the Lua harness over its twelve
messages: the expert exactly where the backends refuse, and fails with the
change reverted. Real tshark, given git's index in a user-DLT capture,
shows nothing for it and "`names` is not in ascending order" for the same
index with two names swapped.
