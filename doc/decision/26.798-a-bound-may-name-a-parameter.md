# 26.798: A constraint's bound may name a `parameter`

Status: recorded -- fixed
Date: 2026-11-02
Source: found while building 0068 step 2

    struct note { parameter u8 mode; u8 v [max = mode]; }

0050 lets a parameter decide meaning freely, and a bound is meaning. The
schema was accepted, and the generated code was wrong in all four
backends:

- C called `situ_note_mode_get(view)`. Nobody emits that accessor, so it
  did not compile.
- C++, Rust and Python read `mode()` / `self.mode`, which a view does not
  have.

A bound naming a sibling is rendered by `invariant.bound` through each
backend's `value` hook, and the hook reads a member's getter. A size, an
offset and an `at` reach a parameter through `_over_fields`, which has
known since 0050 that a parameter is the argument. `value` never learned
it.

## The change

Each backend's `value` returns the argument's spelling for a parameter
(`arg_mode` in C, `this->arg_mode` in C++, `self.arg_mode` in Rust and
Python), in the same terms its `_over_fields` uses.

## Tests

`test_a_bound_reads_a_parameter.py` builds the schema in all four, and
holds Python's `validate` to `v <= mode` for the argument given. With
`situc/codegen` reverted, both fail.
