# 26.784: `max N` on a `while` run is N elements in Python too

Status: recorded -- fixed
Date: 2026-10-31
Source: found while writing the arm walk for a `while` run (26.785)

    struct top { u8 kind; pt recs[] while (x != 0) max 2; u16 after; }

Python's `while` walk capped with `len(starts) <= N`. `starts` holds the
elements read so far, so the walk took N + 1, where C, C++, Rust and
both walkers take N (`n < N`). Python's `required` was already right
(`seen == N`). Over `00 0101 0202 aabb`, with the condition still true
at the cap, Python took `aabb` for a third element, found no `after`
and refused a message the other five accept. Over a longer frame it
counted three and read `after` from the wrong bytes.

The corpus reaches it: `example/ipv6ext` caps its chain at 8,
`example/dnsname` its labels at 128, and `edges.situ` two runs at 6. No
differential caught it, since a random message rarely holds N elements
in a row whose condition stays true.

## The change

`<` for `<=` in `_repeat_while`. The generated Python changes on four
lines across those three schemas, and nothing else in the corpus moves.

## Tests

`test_a_while_cap_is_n_elements.py`: the four answer alike over three
messages and Python counts two. It fails with the fix reverted.
