# 26.896: A size may be what a table of lengths adds up to

Status: recorded
Date: 2026-11-06
Source: `suggestion/fuzznet.md`, section 1, and the holder's rule that a sane
protocol's need is ours

    u16 leaf_len[count];
    u8  payload[sum(leaf_len)];
    u8  trailer;

Lengths first and then what they size is a different wire layout from a
length-prefixed chunk array, and it could not be written: the payload had to be
an opaque `[remaining]`, which nothing tied to the table and nothing could
follow. This was on the last run's list as `sum`, and 26.893's `byte_sum`, built
first under that name, answers a different report. The name hid that for a
while.

## How it reaches six readers

`sum(run)` takes a counted run of unsigned integers declared earlier, whole
bytes wide. It is a size only, since nothing else in the language reads a run's
elements, and `wellformed.check_sums` refuses anything else.

**Each backend renders it in one place.** Every size expression goes through
`_over_fields`, so `names.with_sums` lifts the call out and hands it back as an
`extra`, and length, offsets, `validate` and `required` all have it with no
further branch. The bytes are added by `situ_sum_run`, `sum_run` in Rust and
Python, which takes the run's offset, count, width and order. A name in a size
is a field's read and a run has none, which is why the call has to come out
first.

**Each walker gains an opcode**, `SUM` at 0x0A, answered from the bytes.

All five agree on what a lie does: only the elements the frame holds are added,
and the total saturates at 32 bits, so a table claiming more than the frame
holds is a run reaching the frame's end and `validate` refuses what follows.

The interval is `[0, unbounded)`, though a tighter one exists: nothing is yet
gained by `count * max` beyond a larger number in the map.

The dissector declines it by name, as it does any size it cannot spell, and
what follows such a run is not shown.
