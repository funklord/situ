# 26.1112: the dissector computes every named value, in `UInt64`

Status: recorded
Date: 2026-11-20
Source: the goal-gap walk at the end of /go run 7; 0a's open item "the
dissector shows a `let` ... without evaluating"

26.1060 showed a `let` only where Lua's doubles are exact -- an `|` of
shifted unsigned fields -- and declined the rest by comment: a
subtraction, a division, a variable shift, a wrapping product, anything
reading a signed field. `edges`' `assembled` showed two values of ten.

## The change

Where the doubles path declines, the value is spelled in Wireshark's
`UInt64` through `traverse.let_source`, as the four backends spell
theirs. `UInt64` is in every Wireshark's Lua, 5.2 included, so 0021's
floor holds; its arithmetic is modulo 2^64; the helpers carry the guards
every reader uses (`/` and `%` by zero are 0, a shift by 64 or more is 0,
a comparison is 1 or 0). Each field read is a Lua number, so a field
wider than 32 bits is still declined, and so are a text number and a
token. The result is held to the value's width as the getters hold it.

A signed field reads in this dissector as its unsigned bytes -- its row
shows right because its ProtoField is `int` -- so it is sign-extended
before it is widened. Real tshark found that: `a - b` with `a = -3` came
out 248. The `edges` walker sweep did not, because it compares on random
draws and none had put a negative `a` in `assembled`; the new test's
values are worked by hand.

The Lua stub gains `UInt64`'s arithmetic over Lua 5.4's integers, with
unsigned comparison and division written out.

## Measured

`assembled` shows all ten. `test_a_dissector_computes_every_named_value`
holds the stub and tshark 4.4 to hand-worked values for one packet that
divides by zero, shifts by 70 and wraps a product; flipping `-` to `+`
in the spelling turns the `edges` walker comparison red.
