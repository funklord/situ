# 26.742: A run of varints the frame sizes is walked to its end

Status: recorded -- implemented
Date: 2026-10-29
Source: `project.md` section 26

The feature 26.691 asked for and 26.733 left open. `uvar v[remaining]`
compiled after 26.691, C answered its count with the constant `0u`
until 26.733, and after that all four backends declined the member in
words -- "this backend cannot resolve how many elements it holds" --
while both walkers left it out of what they report. Honest, and not a
construct anybody could use.

## What it means

A bare `[remaining]` states BYTES: the run reaches to the end of the frame
it is in. Varints have no stride to divide bytes by, so nothing says how
many there are, and the only way to the number is to walk. **The count is
the whole varints from the run's start to the end of the view.** The walk
is the cost the construct's `access = Sequential` already names, and it is
the same walk `_span` and `_at` already make for `uvar v[n]`.

An element the frame cuts short is not counted, and **`validate` refuses
that frame** with BOUNDS: the bytes after the last whole varint are a
varint nobody can read. That is the question 26.735 asked of a counted
varint run and 26.736 of a `[remaining]` run of fixed-size elements, asked
of this one. The counted run's test cannot serve: its count stops where
the frame does, so `_span_min` equals `_span` and the frame always holds
it. The test is that `_span` reaches the frame's end exactly.

Over `u8 lead; uvar v[remaining];` (leb128), all four and both walkers:

    09 01 02 03     count=3 span=3 [0]=1     valid
    09 81 01 05     count=2 span=3 [0]=129   valid
    09 01 81        count=1 span=1 [0]=1     refused, BOUNDS
    09              count=0 span=0           valid, the empty run

## Where it lives

`traverse.walks_to_the_frame_end` replaces `elements_are_countable`,
which was False for exactly this arrangement and is now the condition for
the other way of counting. Its askers are unchanged: the four emitters,
`gen-checks` and the differ, which is why it is one predicate rather than
three conditions (26.733's lesson).

- Each backend's `_count` walks for it; `_span`, `_span_min` and `_at`
  keep the walk they had, bounded by that count. Each `check` gains the
  frame-end test beside 26.736's whole-elements test, which is where the
  three non-C backends already reach for a `[remaining]` run -- in C
  `_varint_run_fits` was never reached for this member, so the test is
  `_varints_reach_the_end`, called beside `_remaining_divides`.
- `walk.py` gains `varint_run_count`, which the span walk, `varint_run_at`
  and the report all ask, and `_varints_reach_the_end` for the fit. The C
  walker's `varint_run_bits` walks the bare form to the frame's end and
  hands its count to `situ_walk_count`.
- **Both walkers measured the run as ONE varint.** Their extent branches
  excluded the bare form, as their report did, so it fell through to the
  single-varint read. It was invisible because nothing followed it and
  nothing asked.
- The differ asks the run `count= span= [0]=` again, and `gen-checks`
  skips it for the shape of its accessor rather than its absence: a
  varint run's `_at` yields a value, and that harness asks element views
  where they start.

## What it did not change

No committed schema other than `test/schema/edges.situ` has the
construct, which carries `countless_varints` for the differential.
