# 26.890: An augmented CRC is a constant

Status: recorded
Date: 2026-11-06
Source: `suggestion/openmlx4.md`, and the holder's rule that a sane protocol's
need is ours

openmlx4 found a Mellanox CRC agreeing with situ's on 5000 of 5000 messages at
`init = 0` and on none at `0xFFFF`. Both are correct. The catalogue's model
folds each message bit in at the top of the register. The augmented model
shifts it in at the bottom and flushes `width` zero bits at the end. Nothing in
a schema said which was meant, and `init = 0xFFFF` compiled to the wrong digest
in silence.

    kernel = polynomial(width = 16, poly = 0x100B, init = 0xFFFF, augmented);

## It needs no second algorithm

The two are one CRC with different starting values: the augmented `init`,
clocked `width` times with nothing coming in, is the catalogue's. The classic
direct and non-direct init. So `kernel_math.crc_init` works the constant out at
compile time, the three generators and the packer call it where they read
`init`, and the table-driven code is unchanged.

    init 0xFFFF, poly 0x100B, width 16:  start 0xF6AA

Measured before it was relied on: 18000 random messages over six polynomials
against the bit-by-bit augmented algorithm, no mismatch. `clock(0)` is zero,
which is why the two agree there and why nothing noticed.

A reflected code is the same constant, because `init` is stated unreflected
and `crc_start` reflects it after. The test holds both against a reference
that nothing in situ runs.

## Rejected

**Refusing a nonzero `init` on an unlisted polynomial.** The catalogue model is
right for most of them, and refusing would lose CRCs that work.

**A `model =` argument.** There are two models, the catalogue's is the
default every schema already means, and `reflect` is the flag beside it.
