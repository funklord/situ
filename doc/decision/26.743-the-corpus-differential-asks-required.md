# 26.743: The corpus differential asks `required`

Status: recorded -- implemented, and two faults found and fixed
Date: 2026-10-29
Source: `project.md` section 26

26.725 measured that `situc/codegen/differ.py` mentioned neither `required`
nor `framed`. That file is the corpus differential, which every committed
message, every random draw and every composed schema goes through, and it
is also the source of the C++ libFuzzer harness. So the framing layer, with
more decision records against it than any other function here, was compared
across the four backends only by `test_four_backends_frame_alike.py`'s own
probes over uniform fills.

## The probe

Each driver prints a `required()` line after each framed struct's section,
with one answer per prefix of its input: every prefix from 0 to 64 bytes,
then the whole buffer if it is longer. The tokens are the agreement test's:
`*n` for complete at n bytes, `n` for truncated with a need of n, and `x`
for anything else. C copies each prefix into a `malloc` of exactly its
length and C++ into a vector of exactly its length, so a read past the
prefix is a sanitizer's finding rather than a read of the slack behind it
(26.725's lesson). Rust's slices and Python's byte strings carry their own
edges.

The line opens `required()`, which no member can be called. The walker
comparison keys lines by their first word, so a member named `required`
would otherwise be compared against this line.

`differ.framed` decides which structs get the line. It asks
`frame.framed_structs`, which is the frame layer's own authority and what
C's `_required` asks first (26.729), less any struct taking a `[stream]`
argument. Measured before it was wired in: over the corpus this is 222
structs, and **all four backends emit a bytes-only `required` for exactly
those**. C++ spells `framed` as `framed_` with a `using` alias, which is a
spelling and not a disagreement. `test_the_differential_frames.py` holds
each backend's artifact to the set, schema by schema, and fails if the set
goes empty.

The walker is not compared. Its `frame_min` is one-sided by design: it may
answer more than a whole message needs, so it is a bound rather than a
fifth spelling of the number.

## What it found on its first corpus run

Five failures, two faults, both in C, and one of them also in C++.

**C scanned for a delimiter from the wrong place.** Its `required` passed
`at`, the running total, as the start offset of a delimited member. `at`
already holds every fixed member after that one, so the scan for
`until "\0"` began that many bytes past where the label begins. 26.684 had
added the cursor `pos` for exactly this, and the delimiter branch and the
`_from` length it asks for still took `at`. With a terminator in the
skipped bytes the label came out short, and C called a message complete
before its run had arrived:

    u8 ver; u8 n; u8 label[] until "\0" max 8; rec run[n]; u16 tail; ...
    C = 162     C++ = Rust = Python = 166

    stuffed_seal (a sealed region until 0xC0, then a 16-byte tag)
    C = *31     the other three = *47

That is the dangerous direction: a caller told "complete" parses bytes
that are not there. Three composed schemas and two `edges.situ` structs
showed it. Both the scan and the length now start from the cursor.

**C and C++ wrapped a count times a width.** For `required` the count is
deliberately not held to `SITU_LEAF_MAX` (26.651), and the product with the
element width was a plain 32-bit multiplication.
`pickle.pickle_wstring`'s count 3436581234 times 2 wrapped to 2578195172,
a need a caller can meet, where Rust's `need_mul` (26.732) and Python
answer 4294967295. Both now use `situ_need_mul_u32` for `required`'s
caller. The accessors keep the plain product, since their count is
bounded first.

## Why the fill sweeps could not see either

- With the 0xFF fill a wrapped product is still enormous, and the
  saturating add on top of it hid the wrap. 26.732 listed
  `pickle_wstring` at 0xFF as Rust's divergence alone, because C had
  saturated there by luck.
- With the 0x00 fill the terminator is wherever the scan starts, so both
  offsets find it. The other fills put a terminator nowhere.

A random count and a buffer with structure are what found them, which is
why the fill sweeps stay as well: they own the extremes and the exact-size
allocations, and the differential owns messages.

## Tests

`test_the_differential_frames.py` holds the probe's population. It also
pins both faults as exact answers rather than as agreement:

- a label followed by a record whose first byte is zero is complete at 8;
  with the fix reverted, C says 7;
- `u32 count; u16 data[count]` with a count of 0xCCCCCCCC needs
  4294967295; with the fix reverted, C and C++ say 2576980380.

Each fix was also controlled against the corpus case that found it.
