# 26.369: The loop that runs at the top of a byte

Status: recorded
Date: 2026-09-16
Source: `project.md` section 26, where it was written

**0046's third change, and the one its own record priced at "three changes
in four backends".** A NON-reflected CRC narrower than the byte it consumes
cannot index a table with `byte << (width - 8)` -- the shift is negative --
so `crc_width` declined it, correctly, and `crc7_mmc` was described and
generated by nobody. It runs left-aligned instead: the polynomial, the
table and the initial value shifted up to the top of a byte, the loop
identical to the width-8 one, and the result shifted back down before the
final xor.

**The arithmetic was proved before any backend was touched**, against two
published check values with different widths and initial values -- CRC-7/MMC
0x75 with residue 0x00, and CRC-5/EPC 0x00, which is a second parameter set
rather than the same one read twice. Then `crc_shift` and `crc_register`
went into `kernel_math`, which is what the four emitters ask: the register
is a byte whatever the code's width, so its table and its start are written
in the REGISTER's digits and `width // 4` would print them a digit short.

**Two things it caught that were not the subject.**

`crc7_mmc` came out of Rust as 0x1F. The narrowing mask a register wider
than its code needs -- `crc & 0x7F` after every step -- is exactly wrong for
a left-aligned one, where the register IS the word and the top bit is part
of the value. C never had it because its width-8 branch emits no mask, so
the same fix landed in one backend by luck and in the other by measurement.

**And `crc5_usb` did not compile in Rust at all, on master, today.** A
reflected code whose register is a byte emits `crc >> 8` on a `u8`, which
rustc refuses as an overflow -- the trap that module's own comment describes
for width 8, reaching every reflected CRC with a byte-wide register. 0046
records `crc5_usb` as deriving and being checked, and it does: the
check-value test reaches it through C. **One backend's verdict was standing
in for four**, which is what a per-language gate exists to prevent, and the
fix is to key the branch on the REGISTER's width rather than the code's --
at eight bits both shift terms are zero and the expression reduces to one
lookup whichever direction the code runs.

**What moved in the tests.** `crc7_mmc` left `CRC_UNCHECKED`, whose entry
had recorded 0x75 "against the day it is generated", for `CRC_CHECK_VALUES`,
where the generated C is run over "123456789" and compared. The four-way
guard from 26.368 had `crc7_mmc` as its underivable fixture and would have
gone on passing while asking nothing, so it now asks a RELATIONSHIP instead:
for each backend, does it name the codec if and only if it can write one?
That fixture is a Reed-Solomon code, and the reason the shape had to change
is worth keeping -- **C writes every kernel family and Rust and Python write
two**, so no fixture is underivable in all four and one that is underivable
today stops testing anything the day somebody implements it.
