# 26.786: A run of a recursive element in an arm is walked

Status: recorded -- fixed
Date: 2026-10-31
Source: the shapes 26.779 left unwalked

    struct node [depth = 4] { u8 n; node kids[n]; }
    ... variant body switch (kind) { case 1: node recs[n]; default: u8 raw; }
        u16 after;

26.779's arm walk declined a recursive element because `check` carries
no depth. So a second `node` the frame does not hold (`01 02 00`), and
an `after` cut short behind the run, validated clean in all four, while
both walkers refused them.

## The change

Each backend's `_arm_run_walk` takes a recursive element and measures
each one at depth one, through `extent_at(element, 1)`. That is what the
top-level `_run_fits_at` does from `check`'s zero. A `[depth]` cap makes
the extent zero, and the walk stops there, as at the top level. The
walkers needed no change. The corpus generates byte-identically.

## Not changed, and the same at the top level

- **An element's own overrun is not refused.** `01 02 00 01` holds a
  second `node` whose kid is missing. Its extent stops at the frame, so
  the run fits, and all six accept it. Elements of a run are not
  validated anywhere (26.780).
- **A tree deeper than `[depth]` is not refused through a run.**
  Validating `node` itself refuses one in all four (2), with the walkers
  answering `cannot-say`. A run of `node` inside another struct, at the
  top level or in an arm, is accepted by the four. project.md's "validate
  refuses a too-deep message in all four" holds for the recursive struct
  itself and not for a struct holding a run of it. That is the open
  question 26.780 leaves: whether a run's elements are validated at all.

## Tests

`test_a_run_in_an_arm_is_walked.py` gains the shape with eight messages,
all six agreeing. With `situc` reverted the four-backend case fails.
