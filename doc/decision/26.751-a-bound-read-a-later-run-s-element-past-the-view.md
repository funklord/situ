# 26.751: A bound read a later run's element past the view

Status: recorded -- fixed
Date: 2026-10-29
Source: `project.md` section 26

`[max = n[0].f]` bounds a member by a field of element zero of a run.
`validate` guarded that the run's COUNT reaches the element, and then
loaded it -- but a count is what the message claims, not what the frame
holds. Where the run is declared after the bounded member, its own frame
check comes after the comparison, so nothing had checked the bytes:

    struct s { u8 v [max = n[0].f]; u8 c; rec n[c]; }      over  00 01

    if (count <= 0u) return CONSTRAINT;               /* 1 > 0: passes */
    if (v > base[2]) return CONSTRAINT;               /* base[2]: past */

In C and C++, under ASan with an exact-size buffer:

    ERROR: AddressSanitizer: heap-buffer-overflow ... READ of size 1
      #0 situ_s_check                 unit.c:66
      #0 situ::s::check(...) const    unit.hpp:275

Rust and Python read safely and answered BOUNDS.

## How it was found

From 26.747's lens: a load at a computed offset in C++ that nothing had
bounds-checked. `element_value` is the other such load in that emitter,
and its docstring said the refusal was "emitted beside the comparison" --
which is true and is not the same as before the load. Asking which loads
`validate` makes ahead of any frame check found this one, in C as well.

## The fix

The guard gains a second test, in both: the element's bytes are inside
the frame, or BOUNDS -- which is what Rust and Python answer, so the four
agree. `test_a_bound_naming_a_later_run.py` runs C and C++ under ASan and
UBSan and holds all four to three verdicts; both sanitized tests fail
with the guard removed.
