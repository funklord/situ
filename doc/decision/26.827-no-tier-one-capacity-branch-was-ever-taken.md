# 26.827: no tier-1 codec's capacity branch was ever taken

Status: recorded -- fixed, with the positive control measured
Date: 2026-11-03
Source: `situc/codegen/c/codectests.py`; 26.826; `project.md` sections 13.1
and 13.2a

26.826 found that every generated codec property test fed a decoder only
the output of its own encoder, and fixed it for the DERIVED half. Writing
that up parked the tier-1 half as "the same question, smaller", and
re-reading section 13.1 says that was wrong.

**13.1's whole argument is that a tier-1 codec is trusted and unverified,
so it can lie, and that what the compiler can do is generate the tests
that would catch a lying one.** `codectests.py`'s own opening paragraph
says exactly that. **"I respect `out_cap`" is such a claim** -- it is the
one thing section 13.2a's ABI asks of an implementation in writing -- and
nothing was checking it. So this is inside the module's stated purpose
rather than a widening of it, and parking it was the error
`working-practice.md` names: a wrongly-deferred question is caught by
nothing and wears the appearance of care.

## What was not covered

Every tier-1 test passes `sizeof(coded)` -- `SITU_CODEC_MAX_OUTPUT`, 2048
-- against an input of at most `SITU_CODEC_MAX_INPUT`, 256. **So no tier-1
implementation's capacity branch has ever been taken by this suite**, and
an implementation that ignored `out_cap` entirely passed all of it.

That is the same slab 26.826 found on the derived side, and the difference
makes the fix sharper rather than harder: there the capacity is implicit
in the kernel and had to be derived, here it is a PARAMETER. Pass `n`, and
an implementation that needs more must say so with `SITU_ERR_BOUNDS`
rather than write.

## The test

Per bound codec, over ten input lengths and seven patterns: decode the
bytes with a capacity of exactly `n` and a guard immediately behind it,
then encode into the same tight capacity -- the branch a 2048-byte buffer
never takes. What is asserted holds for any tier-1 codec whatever its
signature claims, which is what lets one body serve all of them: the guard
is untouched, and a call reporting `SITU_OK` wrote no more than the
capacity it was given. Nothing is asserted about the decoded content,
because over an input no encoder made there is nothing to compare against.

The input patterns are 26.826's: the four bytes a framing or stuffing
codec is driven by, two pseudo-random fills, and `0xFF`.

## The positive control

**`my_doubling_encode` with its `out_cap < in_len * 2u` check removed
fails `test_doubling_hostile_input` and nothing else.** 28 of 29 pass, so
`length`, `deterministic`, `invertible`, `seekable_linear` and
`systematic` are all blind to an implementation that ignores its capacity
-- which is the lie 13.1 says this suite exists to catch.

`edges.situ` goes 23 tests to 29: five tier-1 codecs and one derived.
`std/codecs.situ` gains none and correctly -- its signatures have no
`impl` bound, so there is no ABI to attack and `_declined` says so.

## A test this one made false, and the honest repair

`test_a_signature_claiming_nothing_produces_no_tests` asserted that a
codec declaring only `expansion = unbounded` produces no tests at all, and
that the generated `main` says why rather than reporting a pass -- because
silence would read as coverage, which is this file's own rule.

The new test fires for such a codec, correctly: the ABI contract is not
one of the declared properties. **So the file is no longer silent and the
sentence it has to carry is a different one** -- a non-empty suite reads as
coverage of the SIGNATURE, and all this one covers is the ABI.

`_codec_suite` therefore reports which of its names came from a declared
property, and `_main` says which case it is in: no tests at all, or tests
but none from a claim. A derived hostile-input test needs no such
separation, being gated on `invertible`, which is a declared property.

The test is renamed to what it is about and gained a sibling for the
branch above it -- a schema with no `impl` bound at all, where the
original sentence still applies. That is the second time in this run a
gate asserting "and nothing else happens" had to be narrowed because the
catalog it was about grew; the first was `advise.py`'s
`test_a_well_ordered_schema_gets_nothing` at 26.824.

## And 26.826's own limitation, closed in the same pass

26.826 said an over-READ was caught by neither guard, because the input
sits inside a `SITU_CODEC_MAX_INPUT` array and reading past `n` stays in
bounds of the object. That needed two changes and the order mattered,
because the Makefile half alone would have run a test that cannot
overflow:

- **The sweeps reach `MAX_INPUT`.** ASan redzones a stack array, so it
  sees a read past the array itself -- but only where `n` leaves no slack.
  At 255 in a 256-byte array there is a byte between the input and the
  redzone, and ASan cannot tell that byte from legitimate use. So the last
  entry of `HOSTILE_SIZES` is load-bearing rather than round, and the
  constant says so.
- **`make test-codec-san`** rebuilds both codec suites with
  `-fsanitize=address,undefined -fno-sanitize-recover=undefined`, from the
  generated SOURCES rather than `test`'s objects, since an object compiled
  without the sanitizer is one ASan cannot see inside. The recover flag is
  load-bearing for the reason it is in `fuzz`: with recovery a UBSan report
  leaves the harness exiting 0, which is a gate that prints a finding and
  passes.

**Both suites are clean under it**: 95 tests for `std/kernels.situ`, 29 for
`edges.situ`, no ASan or UBSan finding. That is a negative result and it is
the one worth having, because the positive control says the instrument
works.

**The control, which is the whole argument for the target existing.** One
byte read past the input -- `if (len > 0u && in[len] == 0xFFu)` added to
the generated `situ_slip_framing_decode` -- is:

- **invisible** to the ordinary build: 95 of 95 pass, exit 0;
- **caught** by the sanitized one, as
  `stack-buffer-overflow ... [32, 288) 'input' <== Memory access at offset
  288 overflows this variable`, reached from
  `test_slip_framing_derived_hostile_input`, exit 1.

Offset 288 is 32 + 256: the array exactly consumed and the read landing in
the redzone, which is the mechanism the `MAX_INPUT` sweep entry exists to
produce. So the guard and the sanitizer catch different faults and the
pair is what covers both -- the guard a write, with no sanitizer needed,
and the sanitizer a read, which no guard can be placed to see.
