# 26.969: a TIFF directory through every generator

Status: recorded
Date: 2026-11-12
Source: adding the first directory to `example/tiff` (26.968)

`example/tiff` describes the header and now the first directory too:
`tiff_file` places `ifd(order = byte_order) first at ifd_offset`, and
each `ifd_entry` is in the header's order. The oracle reads the entry
count through the generated code rather than by hand, after `validate`
has walked the directory, and agrees with `file` over ImageMagick's files
in both orders; its planted lie now swaps `tiff_file`'s members.

A fixed-size struct handed an argument had reached none of the
generators beyond the four readers, and four were wrong:

- **The owned form** decoded `ifd_entry` naming the order as a marker it
  has not got, and called `validate` without the argument. An owned form
  decodes from bytes alone and an argument is not in them, so a struct
  taking one is refused there, with that reason, as the generator's other
  refusals are.
- **Rust's `required` for a fixed struct** took the argument and never
  used it, an error under `-D warnings`.
- **The check suites' baseline** zeroes the buffer, which puts a struct
  placed by `at` over the bytes before it: `tiff_file.first` at offset 0
  read the header as a directory of 19789 entries and the baseline did
  not validate. No baseline stands for a struct holding one.
- **Python named no member** for a located struct's refusal: its
  relabelling recognises the lines that propagate a nested `validate`,
  and 26.967's spelling of that was not among them.
